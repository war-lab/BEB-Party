# 開発ガイド

## 結論

Claude Codeでの実装を前提に、複数人（複数エージェント）が並行して安全に修正できるよう、モジュール境界とドキュメント更新をPRの単位に揃える。

作業の基本形は「対象モジュールの基本設計を読む → `task/` ブランチで実装 → 正本ドキュメントを同PRで更新 → ドラフトPR」である。

## 環境構築

前提: Node.js LTS、pnpm、Cloudflareアカウント（無料プラン）。

```bash
pnpm install
pnpm dev          # client(Vite) + server(wrangler dev) 同時起動
pnpm test         # ユニットテスト
pnpm validate:content
pnpm check        # lint + 型チェック
wrangler deploy   # 手動デプロイ(通常はCIが行う)
```

コマンドの定義は [基本設計/07_リポジトリとツールチェーン.md](./基本設計/07_リポジトリとツールチェーン.md)、実体を作るのはM0のPR0とする。

## モジュール境界と並行作業

pnpm workspaceのパッケージ境界を、そのまま並行作業の分担境界とする。

| パッケージ | 内容 | 依存 |
| --- | --- | --- |
| `shared/core/` | 共通コアの型・プロトコル定数 | なし |
| `shared/engine/` | 汎用前方推論エンジン（ゲーム非依存） | なし |
| `shared/games/<id>/` | ゲーム固有の型・ステージ定数・コンテンツスキーマ | shared/core |
| `server/core/` | Worker + RoomDO（ゲーム非依存） | shared/core |
| `server/games/<id>/` | GameModule実装・コンテンツ検証 | shared, shared/engine |
| `client/core/` | ホーム・ロビー・接続管理・共通UI | shared/core |
| `client/games/<id>/` | ステージごとの画面 | shared, client/core |
| `tools/` | コンテンツ検証CLI | shared, shared/engine, server/games |
| `content/<id>/` | ゲームごとのコンテンツJSON | （tools が検証） |

並行作業の衝突を避けるルールは3つ。

* `shared/core/` の変更（共通の型・プロトコル）は単独PRとし、先にマージする。server/clientの対応はその後の別PRで行う
* ゲームモジュールは `shared/games/<id>/` → `server/games/<id>/` → `client/games/<id>/` の順に作る。異なるゲームのモジュールは互いに独立しているため、並行して作業できる
* 同一パッケージを複数ブランチで同時に触る場合は、着手前にIssue（またはPRのドラフト）で作業範囲を宣言する

`core/` と `games/` の境界を越える変更（共通コアへゲーム固有の概念を持ち込む変更）は、実装を止めて [基本設計/05](./基本設計/05_ゲームモジュール.md) の境界定義の議論に戻す。

## ブランチ・コミット・PR

ブランチは3層とする。

| ブランチ | 役割 | マージ元 |
| --- | --- | --- |
| `main` | リリース済みの状態。マージすると本番へデプロイされる | `dev` |
| `dev` | 常設の統合ブランチ。日常の開発はここへ集約する | `task/` `userstory/` |
| `task/<内容>` `userstory/<内容>` | 作業ブランチ | — |

* 作業ブランチは `dev` から切り、`dev` へPRする。`main` へ直接PRしない
* `feature/` は使わない（ブランチポリシーによりpush不可）
* `main` へのマージは、遊ぶ予定のない時間帯にまとめて行う。マージが進行中の全部屋を切断するためである（後述）
* コミットメッセージ: 日本語 + プレフィックス

| プレフィックス | 用途 |
| --- | --- |
| `機能:` | 機能の追加・変更 |
| `修正:` | バグ修正 |
| `文書:` | ドキュメントのみの変更 |
| `整備:` | ビルド・CI・依存関係・リファクタリング |
| `テスト:` | テストの追加・変更 |

* PRはドラフトで作成する。本文は次のテンプレートに従う

```markdown
## 目的
(1-2文。関連Issue/ADRへのリンク)

## 変更内容
(箇条書き)

## 確認
- [ ] pnpm check / test / validate:content PASS
- [ ] 正本ドキュメント更新済み(不要な場合は理由)
- [ ] 設計判断の変更がある場合、ADR追加済み
```

## CI

GitHub Actionsで `dev` および `main` 宛の全PRに対して次を実行し、すべて必須チェックとする。

1. lint + 型チェック
2. ユニットテスト（`shared/engine` の推論エンジン、DOは `@cloudflare/vitest-pool-workers` で統合テスト）
3. 事件データ検証（`validate:content`。検証7項目は [基本設計/04](./基本設計/04_事件データと検証.md)、判定手順は [基本設計/06](./基本設計/06_推論エンジンと検証アルゴリズム.md)）
4. フォントサブセットの再生成と差分チェック（`content/` の日本語グリフを含む。詳細は [基本設計/04](./基本設計/04_事件データと検証.md)）
5. mainマージ時のみ `wrangler deploy`

### デプロイのタイミング

Cloudflareはデプロイ時にすべてのDurable Objectを再起動し、Hibernation中のWebSocketも切断する。
つまり **mainへのマージは、進行中の全部屋を強制的に切断する**。

`dev` を常設の統合ブランチにしているのは、この切断をリリース時だけに閉じ込めるためでもある。
日常の作業は `dev` へマージされ、デプロイを伴わない。

* クライアントは自動再接続し、プロトコルバージョン不一致の場合は強制リロードする（[基本設計/02](./基本設計/02_クライアント.md)）ため、データは失われない
* ただし演出中・投票中の中断は体験を損なうため、プレイ予定の時間帯はmainへのマージを避ける
* 友人グループ数組の規模では運用ルールで足りる。ブルーグリーン相当の仕組みは作らない

### 実プレイ前のリリース手順

1. `dev` のCIが緑であることを確認する（`check` / `test` / `e2e` / `validate:content` / 生成物の差分チェック）
2. GitHubのリポジトリシークレットに `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` が設定されていることを確認する。未設定の場合、CIのデプロイジョブは成功のままスキップされる（デプロイされない）
3. `dev` を `main` へマージする。CIが `wrangler deploy` を実行する
4. デプロイ後に部屋を1つ作り、ゲーム選択・事件選択・開始までを実機のスマホで確認する
5. 実プレイ後、市民勝率を [設計.md](./設計.md) のリスク表へ追記する

## テスト方針

| 層 | 手段 | 何を防ぐか |
| --- | --- | --- |
| 推論エンジン | vitest ユニットテスト | 事件検証の判定ロジック自体の誤り |
| 事件データ | validate:content（CI必須） | 推理が破綻した事件のリリース |
| Durable Object | vitest-pool-workers 統合テスト | 状態遷移・秘密情報の誤配布・アラーム多重化の退行 |
| クライアント | Playwrightで主要フロー（M2以降） | 部屋作成→投票→開示の導線切れ |
| 実プレイ | リリース前の手動プレイテスト | 自動テストで測れない「ゲームとして面白いか」「英語レベル配分の妥当性」 |

秘密情報の誤配布は最も重大な欠陥として扱い、DO統合テストに専用のテストケースを常設する。対象は2種類ある。

* 証言や犯人フラグが `state` に混入する退行（[ADR-0003](./adr/0003-サーバ権威と秘密情報の個別送信.md)）
* 公開値を認証情報として受理する退行。他人の `playerId` で再接続して `secret` を得られないこと（[ADR-0006](./adr/0006-公開IDと再接続シークレットの分離.md)）

## AIエージェント協働ルール

Claude Codeで実装する際の約束事。人間の開発者にも同じルールを適用する。

### セッションの始め方

1. ルート `CLAUDE.md` の不変条件を確認する
2. `docs/README.md` の正本マップから、触るモジュールの基本設計を読む
3. 作業範囲（触るパッケージ・変えないもの）を最初に宣言する

### 実装中

* 基本設計と矛盾する実装が必要になったら、実装を止めてドキュメント側の議論に戻す。「動くから」でdocと乖離したコードを積まない
* 不変条件（CLAUDE.md）に抵触する要求は、抵触する旨を明示して代替案を出す
* 各基本設計文書の「未決事項」節にある項目を独断で決めない。決めるときは合意を取り、下記「ADRの運用」の基準に該当すればADRを追加し、該当しなければ基本設計の本文へ昇格させる

### 完了時

* Definition of Done（CLAUDE.md）を満たす
* コードから読み取れること（関数の動作・構造）をドキュメントに複製しない。ドキュメントには意図・不変条件・理由だけを書く

### ドキュメントの鮮度維持

* ルート `CLAUDE.md` は50行程度を上限とし、詳細はdocsへ逃がす
* 基本設計の「未決事項」は、決定したら本文へ昇格させて項目を消す
* 四半期に一度、`docs/` 全体とコードの乖離チェックを行う（乖離の検出自体をClaude Codeに依頼してよい）

## ADRの運用

次のいずれかに該当する決定はADRとして `docs/adr/` に記録する。

* 後から覆すコストが高い決定（技術選定、プロトコル形式、データ形式）
* 不変条件の追加・変更
* 一見不自然で、理由を知らないと「直したくなる」実装方針

形式は [adr/README.md](./adr/README.md) のテンプレートに従う。
