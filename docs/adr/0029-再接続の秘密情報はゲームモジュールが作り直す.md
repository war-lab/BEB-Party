# 0029: 再接続の秘密情報はゲームモジュールが作り直す

* ステータス: accepted
* 日付: 2026-09-29

## 決定

`GameModule` に `rebuildSecret` を加える。
再接続したプレイヤーへ送る秘密情報は、保存済みの値ではなく、この関数が `room` と `publicState` と `gameSecret` から作り直した値とする。

`rebuildSecret` が例外を投げた場合に限り、共通コアは保存済みの値を送り、ログに残す。
開示済みの結果（`lastResult`）は作り直さず、保存済みの値の再送を続ける。

`rebuildSecret` は任意のメソッドとして加え、収録済みの全ゲームが実装した時点で必須に変える。

## 背景

共通コアは、ゲームモジュールが返した秘密情報をプレイヤーごとに `secrets.playerSecrets` へ上書きで保存し、再接続したプレイヤーへそのまま再送していた（[基本設計/01](../基本設計/01_サーバ.md)）。
保存済みの値は、送った時点のコードが作った形と内容のまま残る。

デプロイはすべてのDurable Objectを再起動するが、部屋の状態は storage に残る。
部屋は最終アクセスから2時間保持されるため、遊んでいる最中にデプロイすると、再接続したプレイヤーへ旧版のコードが作った秘密情報が届く。

DON'T SAY IT で実際に起きた。
秘密情報に別名の一覧を加えたところ、新しい画面が一覧の長さを直接読む箇所で例外になり、説明者の画面が描けなくなった（GitHub Issue #29、PR #27）。

PR #27 では、DON'T SAY IT の側で欠けた欄を補う処理を置いた。
この対処には2つの限界がある。

* 補えるのは形だけで、内容は旧版のまま届く。禁止語の一覧や提示数が現行のルールと違うまま、次のカードへ進むまで判定が続く
* ゲームごとに書く必要があり、他のゲームで秘密情報の形を変えたときに、同じ対処が要ると気づく仕組みがない

## 理由

### 作り直せる根拠

ゲームモジュールは、乱数を `start` に注入される `seed` からしか作れない（[基本設計/05](../基本設計/05_ゲームモジュール.md)の呼び出し規約）。
そのため抽選の結果は `start` で確定し、`gameSecret` か `publicState` に残る。

共通コアは、ゲーム中に参加者の増減もレベルの変更も受け付けない。
参加と `kick` はロビーでしか受理せず、レベルは参加時にだけ決まる。

したがって、各プレイヤーへ最後に送った秘密情報は `room` と `publicState` と `gameSecret` から決まる。
収録済みの6本について、コードを読んでこれを確かめた（2026-09-29）。
テストでの突き合わせは各ゲームの実装で行う。

### 作り直しをゲームモジュールに任せる

どの値を作り直すかはゲームごとに違い、終局後や開示中には現在のステージと食い違う場合がある。
たとえば DON'T SAY IT は終局時に次のカードを引いてから `gameSecret` を保存するため、現在の状態のまま作り直すと、最終ラウンドの説明者に誰も見ていないカードが届く。

この場合分けを共通コアに置くと、共通コアがゲーム固有の概念を持つことになる（不変条件4、[ADR-0009](./0009-部屋基盤とゲームモジュールの分離.md)）。
そのため `room` の `lifecycle` と `stage` を渡し、場合分けはゲームモジュールが行う。

### 例外のときは保存済みの値を送る

作り直しは、再接続した時点のコンテンツを引く場合がある。
デプロイでコンテンツのIDが消えると、ゲームによっては例外になる。

例外のときに保存済みの値を送れば、挙動はこの決定より前と同じになり、悪化しない。
何も送らない案は、説明者がカードを見られない状態を作るため採らない。

この退避のために、`playerSecrets` の保存は続ける。

### 開示済みの結果は作り直さない

結果はコンテンツを引いて作るゲームが多い。
作り直すと、デプロイをまたいだときに、すでに全員に見せた開示と中身が変わりうる。

結果は開示した時点で内容が確定したものとして扱い、保存済みの値を再送する。

### 任意から始めて必須にする

`shared/core` の変更は単独のPRで先にマージし、各パッケージの対応は別のPRで行う（[開発ガイド](../開発ガイド.md)）。
最初から必須にすると、`shared/core` のPRだけで全ゲームが型エラーになり、この規約に従えない。

一方、任意のまま残すと、実装していないゲームは保存済みの値を送り続け、形の変更に気づく仕組みが無いという問題が残る。
そのため全ゲームの実装が揃った時点で必須に変え、新しいゲームは型検査で実装を強制する。

## 代案

### ゲームごとに旧形式を補う処理を続ける

PR #27 の方式である。
内容の古さを直せず、他のゲームで同じ対処が要ることに気づけないため採らない。

### 秘密情報に版番号を持たせ、一致しない値を送らない

旧形式の値が画面へ届くことは防げる。
しかし送らないと、説明者がカードを見られない状態が次の遷移まで続くため採らない。

### プロトコルバージョンを上げる

古いクライアントを弾くことはできるが、サーバに保存された旧形式の値は残る。
問題はサーバ側の保存値にあるため、解決にならない。

### 保存をやめ、作り直しだけにする

storage は減るが、作り直しが例外になったときに送れる値が無くなるため採らない。

## 影響

* `shared/core` の `GameModule` に `rebuildSecret` が加わる。最初は任意で、全ゲームの実装後に必須にする
* `server/core` の再接続は、`rebuildSecret` があればその戻り値を送り、例外なら保存済みの値を送る。戻り値が `undefined` なら秘密情報を送らない
* 各ゲームは、遷移で送った値と作り直した値が全ステージで一致することをユニットテストで確かめる。終局後や開示中に単純に作り直すと食い違うゲームがあるためである
* 作り直しは再接続した時点のコンテンツを引く場合がある。デプロイをまたいだ部屋では、接続を保っている人と再接続した人とで、表示が食い違う可能性がある。前者は次の遷移で新しい値を受け取るため、この食い違いは受け入れる
* `gameSecret` 自体の形が変わる問題は対象外である。`handleAction` と `onDeadline` も同じ `gameSecret` を読むため、この決定の前から各ゲームモジュールが扱っている
* DON'T SAY IT の旧形式を補う処理のうち、秘密情報の分は不要になる。結果の分は残る。削除するかは DON'T SAY IT の対応PRで判断する
* [基本設計/01](../基本設計/01_サーバ.md) と [05](../基本設計/05_ゲームモジュール.md) を、それぞれの変更と同じPRで更新する
