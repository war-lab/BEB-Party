# 0006: 公開IDと再接続シークレットの分離

* ステータス: accepted
* 日付: 2026-08-10

## 決定

プレイヤーの識別子を2つに分ける。

* `playerId`: 公開ID。`state` のプレイヤー一覧に載り、`vote` の対象指定に使う
* `reconnectToken`: 再接続用の秘密値。`joined` で本人にのみ渡し、`state` を含むどのブロードキャストにも載せない

再接続の認証は `reconnectToken` のみで行う。`playerId` を認証情報として受理しない。

## 理由

当初案は `playerId` を再接続トークンと兼用していたが、これは成立しない。

`vote` は投票先を `targetPlayerId` で指定するため、全クライアントが全員の `playerId` を知っている必要がある。
トークンを兼用すると、全員のトークンが全員に配られることになり、`join{token: 他人のplayerId}` でなりすまして他人の `secret`（証言・犯人フラグ）を受信できる。

これは [ADR-0003](./0003-サーバ権威と秘密情報の個別送信.md) が主張する「クライアントに秘密を渡さなければ自分の情報以上は得られない」という構造的安全性を、通信内容の傍受すら不要な形で破る。

代替案として「投票先をプレイヤー一覧のインデックスで指定する」も検討したが、`playerId` は再接続・切断表示・投票内訳の開示でも参照されるため公開が避けられず、秘密値との兼用そのものをやめる方が単純である。

## 影響

* `reconnectToken` は推測不能な乱数（128bit以上）とし、DOが発行する。連番・部屋コード由来の値にしない
* `Player` 型に `reconnectToken` を持たせない。DOの秘密状態（`secrets` キー）側で `playerId → reconnectToken` を保持する
* クライアントは `reconnectToken` を `sessionStorage` に保存する。画面表示・ログ出力・URLに載せない
* `state` へ新フィールドを追加するレビューでは、ADR-0003の観点に加えて「認証に使える値でないか」も確認する
