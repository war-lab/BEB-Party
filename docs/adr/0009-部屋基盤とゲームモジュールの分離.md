# 0009: 部屋基盤とゲームモジュールの分離

* ステータス: accepted
* 日付: 2026-08-12

## 決定

BEB Partyを単一ゲームではなく**英語パーティゲーム集**として設計する。

コードを2層に分ける。

* **共通コア**: 部屋・参加者・レベル・接続・ホスト権限・ゲーム選択・ステージ進行の駆動・秘密情報の配信機構。ゲーム固有の概念を一切持たない
* **ゲームモジュール**: ステージ定義、配役、秘密情報の中身、ルール判定、結果生成、コンテンツ検証。ゲーム1本につき1モジュール

共通コアはゲーム固有のメッセージ名・フェーズ名・データ形式を知らない。
プロトコルはゲーム固有の操作を `action` 1種類に集約し、共通コアはそれをゲームモジュールへディスパッチするだけとする。

MVPで収録するゲームは引き続きENGLISH DETECTIVES 1本とする（[ADR-0005](./0005-MVPはENGLISH-DETECTIVES.md)は維持）。

## 理由

プロダクトの想定は最初から複数ゲームの詰め合わせであり、DETECTIVESはその1本目である。
`BEB Party` という名称もゲーム集を前提にしている。

しかし当初の設計はDETECTIVES固有の語彙を共通部分に焼き付けていた。

* `Room.phase` が `briefing | investigation | voting | reveal`
* `Room.settings` が `caseId`（事件という概念はDETECTIVES固有）
* `SecretPacket` が `isCulprit`（犯人フラグを持つのはこのゲームだけ）
* C→Sメッセージが `selectCase` / `ready` / `vote`
* エンドポイントが `GET /api/cases`

この状態で2本目を追加すると、プロトコルの互換性を壊す変更（`v` のインクリメント）と、部屋基盤の書き直しが同時に必要になる。

分離を今行う理由は、実装がまだ1行もない（M0前）ためである。
`shared/` の型を書いた後では、server・client・contentすべてに変更が波及する。今なら書き直しコストが0である。

代替案として「DETECTIVES専用に作り、2本目の時点で実際の差分を見て切り直す」も検討した。
過剰抽象化を避けられる利点はあるが、切り直しの時期がMVPリリース後になり、稼働中のプロトコルを壊す変更になるため採らなかった。

## 影響

* 共通コアに何かを入れる判断基準は「2本目以降でも確実に必要と言えるか」とする。**迷ったらゲームモジュール側に置く**。これは過剰抽象化を防ぐための歯止めであり、共通コアの肥大化はこのADRの目的に反する
* 共通コアのコードがゲームIDで分岐（`if (gameId === 'detectives')`）していたら設計の失敗とみなす。分岐はディスパッチテーブル1箇所に閉じる
* [ADR-0004](./0004-事件データの静的JSON化とCI検証.md)の決定（静的JSON + CI必須検証）は維持し、格納パスのみ `cases/` から `content/detectives/` へ変更する。検証コマンドは `pnpm validate:content` とし、ゲーム別の検証プラグインを呼び分ける
* 前方推論エンジン（`tools/engine`）は既に汎用推論器として設計済みであり、この分離と整合する
* レベル1〜5の定義は共通コアに置く。ゲーム横断でプレイヤープロファイルとして使う既定方針（[構想v2](../構想v2.md)）を実装に反映する
* 境界の詳細と、ゲームを追加する手順は [基本設計/05_ゲームモジュール.md](../基本設計/05_ゲームモジュール.md) を正とする
