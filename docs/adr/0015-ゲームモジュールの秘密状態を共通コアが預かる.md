# 0015: ゲームモジュールの秘密状態を共通コアが預かる

* ステータス: accepted
* 日付: 2026-08-17

## 決定

`GameModule` が呼び出しをまたいで保持する秘密状態を `gameSecret` として定義し、共通コアが不透明な値として預かる。

`start` と `GameTransition` が新しい値を返し、共通コアはそれを `secrets` キーへ保存する。
`handleAction` と `onDeadline` の入力に、保存されている値をそのまま渡す。
共通コアは中身を解釈せず、ブロードキャストにも載せない。

## 理由

DETECTIVESの投票先は、開示まで伏せたまま蓄積する必要がある。

投票先を公開状態（`room.gameState`）に置くと `state` ブロードキャストに載り、開示前に全員へ漏れる（[ADR-0003](./0003-サーバ権威と秘密情報の個別送信.md)）。
`GameTransition.secrets` は投票者本人へ個別送信する値であり、集計時に全員分を読み戻す経路がない。
そのため、モジュールが自分のためだけに持つ秘密状態の置き場が要る。

[基本設計/01](../基本設計/01_サーバ.md)は当初から `secrets` キーの内容に「ゲームモジュールが保持する秘密状態」を挙げていた。
[基本設計/05](../基本設計/05_ゲームモジュール.md)のインターフェースにその受け渡し口がなく、両者が食い違っていた。
この決定は、01の設計に合わせて05のインターフェースを補うものである。

代替案として「投票を受けた時点で結果を確定し、投票先を保持しない」も検討した。
最後の1人が投票するまで集計できず、締切による棄権の扱い（[基本設計/08](../基本設計/08_DETECTIVESゲームモジュール.md)）も表現できないため採らない。

代替案として「共通コアが全プレイヤーの `secrets` をモジュールへ渡す」も検討した。
モジュールが他人へ配った秘密を読めるようになり、秘密の配布先と保持者の対応が曖昧になるため採らない。
モジュールが自分の状態を持つ形のほうが、公開・個別送信・モジュール内部の3種類の切り分けが明確になる。

## 影響

* `GameModule` と `GameTransition` に型引数 `TGameSecret`（既定 `unknown`）が増える。既存のゲームは指定しなくてよい
* 共通コアは `gameSecret` の内容を検査しない。ゲーム固有の概念が共通コアへ流入しない（[ADR-0009](./0009-部屋基盤とゲームモジュールの分離.md)）
* `gameSecret` は `state` にも `result` にも自動では載らない。開示したい値はモジュールが `result` へ明示的に詰める
* `nextGame` で `playerSecrets` とともにクリアする。前のゲームの秘密状態を次のゲームへ持ち越さない（[ADR-0011](./0011-部屋単位の通算スコアを持たない.md)）
* 秘密状態が呼び出しをまたいで戻ることは、スタブ `GameModule` を使ったRoomDOのテストで検証する。戻していなくてもゲームは動いてしまい、投票が1票も蓄積されない形で壊れるためである
