# 0028: ロビーでホストが切断中の参加者を外せるようにする

* ステータス: accepted
* 日付: 2026-09-28

## 決定

共通メッセージに `kick`（`playerId`）を加え、ロビーでホストが切断中の参加者を部屋から外せるようにする。

受理するのは次の4条件をすべて満たす場合に限る。

* `lifecycle` が `lobby` である
* 送信者がホストである
* 対象が部屋の参加者で、送信者自身ではない
* 対象が切断中（`connected: false`）である

受理したら、対象の席を `players` から消し、再接続トークンと配布済みの秘密を `secrets` から消す。
消したトークンは失効済みとして `secrets` に残す。

失効済みのトークンで `join` が届いたら、lifecycleによらず `kicked` を返し、席を作らない。
この `join` に対してはソケットを閉じない。閉じると、`kicked` を知らない旧SPAが再接続を繰り返す。

一方、外した時点で対象の席のソケットが残っていれば、`kicked` を送ってから閉じる。
通常は死活判定がすでに閉じており、残るのは閉じきる前のソケットに限られる。

クライアントは `kicked` を受けたら再接続をやめ、保存していたトークンを捨てて、部屋コードを入れたホーム画面へ戻す。
入り直すかは本人が決める。
戻るボタンやリロードで本人の選択を経ずに入り直さないよう、履歴を置き換え、名乗った記録に外された印を付ける（[基本設計/02](../基本設計/02_クライアント.md)）。

ゲーム中（`playing` / `finished`）には外せない。
プロトコルバージョン `v` は据え置く。

## 背景

参加者には退室の操作が無く、切断しても席は残る（[ADR-0026](./0026-対象人数を2人から6人に広げる.md)）。

入室は選択中のゲームの上限人数で止まる（[基本設計/01](../基本設計/01_サーバ.md)）。
2〜4人用のESCAPE CALLでは、戻ってこない人が1人いると4席のうち1席が埋まったままになり、代わりの人が入れない。
部屋を作り直すしか手が無かった。

## 理由

### ロビーに限る

ゲーム中に参加者を消すと、ゲームモジュールが配った役割や断片の持ち主がいなくなる。
ESCAPE CALLでは抜けた人の断片が無いと錠が解けず、DETECTIVESでは犯人役が抜けるとゲームが成り立たない。

これに対処するには、人が抜けたことをゲームモジュールへ知らせるフックが要る。
フックは境界の変更（[基本設計/05](../基本設計/05_ゲームモジュール.md)の手順6）であり、収録6本それぞれで抜けたときの扱いを決める必要がある。
ロビーであれば席を消すだけで済み、ゲームモジュールは関わらない。

### 切断中の人に限る

困っているのは、戻ってこない人の席が空かないことである。
接続中の人は同じ部屋にいるため、口頭で頼めば済む。

対象を絞れば、ホストが誤って接続中の人を外す事故も起きない。

### トークンを失効済みとして残す

トークンを消すだけでは、外された端末が自動の再接続で戻ってくる。
照合できないトークンは、ロビーでは新規参加として扱うためである（[基本設計/01](../基本設計/01_サーバ.md)のプレイヤーの認証と再接続）。
鞄の中の端末が復帰するたびに、本人の意思と関係なく席を取り直すことになる。

失効済みとして残せば、戻ってきた端末に `kicked` を返して止められる。
本人が入り直すことは止めない。
ホーム画面から入り直すと、トークンを持たない `join` になり、新しい席を得る。

失効済みのトークンは部屋の破棄（最終アクセスから2時間）で消える。
1部屋で外す人数は数人にとどまる。

storageの肥大を止める保険として直近100件までを残し、超えたら古いものから捨てる。
捨てたトークンの端末は、戻ってくると新しい席を得る。

### `playerId` を対象の指定に使う

`playerId` は `state` で全員に配られる公開値であり、認証情報として受理しない（[ADR-0006](./0006-公開IDと再接続シークレットの分離.md)）。
`kick` での `playerId` は対象の指定であり、権限はホストのソケットであることで確かめる。
ADR-0006が禁じる使い方には当たらない。

## 代案

### 切断から一定時間で自動的に外す

採らない理由は、席が消える時期を誰も制御できないことである。
トイレや電話で一時的に離れた人の席まで消える。
ホストが見て判断する方が、同室で遊ぶ前提に合う。

### 参加者に退室の操作を持たせる

困っているのは戻ってこない人の席であり、本人は操作できない。
退室の操作だけでは解決しない。

## 影響

* `shared/core` に `KickMessage` とエラーコード `kicked` が加わる。`parseClientMessage` が `kick` を受け付ける
* `server/core` の `SecretsState` に失効済みトークンの一覧が加わる。既存の部屋の `secrets` には一覧が無いため、無い場合は空として扱う
* ロビーのホストの画面で、切断中の人の席に「外す」操作が出る
* 互換を壊さないため `v` は据え置く。旧SPAは `kick` を送らない。旧SPAが `kicked` を受けた場合は未知のコードとして扱う。サーバは `join` への `kicked` でソケットを閉じないため再接続の繰り返しは起きないが、席も作られず、画面は更新されないまま残る。リロードすれば新しいSPAになる
* `kicked` を返した未参加のソケットは、サーバが回収しない。死活判定は参加していないソケットを対象にしないためで、`game_in_progress` を返したソケットと同じ扱いである。旧SPAはハートビートを送り続けるため部屋の破棄まで残りうるが、自動応答はDurable Objectを起こさず、ブロードキャストの宛先にも観戦の枠にも入らない。新しいSPAは自分で閉じる
