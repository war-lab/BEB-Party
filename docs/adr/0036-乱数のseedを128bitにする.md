# 0036: 乱数のseedを128bitにする

* ステータス: accepted
* 日付: 2026-11-19

## 決定

共通コアが `GameModule.start` へ注入する `seed` を、32bit から 128bit（32bit×4）に広げる。
seed は RoomDO が `crypto.getRandomValues` で作る（`server/core/src/ids.ts` の `generateSeed`）。

乱数の生成器は、128bit の seed に対して sfc32 を使う（`shared/core/src/rng.ts` の `createRandom`）。
初期の出力の偏りを避けるため、最初の12回の出力を捨てる。

`seed` の型は `Seed = number | readonly [number, number, number, number]` とする。
数値の seed は、テストと再現用の短い表記として残し、従来どおり 32bit の mulberry32 で回す。
実行時に数値の seed を渡す経路は作らない。

ゲームモジュールは `createRandom(seed)` を呼ぶだけで、seed を数値として計算に使わない。
そのため、ゲームモジュールとそのテストは変更しない。

## 理由

### 32bitでは、公開された並びから秘密が割れる

2026-11-19の多角レビュー（敵対的レビューの担当）で、SECRET TEAMS のチーム所属と全員の単語を、参加者が自分の端末で特定できることを実測した。

手順は次のとおりである。

1. 公開状態の説明の順番（`speakerOrder`）から、シャッフルで使われた添字の列を逆算する
2. mulberry32 の状態は「seed + k × 定数」で進むため、k 番目の出力は seed から直接計算できる。2^32 通りの seed を、手順1の列と合うものに絞る
3. 残った候補で `start` を再実行し、選択肢の並び（`themeChoices`）と、自分の単語とテーマが一致するものを選ぶ

8人の卓で、手順2は約59秒、手順3は約9秒で候補が1つに絞れ、本当のチーム分けと一致した（シングルスレッドの JavaScript での実測。担当の報告による）。

SECRET TEAMS は、チーム分け、単語の配布、選択肢の並び、説明の順番を、同じ乱数列から作っている。
公開する値と秘密の値が同じ列から出るため、公開する値から列を復元すれば秘密も割れる。

同じ原理で、TWO-HEADED SPEAKER の山札の先読みもできる見込みである（未検証）。
お題を終えるたびに答えが開示され、1枚ごとに状態の手がかりが増えるためである。

この弱点は [基本設計/11](../基本設計/11_WHOWROTETHISゲームモジュール.md) の「識別子」の節で既に認識しており、WHO WROTE THIS? は乱数から識別子を振らない設計で避けていた。
新しい3本の設計では、この知見を共通コアの側で塞いでいなかった。

### 128bitにすれば総当たりは成り立たない

2^128 通りの総当たりは現実的な時間で終わらない。
seed を作る側（RoomDO）だけを変えればよく、ゲームモジュールの設計には手を入れずに済む。

sfc32 は暗号学的に安全な生成器ではない。
出力から状態を推定する解析の余地は残るが、この製品の脅威（同じ部屋の参加者が手元で試す）に対しては、総当たりを不可能にすれば足りると判断した。

### 数値のseedを残す

既存のテストは、数値の seed で特定の配役やシャッフルの結果を期待している。
数値の seed の出力まで変えると、10本のテストの期待値をすべて書き換えることになり、変更の理由と無関係な差分が混ざる。
数値の seed は実行時に使わないため、32bit のまま残しても今回の脅威には当たらない。

## 代案

### 公開用と秘密用で乱数列を分ける

公開する値と秘密の値を、別々の seed から作る案である。

それぞれの列が 32bit のままだと、山札のように少しずつ開示される秘密は、開示された値から秘密の列を総当たりで復元できる。
分けるだけでは足りないため採らない。

### 暗号学的に安全な生成器を使う

ChaCha などを使う案である。
Web Crypto の決定的な乱数は非同期の API であり、同期関数として書く `start` から使えない。
自前で実装するとコードが大きくなり、今回の脅威に対して過剰である。

## 影響

* `shared/core` に `Seed` 型を加え、`createRandom` が 128bit の seed を受ける。`GameModule.start` の `seed` の型を `Seed` にする
* `server/core` の `generateSeed` が 32bit×4 を返す
* ゲームモジュールとそのテストは変更しない
* [基本設計/05](../基本設計/05_ゲームモジュール.md) の GameModule インターフェースと、[基本設計/01](../基本設計/01_サーバ.md) のゲームモジュールの呼び出し規約に反映する
