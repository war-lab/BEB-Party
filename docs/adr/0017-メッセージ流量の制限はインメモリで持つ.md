# 0017: メッセージ流量の制限はインメモリで持つ

* ステータス: accepted
* 日付: 2026-08-18

## 決定

RoomDOはWebSocketメッセージの流量制限を、ソケットごとのカウンタとして**インメモリ（`WeakMap`）に**持つ。

storageにも `serializeAttachment` にも書かない。Hibernationやデプロイでカウンタが消えることを許容する。

上限は1ソケットあたり20通 / 10秒とし、超過分は処理せず `rate_limited` を返す。

## 理由

接続確立時のレート制限（Workers Rate Limiting API、[基本設計/01](../基本設計/01_サーバ.md)）は、確立後のメッセージには効かない。
1本のソケットから毎秒100通以上を送れることを実測した。書き込みを伴うメッセージが混ざると、無料枠のうち**SQLite rows written（10万/日、アカウント単位）**が最初に枯渇する。

カウンタをstorageに置く案は採らない。
「書き込みを抑えるための仕組み」が、判定のたびに書き込みを増やす。守ろうとしている資源を守る過程で消費するため、目的と手段が矛盾する。

`serializeAttachment` に持たせる案も同じ理由で採らない。`serializeAttachment` の書き込みもstorage操作である。

インメモリで許容できるのは、カウンタの消失が**制限を緩める方向にしか働かない**ためである。
消えた直後は攻撃者が窓1つ分（20通）を余分に通せるが、部屋の状態・席・秘密情報のいずれにも影響しない。
Hibernationは無通信が続いたときに起きるものであり、連打の最中には起きない。

## 影響

* この決定は流量カウンタに限る。部屋の状態・席とソケットの対応・秘密情報は引き続きstorageと `serializeAttachment` が正であり、インメモリに置かない（[ADR-0002](./0002-CloudflareDurableObjects採用.md)、[ADR-0003](./0003-サーバ権威と秘密情報の個別送信.md)）
* DO内にインメモリ状態を見つけても、storageへ移すのが常に正しいとは限らない。移す前にこのADRを読む
* ハートビート（`ping`）は `setWebSocketAutoResponse` で返るためカウンタを消費しない。上限に数えるのはクライアントの明示的な操作だけである
* 上限を超えた送信元には `rate_limited` を返す。クライアントは致命的エラーとして扱わず、再接続もしない（通常のプレイでは到達しない値である）
