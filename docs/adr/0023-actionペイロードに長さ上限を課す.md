# 0023: actionペイロードに長さ上限を課す

* ステータス: accepted
* 日付: 2026-09-01

## 決定

共通コアの `parseClientMessage` が、`action` の残余ペイロードに長さの上限を課す。

* 定数は `shared/core/src/validate.ts` に `ACTION_MAX_CHARS = 512` として置く
* 判定は残余ペイロードを `JSON.stringify` した文字数で行う（`SETTINGS_MAX_CHARS` と同じ方式）
* 超過とシリアライズ不能（循環参照等）は `null` を返し、サーバは `invalid_payload` を返す
* プロトコルバージョン `v` は据え置く

これは[実装計画](../実装計画/ゲーム構想20案の収録計画.md) が C-1 として挙げていた変更である。

## 背景

現状、`action` の残余キーは検証を経ずに透過する。
既収録3本が `action` に載せるのはプレイヤーIDと5要素の順位配列であり、上限がなくても問題が出ていない。

4本目の WHO WROTE THIS?（[基本設計/11](../基本設計/11_WHOWROTETHISゲームモジュール.md)）は、プレイヤーが書いた英文を `action` に載せる。
提出テキストは `gameSecret` へ蓄積され、開示ステージで公開状態と `result` を経由して全員へ再配信される。

## 理由

1件の入力が以後の配信量を増幅する構造は、表示名（`name`）と同じである。
`name` は `state` ブロードキャストに毎回載るため共通コアが1〜24文字に制限している（[基本設計/01](../基本設計/01_サーバ.md)）。
提出テキストも同じ性質を持つため、上限は器の側が持つ。

上限がない場合の影響は2つある。

* storage の rows written とメッセージ量が1人の入力で伸びる
* SQLiteバックエンドは1キーあたり2MBが上限であり、超えた部屋は以後すべての書き込みが失敗して復旧できない（[基本設計/01](../基本設計/01_サーバ.md)）

ソケットあたりの流量制限（20通/10秒。[ADR-0017](./0017-メッセージ流量の制限はインメモリで持つ.md)）は通数を数えるだけであり、1通の大きさを抑えない。
このため流量制限とは別に長さの上限が要る。

## 512文字の根拠

WHO WROTE THIS? の提出は140文字を上限とする（[基本設計/11](../基本設計/11_WHOWROTETHISゲームモジュール.md)）。
JSON化でキー名・引用符・エスケープが加わっても512文字に収まる。

`SETTINGS_MAX_CHARS`（2048）より小さくするのは、`settings` がロビーで1回だけ送られるのに対し、`action` はゲーム中に繰り返し送られるためである。

共通コアの上限は、ゲームモジュール側の上限より常に大きく保つ。
ゲームが必要とする長さを共通コアが決める形にしない。
512文字を超える提出を許すゲームを収録する場合は、この値の見直しが新しいADRを要する判断になる。

## 代案

### ゲームモジュール側だけで検証する

`submit` の受理時にモジュールが長さを見れば、そのゲームについては同じ効果が得られる。

採らない理由は、モジュールが検証を書き忘れた経路がそのまま通ることである。
上限の欠落は無料枠の消費とstorageの破損に直結するため、個々のゲームの実装品質に依存させない。

ゲームモジュール側の検証（`too_long`）は引き続き必要である。
共通コアの上限は器を守る値であり、ゲームのルールとして適切な長さとは別の水準にある。

### メッセージ全体のバイト数で制限する

WebSocketの受信サイズで一律に切る案である。

採らない理由は2つある。
ランタイム側の制約と混ざって上限の所在が分かりにくくなること、`name` と `settings` で採った「フィールド単位のシリアライズ長」という既存の形と揃わないことである。

## 影響

* `shared/core` に `ACTION_MAX_CHARS` が加わり、`parseClientMessage` の `action` 分岐が長さを見る
* [基本設計/03](../基本設計/03_プロトコル.md) と [基本設計/01](../基本設計/01_サーバ.md) の受信値検証の記述を同じPRで更新する
* 既収録3本への影響はない。3本の `action` がいずれも上限に触れないことをテストで固定する
* 互換を壊さないため `v` は据え置く。既存クライアントが送る `action` はすべて512文字未満であり、`unsupported_version` の判定に影響しない
* クライアントは提出フォームの入力を140文字で止める。共通コアの上限に到達する前にゲーム側の上限で止まるため、`invalid_payload` は通常の操作では発生しない
