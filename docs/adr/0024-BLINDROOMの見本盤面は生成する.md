# 0024: BLIND ROOMの見本盤面はコンテンツに持たず生成する

* ステータス: accepted
* 日付: 2026-09-11

## 決定

BLIND ROOMの見本盤面（3×3のどのマスにどのアイテムを置くか）を `content/blindroom/*.json` に持たない。
`GameModule.start` が、共通コアから注入された `seed` とアイテムセットから全ラウンド分を生成する。

コンテンツが持つのはアイテムセット（アイテムの一覧と難度の段）と言い回しであり、`validate:content` はそちらだけを検査する。
生成物が満たす不変条件（アイテムがちょうど5個・重複なし・すべてが現ラウンドのアイテムセットに含まれる）は、モジュールのユニットテストで固定する。

## 理由

収録4本のコンテンツは、人手でしか作れない情報を持つ。
事件データは推理構造（[ADR-0004](./0004-事件データの静的JSON化とCI検証.md)）、禁止語は語と語の関係、目標カードは同時達成可能性、質問は答えの一意性である。
いずれも作者の判断が入っており、機械検証はその判断の誤りを見つけるために置いている。

見本盤面はこれに当たらない。
盤面はアイテムセットと配置の直積であり、どのアイテムをどこへ置いても遊びとして成立する。
人手で書いても情報が増えず、ラウンド数（6人なら6件）とパックの多様性の積だけファイルが伸びる。

生成にすると、同じパックを続けて遊んでも見本が変わる。
`nextGame` で `gameSecret` は破棄され、使用済みを持ち越す口が `GameModule` に無いため、静的な盤面を持つ形では同じ配置が続けて出る（DON'T SAY ITの `usedCards` と同じ制約）。

## 代案

### 盤面をJSONで持ち、`validate:content` で検査する

収録4本と形が揃う。

採らない理由は、検査すべき対象が無いことである。
「5個ある」「重複が無い」「idが存在する」は生成側の不変条件であり、生成器を1つ書いてユニットテストで固定すれば、パックが増えても再検査が要らない。
JSONで持つと同じ検査をパックの件数だけ繰り返すことになる。

### 盤面のパターンを人手で数種類作り、抽選する

「1列に並ぶ」「四隅へ散る」のような配置の質を作者が決められる。

採らない理由は、配置の質が説明の難しさを決めるという前提が未検証であることである。
BLIND ROOMの難度はアイテムの区別しにくさに主に依存すると見ており、その前提でアイテムセットを2段に分けている（[基本設計/12](../基本設計/12_BLINDROOMゲームモジュール.md) のレベル差の吸収）。
実プレイで配置の質が効くと分かった時点で、生成に制約を足すか本案へ移る。

## 影響

* `content/blindroom/*.json` に盤面を書く欄を設けない。追加した場合、`validateContent` はスキーマ違反として落とす
* 見本の再現には `seed` が要る。不具合の再現手順に部屋のseedを含める必要がある（収録4本の配役・山札と同じ扱い）
* 生成器は `start` の中だけで動く。`handleAction` と `onDeadline` にはシードが渡らないため、ラウンドごとに生成する形は取れない（[基本設計/05](../基本設計/05_ゲームモジュール.md) の呼び出し規約）
* この決定はBLIND ROOMの盤面に限る。コンテンツを生成に置き換えてよい条件は「作者の判断が入らない」ことであり、判断が入るものは[ADR-0004](./0004-事件データの静的JSON化とCI検証.md)のとおり静的JSONと機械検証で扱う
