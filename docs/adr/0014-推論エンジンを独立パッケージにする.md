# 0014: 推論エンジンを独立パッケージにする

* ステータス: accepted
* 日付: 2026-08-17

## 決定

汎用前方推論エンジンを `shared/engine`（`@beb/engine`）という独立したパッケージに置く。

このパッケージは他のどのパッケージにも依存しない。
`server/games/<id>` の `validateContent` と `tools` の検証CLIが、ともにこのパッケージへ依存する。

当初 [基本設計/05](../基本設計/05_ゲームモジュール.md) と [実装計画/M1](../実装計画/M1.md) はエンジンを `tools/engine` に置く前提で書かれていたが、この決定で置き場所を変える。

## 理由

エンジンを `tools` の中に置くと、依存の向きが閉じない。

`validateContent` の実装はゲームモジュール（`server/games/<id>`）に置くと決めており（[ADR-0009](./0009-部屋基盤とゲームモジュールの分離.md)、[基本設計/05](../基本設計/05_ゲームモジュール.md)）、その実装はエンジンを使う。
一方 `tools` は `validateContent` を呼ぶために `server/games/<id>` へ依存する（[基本設計/07](../基本設計/07_リポジトリとツールチェーン.md)）。
エンジンが `tools` の中にあると `tools → server-detectives → tools` の循環になり、07が「逆向きは lint で禁じる」と定めた依存が実際に発生する。

検討した代替案は2つある。

第一に、エンジンを `tools` に残し、`validateContent` に関数として注入する案。
パッケージ境界は保てるが、エンジンの型を `server/games/<id>` 側で二重に宣言することになり、`GameModule.validateContent(content)` のシグネチャからエンジンの供給元が消える。
M2でゲームモジュールを組み立てる際に、CI専用の依存をランタイムの構築経路へ持ち込む必要が生じるため採らない。

第二に、DETECTIVESの検証そのものを `tools` へ移す案。
`validateContent` を `GameModule` の責務から外すことになり、「ゲーム固有の判定はゲームモジュールに置く」という分離（[ADR-0009](./0009-部屋基盤とゲームモジュールの分離.md)）を崩すため採らない。

エンジンを独立パッケージにすると、依存は `engine ← server-detectives ← tools` の一方向で閉じる。
エンジンがゲームを知らないことは、`@beb/*` のimport禁止としてlintで機械的に担保できる。

## 影響

* `shared/engine` は他パッケージをimportしない。ESLintで `@beb/*` のimportを禁止する
* エンジンはWorkerのバンドルに入る（`server/games/<id>` が依存するため）。ランタイムでは検証を呼ばないが、コードは含まれる。Nodeのグローバル（`node:fs` 等）に触れてはならない
* `server/` から `tools` を参照しない制約は変わらない。ESLintで `@beb/tools` のimportを禁止する
* パッケージ数は8から9になる（[基本設計/07](../基本設計/07_リポジトリとツールチェーン.md)のパッケージ表）
* 将来ESCAPEモードの解法グラフ検証を追加する場合も、同じ `@beb/engine` を参照する
