# 0032: チーム編成は自己申告レベルで揃えて開始時に抽選する

* ステータス: accepted
* 日付: 2026-11-11

## 決定

チーム戦のゲームは、`start()` の中でチームを編成する。
編成には共通コアの関数 `formBalancedTeams` を使う。
ロビーにチーム分けの画面と状態は持たせない。

`formBalancedTeams` は、参加者の自己申告レベル（`Player.level`、1〜5）を使い、チーム間のレベルの偏りが小さい編成の中から乱数で1つを選ぶ。

```ts
// shared/core/src/teams.ts
export function formBalancedTeams<T extends { id: string; level: Level }>(
  players: readonly T[],
  sizes: readonly number[],
  random: () => number,
): T[][];
```

チームの人数構成（`sizes`）はゲームモジュールが決める。
たとえば6人のペア戦なら `[2, 2, 2]`、7人なら `[2, 2, 3]` のように渡す。
人数が奇数のときの扱いはゲームごとのルールであり、共通コアは決めない。

編成の手順は次のとおりとする。

1. 参加者を `sizes` に従って分けるすべての分け方を列挙する。同じ人数のチームを並べ替えただけの分け方は1通りと数える
2. 各分け方について、チームごとの平均レベルに最大のチーム人数を掛けた値（合計レベルの尺度にそろえた値）を求め、その最大と最小の差を偏りとする
3. 偏りが「最小の偏り + 2」以下の分け方を候補とし、`random` で1つを選ぶ
4. 選んだ分け方のチームの並び順を `random` で入れ替えて返す

チームを公開するか伏せるかはゲームモジュールが決める。
公開するゲームは `publicState` に載せ、SECRET TEAMSのように伏せるゲームは秘密情報として本人にだけ配る（不変条件2）。

## 理由

### 完全な乱数ではレベル差がチームの勝敗に出る

[ゲーム構想.md](../ゲーム構想.md)の追加案27〜33は、チームの強さをレベルの合計で揃えることを前提にしている。
乱数だけで分けると、6人のペア戦でレベル5どうしと1どうしが組む編成が一定の確率で出る。
この編成では、勝敗が英語力の差でほぼ決まる。

アプリは英語を理解しないため（[ADR-0001](./0001-ランタイムAI不使用.md)）、参加者の実力を測る手段は自己申告レベルしかない。
自己申告レベルは参加時に必ず入力され、部屋を出るまで保持されている（[構想v2.md](../構想v2.md)の「レベル設計の共通基盤」）。
新しい入力を求めずに使える。

### 最小の偏りだけを候補にすると、同じ顔ぶれで毎回同じ編成になる

最も偏りの小さい分け方は、レベルの組み合わせによっては1通りに定まる。
たとえばレベル5、4、2、1の4人をペアに分けると、偏りが最小になるのは「5と1、4と2」だけである。
同じ部屋でチーム戦を続けて遊ぶと、毎回同じペアになる。

許容幅2を設けるのは、編成に変化を残すためである。
上の例では、合計が7と5になる「5と2、4と1」も候補に入る。

許容幅を1にすると、2ペアの場合は候補が増えない。
4人の合計レベルが決まっていると、2ペアの合計の差は偶数か奇数のどちらかに固定され、最小の差から1だけ大きい差の分け方は存在しないためである。

幅を広げるほど編成は変わりやすくなり、レベル差は勝敗に出やすくなる。
4人ずつ2チームでは、許容幅2は平均レベルの差0.5にあたる。
2は暫定値であり、各ゲームの机上プレイで見直す。

### 全列挙で足りる

部屋の上限人数の範囲では、分け方の数は小さい。

8人を2人ずつ4チームに分ける場合は105通り、4人ずつ2チームは35通り、3人と3人と2人の3チームは280通りである。
探索の工夫をせず全列挙しても、`start()` 1回あたりの計算量は問題にならない。

### 共通コアへ置く理由

チーム戦の初期候補（MIND MELD、TWO-HEADED SPEAKER、SECRET TEAMS）は3本を並行して作る。
着手の時点で同じ実装が3つ要ることが確定しており、[ADR-0020](./0020-ゲーム間で重複する部品は共通コアへ置く.md)の条件2を満たす。

`formBalancedTeams` は、IDとレベルと人数構成だけを扱う。
チームの意味（ペア、陣営、泥棒と警備）は呼び出し側が与えるため、ゲーム固有の語彙を含まず、条件1と不変条件4にも抵触しない。

置き場所は `shared/core/src/rng.ts` の隣とする。
seedから再現できる抽選であり、`createRandom` と同じ性質の部品だからである。

## 代案

### ロビーでホストがチームを組む

共通コアの `Room` にチームの状態を持たせ、ホストがロビーで入れ替えてから開始する案である。

参加者の実際の力関係を一番よく知っているのは同室の人間であり、編成の精度は最も高い。

採らない理由は3つある。

* 共通コアの変更が大きい。`Room` の型、ロビーのメッセージ、入室と追放と再接続との整合、ゲーム選択を変えたときの扱いを新たに設計する必要がある
* 開始までの操作が増える。チーム戦以外のゲームでは不要な画面がロビーに残る
* チームを伏せるSECRET TEAMSでは使えず、編成の仕組みが2系統になる

自動編成が実際の場で不満を生むことが分かった時点で、手で入れ替える操作を足す選択肢は残る。

### ゲームごとに編成のステージを持つ

開始直後に各ゲームが「編成」のステージを置き、参加者が自分で組む案である。

採らない理由は、ステージ、action、締切の処理を各ゲームが重複して持つことである。
共通化しようとすると進行の判断が共通コアへ漏れる（[ADR-0020](./0020-ゲーム間で重複する部品は共通コアへ置く.md)の `handleReady` と同じ構造）。

### 乱数だけで分ける

最も簡単だが、前節のとおりレベル差がチームの勝敗に出る。

## 影響

* `shared/core` に `formBalancedTeams` を追加する。`server/core`（RoomDO）とプロトコルは変えない
* 自己申告レベルは参加者の自己評価であり、実力とずれることがある。ずれは許容幅の内側に収まる場合に限り吸収される。大きくずれた申告は編成の偏りとしてそのまま出る
* 「もう一回」で同じゲームを遊ぶと、新しいseedで編成し直す。前回のチームは引き継がない
* チームを公開するか伏せるかと、奇数人数の扱いは、各ゲームの基本設計に書く
* [基本設計/05](../基本設計/05_ゲームモジュール.md)の「収録予定ゲームと共通コアへの要求」に、チーム戦の行と本ADRへの参照を加える
