# 0012: ゲーム固有設定の検証をゲームモジュールに委ねる

* ステータス: accepted
* 日付: 2026-08-13

## 決定

`configure` メッセージで送られるゲーム固有設定（`settings`）のスキーマ検証は、`GameModule` が行う。

共通コアはバリデーションライブラリを持たず、`settings` を `unknown` のまま `GameModule.validateSettings()` へ渡し、返された可否だけを見る。
拒否された場合は `error(invalid_payload)` を送信者へ返し、部屋の状態を変えない。

共通コアが検証するのは共通メッセージのフィールド（`name` / `level` / `gameId` / `contentId` の型と範囲）に限る。

## 理由

共通コアで汎用的に検証するには、スキーマの記述形式を共通コアが規定する必要がある。
JSON Schemaにせよzod等のライブラリにせよ、形式を決めた時点で「ゲーム固有設定はこの形式で書く」という制約をゲームモジュールへ課すことになり、共通コアがゲーム側の記述方法を決める構図になる。

これは[ADR-0009](./0009-部屋基盤とゲームモジュールの分離.md)が禁じるゲーム固有概念の流入そのものではないが、境界を共通コア側へ押し出す方向の変更である。
共通コアに入れる基準は「2本目以降でも確実に必要と言えるか」であり、`settings` の形はゲームごとに異なるため、共通化して得られるのは検証の起動処理だけになる。

実装上の利点もある。
DETECTIVESの `settings` は捜査時間の秒数1つで、妥当な範囲（下限・上限）はゲームのバランス上の判断である。
この範囲の根拠はゲームモジュール側にあり、型と検証を同じディレクトリに置いたほうが変更時に離れない。

依存関係の観点も採用理由に含む。
共通コアにバリデーションライブラリを入れるとWorkerのバンドルへ常時載る。
ゲームモジュール側で必要になったときだけ導入すれば、依存の増加を局所化できる。

代替案として「共通コアがzodを持ち、`GameModule` がzodスキーマを申告する」も検討した。
記述量は最も少ないが、`GameModule` インターフェースがzodの型に依存し、ライブラリの差し替えが全ゲームモジュールの変更になるため採らなかった。

## 影響

* `GameModule` に `validateSettings(settings: unknown): ValidationResult` を追加する（定義は [基本設計/05](../基本設計/05_ゲームモジュール.md)）
* 共通コアは `configure` 受理時に必ず `validateSettings` を呼ぶ。検証を省いて `settings` を保存する経路を作らない。検証しないまま保存すると、不正値が `start` まで持ち越されてゲームモジュール内で例外になる
* 検証失敗のエラーコードは共通の `invalid_payload` を使う。ゲームごとの詳細コードを増やさない
* ゲームモジュールを追加するときは `validateSettings` の実装が必須になる。設定を持たないゲームは常に成功を返す
