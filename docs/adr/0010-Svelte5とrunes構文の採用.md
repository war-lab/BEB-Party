# 0010: Svelte 5とrunes構文の採用

* ステータス: accepted
* 日付: 2026-08-13

## 決定

クライアントはSvelte 5を使い、リアクティビティはrunes（`$state` / `$derived` / `$effect` / `$props`）で記述する。

Svelte 4系のレガシー構文（`export let`、`$:` リアクティブ文、`on:` イベントディレクティブ、`<slot>`）は新規コードで使わない。

禁止の機構はコンパイラのrunesモードとする。
runesモードでは `export let` と `$:` が使えず、混在はビルドエラーになる。
Viteの `dynamicCompileOptions` で自プロジェクトのファイルにのみ適用する。`svelte.config.js` に `runes: true` を置くと `node_modules` のコンポーネントまでrunesモードになるため、公式ドキュメントがこの方法を勧めている。

`on:` と `<slot>` がrunesモードでエラーになるかは**未検証**である。
コンパイラが弾かないものはESLintで補う。どちらで止まるかはM0のPR0で実測して確定させる。

サーバ受信状態を保持するストア（`serverState` / `secret` / `result` / `ui`）は `svelte/store` の `writable` ではなく、`client/core/*.svelte.ts` に置いた `$state` で実装する。
`$state` はコンポーネント外では拡張子 `.svelte.ts` / `.svelte.js` のモジュールでのみ使えるため、ファイル名の規約として固定する。

## 理由

Svelte 5が現行の安定版であり、runesが推奨APIである。
新規実装でレガシー構文を選ぶ理由がない。

runesを選ぶ実務上の利点は2つある。

第一に、リアクティビティの依存関係がコンパイラの静的解析ではなく実行時の参照追跡で決まるため、コンポーネント外のモジュールでも同じ書き方が通る。
共通コア（`client/core/`）が状態を持ち、ゲームモジュール（`client/games/<id>/`）がそれを読む構成では、状態の実体がコンポーネント外にあるため、この性質が効く。

第二に、`$state` は型パラメータをそのまま通せる。
`serverState` はゲーム固有の `gameState` を型引数で受ける設計であり（[基本設計/02](../基本設計/02_クライアント.md)）、ストアのラッパを介さないほうが型が素直になる。

`svelte/store` の `writable` を使う代替案も検討した。
Svelte 5でも動作するが、runesと2つのリアクティビティ機構が併存し、どちらで書くかの判断が実装者ごとに割れるため採らなかった。

レガシー構文の禁止を機械化するのは、混在の検出を人手のレビューに依存させないためである。
Svelte 5は既定でコンポーネントの記述からモードを推論するため、runesモードを明示しない限りレガシー構文が警告なしに混ざる。

機構としてlintではなくコンパイラを選ぶのは、`eslint-plugin-svelte` の公式ルール一覧にレガシー構文を禁止するルールが存在しないためである（2026年8月時点で確認）。
コミュニティ製のプラグインは存在するが、初期開発段階で破壊的変更が予告されており、不変条件の担保を委ねる先として適さない。
コンパイラで止まるものはコンパイラで止めるほうが、ルールの追随も不要になる。

## 影響

* `client/` のリアクティブな状態は `.svelte.ts` モジュールに置く。通常の `.ts` に `$state` を書くとビルドエラーになる
* Viteの `dynamicCompileOptions` でrunesモードを強制する。`node_modules` を対象に含めない
* コンパイラが弾かない構文が残った場合のみ、ESLintのルールを足す。ルールを足すときは何を防ぐためかをコメントに書く
* 1つのコンポーネントでrunesとレガシー構文を混在させられない（Svelte 5の制約）。移行の途中状態を作らない
* Svelte 4向けに書かれた外部コンポーネントライブラリは、動作を確認せずに導入しない。UIライブラリを入れない方針（[ビジュアルデザイン](../ビジュアルデザイン.md)）と整合する
