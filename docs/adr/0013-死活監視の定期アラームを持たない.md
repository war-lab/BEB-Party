# 0013: 死活監視の定期アラームを持たない

* ステータス: accepted
* 日付: 2026-08-13

## 決定

RoomDOは接続の死活監視のための定期アラームを持たない。

クライアントは25秒間隔でハートビートを送り、サーバは `setWebSocketAutoResponse()` の自動応答で返す。
自動応答はDurable ObjectをHibernationから起こさないため、この往復に実行時間の課金が発生しない。

サーバ側の死活判定は、別の理由でDurable Objectが起きたとき（メッセージ受信時とアラーム発火時）にまとめて行う。
`getWebSocketAutoResponseTimestamp()` が返す最終ハートビート時刻が90秒より古いソケットを切断済みとみなし、`connected: false` にして閉じる。

その結果、無通信の時間帯には「実際は切れているが `connected: true` のまま表示されるプレイヤー」が最大でステージ締切まで残る。これを許容する。

## 理由

死活監視を目的に定期アラームを置くと、監視の間隔ごとにDurable Objectが起きる。
捜査ステージは既定600秒あり、この間サーバを流れるメッセージは原則ない（会話は対面の生声で行う）。
30秒間隔の監視を入れると、本来1回も起きない時間帯にDurable Objectが20回起きることになり、Hibernationを採用した目的（[ADR-0002](./0002-CloudflareDurableObjects採用.md)）と正面から衝突する。

幽霊接続を放置しても進行が止まらないのは、すべてのステージに締切があるためである（[基本設計/01](../基本設計/01_サーバ.md)）。
「接続中の全員から入力が揃う」ことだけを遷移条件にしていれば幽霊接続はデッドロックを生むが、締切による強制遷移が併存するため、遅延は最大でも現ステージの残り時間に収まる。

`webSocketClose` の発火だけに頼らない理由は、モバイル網の切断やスリープでは終了フレームが届かず、ハンドラが呼ばれない経路があるためである。
このため最終ハートビート時刻による判定を併用する。

判定に使う値をアプリケーション側で記録しないのは、記録のためにDurable Objectを起こしては本末転倒になるためである。
`getWebSocketAutoResponseTimestamp()` はランタイムが自動応答時に更新するため、起きたときに読むだけでよい。

代替案として「クライアントのハートビートを自動応答ではなく通常のメッセージとして処理する」も検討した。
サーバが正確な接続状態を常に持てるが、25秒ごとに全部屋のDurable Objectを起こすことになるため採らなかった。

## 影響

* ハートビートのペイロードは `setWebSocketAutoResponse()` に登録した固定文字列と完全一致させる。値を変えると自動応答が効かず、全ハートビートがDurable Objectを起こす。プロトコル変更時の検査項目とする（[基本設計/03](../基本設計/03_プロトコル.md)）
* リクエストとレスポンスはそれぞれ2,048文字以内という制約がある。ハートビートに動的な値（連番・時刻）を載せられない
* ロビーの参加者一覧は、無通信時に最大で数分古い接続状態を表示しうる。ホストが「切断したのに残っている」参加者を見て操作に迷わないよう、参加者タイルの接続状態は最新である保証がない前提でUIを作る
* 死活判定のテストは、時刻を進めてから任意のメッセージを送り、その時点で `connected: false` になることを確認する形で書く。「一定時間後に自動で落ちる」テストは書けない（そのような挙動を持たせないため）
