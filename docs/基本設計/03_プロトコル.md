# 基本設計: WebSocketプロトコル

## 結論

メッセージ構造（型）の正本は `shared/core/protocol.ts` とし、この文書はメッセージの意味・受理条件・順序保証を定める。

サーバは常に全量スナップショット（`state`）を配るスナップショット方式とし、差分同期はしない。

ゲーム固有の操作はメッセージ型を増やさず `action` 1種類に集約する。
共通コアがゲーム固有のメッセージ名を知らないための措置である（[ADR-0009](../adr/0009-部屋基盤とゲームモジュールの分離.md)）。

## 設計方針

* **スナップショット方式**: `state` は毎回、公開状態の全量を含む。クライアントは受信順に上書きするだけでよく、取りこぼしがあっても次の `state` で自己修復する。部屋の状態は数KBであり、差分同期の複雑さに見合わない
* **秘密の分離**: 秘密情報は `secret`（個別送信）と `result`（全員開示）にのみ載せる。`state` に混ぜない
* **ゲーム非依存**: 共通コアが解釈するのは共通メッセージのみ。`action` の中身と `state.gameState` / `secret.payload` / `result.payload` の構造はゲームモジュールが定義し、共通コアは透過的に運ぶ
* **バージョニング**: エンベロープに `v`（プロトコルバージョン、整数）を持つ。サーバは非対応バージョンの `join` / `spectate` を `error(unsupported_version)` で拒否する

バージョン不一致が起きる経路は1つに絞られる。
Cloudflareはコードのデプロイ時にすべてのDurable Objectを再起動し、Hibernation中のWebSocketも切断する。
このためデプロイを跨いで接続が維持されることはなく、不一致は「古いSPAを開いたままのタブが自動再接続してきた場合」に限られる。

`unsupported_version` を受けたクライアントは再接続を繰り返さず、強制リロードで新しいSPAを取得する（[02_クライアント.md](./02_クライアント.md)）。
バックオフ再試行のままにすると無限エラーループになる。

## エンベロープ

```typescript
// C→S
{ v: 1, type: string, ...payload }
// S→C
{ v: 1, type: string, ...payload }
```

## クライアント → サーバ

共通メッセージ（共通コアが解釈する）。

| type | payload | 受理条件（詳細は [01_サーバ.md](./01_サーバ.md) の処理表） |
| --- | --- | --- |
| `join` | `name, level, reconnectToken?` | lobby中の新規、または全ステージの `reconnectToken` 再接続 |
| `spectate` | — | 全ステージ。ホスト画面（観戦モード）用 |
| `selectGame` | `gameId` | ホスト、lobby |
| `configure` | `contentId?, settings?` | ホスト、lobby、ゲーム選択済み |
| `start` | — | ホスト、lobby、人数が選択中ゲームの対応範囲内 |
| `nextGame` | — | ホスト、finished |

ゲーム固有メッセージ（共通コアはゲームモジュールへディスパッチするだけ）。

| type | payload | 受理条件 |
| --- | --- | --- |
| `action` | `action: string, ...payload` | `lifecycle: playing`。受理可否は `GameModule.handleAction` が判定する |

DETECTIVESの `action` は `ready`（ブリーフィング読了）と `vote`（`targetPlayerId`）の2つである。
ゲーム固有操作をトップレベルのtypeにしない理由は、共通コアがゲームごとにメッセージ表を持つことになり分離が崩れるためである。

## サーバ → クライアント

| type | payload | 送信先 | タイミング |
| --- | --- | --- | --- |
| `joined` | `playerId`（公開ID）, `reconnectToken`（秘密値） | 本人 | `join` 受理時 |
| `state` | 共通Room状態（`gameState` を含む） + `serverNow`（epoch ms） | 全員 + 観戦ソケット | 状態が変わるたび |
| `secret` | `gameId`, `payload`（ゲーム固有の秘密情報） | 各自個別 | `start` 時、ゲームモジュールの指示時、再接続時 |
| `result` | `gameId`, `payload`（勝敗と開示内容） | 全員 + 観戦ソケット | `lifecycle` が `finished` になったとき |
| `error` | `code, message` | 本人 | 受理できない操作 |

`serverNow` はクライアントの時計補正用（[02_クライアント.md](./02_クライアント.md)）。

DETECTIVESの場合、`secret.payload` は証言カード・役柄・犯人フラグ・制約、`result.payload` は犯人・嘘カード・矛盾解説・投票内訳・勝敗・真相タイムライン・重要表現である。
これらの型は `shared/games/detectives/` が正本とする。

`playerId` と `reconnectToken` を分ける理由は [ADR-0006](../adr/0006-公開IDと再接続シークレットの分離.md) を正とする。
`playerId` は `state` の `players[]` で全員に配られるため、認証情報として使えない。

## 観戦ソケット（ホスト画面）

ホスト画面（大画面表示モード）は `join` の代わりに `spectate` を送り、`state` と `result` のみを受け取る読み取り専用の接続とする。

`join` せずに何も送らない設計は成立しない。
サーバはソケットとプレイヤーの対応を `serializeAttachment` で保持するため、種別の申告がないソケットを扱えず、`01_サーバ.md` の「表にない組み合わせは `error`」に抵触する。
ダミー参加者として扱う案は、`players[]` に幽霊が並び人数検証（事件の対応人数）を汚すため採らない。

観戦ソケットは参加者数・人数上限に数えず、`secret` の配信対象に含めない。

## ハートビート

接続維持と死活判定のため、クライアントは25秒間隔で固定文字列を送る。

| 向き | 値 |
| --- | --- |
| C→S | `{"v":1,"type":"ping"}` |
| S→C | `{"v":1,"type":"pong"}` |

サーバはこの対を `setWebSocketAutoResponse()` に登録する。
一致した受信はランタイムが応答し、Durable Objectを起こさない。
そのためハートビートは共通メッセージの処理表（[01_サーバ.md](./01_サーバ.md)）に現れず、`lifecycle` による受理条件も持たない。

送信文字列は登録した値と1バイトも違ってはならない。
不一致のメッセージは自動応答されず通常の受信として扱われ、25秒ごとに全部屋のDurable Objectを起こす。
JSONのキー順・空白を含めて固定文字列として扱い、オブジェクトを組み立てて `JSON.stringify` した結果に依存させない。

自動応答のリクエストとレスポンスは、それぞれ2,048文字以内という制約がある。
ハートビートに連番・時刻・プレイヤーIDを載せられない。

間隔を25秒とするのは、モバイル網やルータのNATマッピングが無通信で失われる時間として一般に30〜60秒が挙げられるためである。
それより短い間隔で往復させ、経路上の状態を維持する。

クライアントは `pong` が60秒受からなければ自分から接続を閉じ、再接続の手順に入る。
サーバ側の判定基準は最終自動応答時刻が90秒より古いことであり、判定の契機と限界は [01_サーバ.md](./01_サーバ.md) と [ADR-0013](../adr/0013-死活監視の定期アラームを持たない.md) を正とする。

## 順序・冪等性

* WebSocketの順序保証に依存してよい（TCP上の単一接続内）
* `state` は全量スナップショットなので、重複受信・欠落があっても最終的な描画は正しい
* `action` の冪等性はゲームモジュールの責務とする（DETECTIVESの `vote` は二重送信の2回目を `reject` する。初回が正）
* 再接続時、サーバは必ず `joined` → `state` →（ゲーム中なら）`secret` →（開示済みなら）`result` の順で送る
* `spectate` の受理時は `state` →（開示済みなら）`result` の順で送る
* 再接続で発行される `reconnectToken` は初回発行の値を維持する（`joined` は毎回同じ値を返す）

## エラーコード

コードの一覧と意味は [01_サーバ.md](./01_サーバ.md) を正とする。
クライアントは未知のコードを汎用エラー表示にフォールバックする。

## 変更手順

プロトコルを変更するPRは次の順で行う。

1. `shared/core/protocol.ts` と本文書を同一PRで更新する（`shared/` 単独PRの原則に従い、server/client実装は後続PR）
2. 互換性を壊す変更は `v` をインクリメントし、ADRを追加する
3. `v` を変える場合はハートビートの固定文字列も変わる。クライアントの送信値とサーバの `setWebSocketAutoResponse()` の登録値が一致していることを確認する

ゲームを追加するときは共通メッセージを増やさない。
新しい操作は当該ゲームの `action` として定義するため、本文書と `shared/core/` の変更は不要である（[05_ゲームモジュール.md](./05_ゲームモジュール.md)）。
