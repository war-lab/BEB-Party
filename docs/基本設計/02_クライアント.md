# 基本設計: クライアント（SPA）

## 結論

クライアントは「サーバから届いた状態スナップショットを描画するだけの薄い層」として実装する。

ゲームルールの判定・タイマーの確定・集計をクライアントで行わない。

画面はサーバの `lifecycle` と `stage` に1:1で追従し、独自の画面遷移状態を持たない。

コードは共通コア（`client/core/`）とゲームモジュール（`client/games/<id>/`）に分ける（[ADR-0009](../adr/0009-部屋基盤とゲームモジュールの分離.md)）。
共通コアが持つのはホーム・ロビー・ホスト画面・接続管理・デザイントークンで、ゲーム内の画面はゲームモジュールが持つ。

見た目の規定は [ビジュアルデザイン.md](../ビジュアルデザイン.md)、境界の定義は [05_ゲームモジュール.md](./05_ゲームモジュール.md)、メッセージの意味は [03_プロトコル.md](./03_プロトコル.md) を正とする。

## 技術構成

* Vite + Svelte 5 + TypeScript。リアクティビティはrunesで書き、Svelte 4系のレガシー構文は使わない（[ADR-0010](../adr/0010-Svelte5とrunes構文の採用.md)）
* 状態管理ライブラリは追加しない。共有状態は `client/core/` の `.svelte.ts` モジュールに `$state` で持つ
* ルーティングライブラリは使わない。URLは `/`（ホーム）と `/room/:code` の2つだけで、部屋内の画面はサーバの `lifecycle` / `stage` が決める
* ゲームモジュールの画面は `gameId` で動的importする。共通コアのバンドルに全ゲームを含めない（収録数が増えたときの初回ロードを守る）
* ビルド成果物はWorkerの静的アセットとして配信する

## ストア設計

ストアは4つに分離し、混ぜない。
実体は `client/core/` の `.svelte.ts` モジュールが持つ `$state` であり、以下では「ストア」と呼ぶ。

| ストア | 内容 | 書き込み元 |
| --- | --- | --- |
| `serverState` | `state` メッセージの最新スナップショット（`gameState` を含む） | WebSocket受信のみ |
| `secret` | `secret` メッセージの `payload`（自分だけに配られた情報） | WebSocket受信のみ |
| `result` | `result` メッセージの `payload`（勝敗と開示内容） | WebSocket受信のみ |
| `ui` | 接続状態、入力中の値、演出の進行 | クライアント内のみ |

ストアは共通コアが持ち、型パラメータでゲーム固有のペイロード型を受ける。
ゲームモジュールはストアを読むだけで、ストアを増やさない。

`$state` はコンポーネント外では `.svelte.ts` / `.svelte.js` のモジュールでのみ使える。
通常の `.ts` に書くとビルドエラーになるため、ストアを置くファイルの拡張子を規約として固定する。

`serverState` / `secret` / `result` へクライアント側のロジックから書き込むことを禁止する。
楽観更新はしない（操作 → サーバ反映 → 再描画の一方向で、パーティゲームには十分速い）。

## 接続管理

* 初回 `join` 成功時にサーバが `joined` で返す `reconnectToken` を `sessionStorage` に部屋コードと組で保存する。`playerId` は認証に使えないので保存しても再接続には使わない（[ADR-0006](../adr/0006-公開IDと再接続シークレットの分離.md)）
* `reconnectToken` は画面に表示しない。URL・ログ・エラー通知にも載せない
* 接続中は25秒間隔でハートビート（`ping`）を送り、`pong` が60秒受からなければ自分から接続を閉じて再接続へ移る。送信する文字列は [03_プロトコル.md](./03_プロトコル.md) の固定値をそのまま使い、オブジェクトを組み立てて生成しない
* 切断時は指数バックオフ（1s→2s→4s、上限10s）で自動再接続し、`reconnectToken` つき `join` を送る
* アップグレード要求にHTTP 429が返った場合は、レート制限に達している。バックオフを継続したうえで最低30秒待ってから再試行し、UIには混雑した旨を表示する。同室の全員が同じIPから接続するため、全員の同時再接続でこの経路に入りうる（[01_サーバ.md](./01_サーバ.md)）
* 再接続中はUIに接続状態バナーを表示する。ゲーム画面は最後のスナップショットのまま維持する
* タブ復帰（`visibilitychange`）時は即時に再接続を試みる
* `error(unsupported_version)` を受けたら再接続を中止し、`location.reload()` で新しいSPAを取得する。バックオフ再試行を続けると、古いSPAのまま無限にエラーを受け続ける
* `error(rate_limited)` は致命的エラーとして扱わない。再接続もリロードもしない（通常のプレイでは到達しない値である。[ADR-0017](../adr/0017-メッセージ流量の制限はインメモリで持つ.md)）
* 再試行しても結果が変わらないエラー（`spectator_limit` / `room_full` / `game_in_progress`）を受けたら再接続をやめ、理由を画面に出す。叩き続けると同室の全員が共有するIPの再接続予算まで使い切る
* 一度もハンドシェイクが成立しないまま閉じた場合は、部屋コードの誤りとレート制限を区別できない。両方を含む文言で知らせたうえで再試行を続ける
* 参加時の名前とレベルは部屋コードと組で `sessionStorage` に保存し、URLからの復帰にはその値を使う。保存が無ければ自動接続せず、ホームで名前とレベルを申告させる。QRや共有リンクから開いた人が、名前もレベルも申告しないまま参加者として登録されるのを防ぐ

デプロイ時はすべてのDurable Objectが再起動され、全員のWebSocketが切断される（Cloudflareの仕様）。
上記の自動再接続はこの経路の復帰も兼ねる。

## タイマー表示

サーバの `deadline`（epoch ms）から残り時間を毎秒描画する。

端末時計のずれを吸収するため、`state` 受信時に「サーバ時刻とのオフセット」を推定して補正する（`state` にサーバ現在時刻を含める。プロトコル側の項目参照）。

残り時間は `deadline - (現在時刻 + 補正値)` で描く。
補正値は `state` を受けた時点の `serverNow` と端末時計の差であり、毎秒測り直さない。
測り直すと補正後の時刻が受信時のサーバ時刻に固定され、残り時間が減らない。
この規則はゲーム側のタイマーバーとホスト画面の両方に適用する。

クライアントの残り0秒はあくまで表示であり、ステージ遷移は必ずサーバからの `state` で行う。

## 画面の対応

共通コア（`client/core/`）。

| 状態 | 画面 | 備考 |
| --- | --- | --- |
| （未接続） | ホーム | 部屋作成 / コード入力 |
| `lifecycle: lobby` | ロビー | 参加者グリッド、ホストのみゲーム・コンテンツ選択と開始。カタログは `GET /api/catalog` を入室時に取得する |
| `lifecycle: playing` / `finished` | ゲームモジュールへ委譲 | `gameId` で動的importし、`stage` を渡す |
| （どの画面からも） | 遊び方 | 共通の進め方とゲームごとのルール。全画面共通のフッターから開く |

### 遊び方

共通コアが持つのは「同室で声で遊ぶ」「部屋の作り方と参加のしかた」「レベルの自己申告」「切断時の挙動」「困ったときの対処」「英語に詰まったときの言い方」までとする。

英語のフレーズのうち共通コアが持つのは、ゲームの内容に依存しないもの（聞き返し・ゆっくり・順番の受け渡し）に限る。
質問や突き合わせの言い方は証言というゲーム固有の概念に紐づくため、ゲームモジュール側に置く。

ゲームのルールはゲームモジュールが持ち、`gameId` で動的importする。
画面本体（`gameScreens`）と同じく、`client/app` が `gameId → ローダー` のテーブル（`gameGuides`）を組み立てて共通コアへ渡す（[07](./07_リポジトリとツールチェーン.md)）。
共通コアはどのゲームが登録されているかを知らない。

どの画面からも開けるようにするのは、捜査中に制約や勝敗条件を確認したい場面があるためである。
開いている間もサーバの状態は進むため、閉じれば最新の画面に戻る。

節は折りたたみ（`details`）にし、卓上で目的の項目へ短い操作で到達できるようにする。
最初に開いておくのは「英語に詰まったら」と、選択中のゲームのルールとする。

### ステージの案内

各ステージの画面に「いまやること」を出す。進行役が台本を読まなくても卓が進む状態を既定とする。

文言はサーバから届いた `stage` と `deadline` だけで決まる。
捜査は長いため残り時間で文言を切り替えるが、これは表示上の目安であり、ステージ遷移も時間切れの判定も行わない。
捜査の長さはロビーで変更できるため、切り替えは全体に対する割合ではなく残り時間の絶対値で判断する。

DETECTIVESモジュール（`client/games/detectives/`）。

| stage | 画面 | 備考 |
| --- | --- | --- |
| briefing | 事件概要 → 配役カットイン | `secret` 受信で役柄演出。readyボタン（`action: ready`） |
| investigation | 捜査 | 証言カード、制約、タイマー。L1-2は質問テンプレート |
| voting | 投票 | 容疑者グリッド、選択と確定（`action: vote`） |
| reveal | 開示 → 振り返り | `result` の内容を段階的に演出表示 |

演出（カットイン・ズーム）は `ui` ストアで進行を管理し、`prefers-reduced-motion` では即時表示に落とす。

未知の `gameId` / `stage` を受け取った場合は汎用の待機表示にフォールバックする（デプロイ直後の古いSPAで起こりうる）。

### 配役カットイン

役柄の表示は覗き見の防止を優先し、`secret` の受信で自動的に開かない。
手順は3段階とする。

1. **伏せ面**: `secret` 受信と同時に全画面へ切り替える。役柄を示す色（赤・青）は出さず、共通の中立色を使う。文言は「役柄が届きました」「まわりに画面を見られていないか確認してから、タップして開いてください」。表示時間は無制限で、タップを待つ
2. **溜め**: タップから600ms。斜めワイプとスピードラインで転換を作る
3. **役柄カード**: 犯人は赤地、市民は青地。上部に「他の人に見せない」を固定表示する。「確認した」ボタンで閉じる

伏せ面を挟むのは、隣の席から画面が見える状態で役柄が表示される事故を防ぐためである。
表示までに一定時間を置くだけの方式では、本人が画面を見ていない間に周囲へ露出しうる。

役柄カードは捜査ステージ中も再確認できるようにし、再表示のたびに同じ伏せ面を経由させる。

`prefers-reduced-motion` では溜めとワイプを0にし、タップ直後に役柄カードを表示する。
伏せ面とタップは演出ではなく秘密保持の手段であるため、この設定でも省略しない。

`briefing` の締切は120秒であり、伏せ面を開かないまま締切に達した場合も `investigation` へ進む。
その場合でも役柄カードは捜査画面から再確認できる。

## 表示モード

* 通常（スマホ縦）: 上記の画面
* ホスト画面: `/room/:code?mode=host`。ステージ名・タイマー・参加者だけを大きく表示する読み取り専用モード。接続時に `join` ではなく `spectate` を送り、`state` と `result` のみを受信する（[03_プロトコル.md](./03_プロトコル.md) の観戦ソケット）。入力系UIは一切出さない。共通コアが持ち、ステージ名の表示文言だけをゲームモジュールから引く

ホスト画面の詳細は次のとおりである。

* ステージ名の表示文言は `gameId → ステージ → 文言` のテーブルをclient/appが組み立てて渡す（`gameScreens` / `gameGuides` と同じ形。[07](./07_リポジトリとツールチェーン.md)）。共通コアはゲームIDで分岐しない
* 同じテーブルをゲーム側の画面（タイマーバー）も使う。同じステージに2つの文言を持たない
* ロビー中はステージ名の代わりに待機表示を出す。ゲーム中の表示は `state` の `stage` と `deadline` だけで決まる
* フッターの「遊び方」「書体のライセンス表記」は出さない。操作を置かないためであり、書体の表記は画面内に静的な1行として置く（[ビジュアルデザイン.md](../ビジュアルデザイン.md) のライセンス表記）
* 残り時間の描き方は共通で、上記「タイマー表示」の時刻補正の規則に従う
* `?mode=host` を見るのは `/room/:code` にマッチしたときだけとする。部屋コードを含まないURL（`/?mode=host`）はホームからの通常の参加導線であり、ここでホスト画面を描くと、参加者として `join` した席を投影用の画面が占有したまま操作できない状態になる

## その他の機能要件

* **Wake Lock**: 捜査・投票ステージ中は Screen Wake Lock API でスリープを抑止する。非対応ブラウザでは何もしない
* **QRコード**: ロビーの参加用QRは `uqr`（MIT、依存なし、ESM、`renderSVG` でSVG文字列を返す）を使う。ロビー画面からのみ動的importし、初回ロードのバンドルに含めない。画像を生成せずSVGで描くため、追加のアセット配信が要らない
* **オフライン**: 対応しない。切断は再接続バナーで扱う

## 不変条件

* クライアントはゲームルールを判定しない（勝敗・時間切れ・投票集計をクライアントで計算して表示しない）
* `client/core/` にゲーム固有の概念（証言・犯人・お題等）を持ち込まない。共通コアがゲームIDで分岐しない
* `secret` の内容を自分以外に見せるUIを作らない（画面共有的な機能を追加しない）
* `reconnectToken` を画面・URL・ログに出さない
* 役柄を本人のタップなしに画面へ表示しない。伏せ面を省略する実装をしない
* 証言カードは英文を主、日本語ヒントを従として表示する。英文より日本語を目立たせない（日本語だけ読んで済ませる動機を作らないため）
* 全レベルの捜査画面に「証言は英語で読み上げる」制約を表示する。レベル1〜2も例外にしない

## テスト観点

* Playwright（M0）: 6つのブラウザコンテキストを同時接続し、同じロビー状態が同期すること（M0の完了条件の自動検証）
* Playwright（M2以降）: 部屋作成 → 6人参加 → 開始 → 投票 → 開示の一連導線
* 再接続: 捜査中にWebSocketを切断し、スナップショットが維持されたまま自動復帰すること
* バージョン不一致: `unsupported_version` を返すサーバに対し、再接続ループに入らずリロードが1回だけ走ること
* 配役カットイン: `secret` 受信だけでは役柄の文字列がDOMに現れず、タップ後に現れること
* ホスト画面: 参加者に数えられず、操作要素を持たず、`secret` を受け取らないこと。ステージ名が遷移に追従し、残り時間が実際に減ること
