# 基本設計: ESCAPE CALLゲームモジュール

## 結論

ESCAPE CALLは3ステージ（`briefing` / `solving` / `debrief`）を持つ2〜4人用の協力型ゲームモジュールであり、`GameModule` インターフェースの実装として完結する。

参加者は3つの錠を順に開けて部屋から脱出する。
錠の手がかりは断片に分かれて各自の画面にだけ出る。
自分の画面は他人に見せず、断片を英語で伝え合って答えの数字を組み立てる。

勝敗はチーム単位とし、制限時間内に3つ目の錠を開ければ脱出成功、届かなければ失敗とする。
個人の得点は持たない。

錠は `start` で `seed` から生成し、コンテンツに持たない（[ADR-0027](../adr/0027-ESCAPECALLの謎はテンプレートとseedから生成する.md)）。
コンテンツが持つのは規則の言い回しと舞台の文言だけである。

gameIdは `escapecall` とする。
`dontsayit` `whowrotethis` `blindroom` と同じく、空白と句読点を落として連結する規則を適用する。

共通コアへの追加要求はない。
全員同時の入力と、秘密情報の全量の送り直しという既存の形で足りる。

旧ESCAPE（2026-08に設計、未マージ。ブランチ `task/escape-設計`）から、ステージ構成、提出の扱い、誤答に時間の罰則を置かない判断を引き継いだ。
対応人数、謎の出どころ、ヒントの中身は変えた（末尾の「旧ESCAPEからの変更」）。

共通コアとの境界は [05](./05_ゲームモジュール.md)、メッセージの意味は [03](./03_プロトコル.md) を正とする。

## ステージ

| stage | 締切 | 遷移条件 |
| --- | --- | --- |
| `briefing` | 90秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `solving` | `escapeSeconds`（既定600秒） | 3つ目の錠が開く、または締切到達 |
| `debrief` | なし | 遷移しない（`lifecycle: finished`） |

錠ごとにステージを分けない。

脱出の制限時間は通しの1本であり、錠ごとの締切ではない。
共通コアの締切はステージ単位に1つであるため（[01](./01_サーバ.md)）、錠をステージにすると錠ごとに締切を置き直すことになる。
いま挑戦中の錠は公開状態で表す。

錠が開いたときの遷移では `deadlineSeconds` を返さない。
返すと、共通コアが「適用時刻 + 秒数」で締切を置き直し、制限時間が延びる（`server/core/src/room-do.ts`）。

`briefing` の締切を90秒とするのは、記号の色と形の英語名と、自分の画面を見せないという約束を読む時間を取るためである。
手がかりは `solving` に入るまで配らない。

`solving` では Wake Lock を取得する。
断片を読み上げながら相手の話を聞く時間が長く、画面に触らない時間が続く。

## 錠の仕組み

### 記号

記号は色4種と形4種の組み合わせで16種とする。

| 色 | 英語 | 塗り |
| --- | --- | --- |
| 赤 | red | `#FF3D3D` |
| 青 | blue | `#2E7CF6` |
| 黄 | yellow | `#FFC400` |
| 黒 | black | `#161B33` |

| 形 | 英語 |
| --- | --- |
| 星 | star |
| 円 | circle |
| 三角 | triangle |
| 四角 | square |

記号のidは `<色>_<形>`（例: `red_star`）とする。

色は [ADR-0025](../adr/0025-盤面アイコンはSVGで持つ.md) の5色から白を除いた4色とする。
5色は色覚特性（2型・1型）でも分離する組み合わせとして選ばれており、赤と緑を同時に使わない。
白を除くのは、画面の地が白に近く、白い記号の輪郭しか見えないためである。

形は色がなくても区別できる4種とする。
色を取り違えても形で絞れるため、1語の聞き違いで錠が止まる確率を下げる。

記号はクライアントがインラインSVGで描く。
画像ファイルを持たない。

記号は明るい下地の上に濃い輪郭で描く。
暗い画面の地にじかに置くと、黒の記号が輪郭だけの白い図形に見え、`white triangle` と読まれる（390px幅の実画面で確認した）。
16種は4つの図形と4つの塗りの組み合わせであり、図形の定義をコードに持てば足りる。

画面の記号に英語名を添えない。
名前が書いてあれば読み上げるだけになり、色と形を英語で言い表す工程が消える。
色と形の英語名は `briefing` の画面と、`solving` 中に開ける早見表にだけ出す。

### 断片

1つの錠の手がかりは3種類の断片に分かれる。

| 断片 | 中身 | 必要な英語 |
| --- | --- | --- |
| 並び（order） | 錠に描かれた記号の列（左から右） | 色と形の名前、順序（first, then, last） |
| 対応表（map） | 記号と数字の対応（例: red star → 3） | 色と形の名前、数字 |
| 規則（rule） | 並びをどう読み替えるかの英文 | 指示文の理解と言い換え |

答えは次の手順で一意に決まる。

1. 並びに規則を書かれた順に適用する
2. 残った記号を対応表で数字に置き換え、左から連結する

規則には記号に作用するものと数字に作用するものがある（後述）。
生成時に、記号に作用する規則を数字に作用する規則より前に並べる。
これにより「書かれた順に適用する」と「記号の規則は手順1、数字の規則は手順2の後」が常に一致し、規則を持つ人は書かれた順に伝えればよい。

答えの計算は `shared/games/escapecall/` の関数1つが持つ。
サーバの照合とユニットテストが同じ関数を使う。

### 錠ごとの難度

| 錠 | 規則の数 | 答えの桁数 | 対応表の記号数 |
| --- | --- | --- | --- |
| 1 | 0 | 4 | 6 |
| 2 | 1 | 4 | 8 |
| 3 | 2 | 5 | 8 |

錠1に規則を置かないのは、断片を伝え合う手順そのものに慣れる段にするためである。
錠2で規則が1つ加わり、錠3で規則が2つと桁が1つ増える。

対応表には、並びに現れない記号を必ず含める（錠1で2個以上、錠2と錠3で1個以上）。
並びに出る記号だけの表だと、対応表を持つ人が表を全部読み上げれば済み、並びを聞く理由が消える。

### 規則

規則の意味はコードに置き、規則IDで参照する（[ADR-0027](../adr/0027-ESCAPECALLの謎はテンプレートとseedから生成する.md)）。

| 規則ID | 作用 | 生成時の制約 |
| --- | --- | --- |
| `skip_color` | 指定の色の記号を並びから除く | 並びに指定色の記号をちょうど2個混ぜる。残りの記号はその色を持たない |
| `skip_shape` | 指定の形の記号を並びから除く | 並びに指定形の記号をちょうど2個混ぜる。残りの記号はその形を持たない |
| `reverse` | 並びを右から左へ読む | なし |
| `swap_ends` | 最初と最後の数字を入れ替える | なし |
| `add_one` | すべての数字に1を足す。9は0にする | なし |

`skip_color` と `skip_shape` は記号に作用し、並びが2個長くなる。
`reverse` は記号に作用する。
`swap_ends` と `add_one` は数字に作用する。

錠3の2つの規則には、除く規則（`skip_color` / `skip_shape`）を1つまでとし、同じ規則IDを2度使わない。
除く規則を2つ重ねると並びが最大9個になり、1画面の横幅に収まらない。

どの規則も、適用すると答えが必ず変わる。
並びの記号は重複させず、対応表の数字も重複させないため、`reverse` と `swap_ends` は桁の入れ替えとして必ず効き、`add_one` はすべての桁を変える。
除く規則は並びそのものを変える。

規則を持つ人の情報を欠くと答えが決まらないことは、この性質で保証される。

### 生成

`start` で3つの錠をすべて生成する。
`handleAction` と `onDeadline` にはシードが渡らないため（[05](./05_ゲームモジュール.md) の呼び出し規約）、錠が開くたびに生成する形は取れない。

錠1つの生成手順は次のとおりである。

1. 規則を選ぶ（錠1は無し、錠2は1つ、錠3は2つ。前節の組み合わせ制約を守り、記号に作用する規則を前に並べる）
2. 除く規則があれば、除く色または形を選ぶ
3. 答えの桁数ぶんの記号を、除く対象に当たらない記号から重複なしで選ぶ
4. 除く規則があれば、除く対象に当たる記号を2個選び、手順3の列の任意の位置へ挿入する
5. 対応表の記号を、並びの記号に、並びに無い記号を足して所定の数まで埋める
6. 対応表の各記号へ0〜9の数字を重複なしで割り当てる
7. 答えを「断片」の手順で計算する

答えを先に決めて逆算しない。
並び、規則、対応表を決めてから答えを計算するため、生成した錠には必ず答えがあり、それは1つに決まる。

生成が満たす不変条件をユニットテストで固定する。
多数の `seed`（1000件以上）と2〜4人の全人数で回す。

* 答えの桁数が錠の定義と一致する
* 並びの記号に重複が無く、対応表の数字に重複が無い
* 除いた後に残る記号がすべて対応表に含まれる
* 対応表に並びへ現れない記号が所定の数以上ある
* 規則を1つずつ外すと、答えが元と変わる
* 断片の割り当て（次節）で、どの参加者の断片を外しても答えを計算できない

最後の2項目は、答えの計算関数に断片の一部だけを与えて確かめる。
計算関数は、与えられた断片が不足していれば答えを返さない形にする。

### 断片の割り当て

錠ごとに断片を参加者へ割り当てる。
人数が断片の種類より多い場合は、対応表または並びを半分に分けて渡す。

| 人数 | 錠1 | 錠2 | 錠3 |
| --- | --- | --- | --- |
| 2 | A: 並び / B: 対応表 | A: 並び・規則 / B: 対応表 | A: 並び・規則2つ / B: 対応表 |
| 3 | A: 並び / B: 対応表の前半 / C: 対応表の後半 | A: 規則 / B: 並び / C: 対応表 | A: 規則2つ / B: 並び / C: 対応表 |
| 4 | A: 並びの前半 / B: 並びの後半 / C: 対応表の前半 / D: 対応表の後半 | A: 規則 / B: 並び / C: 対応表の前半 / D: 対応表の後半 | A: 規則2つ / B: 並び / C: 対応表の前半 / D: 対応表の後半 |

A〜Dは、その錠での参加者のレベルの降順とする（次節）。

対応表を半分に分けるときは、前半と後半のどちらにも、答えに使う記号を1個以上含める。
片方が答えに使わない記号だけになると、その人の断片を欠いても解けてしまう。

並びを半分に分けるときは、左から順に前半と後半に分ける。
前半を持つ人と後半を持つ人が、自分の分がどこから始まるかを知っている必要があるため、断片に `part: 'front' | 'back'` を持たせる。

どの錠でも全員が1つ以上の断片を持つ。
断片を持たない人がいる錠では、その人は見ているだけになる。

## レベル差の吸収

3層で吸収する。

第1層は断片の割り当てである。
錠ごとに参加者をレベルの降順に並べ、規則、並び、対応表の順に割り当てる（前節の表のA〜D）。

規則を最もレベルの高い人に渡すのは、指示文を理解して言い換える工程が最も難しいためである。
対応表を最もレベルの低い人に渡すのは、「red star, three」のような名詞と数字の読み上げで済むためである。

同じレベルの参加者の順は、錠ごとに `seed` でシャッフルして決める。
全員が同じレベルの卓で、同じ人が3つの錠すべてで規則を持つことを避ける。

第2層は規則の言い回しである。
規則を持つ人のレベルで、英文の段を切り替える。

| 規則を持つ人のレベル | 英文 | 日本語の補足 |
| --- | --- | --- |
| 1〜2 | `easy`（短い命令文。例: "Skip the black ones."） | 表示する |
| 3〜5 | `standard`（条件を含む文。例: "Ignore every black symbol when you read the row."） | 表示しない |

日本語の補足は規則を理解するためのものであり、伝えるのは英語で行う。
補足を読み上げることは「自分の画面を見せない」約束と同じく場の指摘に委ね、機械では検出しない。

第3層は勝敗をチーム単位にすることである。
個人の得点を持たないため、1対1のレベル差が勝敗に出ない（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md)の「1対1のレベル差を吸収する」）。

2人卓では、レベルの低い人が3つの錠すべてで対応表を持つ。
読み上げる英語が名詞と数字に偏るが、並びを聞き取って該当する数字を探す工程は毎回ある。
この偏りが遊びとして退屈かどうかは**未検証**である。

## 公開状態（gameState）

```typescript
interface EscapeCallPublic {
  packId: string;
  scene: SceneText;                   // 舞台の文言
  locks: LockPublic[];                // 3件。index昇順
  currentLockIndex: number;           // 0〜2。脱出後は3
  holders: HolderEntry[];             // いま挑戦中の錠で、誰がどの種類の断片を持つか
  readyPlayerIds: string[];           // briefing の収集状況
  attempts: AttemptEntry[];           // 提出の履歴。全錠ぶん
  hints: HintEntry[];                 // 開示済みのヒント。全錠ぶん
  keyExpressions: KeyExpression[];    // 質問と確認に使う言い回し
  escapeSeconds: number;              // 確定した制限時間
}

interface SceneText {
  titleEn: string;
  titleJa: string;
  introEn: string;
  introJa: string;
}

interface LockPublic {
  index: number;
  labelEn: string;                    // 'The lab door'
  labelJa: string;
  codeLength: number;                 // 4 または 5
  opened: boolean;
}

interface HolderEntry {
  playerId: string;
  kinds: PieceKind[];                 // 'order' | 'map' | 'rule'。中身は載せない
}

interface AttemptEntry {
  lockIndex: number;
  playerId: string;
  code: string;
  accepted: boolean;
}

interface HintEntry {
  lockIndex: number;
  position: number;                   // 0始まり。左からの桁位置
  digit: string;
}
```

錠の答え、並び、対応表、規則は公開状態に置かない。
`state` は全員へブロードキャストされるため、ここに置いた値は断片を持たない人にも届く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。

`holders` には断片の種類だけを載せ、中身を載せない。
誰が対応表を持つかが分かれば「対応表の人、red star は？」と相手を指して聞ける。
種類を伏せると、全員が全員に聞き回ることになる。

`currentLockIndex` を公開状態に持つ。
`locks[].opened` から導けるが、秘密の送り直しとヒントの対象を決めるたびに毎回導くと、導き方がサーバとクライアントで二重になる。
`opened` との整合はテストで固定する。

`attempts` を全員に公開する。
同じ誤答を別の人が打ち直すのを防ぐためである。
件数に上限を置かない。1ゲームの提出は制限時間とレート制限で頭打ちになる（「未解決の論点」の提出の件数）。

## 秘密情報（secret.payload）

```typescript
interface EscapeCallSecret {
  lockIndex: number;
  pieces: Piece[];                    // いま挑戦中の錠で自分が持つ断片の全量
}

type Piece = OrderPiece | MapPiece | RulePiece;

interface OrderPiece {
  kind: 'order';
  part: 'whole' | 'front' | 'back';
  symbols: SymbolId[];                // 左から右
}

interface MapPiece {
  kind: 'map';
  part: 'whole' | 'front' | 'back';
  entries: { symbol: SymbolId; digit: string }[];
}

interface RulePiece {
  kind: 'rule';
  rules: RuleEntry[];                 // 適用する順
}

interface RuleEntry {
  ruleId: RuleId;
  param?: ColorId | ShapeId;          // skip_color は色、skip_shape は形
  textEn: string;
  textJa?: string;
}
```

秘密は `solving` へ入るときと、錠が開くたびに、全員へ全量を送り直す。
`playerSecrets` は上書きであり結合ではないため（`server/core/src/room-do.ts`）、差分だけを送ると再接続した人の手元から断片が消える。

秘密には、いま挑戦中の錠の断片だけを入れる。
開いた錠の断片は結果画面で全員に開示するため、持ち続ける理由がない。
次の錠の断片を先に配ると、錠が開く前に次の錠の相談が始まる。

`textJa` は規則を持つ人のレベルが1〜2のときだけ入れる（「レベル差の吸収」の第2層）。

`param` は英文に含まれる色または形と同じ値であり、規則を持つ人にだけ届く。
英文と同じ情報であるため、秘密の範囲は広がらない。
英文に依存せずに答えを組み立てられる形を持たせるのは、E2Eが画面から答えを計算するためである。

`briefing` 中は断片を配らない。
開始時点の秘密は `pieces: []` とする。

## ゲーム秘密状態（gameSecret）

```typescript
interface EscapeCallGameSecret {
  locks: LockSecret[];                // 3件。startで生成する
}

interface LockSecret {
  order: SymbolId[];
  map: { symbol: SymbolId; digit: string }[];
  rules: { ruleId: RuleId; param?: string }[];   // skip_color は色、skip_shape は形
  code: string;
  assignments: Record<string, Piece[]>;          // playerId -> 断片
}
```

3つの錠と断片の割り当てを `start` ですべて決めて持つ。
錠が開いたときは、次の錠の `assignments` から秘密を組み立てて送る。

`code` を持つのは、提出の照合とヒントの開示のたびに答えを計算し直さないためである。
計算し直した値と `code` が一致することを、生成のテストで固定する。

`assignments` は参加者のidで引く。
開始後に参加者は増えないため（ロビー以外への途中参加は拒否する。[設計.md](../設計.md)）、割り当ては開始時点で確定する。

## action の受理規則

| action | 送れる人 | ステージ | 効果 |
| --- | --- | --- | --- |
| `ready` | 全員 | `briefing` | 収集に加える。接続中の全員が揃えば `solving` へ進む |
| `submit` | 全員 | `solving` | いま挑戦中の錠へ答えを提出する |
| `hint` | ホスト | `solving` | いま挑戦中の錠の答えを1桁開示する |

ステージ違いはすべて `invalid_stage` で拒否する。

拒否のコードはすべてゲームモジュール側で定義し、共通コアのエラーコード表には載せない（[12](./12_BLINDROOMゲームモジュール.md) と同じ）。
`invalid_stage` / `invalid_code` / `already_attempted` / `not_host` / `no_more_hints` の5つを持つ。

### ready

二重送信は拒否せず冪等に扱う（収録5本と同じ）。

### submit

payloadは `{ code: string }` とし、錠の番号を含めない。
対象は常に `currentLockIndex` の錠とする。
クライアントから対象を指定できると、まだ手がかりの無い先の錠へ総当たりを掛ける経路ができる。

提出者をホストに限らない。
協力型であり、最後の入力を誰が打つかに意味を持たせない。
提出をホストに限ると、対応表しか持たない人が解錠の操作に一度も関与できないまま終わる。

拒否する条件は2つある。

| 条件 | code |
| --- | --- |
| `code` が文字列でない、数字以外を含む、桁数が錠の `codeLength` と違う | `invalid_code` |
| 同じ錠へ同じ答えをすでに提出している | `already_attempted` |

同じ答えの再提出を拒否するのは、受理しても状態が進まないうえに、永続化とブロードキャストだけが発生するためである。
拒否は状態を変えない。

答えが一致した場合は次を行う。

1. `locks[currentLockIndex].opened` を `true` にし、`currentLockIndex` を1つ進める
2. `attempts` に `accepted: true` の行を追加する
3. 最後の錠なら `result` を返す（`outcome: 'escaped'`）。ステージは `debrief` とする
4. 最後の錠でなければ、次の錠の `holders` を公開状態に入れ、全員の秘密を次の錠の断片で送り直す

一致しない場合は `attempts` に `accepted: false` の行を追加するだけとし、ステージも締切も変えない。

クライアントは、提出の結果が状態として返るまで入力欄を無効にする。
連打すると流量制限（10秒に20通。[ADR-0017](../adr/0017-メッセージ流量の制限はインメモリで持つ.md)）に触れ、以降の提出が落ちる。

### hint

いま挑戦中の錠の答えを、左から1桁ずつ公開状態の `hints` へ開示する。

ホスト操作に限る。
誰でも押せると、1人の判断で卓全体のヒント数が増え、結果のランクが下がる。
ホストが場の合意を取って押す形にすれば、使うかどうかの判断が卓に残る（旧ESCAPEと同じ判断）。

1つの錠で開示できるのは `codeLength - 1` 桁までとし、超える要求は `no_more_hints` で拒否する。
全桁を開示すると、錠を解く工程が消える。

ヒントを置くのは、詰みがこの設計で自然に起きるためである。
錠が開かないまま制限時間に達すると、後の錠の断片に1枚も触れずに終わる。
残り1桁まで開示すれば、残る候補は10通りであり、総当たりでも必ず開けられる。

断片を持つ人が切断したまま戻らない場合も、この経路で先へ進める。

### 誤答に時間の罰則を置かない

共通コアの `GameTransition.deadlineSeconds` は「適用時刻 + 秒数」で締切を置き直す実装であり、残り時間からの減算ではない（`server/core/src/room-do.ts`）。
`handleAction` は時刻に触らないと定めているため（[05](./05_ゲームモジュール.md)）、モジュール側で残り時間を求められない。

残り時間を削る罰則は、共通コアに「現在時刻または残り秒数をゲームモジュールへ渡す」変更を要求する。
共通コアの変更が必要になった場合は実装を止めて境界定義の議論へ戻ると定めているため（[05](./05_ゲームモジュール.md) の手順6）、変更を伴わない設計を採る（旧ESCAPEと同じ判断）。

試行回数の上限も置かない。
上限に達した時点で誰も先へ進めなくなり、協力型で詰みが生じる。

罰則の代わりに、誤答の数を結果のランクに反映する（「結果」を参照）。
4桁の答えは1万通りあり、制限時間とレート制限のもとで総当たりで開けるのは現実的でない。
ただし、ヒントで桁を開示した後の総当たりは起こる前提とする。

| ステージ | 締切到達時の扱い |
| --- | --- |
| `briefing` | `ready` が揃っていなくても `solving` へ進み、錠1の断片を配る |

## 結果（result.payload）

```typescript
interface EscapeCallResult {
  outcome: 'escaped' | 'time_up';
  rank: 'S' | 'A' | 'B' | 'C' | 'D';
  openedCount: number;                // 0〜3
  hintCount: number;                  // 全錠の合計
  wrongCount: number;                 // 全錠の合計
  locks: LockSolution[];              // 3件。開かなかった錠も含む
}

interface LockSolution {
  index: number;
  labelEn: string;
  labelJa: string;
  opened: boolean;
  order: SymbolId[];
  map: { symbol: SymbolId; digit: string }[];
  rules: { ruleId: RuleId; textEn: string; textJa: string }[];
  code: string;
  holders: HolderEntry[];
}
```

ランクは次の表で決める。

| ランク | 条件 |
| --- | --- |
| S | 脱出し、ヒント0回、誤答2回以下 |
| A | 脱出し、ヒント2回以下、誤答5回以下 |
| B | 脱出した（SとA以外） |
| C | 脱出できず、錠を1つ以上開けた |
| D | 錠を1つも開けられなかった |

残り時間をランクに使わない。
`handleAction` は時刻に触れないため、脱出した時点の残り時間をモジュール側で求められない（「誤答に時間の罰則を置かない」と同じ理由）。

ランクの閾値は**未検証**の仮置きである。
実プレイでSとAがほとんど出ない、または大半がSになる場合は閾値を見直す。

開かなかった錠の答えと断片も結果に含める。
開かなかった理由（聞き違いか、規則の読み違いか）を振り返れるようにするためである。

`rules[].textEn` は、その錠で規則を持った人のレベルで配った英文とする。
振り返りで見るべきものは、場で実際に読み上げられた文である（[08](./08_DETECTIVESゲームモジュール.md) と同じ理由）。
`textJa` は全員の振り返り用に常に含める。

`finished` のまま再接続した人へ共通コアが `lastResult` を再送するため、結果画面は公開状態に依存しない（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断）。

## ロビーの記述子

ゲーム選択画面とロビーへ配る値である（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）。

| 項目 | 値 |
| --- | --- |
| `title` | `ESCAPE CALL` |
| `tagline` | 別々の手がかりを英語で伝え合い、3つの錠を開けて脱出する |
| `icon` | 🔐 |
| `playerCount` | `[2, 4]` |
| `contentLabelJa` | 舞台を選ぶ |

対応人数を2〜4人とする（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md)）。
5人以上では断片の種類（並び、対応表、規則）より人数が大きく上回り、半分に分けた断片をさらに分けることになる。
分けるほど1人の断片が短くなり、読み上げる量が数語まで減って、見ているだけに近い人が出る。

## 設定

| key | labelJa | 型 | 範囲 | 既定 |
| --- | --- | --- | --- | --- |
| `escapeSeconds` | 制限時間（秒） | number | 300〜900、step 60 | 600 |

既定を600秒とするのは、錠1つに3分強を見込むためである（未検証）。
下限を300秒に置くのは、錠1つに100秒を下回ると、断片の読み上げと聞き返しが1往復で終わらないためである。
上限を900秒に置くのは、1晩に3ゲームという想定（[設計.md](../設計.md) のロードマップ）に収めるためである。

`validateSettings` は範囲外、型違い、欠損を拒否する。
記述子の `min` / `max` と受理範囲を一致させ、その一致をテストで固定する。

`step` は入力の刻みであり、受理の条件にしない。
範囲内の整数であれば受理する（収録5本と同じ扱い）。

## start の処理順

1. `contentId` からパックを引く。`listContents` に載るidだけを受理する
2. `settings.escapeSeconds` を確定する（既定600秒）
3. 3つの錠を生成する（「生成」を参照）
4. 錠ごとに、参加者をレベルの降順に並べ、同じレベルの中を `seed` でシャッフルし、断片を割り当てる
5. 規則の英文を、規則を持つ人のレベルの段で組み立てる
6. 全員へ `pieces: []` の秘密を配る
7. `stage` を `briefing`、`deadlineSeconds` を90として返す

抽選と生成は共通コアが注入した `seed` からのみ行う。
`Math.random()` と時刻を使わない（[05](./05_ゲームモジュール.md) の呼び出し規約）。
乱数は共通コアのシード付き乱数を使う（[ADR-0020](../adr/0020-ゲーム間で重複する部品は共通コアへ置く.md)）。

```typescript
{ id: "lab", title: "深夜の研究所" }
```

規則の言い回しをカタログに載せない。
ロビーで規則の一覧が分かると、`solving` に入る前に意味を調べられる。

## 画面

画面は `client/games/escapecall/` に置く。

| ステージ | 画面 |
| --- | --- |
| `briefing` | 舞台の導入文、色と形の英語名の一覧、自分の画面を見せない約束、準備完了ボタン |
| `solving` | 錠の名前と桁数、自分の断片、誰がどの種類の断片を持つか、答えの入力、提出の履歴、開示済みのヒント、残り時間 |
| `debrief` | 脱出の成否とランク、3つの錠の答えと断片の全部 |

`solving` の画面の要点を挙げる。

* 答えの入力は数字だけの10キーとし、錠の桁数ぶんの枠を出す。英字キーボードを開かない
* 自分の断片を画面の上半分に置き、入力を下半分に置く。断片を見ながら入力できるようにする
* 色と形の英語名の早見表を、断片の横から開けるようにする。開いている間も断片は見える
* ホストの画面にだけ、ヒントの要求ボタンを出す
* 錠が開いたときは、[ビジュアルデザイン.md](../ビジュアルデザイン.md) のカットインの文法で解錠を見せてから、次の錠の断片へ切り替える

画面の記号に座標や番号を添えない。
並びの記号に番号が振ってあれば「1番は」と言えば済み、`first` `second` `last` のような順序の表現を使う理由が消える（[12](./12_BLINDROOMゲームモジュール.md) の「座標を画面に出さない」と同じ理由）。

## 所要時間の見積り

締切は上限であり、実際は `ready` と解錠で先に進む。
3人、`escapeSeconds` 600秒で見積る。

| 区間 | 見積り |
| --- | --- |
| `briefing` | 60秒（締切90） |
| 錠1 | 120秒 |
| 錠2 | 180秒 |
| 錠3 | 240秒 |
| 結果の確認 | 60秒 |
| 1ゲーム | 約660秒（約11分） |

**実測はしていない。**
錠ごとの所要時間は、断片の読み上げと聞き返しの往復数から置いた仮の値である。

1ファイルが1パック（舞台）であり、ロビーで選ぶ単位はパックである（収録5本と同じ形）。

色と形の名前はコードに持ち、コンテンツに持たない。
記号の描画と名前が同じ定義から出ないと、画面の色と文の色名が食い違う。

`skip_shape` の `easy` にある `{shape}s` は、置き換え後に `stars` のような複数形になる。
4つの形はどれも `s` を付ければ複数形になる語として選んでいる。

錠の答え、並び、対応表を書く欄を設けない（[ADR-0027](../adr/0027-ESCAPECALLの謎はテンプレートとseedから生成する.md)）。

## 検証項目

`pnpm validate:content` で検査する。

| # | 内容 |
| --- | --- |
| 1 | スキーマ。必須欄の欠落と型違いを落とす。定義に無い欄（錠の答えなど）があれば落とす |
| 2 | `id` が `[a-z0-9_]` の1〜16文字 |
| 3 | `lockLabels` がちょうど3件 |
| 4 | `rulePhrases` が、コードに定義されたすべての規則IDの言い回しを持ち、未知の規則IDを持たない |
| 5 | 各規則の `easy` / `standard` / `ja` が空でない |
| 6 | `skip_color` の3文がすべて `{color}` を1回だけ含み、`{shape}` を含まない |
| 7 | `skip_shape` の3文がすべて `{shape}` を1回だけ含み、`{color}` を含まない |
| 8 | それ以外の規則の文が `{color}` も `{shape}` も含まない |
| 9 | `keyExpressions` が3件以上 |
| 10 | すべての `ja` と `titleJa` / `introJa` が空でない |

検証4が、規則を足したときの言い回しの書き漏らしを落とす（[ADR-0027](../adr/0027-ESCAPECALLの謎はテンプレートとseedから生成する.md)の影響）。

検証6〜8が、置き換えの穴の過不足を落とす。
穴が無い文では除く対象が伝わらず、余分な穴は置き換えられずに `{color}` のまま画面に出る。

検証10を置くのは、`ja` がフォントサブセットの入力になるためである（[07](./07_リポジトリとツールチェーン.md)）。

### 機械で検査しないもの

* 規則の英文が、コードの作用と同じ意味を述べているか
* `easy` の英文がレベル1〜2に通じる語だけでできているか
* `standard` の英文が、`easy` の言い換えにとどまらず条件の読み取りを要求しているか
* `keyExpressions` が、この遊びで実際に使う質問になっているか

いずれも人手のレビューで見る。
記録は `docs/お題レビュー/` に置く（収録3本と同じ形）。

## 判定の規則

解錠の判定は、提出された数字列と、生成時に計算した答えの文字列一致だけで行う。
話し方、質問の回数、誰が入力したかは判定に影響しない。

アプリは英語を解釈しない（不変条件1、[ADR-0001](../adr/0001-ランタイムAI不使用.md)）。
規則の英文は表示するだけであり、判定に使わない。

## 未解決の論点

| 論点 | 内容 |
| --- | --- |
| 同じ系統の錠の繰り返し | 3つの錠がすべて「並び、規則、対応表」の系統である。錠2と錠3で飽きが出るかは未検証であり、出た場合は錠の系統を足す（[ADR-0027](../adr/0027-ESCAPECALLの謎はテンプレートとseedから生成する.md)） |
| 2人卓の役割の偏り | 2人卓では、レベルの低い人が3つの錠すべてで対応表を持つ。同じレベルなら錠ごとにシャッフルするが、レベル差がある卓では偏りが固定される |
| 切断したまま戻らない参加者 | その人の断片が無いと錠が解けない。ヒントを残り1桁まで開示して総当たりすれば進めるが、断片の割り当てを残った人へ付け替える機構は持たない |
| 総当たり | 誤答に罰則が無く、ヒントで桁を開示した後の総当たりは防がない。ランクに誤答数を反映するだけである |
| 提出の件数 | `attempts` に上限を置かない。1ゲームの提出は制限時間とレート制限で頭打ちになるが、公開状態の大きさは実測していない |
| ランクの閾値 | S、A、Bの閾値は仮置きである |
| 所要時間 | 錠ごとの所要時間と、既定600秒の妥当性は実測していない |
| 画面を見せない約束 | 画面を見せ合うと英語で伝える理由が消える。機械では検出せず、場に委ねる |
| 色の聞き分け | 4色は色覚特性でも分離する組み合わせから選んだが、赤と黒を実機の画面で取り違えないかは確認していない |

## 旧ESCAPEからの変更

旧ESCAPE（ブランチ `task/escape-設計` の基本設計09と10）から変えた点と、その理由を挙げる。

| 変更 | 理由 |
| --- | --- |
| 対応人数を5〜6人から2〜4人にした | 少人数で遊べるゲームが無い（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md)） |
| 手作りのシナリオをやめ、錠を生成にした | シナリオを1本解くと同じ卓では二度遊べない（[ADR-0027](../adr/0027-ESCAPECALLの謎はテンプレートとseedから生成する.md)） |
| 推論エンジンによる可解性の検証をやめた | 断片の組み合わせ方がコードで固定され、網羅して確かめる対象が無い。可解性は生成の手順とユニットテストで保証する |
| ロールの配役を、錠ごとの断片の割り当てにした | ロールは5〜6人を前提とした固定の役割だった。2〜4人では錠ごとに割り当て直す方が、全員が毎回断片を持てる |
| ヒントを事前収録の文から、答えの桁の開示にした | 生成した錠に合わせた文を事前に書けない。桁の開示は、どの錠にも同じ形で使える |
| ヒントの上限を「残り1桁まで」にした | 全桁を開示すると錠を解く工程が消える。残り1桁なら総当たりで必ず開けられ、詰みが残らない |
| 答えを英単語と数字の組から、数字だけにした | 英単語の答えは、綴りの揺れを照合でどこまで許すかの判断が要る。数字なら文字列一致で足りる |
| ランクを置いた | 旧ESCAPEは成否だけだった。成否だけでは、ヒントを使い切った脱出と使わない脱出が同じ結果になる |

## テスト観点

`GameModule` は純粋関数のため、Durable Objectなしで全項目をテストする。

* 決定性: 同じ `seed` と同じ参加者から、同じ錠と同じ断片の割り当てが得られること
* 生成: 1000件以上の `seed` と2〜4人の全人数で、「生成」の不変条件がすべて成り立つこと
* 生成: 規則を1つずつ外すと答えが変わること
* 生成: どの参加者の断片を外しても、答えの計算関数が答えを返さないこと
* 生成: 錠3の規則に除く規則が2つ入らず、同じ規則IDが重ならないこと
* 生成: 対応表を半分に分けたとき、前半と後半のどちらにも答えに使う記号が入ること
* 割り当て: 規則がレベルの最も高い参加者に、対応表がレベルの最も低い参加者に渡ること
* 割り当て: 全員が同じレベルのとき、錠ごとに割り当てが変わりうること（seedを変えて確かめる）
* 割り当て: どの錠でも全員が1つ以上の断片を持つこと
* 言い回し: 規則を持つ人のレベル1〜2で `easy` と `textJa`、3〜5で `standard` が配られ `textJa` が入らないこと
* 言い回し: 置き換え後の文に `{color}` `{shape}` が残らないこと
* 秘密の非混入: 公開状態に答え、並び、対応表、規則の文が現れないこと
* 秘密の非混入: `listContents()` の戻り値に規則の言い回しが含まれないこと
* 秘密の配布: `briefing` 中の秘密が `pieces: []` であること
* 秘密の配布: `solving` へ入るときに全員へ錠1の断片が送られること
* 秘密の配布: 錠が開いたときに、全員へ次の錠の断片の全量が送られ、前の錠の断片が残らないこと
* `submit`: 桁数違い、数字以外、文字列以外が `invalid_code` で拒否されること
* `submit`: 同じ錠への同じ誤答が `already_attempted` で拒否され、状態が変わらないこと
* `submit`: 誤答で `attempts` に1行増え、ステージも締切も変わらないこと
* `submit`: 正答で錠が開き、`currentLockIndex` が進み、`deadlineSeconds` を返さないこと
* `submit`: 3つ目の錠の正答で `result` が返り、`outcome` が `escaped` になること
* `submit`: 開いた錠の答えを次の錠へ提出しても開かないこと
* `hint`: ホスト以外からの送信が `not_host` で拒否されること
* `hint`: 左から1桁ずつ開示され、`codeLength - 1` 桁を超える要求が `no_more_hints` で拒否されること
* 締切: `briefing` の締切で `solving` へ進み、錠1の断片が配られること
* 締切: `solving` の締切で `result` が返り、`outcome` が `time_up` になること
* 結果: 開かなかった錠の答えと断片も `locks` に含まれること
* 結果: 表の条件どおりにランクが決まること（各ランクの境界の前後で確かめる）
* 結果: `rules[].textEn` が、その錠で規則を持った人に配った英文と一致すること
* ペイロード: `submit` のペイロードが `ACTION_MAX_CHARS`（512）未満であること
* 設定: 記述子の `min` / `max` と `validateSettings` の受理範囲が一致すること
* 人数: 2人、3人、4人で開始でき、1人と5人では共通コアが開始を拒否すること
