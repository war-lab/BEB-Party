# 基本設計: WHO WROTE THIS?ゲームモジュール

## 結論

WHO WROTE THIS?は5ステージ（`briefing` / `writing` / `guessing` / `judging` / `reveal`）を持つゲームモジュールであり、`GameModule` インターフェースの実装として完結する。

全員が同じ質問へ英文1つを書いて提出する。
提出は匿名で1件ずつ開示され、その都度、全員が作者を指名する。

指名が正解した人に1点、自分の提出を誰にも当てられなかった人に1点を与える。
アプリが照合するのは提出者と指名先だけであり、英文の質は判定しない（不変条件1）。

1ゲームは2ラウンドとし、ラウンドごとに質問が入れ替わる。

収録済み3本と違い、プレイヤーの入力がテキストになる。
このため `action` のペイロードに長さ上限が必要であり、共通コアへの変更を1件伴う（[ADR-0023](../adr/0023-actionペイロードに長さ上限を課す.md)）。
手番制は要らない。全員同時の提出と、全員から1件を収集する既存の形で足りる。

gameIdは `whowrotethis` とする。
既収録の `dontsayit` が句読点を落として連結する形を採っているため、同じ規則を適用する。

ルールの原案は [収録候補ゲームのルール案.md](../収録候補ゲームのルール案.md) の案11であり、実装順と受入条件は [実装計画/ゲーム構想20案の収録計画.md](../実装計画/ゲーム構想20案の収録計画.md) を正とする。
本文書は、そこで未定のまま残した点を決め、ルールの正本となる。
原案から変更した点は末尾の「原案からの変更」に列挙する。

共通コアとの境界は [05](./05_ゲームモジュール.md)、メッセージの意味は [03](./03_プロトコル.md) を正とする。

## ステージ

| stage | 締切 | 遷移条件 |
| --- | --- | --- |
| `briefing` | 60秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `writing` | `writingSeconds`（既定90秒） | 接続中の全員が `submit` を送る、または締切到達 |
| `guessing` | 40秒（開示1件ごとに張り直す） | 表示中の提出の作者を除く接続中の全員が `guess` を送る、または締切到達 |
| `judging` | 12秒 | 締切到達のみ |
| `reveal` | 90秒（最終ラウンドはなし） | 接続中の全員が `ready` を送る、または締切到達 |

`guessing` と `judging` は提出1件につき1往復する。
最後の1件の `judging` が終わると `reveal` へ進み、`reveal` が終わると次のラウンドの `briefing` へ戻る。
最終ラウンドの `reveal` へ入る時点で `result` を返し、部屋は `finished` になる。

`judging` を独立したステージにするのは、答え合わせを読む時間を確保するためである。
指名が揃った直後に次の件の締切が動き出すと、作者が誰だったかを見る前に次の英文が表示される。

`judging` に操作を置かない。
場が沸いている最中に1人が先へ進められる経路を作らないためである（[10](./10_ENGLISHRANKINGゲームモジュール.md) の `discussion` に早期終了を置かない判断と同じ）。

`guessing` では Wake Lock を取得する。
提出を読んで英語で言い合うステージであり、指名を押すまで画面に触らない時間が続く。

`briefing` の秘密（言い回しの例）は伏せ面のカットインで開かない。
他人に見られても失われる情報がなく、DETECTIVESの配役やRANKINGの目標と性質が違う。

最終ラウンドの `reveal`（`finished`）には2つの操作を置く。
「ロビーへ戻る」は `nextGame` を送る操作でホストにのみ出し、「部屋を出る」は自分の接続を切る操作で全員に出す。
`nextGame` はホストしか受理されないため、他の参加者にボタンを出すと押しても拒否されるだけになる（[08](./08_DETECTIVESゲームモジュール.md)と同じ扱い）。

## 進行の要点

### 開示順は start で固定する

ラウンドごとに参加者の並びをシャッフルし、その順に提出を開示する。
順序は `start` の `seed` から決め、`gameSecret` に保持する。

提出順を開示順にしない。
早く書き終えた人が先頭に来ると、開示順そのものが英語力の手がかりになる。

未提出者は開示から飛ばす。
提出が無い人の枠を空で開示しても指名の対象がない。

### 指名の内訳は judging まで伏せる

`guessing` の公開状態には、指名を済ませた人のidだけを載せる。
誰が誰を指名したかは `judging` で開示する。

指名中に他人の指名先が見えると、先に押した人へ同調するだけになり、各自が推理する意味が消える。

### 作者は自分の件で指名しない

表示中の提出の作者からの `guess` は拒否する。
作者は自分の文だと知っているため、指名は棄権でも誤答でもなく、成立しない操作である。

その件の収集対象は「作者を除く接続中の全員」となる。

画面が「自分の文が出ているか」を判定するために、提出には識別子（`submissionId`）を振る。
`start` で全ラウンド分をseedから振り、本人へは `secret` で、開示中の1件については `presented` で配る。
他人の識別子は配らないため、この値から作者は割れない。

提出テキストの一致で判定しない。
同じ英文は合法であり（重複を弾く規則を置いていない）、2人が同じ文を出すと作者でない側まで作者として扱われる。
その人の画面から指名の候補が消える一方、サーバはその人の指名を待ち続けるため、締切まで進行が止まって得点機会も失われる。

識別子は `playerId` から導かない。導くと識別子から作者を逆算できる。

### 消去法は禁じない

`judging` で作者を明かすため、後半の件では候補が絞れる。
候補の一覧は開示済みの人を含めて変えない。

開示順は `seed` で決まるため、最後に開示された人は消去法で当てられやすく、隠し通しの1点を失いやすい。
この偏りは残る（「未解決の論点」に記録する）。

## 公開状態（gameState）

```typescript
interface WhoWroteThisPublic {
  packId: string;
  roundIndex: number;               // 0始まり
  totalRounds: number;              // 2
  question: { en: string; ja: string };
  keyExpressions: KeyExpression[];  // 指名の議論に使える言い回し
  readyPlayerIds: string[];         // briefing / reveal の収集状況
  submittedPlayerIds: string[];     // writing の収集状況。テキストは載せない
  presented: PresentedItem | null;  // guessing / judging で表示中の1件
  revealedItems: RevealedItem[];    // 答え合わせを終えた件（現ラウンド）
  scores: ScoreEntry[];
  rounds: RoundRecord[];            // 確定したラウンドの記録
  writingSeconds: number;
}

interface PresentedItem {
  index: number;                // 現ラウンドの何件目か（0始まり）
  total: number;                // 現ラウンドの開示件数
  text: string;                 // 提出テキスト。作者は載せない
  submissionId: string;         // 提出の識別子。作者を表さない値（startでseedから振る）
  guessedPlayerIds: string[];   // 指名を済ませた人。指名先は載せない
}

interface RevealedItem {
  index: number;
  text: string;
  authorId: string;
  guesses: GuessRecord[];       // 指名の内訳
}

interface GuessRecord {
  playerId: string;
  targetPlayerId: string;
}

interface RoundRecord {
  questionId: string;
  question: { en: string; ja: string };
  items: RevealedItem[];
}

interface ScoreEntry {
  playerId: string;
  points: number;
}
```

`writing` 中は提出テキストを公開状態に置かない。
`state` は全員へブロードキャストされるため、ここに置いた値は他のプレイヤーにも届く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。
公開してよいのは提出済みの人のidだけである。

`keyExpressions` は `guessing` の画面に出す。
指名の議論で使う言い回しであり、出さなければ公開状態に載せる意味がない。

`presented.text` は公開する。
開示中の1件は全員が読むための値であり、伏せると指名ができない。
作者は `gameSecret` に置いたままにする。

未使用の質問と、抽選で選ばれた質問のidを公開状態に置かない。
次のラウンドの質問が分かると、指名の最中に先の英文を考えられる。

`revealedItems` は現ラウンドの答え合わせ済みの件だけを持つ。
`reveal` へ入るときに `RoundRecord` として `rounds` へ移し、`revealedItems` を空へ戻す。

`scores` はゲーム全体の通算とする。
ラウンドごとの得点は `rounds` の内訳から読めるため、別に持たない。

## 秘密情報（secret.payload）

```typescript
interface WhoWroteThisSecret {
  roundIndex: number;
  hintEn: string[];      // 英文を書くときに使える言い回し
  submission?: string;   // 自分の提出。未提出なら省略する
  submissionId: string;  // このラウンドの自分の提出の識別子。presented と突き合わせる
}
```

`hintEn` はレベルに応じた件数を配る（後述の「レベル差の吸収」）。

`hintEn` は完成した回答文にしない。空欄（`...`）を1箇所以上含む枠とする（検証10）。

理由は配布の仕組みにある。
`hintEn` は先頭から切って配るため、1件目はレベルに関係なく全員へ届く。
検証7が4語以上を保証するので、完成文を置くとそれは「そのまま提出できる合法な文」になり、質問の内容とは独立に複数人が同一の提出を出す経路ができる。
提出が並ぶと作者当ては文体当てに退化し、文体が最も目立つレベル1〜2から順に特定される。

枠であることは画面側で伝える。
`briefing` と `writing` の言い回しの例には「`...` は自分の言葉に置き換えてください」を添え、入力欄の例示（placeholder）には自分の1件目をそのまま出す（[02](./02_クライアント.md) の「英文の入力」）。

`submission` を返すのは、再接続した本人が自分の提出を確認して書き直せるようにするためである。
`submit` を受理するたびに本人へ送り直す。
storageへの書き込みが提出1件につき1つ増えるが、6人・2ラウンドの規模では無料枠に対して問題にならない。

送り直すときは `WhoWroteThisSecret` の全体を組み立てる。
共通コアは `playerSecrets[playerId]` をペイロードごと差し替えるため、`submission` だけを返すと `hintEn` が消える。

秘密は `briefing` のたびに全員へ送り直す。
`playerSecrets` は上書きであり結合ではないため、前のラウンドの `hintEn` と `submission` は残らない。

## ゲーム秘密状態（gameSecret）

```typescript
interface WhoWroteThisGameSecret {
  questionIds: string[];                  // 使う2問。startで抽選して固定する
  revealOrders: string[][];               // ラウンドごとの開示順（playerIdの並び）
  submissions: Record<string, string>[];  // ラウンドごとの playerId -> 提出テキスト
  submissionIds: Record<string, string>[]; // ラウンドごとの playerId -> 提出の識別子
  currentGuesses: Record<string, string>; // 表示中の件の playerId -> 指名先
}
```

質問の抽選と開示順の決定は、どちらも `start` で全ラウンド分を行う。
`handleAction` と `onDeadline` にはシードが渡らないため（[05](./05_ゲームモジュール.md) の呼び出し規約）、ラウンドが進むたびに抽選する形は取れない。

`currentGuesses` は `judging` へ入るときに `RevealedItem.guesses` へ移し、空へ戻す。
公開済みの指名を秘密側に二重で持たない。

`submissions` はラウンドが終わっても残す。
得点の再計算には要らないが、まだ開示していない件を公開状態へ出さない判断をこの側で持つ。

## action の受理規則

| action | 送れる人 | ステージ | 効果 |
| --- | --- | --- | --- |
| `ready` | 全員 | `briefing` / `reveal` | 収集に加える。接続中の全員が揃えば遷移 |
| `submit` | 全員 | `writing` | 提出を登録する。締切まで上書きできる |
| `guess` | 表示中の件の作者以外 | `guessing` | 指名を登録する。二重送信は拒否する |

ステージ違いはすべて `invalid_stage` で拒否する。

拒否のコードはすべてゲームモジュール側で定義し、共通コアのエラーコード表には載せない（[01](./01_サーバ.md)、[10](./10_ENGLISHRANKINGゲームモジュール.md) と同じ）。
`invalid_submission` / `too_short` / `too_long` / `stale_guess` / `own_submission` / `already_guessed` / `invalid_target` / `invalid_stage` の8つを持つ。

### ready

二重送信は拒否せず冪等に扱う（[08](./08_DETECTIVESゲームモジュール.md)・[09](./09_DONTSAYITゲームモジュール.md)・[10](./10_ENGLISHRANKINGゲームモジュール.md) と同じ）。
結果に影響せず、再送を拒否すると画面が止まる経路が増える。

### submit

payloadは `{ text: string }` とする。

サーバは受理前にテキストを正規化する。
改行・タブ・全角空白を半角空白へ置き換え、連続する空白を1つへ畳み、前後の空白を落とす。

全角空白を含めるのは、日本語入力のまま英文を打つと語の区切りに全角空白が混じるためである。
半角空白だけで区切ると、全角空白で区切られた4語の提出が1語と数えられて `too_short` で拒否される。

拒否する条件は3つある。

| 条件 | code |
| --- | --- |
| `text` が文字列でない | `invalid_submission` |
| 正規化後の語数が `MIN_WORDS`（4）未満 | `too_short` |
| 正規化後の文字数が `MAX_CHARS`（140）を超える | `too_long` |

語数は半角空白で区切った要素数で数える。
文字数はコードポイント数で数える。
どちらも英語の意味を解釈しないため、不変条件1に抵触しない。

最低語数を課すのは、`Yes.` のような1〜2語の提出では誰の文かを判別する材料が場に出ないためである。
提出が短いほど隠し通しやすいという方向へ寄せない。

上書きを許すのは、締切まで書き直せる方が英文を組み立てる過程に合うためである。
最後に受理した提出のみが有効になる。

クライアントは入力を140文字で止め、4語未満では送信させない。
サーバの拒否は同室のプレイヤーが通常の操作で踏む経路ではなく、改造したクライアントと通信の遅れに対する歯止めである。

接続中の全員が提出した時点で `guessing` へ進む。

### guess

payloadは `{ index: number, targetPlayerId: string }` とする。

`index` を要求するのは、開示が次の件へ進んだ後に前の件への指名が届く経路を弾くためである。
`guessing` の締切は40秒であり、通信の遅れと締切到達が重なると起こりうる。

拒否する条件は5つある。

| 条件 | code |
| --- | --- |
| `index` が `presented.index` と一致しない | `stale_guess` |
| 送信者が表示中の件の作者 | `own_submission` |
| すでに指名済み | `already_guessed` |
| `targetPlayerId` が現ラウンドの提出者でない | `invalid_target` |
| `targetPlayerId` が送信者自身 | `invalid_target` |

二重送信を拒否するのは、得点に直結する入力であり、上書きを許すと締切直前の変更が続くためである（DETECTIVESの `vote` と同じ扱い）。

クライアントは送信済みの指名を件番号つきで持ち、サーバの応答を待たずに2件目を送らせない。
サーバは初回を採用して2件目を `already_guessed` で拒否するため、画面側で止めないと「押した先」と「採点された先」が食い違う。
件番号を併せて持つのは、次の件へ進んだときにガードが自然に解けるようにするためである。

自分自身への指名を拒否するのは、送信者は自分の提出かどうかを知っており、常に誤りであるためである。
誤操作で1点を失う経路を残さない。

作者を除く接続中の全員が指名した時点で `judging` へ進む。

## onDeadline

| ステージ | 締切到達時の扱い |
| --- | --- |
| `briefing` | `ready` が揃っていなくても `writing` へ進む |
| `writing` | 提出済みの件で `guessing` へ進む。提出が0件ならそのラウンドを飛ばす |
| `guessing` | 未指名者を棄権として `judging` へ進む |
| `judging` | 次の件があれば `guessing`、なければ `reveal` へ進む |
| `reveal` | 次のラウンドの `briefing` へ進む |

提出が0件のラウンドは、得点を動かさずに `reveal` へ進む。
最終ラウンドであれば `result` を返す。
全員が席を外した場合の異常系であり、通常の進行では起きない。

提出が1件のラウンドは成立する。
その1件を作者以外が指名する形になり、得点計算は通常と同じである。

## 得点

| 事象 | 加点 |
| --- | --- |
| 指名が正解した | 指名した人に1点 |
| 自分の提出を誰にも当てられなかった | 作者に1点 |

未提出者には作者側の加点機会がない。
指名する側には参加でき、正解すれば加点される。

減点は置かない。
外した指名に罰を与えると、当てに行かない方が有利になる。

6人・全員提出のラウンドで取り得る最大は6点である（指名5件の正解で5点、隠し通しで1点）。
2ラウンドで12点となり、得点が細かく刻まれるため同点が出にくい。

5人の卓では開示が5件、1件あたりの指名者が4人になるため、1ラウンドの最大は5点になる。
人数で最大値が変わるが、同じ卓の全員に同じ上限が適用されるため、順位付けに影響しない。

隠し通しを原案の2点から1点へ下げた理由は「レベル差の吸収」に記す。

## レベル差の吸収

3層で吸収する。

第1層は言い回しの支援である。
質問は全員へ同じものを公開するため、難度の差をお題側に付けられない。
そのぶん `hintEn` の件数をレベルで変える。

| レベル | `hintEn` の件数 |
| --- | --- |
| 1〜2 | 3件 |
| 3〜5 | 1件 |

RANKINGの目標カードと同じ手法である（[10](./10_ENGLISHRANKINGゲームモジュール.md) のレベル差の吸収）。
件数の差だけで済むのは、この質問に何を書くかが自由であり、ヒントが答えを与えないためである。

第2層は得点の主軸を指名側へ置くことである。
指名の正解は同室の相手の英語を知っているかで決まり、英作文の量では決まらない。
1ラウンドの最大6点のうち5点が指名側にあるため、英語力の差が得点差へ直接には出にくい。

第3層は隠し通しの1点が持つ動機である。
自分らしくない英文を書くほど当てられにくくなるため、レベル5には平易に書く動機が、レベル1〜2には背伸びする動機が生まれる。

ただしレベル1〜2の提出は文体が目立ち、特定されやすい。
隠し通しを厚くすると上級者に偏るため1点に留めたが、この層が隠し通しの点を取りにくい構造そのものは残る。
確度: **未検証**（得点構造からの推論であり、実プレイでの計測はしていない）。

## ロビーの記述子

ゲーム選択画面とロビーへ配る値である（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）。

| 項目 | 値 |
| --- | --- |
| `title` | `WHO WROTE THIS?` |
| `tagline` | 英語で書いた1文を並べ、誰が書いたか当てる |
| `icon` | ✍️ |
| `playerCount` | `[5, 6]` |
| `contentLabelJa` | お題を選ぶ |

対応人数を収録3本と同じ5〜6人にする。
4人でも進行は成立するが、指名の候補が3人に減り、消去法で当たる割合が上がる。

## 設定

| key | labelJa | 範囲 | 既定 |
| --- | --- | --- | --- |
| `writingSeconds` | 英作文の時間（秒） | 60〜150、step 30 | 90 |

ラウンド数は2固定とし、設定にしない。
所要時間がラウンド数と開示件数の積で伸びるため、両方を可変にすると卓が長さを予測できない。

既定を90秒とするのは、原案の60秒ではレベル1〜2が1文を組み立てきれない見込みであるためである（未検証）。

`validateSettings` は範囲外・型違い・欠損を拒否する。
ロビーの記述子（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）の `min` / `max` と受理範囲を一致させ、その一致をテストで固定する。

`step` は入力の刻みであり、受理の条件にしない。
範囲内の整数であれば受理する（RANKINGの `discussionSeconds` と同じ扱い）。

## start の処理順

1. `contentId` からパックを引く。`listContents` に載るidだけを受理する
2. `seed` から乱数を作り、パックの質問を `shuffle` して先頭2件を `questionIds` に固定する
3. ラウンドごとに参加者の並びを `shuffle` し、`revealOrders` に固定する。併せて提出の識別子をラウンドごとに振る
4. ラウンド0の `hintEn` を各自のレベルに応じた件数で配る
5. `stage` を `briefing`、`deadlineSeconds` を60として返す

質問の抽選と開示順の決定は共通コアが注入した `seed` からのみ行う。
`Math.random()` と時刻を使わない（[05](./05_ゲームモジュール.md) の呼び出し規約）。

`revealOrders` は参加者全員を並べる。
提出しなかった人は開示時に飛ばすため、並びの側で除く必要がない。

## カタログ（listContents）

```typescript
{ id: "daily", title: "日常", questionCount: 12 }
```

質問文をカタログに載せない。
ロビーで質問が見えると、`writing` へ入る前に英文を用意できる。

## 結果（result.payload）

```typescript
interface WhoWroteThisResult {
  rounds: RoundRecord[];   // 2ラウンド分
  scores: ScoreEntry[];    // 降順
}
```

使わなかった質問は結果に載せない。
場に出ていない質問を振り返りに混ぜても読む理由がない。

`rounds` は公開状態と同じ内容を持つ。
`finished` のまま再接続した人へ共通コアが `lastResult` を再送するため、結果画面が公開状態に依存しないようにする。

## 所要時間の見積り

締切は上限であり、実際は `ready` と収集で先に進む。
6人・全員提出（開示6件）で見積る。

| 区間 | 見積り |
| --- | --- |
| `briefing` | 30秒（締切60） |
| `writing` | 90秒（設定。締切がそのまま経過する） |
| `guessing` | 30秒 × 6件 = 180秒（締切40） |
| `judging` | 12秒 × 6件 = 72秒 |
| `reveal` | 40秒（締切90） |
| 1ラウンド | 約412秒 |
| 1ゲーム（2ラウンド） | 約14分 |

`writingSeconds` を上限の150秒にすると1ゲームは約16分になり、[収録計画](../実装計画/ゲーム構想20案の収録計画.md) の受入条件「6人で15分以内」を超える。
既定値で収まる見積りであるが、**実測はしていない**。

余裕が小さいため、実測が15分を超えた場合の調整先を先に決めておく。
ラウンド数を1へ落とすより、`judging` を8秒へ、`guessing` の締切を30秒へ詰める順で見直す。
1ラウンドだと得点の段階が半分になり、結果画面が締まらない。

## コンテンツ形式

```json
{
  "id": "daily",
  "title": "日常",
  "keyExpressions": [
    { "en": "This sounds like Ken.", "ja": "これは〇〇っぽい" },
    { "en": "It is not me.", "ja": "私じゃない" },
    { "en": "Did you write this?", "ja": "これ書いた？" }
  ],
  "questions": [
    {
      "id": "q_last_meal",
      "en": "What would you eat for your last meal?",
      "ja": "人生最後の食事に何を食べる？",
      "hintEn": [
        "I would eat ... with rice.",
        "I want ... as my last meal.",
        "My last meal is ... at home."
      ]
    }
  ]
}
```

1ファイルが1パックであり、パックは複数の質問を持つ。
ロビーで選ぶ単位はパックである（DON'T SAY ITのお題セット、RANKINGのお題パックと同じ形）。

`keyExpressions` はパック直下に置く。
指名の議論に使う言い回しは質問の内容に依存しないため、質問ごとに持たせると同じ文が並ぶ。
`hintEn` は質問ごとに持たせる。書く対象が変われば使える言い回しも変わる。

質問数の下限は4とする。
1ゲームで2問使うため、抽選に選択の余地が残る最小の件数である。

同じ部屋で2ゲーム続けたときの重複は、この下限では防げない。
`nextGame` で `gameSecret` は破棄され、ゲームをまたいで使用済みの質問idを持ち越す口が `GameModule` にないためである（DON'T SAY ITの `usedCards` と同じ制約。[09](./09_DONTSAYITゲームモジュール.md)）。
収録するパックは8件以上を目安とし、抽選で同じ質問が続けて出る確率を下げる。

## 検証項目

`pnpm validate:content` で検査する。

| # | 内容 |
| --- | --- |
| 1 | スキーマ。必須欄の欠落と型違いを落とす |
| 2 | 質問が4件以上 |
| 3 | 質問idがパック内で一意 |
| 4 | `en` が `?` で終わる |
| 5 | `en` と `ja` が空でない |
| 6 | `hintEn` が3件以上 |
| 7 | `hintEn` の各文が `MIN_WORDS`（4語）以上 |
| 8 | `keyExpressions` が3件以上 |
| 9 | 正規化した `en` が一致する質問が2件ない |
| 10 | `hintEn` の各文が空欄（`...`）を1箇所以上含む |

検証7を置くのは、`hintEn` をそのまま書き写した提出が `too_short` で拒否される状態を作らないためである。

検証10を置くのは、`hintEn` が「配られる正解」になるのを防ぐためである（理由は「秘密情報」に書いた）。
検証7と検証10は同時に働く。枠は4語以上あり、かつ完成文ではない。

検証9の正規化は `submit` と同じ手順（空白の畳み込みと前後のトリム）で行う。

### 機械で検査しないもの

* 回答が1文で書けるか
* 答えが一意に決まる質問でないか（`What is the capital of Japan?` は全員が同じ英文を書き、作者当てが成立しない）
* 卓の全員が答えを持てるか（家庭環境や特定の趣味に依存しないか）
* 個人情報を尋ねていないか（[ルール案](../収録候補ゲームのルール案.md) の案11が挙げる要件）
* `hintEn` の枠と `keyExpressions` の英文が自然か（枠の前後が文として成立するか）
* `keyExpressions` に否定・質問の型が揃っているか（疑われた側が返せるか）

いずれも人手のレビューで見る。
記録は `docs/お題レビュー/` に置く（DON'T SAY IT・RANKINGと同じ形）。

## 判定の規則

得点の判定は、提出者と指名先の照合に対してのみ行う。
英文の内容、提出の速さ、議論の中身は判定に影響しない。

確定した内訳は `RoundRecord.items` として保存し、後から再計算しない。
コンテンツを差し替えても過去のラウンドの記録が動かないようにする。

## 未解決の論点

| 論点 | 内容 |
| --- | --- |
| 開示順による有利不利 | 最後に開示された提出は消去法で当てられ、隠し通しの1点を失いやすい。順序は `seed` で決まり2ラウンドで均される見込みだが、未検証である |
| 所要時間の余裕 | 6人・既定値で約14分の見積りであり、受入条件15分に対する余裕が小さい。実測で超えた場合の調整順は「所要時間の見積り」に書いた |
| 発話量 | 収録3本と違い、`writing` は無言のテキスト入力になる。`guessing` の議論で補う設計だが、1ゲームあたりの発話量が3本より減るかは未測定である |
| 文体の識別しやすさとレベル | レベル1〜2の提出は特定されやすく、隠し通しの点を取りにくい構造が残る。当て主軸にして影響を小さくしたが、未検証である |
| 書き直しの書き込み量 | `submit` の上書きを許すため、締切直前に全員が書き直すと `writing` 中の書き込みが増える。実測していない |
| 質問が次のゲームで再登場する | `nextGame` で `gameSecret` が破棄されるため、同じ部屋で続けて遊ぶと同じ質問を引きうる。持ち越すには共通コアの変更が要るため、[05](./05_ゲームモジュール.md) の手順6に従って先送りする（DON'T SAY ITの同じ論点と合わせて判断する） |
| 同じ英文の提出 | 重複を弾く規則を置いていない。作者の判定は識別子で行うため進行は壊れないが、開示に同じ文が並ぶと指名の手がかりが消える。実プレイで起きる頻度は未検証 |
| 提出内容の適切さ | 自由英文であり、場を壊す内容を機械で弾かない。同室プレイのため運用に委ねる（[収録計画](../実装計画/ゲーム構想20案の収録計画.md) のリスク表と同じ判断） |

## 原案からの変更

[ルール案](../収録候補ゲームのルール案.md) の案11から変えた点と、その理由を挙げる。

| 変更 | 理由 |
| --- | --- |
| 隠し通しの加点を2点から1点へ下げた | レベル1〜2の提出は文体が目立って特定されやすく、隠し通しを厚くすると上級者に偏る |
| 「全員に当てられたら0点」を規則から外した | 当てられた作者へ加点しないため、0点は独立した規則ではなく結果である |
| 1ゲームを2ラウンド（質問2問）にした | 原案は開示の回数だけを述べ、質問の数に言及がない。1問では得点の段階が半分になり、3問では15分を超える |
| 最低語数（4語）と最大文字数（140）をサーバで課した | 原案に提出の長さの規定がない。1〜2語の提出は判別材料が場に出ず、短いほど隠し通しやすくなる |
| 提出の上書きを許した | 原案は提出の訂正に触れていない。締切まで書き直せる方が英文を組み立てる過程に合う |
| 開示順を `start` で固定した | 提出順に開示すると、早く書き終えた人が先頭に来ることが英語力の手がかりになる |
| 答え合わせを独立ステージ（`judging`）にした | 指名が揃った直後に次の件の締切が動くと、作者を確認する時間がない |
| 指名の内訳を `judging` まで伏せた | 指名中に他人の指名先が見えると、先に押した人への同調が起きる |
| `guess` に `index` を要求した | 開示が次の件へ進んだ後に前の件への指名が届く経路を弾く |
| `hintEn` の件数をレベルで変えた | 原案はレベル差の吸収に触れていない |

## テスト観点

`GameModule` は純粋関数のため、Durable Objectなしで全項目をテストする。

* 決定性: 同じ `seed` と同じ参加者から、同じ2問と同じ開示順が得られること
* 秘密の非混入: `writing` 中の `WhoWroteThisPublic` に提出テキストが現れないこと
* 秘密の非混入: `guessing` 中の公開状態に表示中の件の作者が現れないこと
* 秘密の非混入: `guessing` 中の公開状態に指名先が現れないこと
* 秘密の非混入: `listContents()` の戻り値に質問文が含まれないこと
* 開示順: 提出の順序を変えても開示順が変わらないこと
* `submit`: 4語未満が `too_short`、140文字超が `too_long`、文字列でない値が `invalid_submission` で拒否されること
* `submit`: 改行と連続空白が正規化され、正規化後の語数で判定されること
* `submit`: 上書きが受理され、最後の提出のみが開示されること
* `submit`: 受理のたびに本人へ `submission` を含む秘密が返り、同じペイロードに `hintEn` が残ること
* `submit`: 提出しても他のプレイヤーの秘密が書き換わらないこと
* `submit`: 接続中の全員が提出した時点で `guessing` へ進むこと
* `guess`: 作者からの指名が `own_submission` で拒否されること
* 識別子: ラウンド内で重複せず、`playerId` から導かれていないこと
* 識別子: 同じ英文を2人が提出しても、開示中の識別子が作者だけを指すこと
* 識別子: 本人の秘密に自分の識別子だけが入ること
* `guess`: `index` 不一致が `stale_guess` で拒否されること
* `guess`: 二重送信が `already_guessed` で拒否され、初回が残ること
* `guess`: 未提出者と自分自身への指名が `invalid_target` で拒否されること
* `guess`: 作者を除く接続中の全員が指名した時点で `judging` へ進むこと
* 得点: 正解した指名者に1点入ること
* 得点: 当てた人が0人のとき作者に1点入ること
* 得点: 未提出者に作者側の加点が入らないこと
* `hintEn`: レベル1〜2に3件、レベル3以上に1件が渡ること
* `hintEn`: 空欄を含まない完成文が検証10で落ちること
* 秘密の切り替え: `briefing` のたびに送り直され、前のラウンドの `submission` が残らないこと
* 締切: `writing` の締切で未提出者を除いた件数で開示が始まること
* 締切: 提出0件のラウンドが得点を動かさずに次へ進むこと
* 締切: 提出1件のラウンドが通常どおり得点計算まで進むこと
* 締切: `guessing` の締切で未指名者が棄権として扱われること
* 未接続: 作者が切断していても、その件の開示と指名が進むこと
* 遷移: `reveal` へ入るときに `revealedItems` が `rounds` へ移り、空へ戻ること
* 遷移: 最終ラウンドの最後の `judging` で `result` が返ること
* 得点: `scores` が2ラウンドの通算になっていること
* 結果: `rounds` が2件になり、各件に全員の提出と指名の内訳が入ること
* 設定: 記述子の `min` / `max` と `validateSettings` の受理範囲が一致すること
* 人数: 5人でも6人でも成立すること
