# 基本設計: SECRET RULE ENGLISHゲームモジュール

## 結論

SECRET RULE ENGLISHは5ステージ（`briefing` / `writing` / `checking` / `proving` / `debrief`）を持つ2〜6人用の協力型ゲームモジュールであり、`GameModule` インターフェースの実装として完結する。

画面には規則の候補が6件出ており、そのうち1件だけが秘密の正解である。
全員が毎ラウンド英文を1つ書いて提出し、サーバは各提出が秘密の規則を満たすかだけを開示する。
参加者は成否の並びから規則を英語で推理し、全員が同じ候補を選んだ時点で答えが確定する。

正解したら、最後に全員が規則を満たす英文を1つずつ書く（`proving`）。
勝敗はチーム単位とし、正解の有無、誤答の数、正解までに使った英文の数、最後の英文の通過数からランクを決める。
個人の得点は持たない。

規則は英文の表層を調べる判定関数に限り、規則の意味はコードに置く（[ADR-0030](../adr/0030-SECRETRULEの規則は表層の判定関数に限り候補を公開する.md)）。
アプリが調べるのは語数、語と文字の有無、末尾の記号であり、英語の意味を解釈しない（不変条件1）。

gameIdは `secretrule` とする。
既収録の `whowrotethis` と同じく、空白と句読点を落として連結する規則を適用する。

共通コアへの追加要求はない。
提出は自由英文であり、`action` ペイロードの長さ上限（[ADR-0023](../adr/0023-actionペイロードに長さ上限を課す.md)）の経路に載る。
全員同時の提出と、全員から1件を収集する既存の形で足りる。

ルールの原案は [収録候補ゲームのルール案.md](../収録候補ゲームのルール案.md) の案5であり、実装順と受入条件は [実装計画/ゲーム構想20案の収録計画.md](../実装計画/ゲーム構想20案の収録計画.md) を正とする。
本文書は、そこで未定のまま残した点を決め、ルールの正本となる。
原案は対戦型であり、協力型へ変えた。原案から変更した点は末尾の「原案からの変更」に列挙する。

共通コアとの境界は [05](./05_ゲームモジュール.md)、メッセージの意味は [03](./03_プロトコル.md) を正とする。

## ステージ

| stage | 締切 | 遷移条件 |
| --- | --- | --- |
| `briefing` | 90秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `writing` | `writingSeconds`（既定75秒） | 接続中の全員が `submit` を送る、または締切到達 |
| `checking` | 120秒 | 正解が確定する、接続中の全員が `ready` を送る、または締切到達 |
| `proving` | `writingSeconds` | 接続中の全員が `submit` を送る、または締切到達 |
| `debrief` | なし | 遷移しない（`lifecycle: finished`） |

`writing` と `checking` は1ラウンドにつき1往復し、最大 `MAX_ROUNDS`（4）ラウンド回す。
`checking` で正解が確定すると `proving` へ進む。
正解しないまま最終ラウンドの `checking` が終わると、`proving` を経ずに `debrief` へ進む。

`briefing` の締切を90秒とするのは、候補6件の英文を読む時間を取るためである。
候補は `briefing` から公開状態に載せる。

`checking` は成否の確認と相談と回答を兼ねる。
成否を見て仮説を英語で言い合う時間がこのゲームの発話の中心であり、確認と相談をステージで分けると、相談の途中で締切が切り替わる。

`checking` では Wake Lock を取得する。
英文の並びを見ながら話す時間が長く、画面に触らない時間が続く。

## 規則

### 判定関数

規則の意味はコードに置き、規則IDとパラメータで参照する。
コンテンツは候補ごとに規則IDとパラメータを選び、規則IDごとの言い回しを書く（[ADR-0030](../adr/0030-SECRETRULEの規則は表層の判定関数に限り候補を公開する.md)）。

| 規則ID | パラメータ | 満たす条件 |
| --- | --- | --- |
| `min_words` | `n`（5〜10） | 語数が `n` 以上 |
| `max_words` | `n`（4〜7） | 語数が `n` 以下 |
| `has_word` | `words`（1〜10語） | `words` のどれかを照合語に含む |
| `no_word` | `words`（1〜3語） | `words` のどれも照合語に含まない |
| `has_letter` | `letter`（a〜z） | その英字を含む |
| `no_letter` | `letter`（a〜z） | その英字を含まない |
| `ends_with` | `mark`（`?` / `!`） | 正規化後の最後の文字がその記号 |
| `long_word` | `n`（7〜10） | `n` 文字以上の照合語を含む |
| `short_words` | `n`（4〜6） | すべての照合語が `n` 文字以下 |
| `starts_with` | `letter`（a〜z） | 最初の照合語がその英字で始まる |

判定の対象は、`submit` の正規化（後述）を済ませたテキストである。
用語を次のように定める。

* **語数**: 正規化後のテキストを半角空白で区切った要素の数。[11](./11_WHOWROTETHISゲームモジュール.md) の語数と同じ数え方である
* **照合語**: テキストから英字（a〜z、A〜Z）の連続を取り出し、小文字にしたもの。`I'm` は `i` と `m` の2語になり、`3 cats.` は `cats` の1語になる
* **英字の有無**: 大文字と小文字を区別しない

語数と照合語の数え方を分けるのは、語数は見た目の区切りで数える方が卓の数え方と一致し、語の有無は記号を除かないと `cats.` と `cats` が別の語になるためである。
この2つの定義は `briefing` の画面に例つきで出す（「画面」を参照）。

`max_words` の下限を4に置くのは、提出の最低語数（`MIN_WORDS`、3語）より大きくするためである。
`max_words` の `n` が3なら、満たす英文はちょうど3語に限られ、規則が実質「3語で書く」になる。

`has_word` と `no_word` の `words` は語形変化を含まない。
`cat` を指定した規則は `cats` を満たさない。

候補の英文に語の一覧をそのまま出すため、卓は一覧にある綴りだけが対象だと読める。
語形変化を自動で扱わないのは、活用の解析が英語の理解に当たるためである（不変条件1）。

判定関数は `server/games/secretrule/` に置き、`validate:content` もこれを使う。
`shared/games/secretrule/` には規則IDとパラメータの型だけを置く。
クライアントは判定関数を持たない（「候補を自動で消さない」を参照）。

### 候補の抽選

パックは候補を8件以上持つ（以下、候補の母集団と呼ぶ）。
`start` で母集団から6件（`CANDIDATE_COUNT`）を `seed` で抽選し、その6件から秘密の規則を1件抽選する。

母集団の全組について、検証用の文例集の中で成否が分かれる文が3件以上あることを `validate:content` で保証する（検証7）。
このため、抽選した6件のどの組も、英文の書き方しだいで見分けられる。

母集団から毎回6件を抽選するのは、同じ卓で同じパックを続けて遊んでも、候補の並びと正解が変わるようにするためである。
母集団8件なら、候補の組は28通り、正解を含めて168通りになる。

### 候補を自動で消さない

公式のクライアントは、提出済みの英文に対して各候補の成否を計算して見せない。
計算すれば、矛盾する候補を画面が自動で消せる。
しかし、どの候補が残るかを英文の並びから考える工程がこのゲームの推理であり、それを画面が代わると相談する理由が消える。

改造したクライアントは公開状態の英文と候補から同じ計算ができる。
協力型であり、得をするのはその卓だけであるため、防がない。

### 一度に全候補を満たす英文

1つの英文で多くの候補を同時に満たすと、成否からは何も分からない。
その英文は必ず通るが、`writing` の提出が通ること自体は得点にならない。
正解は候補の選択で決まるため、全候補を満たそうとする書き方は情報を捨てるだけになり、有利にならない。

原案は通った英文1件ごとに1点を与えていた。
この加点があると、通った英文の語を1つ替えて出し直すのが最適になり、推理が消える。
協力型へ変えた際に外した（「原案からの変更」）。

## 進行の要点

### 回答は全員の一致で確定する

`checking` の間、各自が候補を1つ選べる（`select`）。
接続中の全員の選択が同じ候補に揃った時点で、その候補を答えとして判定する。

回答をホストの操作にしない。
ホストだけが回答できると、ホスト以外は回答に一度も関与できないまま終わる。
全員の一致を条件にすると、卓の合意がそのまま回答の操作になる。

投票による多数決にしない。
2人の卓では票が1対1で割れ、3人の卓では1票ずつ割れると決まらない（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md)）。
全員の一致であれば、人数によらず条件が1つに決まる。

選択は公開する。
協力型であり、誰がどの候補を推しているかが見えれば「Why number three?」と相手を指して聞ける。

選択は変更と取り消しができる。
揃った瞬間に判定するため、画面には「全員が同じ候補を選ぶと答えが確定する」を常に出す。
選ぶ操作は候補を開いて読む操作と分け、読むためのタップで選択が入らないようにする。

### 誤答の扱い

答えが秘密の規則と違えば誤答とする。
誤答の候補を公開状態の `answers` に記録し、全員の選択を消す。
ステージは `checking` のまま変えず、締切も置き直さない。

回答は1ラウンドにつき1回とする。
同じ `checking` の中で誤答した後に `select` を受けると `already_answered` で拒否する。

1ラウンドに1回とするのは、候補が6件しかなく、回答を繰り返せば英文を書かずに総当たりで正解できるためである。
誤答の後は次のラウンドの英文で確かめ直す流れになる。

誤答の候補は以後選べない。
誤答だと判明した候補をもう一度選ぶ理由がない。

誤答に回数の上限は置かない。
ラウンド数の上限がそのまま回答の上限になる。

### 正解したら規則を使って書く

正解が確定すると `proving` へ進む。
`proving` では秘密の規則を公開し、全員が規則を満たす英文を1つずつ書く。

`proving` を置くのは、規則が分かった後に、その制約の中で英文を組み立てる工程を全員に回すためである。
推理の段階では、英文は候補を見分けるための試し書きであり、狙って規則を満たす英文を書く機会がない。
`no_letter`（`e` を使わない）のような規則は、満たす英文を書くこと自体が英作文の練習になる。

`proving` の提出は通過の有無を数えるだけとし、通らない英文も受理する。
受理しないと、通るまで書き直す総当たりになる。

`proving` では成否を `debrief` まで伏せる。
提出のたびに成否が見えると、通るまで書き直せる。

### 重複する英文を拒否する

ゲームの中ですでに提出された英文と、正規化後に一致する英文を `duplicate` で拒否する。
大文字と小文字は区別せずに比べる。

同じ英文の成否は同じであり、出し直しても情報が増えない。
`proving` では、通った英文の書き写しで通過数を稼ぐ経路を塞ぐ。

1語だけ替えた英文は拒否しない。
1語の差で成否が変わるかを確かめるのは、正当な推理の手順である。

## 公開状態（gameState）

```typescript
interface SecretRulePublic {
  packId: string;
  candidates: CandidatePublic[];      // 6件。startで抽選した順
  roundIndex: number;                 // 0始まり。proving と debrief では最後のラウンドのまま
  maxRounds: number;                  // 4
  readyPlayerIds: string[];           // briefing / checking の収集状況
  submittedPlayerIds: string[];       // writing / proving の収集状況。テキストは載せない
  entries: Entry[];                   // writing の提出と成否。全ラウンド分
  selections: Selection[];            // 現ラウンドの選択
  answers: AnswerRecord[];            // 回答の履歴。正解が確定したらその行が最後になる
  solvedCandidateId: string | null;   // 正解の候補。正解が確定するまで null
  keyExpressions: KeyExpression[];    // 相談に使う言い回し
  starters: Starter[];                // 英文の書き出しの例
  writingSeconds: number;
}

interface CandidatePublic {
  id: string;
  textEn: string;                     // 言い回しのパラメータを置き換えた後の文
  textJa: string;
}

interface Entry {
  roundIndex: number;
  playerId: string;
  text: string;
  passed: boolean;
}

interface Selection {
  playerId: string;
  candidateId: string;
}

interface AnswerRecord {
  roundIndex: number;
  candidateId: string;
  correct: boolean;
}
```

秘密の規則は公開状態に置かない。
`state` は全員へブロードキャストされるため、ここに置いた値は全員の端末に届く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。
正解が確定した後は `solvedCandidateId` で公開する。

`writing` 中と `proving` 中は提出テキストを公開状態に置かない。
公開してよいのは提出済みの人のidだけである。
`writing` の提出は `checking` へ入るときに成否と一緒に `entries` へ移す。

`proving` の提出は公開状態に置かず、結果にだけ載せる。
`proving` の後は `debrief` しかなく、公開状態で見せる場面がない。

候補の母集団のうち抽選に漏れた候補は公開状態に置かない。
漏れた候補を見せても推理の材料にならず、画面の候補一覧と区別がつきにくくなる。

`entries` は件数の上限を持たない。
1ゲームの提出は最大で6人 × 4ラウンドの24件、1件140文字以内であり、公開状態は数KBに収まる。

現ラウンドで回答済みかは `answers` の最後の行の `roundIndex` から読む。
別のフラグを持つと、`answers` との整合を二重に保つことになる。

## 秘密情報（secret.payload）

```typescript
interface SecretRuleSecret {
  phase: "writing" | "proving";
  roundIndex: number;
  submission?: string;   // 自分の提出。未提出なら省略する
}
```

秘密の規則はどの参加者にも配らない。
全員が当てる側であり、規則を知る参加者はいない。

`submission` を返すのは、再接続した本人が自分の提出を確認して書き直せるようにするためである（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断）。
`submit` を受理するたびに本人へ送り直す。

秘密は `writing` と `proving` へ入るたびに全員へ送り直す。
`playerSecrets` は上書きであり結合ではないため、送り直さないと前のラウンドの `submission` が画面に残る。

### 再接続での作り直し（rebuildSecret）

`rebuildSecret` は、遷移で最後に送った秘密と同じ値を返す（[ADR-0029](../adr/0029-再接続の秘密情報はゲームモジュールが作り直す.md)）。
秘密は `phase`、`roundIndex`、`gameSecret` の提出だけから決まるため、コンテンツを引かずに作り直せる。

| 状態 | 返す値 |
| --- | --- |
| `briefing` | 返さない（`undefined`） |
| `writing` | `phase: "writing"`、現在の `roundIndex`、`currentSubmissions` の本人の提出 |
| `checking` | `phase: "writing"`、現在の `roundIndex`、`entries` にあるそのラウンドの本人の提出 |
| `proving` / `debrief`（正解） | `phase: "proving"`、`currentSubmissions` の本人の提出 |
| `debrief`（正解なし） | `phase: "writing"`、最終ラウンドの `roundIndex`、`entries` にあるそのラウンドの本人の提出 |

`briefing` で返さないのは、`start` で秘密を送らないためである。
最初に送るのは `writing` へ入るときである。

`checking` で `writing` の値を返すのは、`checking` へ入るときに秘密を送り直さないためである。
最後に送った値は、そのラウンドの `writing` の値のままである。

`gameSecret` が無い場合と、参加者でない `playerId` の場合は例外を投げる。
共通コアは例外のときに保存済みの値を送るため、誤った値を返すより安全である（[13](./13_ESCAPECALLゲームモジュール.md) と同じ扱い）。

## ゲーム秘密状態（gameSecret）

```typescript
interface SecretRuleGameSecret {
  ruleCandidateId: string;                    // 秘密の規則。startで抽選する
  rules: Record<string, RuleSpec>;            // 候補id -> 規則IDとパラメータ。抽選した6件分
  currentSubmissions: Record<string, string>; // 現在の writing / proving の playerId -> 提出
}

interface RuleSpec {
  ruleId: RuleId;
  params: RuleParams;
}
```

`rules` を持つのは、判定のたびにコンテンツを引かないためである。
デプロイでパックが差し替わっても、進行中のゲームの判定は開始時の規則のまま変わらない。

`currentSubmissions` は `checking` へ入るときに成否と一緒に `entries` へ移し、空へ戻す。
`proving` の提出は `debrief` へ入るときに結果へ写し、`currentSubmissions` からは消さない。
終局後に再接続した人へ、`proving` で最後に送った秘密を作り直すためである（「再接続での作り直し」）。

## action の受理規則

| action | 送れる人 | ステージ | 効果 |
| --- | --- | --- | --- |
| `ready` | 全員 | `briefing` / `checking` | 収集に加える。接続中の全員が揃えば遷移 |
| `submit` | 全員 | `writing` / `proving` | 提出を登録する。締切まで上書きできる |
| `select` | 全員 | `checking` | 候補を選ぶ、または選択を取り消す |

ステージ違いはすべて `invalid_stage` で拒否する。
参加者でない送信者と未知の action も、専用のコードを設けず `invalid_stage` で拒否する（[13](./13_ESCAPECALLゲームモジュール.md) と同じ）。

拒否のコードはすべてゲームモジュール側で定義し、共通コアのエラーコード表には載せない。
`invalid_stage` / `invalid_submission` / `too_short` / `too_long` / `duplicate` / `stale_round` / `invalid_candidate` / `already_answered` の8つを持つ。

### ready

二重送信は拒否せず冪等に扱う（収録6本と同じ）。

`checking` で全員の `ready` が揃うと、次のラウンドの `writing` へ進む。
最終ラウンドであれば `result` を返して `debrief` へ進む（正解なし）。

### submit

payloadは `{ text: string }` とする。

正規化は [11](./11_WHOWROTETHISゲームモジュール.md) と同じ手順で行う。
改行、タブ、全角空白を半角空白へ置き換え、連続する空白を1つへ畳み、前後の空白を落とす。

拒否する条件は4つある。

| 条件 | code |
| --- | --- |
| `text` が文字列でない | `invalid_submission` |
| 正規化後の語数が `MIN_WORDS`（3）未満 | `too_short` |
| 正規化後の文字数が `MAX_CHARS`（140）を超える | `too_long` |
| 正規化後に小文字へ揃えた文が、`entries` か現在の提出（本人の分を除く）と一致する | `duplicate` |

最低語数を3語とするのは、規則の多くが語や文字の組み合わせを見るため、1〜2語では試せる組み合わせが少なすぎるためである。
[11](./11_WHOWROTETHISゲームモジュール.md) の4語より少ないのは、ここでは文体を見せる必要がなく、短い英文で1つの仮説を確かめる書き方を許すためである。

上書きを許す。
最後に受理した提出のみが有効になる。
本人の前の提出と一致する再送は、上書きとして受理する。

`duplicate` の比較対象に現在の他人の提出を含めるため、同じラウンドで同じ英文を2人が出すと、後から送った方が拒否される。
拒否の画面には「同じ英文がすでに出ています」と出し、書き換えを促す。
他人の未公開の提出が拒否の有無から1件分だけ推せるが、協力型であり、隠す利益がない。

接続中の全員が提出した時点で、`writing` なら `checking` へ、`proving` なら `debrief` へ進む。

### select

payloadは `{ roundIndex: number; candidateId: string | null }` とする。
`null` は選択の取り消しである。

拒否する条件は3つある。

| 条件 | code |
| --- | --- |
| `roundIndex` が現在のラウンドと違う | `stale_round` |
| `candidateId` が候補6件に無い、または誤答済みの候補 | `invalid_candidate` |
| 現ラウンドで回答済み | `already_answered` |

`roundIndex` を要求するのは、`checking` が次のラウンドへ進んだ直後に届いた前のラウンドの選択を弾くためである。
弾かないと、前のラウンドの選択が次のラウンドの選択として残る。

選択を受理した後、接続中の全員の選択が同じ候補に揃っていれば判定する。

1. その候補が `ruleCandidateId` と一致すれば正解とする。`answers` に `correct: true` の行を加え、`solvedCandidateId` を入れ、全員の秘密を `proving` の値で送り直し、`proving` へ進む
2. 一致しなければ誤答とする。`answers` に `correct: false` の行を加え、`selections` を空にする。ステージを変えず、`deadlineSeconds` を返さない

誤答の遷移で `deadlineSeconds` を返さないのは、返すと共通コアが「適用時刻 + 秒数」で締切を置き直し、`checking` の時間が延びるためである（[13](./13_ESCAPECALLゲームモジュール.md) の「誤答に時間の罰則を置かない」と同じ機構）。

切断中の人の選択は待たない。
接続中が1人だけになった卓では、その人の選択だけで判定する。

判定は `select` を受理したときだけ行う。
違う候補を選んでいた人が切断して残りの選択が揃っても、その時点では判定せず、誰かが選び直したときに判定する。
`GameModule` には接続の変化を受け取る口が無く（`handleAction` / `onDeadline` / `rebuildSecret` だけが呼ばれる。[05](./05_ゲームモジュール.md)）、口を足すと共通コアの変更になるためである。

## onDeadline

| ステージ | 締切到達時の扱い |
| --- | --- |
| `briefing` | `ready` が揃っていなくても `writing` へ進む |
| `writing` | 提出済みの件で成否を判定し、`checking` へ進む。提出が0件でも進む |
| `checking` | 最終ラウンドでなければ次のラウンドの `writing` へ、最終ラウンドなら `result` を返して `debrief` へ進む（正解なし） |
| `proving` | 提出済みの件で通過を数え、`result` を返して `debrief` へ進む |
| `debrief` | 締切を置かない |

提出が0件のラウンドも1ラウンドとして数える。
全員が席を外した場合の異常系であり、通常の進行では起きない。

## 結果（result.payload）

```typescript
interface SecretRuleResult {
  outcome: "solved" | "unsolved";
  rank: "S" | "A" | "B" | "C";
  rule: CandidatePublic;              // 秘密の規則
  candidates: CandidatePublic[];      // 6件
  entries: Entry[];                   // writing の提出と成否。全ラウンド分
  answers: AnswerRecord[];
  sentencesUsed: number;              // 正解が確定するまでの writing の提出数
  wrongCount: number;
  proofEntries: ProofEntry[];         // proving の提出と通過。正解なしなら空
  proofPassedCount: number;
  playerCount: number;                // 開始時の参加者数
}

interface ProofEntry {
  playerId: string;
  text: string;
  passed: boolean;
}
```

ランクは次の表で決める。

| ランク | 条件 |
| --- | --- |
| S | 正解し、誤答0回、`sentencesUsed` が8以下、`proving` で参加者全員の英文が通過 |
| A | 正解し、誤答1回以下、`proving` で参加者の過半数の英文が通過 |
| B | 正解した（SとA以外） |
| C | 正解できなかった |

`sentencesUsed` をラウンド数ではなく英文の数で数えるのは、1ラウンドで得られる成否の数が人数に比例するためである。
6人の卓は1ラウンドで6件、2人の卓は2件の成否を得る。
ラウンド数で数えると、人数の多い卓ほど高いランクを取りやすくなる。

ただし、人数の多い卓は全員が提出するため、1ラウンドで8件の上限に近づく。
6人の卓では1ラウンド目で正解しないとSにならず、2人の卓は4ラウンド目まで余裕がある。
英文の数で数えても人数による有利不利は残り、その向きは逆になる。どちらが大きいかは**未検証**である。

`proving` の通過は、提出しなかった参加者を通過していない人として数える。
切断した参加者がいる卓ではSを取れない。

ランクの閾値は**未検証**の仮置きである。
実プレイでSとAがほとんど出ない、または大半がSになる場合は閾値を見直す。

`entries` と `answers` を結果にも持たせるのは、`finished` のまま再接続した人へ共通コアが `lastResult` を再送するため、結果画面が公開状態に依存しないようにするためである（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断）。

正解しなかった卓にも `rule` を開示する。
どの英文がなぜ通ったかを振り返れないと、推理のどこで外れたかが分からない。

## レベル差の吸収

4層で吸収する。

第1層は勝敗をチーム単位にすることである。
個人の得点を持たないため、1対1のレベル差が勝敗に出ない（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md) の「1対1のレベル差を吸収する」）。

第2層は規則を表層の条件に限ることである。
語数、語の有無、文字の有無、末尾の記号は、文法の知識によらず数えて確かめられる。
推理に要るのは英文の巧拙ではなく、成否の並びの読み比べである。

第3層は日本語の補足と書き出しの例である。
候補の `textJa` と `starters` を、レベル1〜2の画面では常に開き、レベル3〜5の画面では折りたたむ。
公開状態は全員に同じ値を配り、出し分けはクライアントが自分のレベルで行う。

候補は全員に共通であり、秘密情報のようにレベル別の値を配る必要がない。

第4層は最低語数を3語に抑えることである。
`I like cats.` のような3語の英文で1つの仮説を確かめられる。

推理の主導が上級者に偏る構造は残る。
上級者が「次はeを使わずに書いて」と指示し、他の人が書き写すだけになる卓がありうる。
`proving` は各自が自分の英文を書く工程であり、指示を受けても自分で組み立てる部分が残るが、偏りが遊びとして問題になるかは**未検証**である。

## ロビーの記述子

ゲーム選択画面とロビーへ配る値である（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）。

| 項目 | 値 |
| --- | --- |
| `title` | `SECRET RULE ENGLISH` |
| `tagline` | 英文を書いて試し、通る英文の隠れた規則を全員で見抜く |
| `icon` | 虫眼鏡の絵文字（U+1F50D） |
| `playerCount` | `[2, 6]` |
| `contentLabelJa` | 規則パックを選ぶ |

対応人数を2〜6人とする（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md)）。
判定がサーバの照合と全員の一致だけで決まり、投票と隠れ役職を使わないため、人数によって成立しなくなる仕組みがない。

人数で変わるのは、1ラウンドで得られる成否の数である。
2人の卓では4ラウンドで8件の英文しか試せず、6件の候補を見分け切れるかは**未検証**である。

## 設定

| key | labelJa | 型 | 範囲 | 既定 |
| --- | --- | --- | --- | --- |
| `writingSeconds` | 英文を書く時間（秒） | number | 45〜120、step 15 | 75 |

既定を75秒とするのは、[11](./11_WHOWROTETHISゲームモジュール.md) の90秒より短い英文（3語から）を許すためである（未検証）。
`proving` も同じ秒数を使う。

ラウンド数（4）と `checking` の締切（120秒）は設定にしない。
所要時間がラウンド数と相談の時間の積で伸びるため、両方を可変にすると卓が長さを予測できない（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ理由）。

`validateSettings` は範囲外と型違いを拒否する。
`settings` が無い場合と `writingSeconds` が無い場合は拒否せず、既定値を使う。
記述子の `min` / `max` と受理範囲を一致させ、その一致をテストで固定する。

`step` は入力の刻みであり、受理の条件にしない。
範囲内の整数であれば受理する（収録6本と同じ扱い）。

## start の処理順

1. `contentId` からパックを引く。`listContents` に載るidだけを受理する
2. `settings.writingSeconds` を確定する（既定75秒）
3. `seed` から乱数を作り、パックの候補を `shuffle` して先頭6件を候補に固定する
4. 候補6件から秘密の規則を1件抽選し、`ruleCandidateId` に固定する
5. 候補6件の言い回しのパラメータを置き換え、`candidates` を組み立てる
6. `stage` を `briefing`、`deadlineSeconds` を90として返す。秘密は送らない

抽選は共通コアが注入した `seed` からのみ行う。
`Math.random()` と時刻を使わない（[05](./05_ゲームモジュール.md) の呼び出し規約）。
乱数は共通コアのシード付き乱数を使う（[ADR-0020](../adr/0020-ゲーム間で重複する部品は共通コアへ置く.md)）。

候補の表示順は抽選した順とし、秘密の規則の位置に偏りを持たせない。

## カタログ（listContents）

```typescript
{ id: "basic", title: "はじめての規則" }
```

候補の母集団をカタログに載せない。
ロビーで候補が分かると、`briefing` に入る前に試す英文を用意できる。

## 画面

画面は `client/games/secretrule/` に置く。

| ステージ | 画面 |
| --- | --- |
| `briefing` | 遊び方、語数と照合語の数え方の例、候補6件、準備完了ボタン |
| `writing` | 候補6件、これまでの英文と成否、書き出しの例、英文の入力、提出状況、残り時間 |
| `checking` | 今回の英文と成否、これまでの英文と成否、候補6件と各自の選択、誤答済みの候補、相談の言い回し、準備完了ボタン、残り時間 |
| `proving` | 正解の規則、英文の入力、提出状況、残り時間 |
| `debrief` | 正解の有無とランク、秘密の規則、全ラウンドの英文と成否、`proving` の英文と通過 |

画面の要点を挙げる。

* 成否は記号と「通過」「不通過」の文字で示し、色だけに頼らない
* 候補は番号つきで並べる。番号は「Number three?」と口で指すためのものであり、規則の中身を表さない
* `checking` の候補には、その候補を選んだ人のアイコンを添える。全員の一致で確定することを候補一覧の上に常に出す
* 誤答の候補は打ち消し線で示し、選べなくする
* `writing` の入力欄は3語未満で送信させず、140文字で止める
* `writing` の画面に、これまでの英文と成否を出す。どの仮説を試すかは過去の結果を見て決めるためである
* 最終ラウンドの `writing` と `checking` には「最後のラウンド」と出す
* `debrief` の英文の一覧には、正解の規則で通った理由を示さない。照合語の分解や語数を自動で添えると読み比べる工程が消えるため、規則の文と英文だけを並べる

`briefing` に出す数え方の例は次の2つとする。

* `I'm happy.` は2語。照合語は `i`、`m`、`happy` の3つ
* `I have 3 cats!` は4語。照合語は `i`、`have`、`cats` の3つ

## 所要時間の見積り

締切は上限であり、実際は `ready` と収集で先に進む。
4人、`writingSeconds` 75秒、2ラウンド目で正解する卓で見積る。

| 区間 | 見積り |
| --- | --- |
| `briefing` | 60秒（締切90） |
| `writing` | 75秒 × 2 = 150秒 |
| `checking` | 100秒 × 2 = 200秒（締切120） |
| `proving` | 75秒 |
| 結果の確認 | 60秒 |
| 1ゲーム | 約545秒（約9分） |

最も長くなるのは、4ラウンド目で正解し、各ステージが締切まで使う場合である。
`briefing` 90秒、`writing` と `checking` が4往復で780秒、`proving` 75秒、結果の確認60秒で約1005秒（約17分）となり、[収録計画](../実装計画/ゲーム構想20案の収録計画.md) の受入条件「15分以内」を超える。

**実測はしていない。**
実測で15分を超える卓が多い場合は、`checking` の締切を90秒へ詰め、次に `writingSeconds` の既定を60秒へ下げる順で見直す。
ラウンド数を3へ減らすのは最後にする。2人の卓で試せる英文が6件まで減り、候補6件を見分け切れない見込みが高くなるためである。

## コンテンツ形式

```json
{
  "id": "basic",
  "title": "はじめての規則",
  "keyExpressions": [
    { "en": "Mine passed. Yours failed.", "ja": "私のは通った。あなたのはだめだった" },
    { "en": "Maybe the rule is number three.", "ja": "規則は3番かも" },
    { "en": "Why did it fail?", "ja": "なぜだめだった？" },
    { "en": "Let's test it. Write a sentence without the word I.", "ja": "試そう。Iを使わずに書いて" },
    { "en": "Number two is out.", "ja": "2番は違う" }
  ],
  "starters": [
    { "en": "My favorite food is ...", "ja": "好きな食べ物は…" },
    { "en": "Yesterday I went to ...", "ja": "昨日…へ行った" },
    { "en": "Do you like ...?", "ja": "…は好き？" }
  ],
  "candidates": [
    { "id": "no_i", "ruleId": "no_word", "params": { "words": ["I"] } },
    { "id": "min6", "ruleId": "min_words", "params": { "n": 6 } },
    { "id": "question", "ruleId": "ends_with", "params": { "mark": "?" } },
    { "id": "colors", "ruleId": "has_word", "params": { "words": ["red", "blue", "green", "yellow", "black", "white"] } },
    { "id": "no_e", "ruleId": "no_letter", "params": { "letter": "e" } },
    { "id": "long7", "ruleId": "long_word", "params": { "n": 7 } },
    { "id": "short4", "ruleId": "short_words", "params": { "n": 4 } },
    { "id": "start_t", "ruleId": "starts_with", "params": { "letter": "t" } }
  ],
  "rulePhrases": {
    "min_words": { "en": "Use {n} or more words.", "ja": "{n}語以上で書く" },
    "max_words": { "en": "Use {n} words or fewer.", "ja": "{n}語以下で書く" },
    "has_word": { "en": "Use at least one of these words: {words}.", "ja": "次の語のどれかを使う: {words}" },
    "no_word": { "en": "Do not use these words: {words}.", "ja": "次の語を使わない: {words}" },
    "has_letter": { "en": "Use the letter {letter}.", "ja": "{letter}の文字を使う" },
    "no_letter": { "en": "Do not use the letter {letter}.", "ja": "{letter}の文字を使わない" },
    "ends_with": { "en": "End the sentence with {mark}", "ja": "文の最後を{mark}にする" },
    "long_word": { "en": "Use a word with {n} or more letters.", "ja": "{n}文字以上の語を使う" },
    "short_words": { "en": "Every word has {n} letters or fewer.", "ja": "どの語も{n}文字以下にする" },
    "starts_with": { "en": "The first word starts with {letter}.", "ja": "最初の語を{letter}で始める" }
  }
}
```

1ファイルが1パックであり、ロビーで選ぶ単位はパックである（収録6本と同じ形）。

`rulePhrases` は規則IDごとの言い回しであり、`{n}` `{words}` `{letter}` `{mark}` を `start` でパラメータに置き換える。
`{words}` は `words` をカンマと空白で連結して置き換える。
`words` は表示する綴りのまま持ち、照合では小文字へ揃える。`I` を `i` と書かせないのはこのためである。

候補ごとに文を書かせず、規則IDごとの言い回しにするのは、同じ規則IDの候補の文を揃えるためである。
候補ごとに書くと、`min_words` の候補どうしで言い回しが違い、文の違いを規則の違いと読む卓が出る。

候補の母集団を規則IDごとに偏らせない。
同じ規則IDの候補が並ぶと（例: `min_words` の5と6）、成否が分かれる英文が限られ、見分けるための英文が語数の調整だけになる。
母集団の全組を検証7が見るため、極端に近い組は落ちる。

### 検証用の文例集

`content/secretrule/corpus/sentences.json` に、検証用の英文を60件以上置く。
パックではないため、`content/secretrule/` の直下に置かない。
パックの読み込み（インデックスの生成、`validate:content`、フォントサブセットの生成）は直下の `*.json` だけを読むためである。

`validate:content` はパックを1ファイルずつ検証関数へ渡すため、文例集はその引数に入らない。
`server/games/secretrule/` の検証関数が文例集を直接importする（パックのインデックスが `content/` のJSONを相対パスでimportするのと同じ形）。
文例集の検証（検証8）は、パックを検証するたびに同じ結果を繰り返し出す。

```json
{
  "sentences": [
    "I like cats.",
    "Do you have a red umbrella?",
    "My brother went to the station yesterday."
  ]
}
```

文例集は、卓が実際に書きそうな英文の代わりとして使う。
3語の短い文から15語前後の文まで、平叙文、疑問文、感嘆文を混ぜる。
構成の目安は人手のレビューで確かめる（「機械で検査しないもの」）。

## 検証項目

`pnpm validate:content` で検査する。

| # | 内容 |
| --- | --- |
| 1 | スキーマ。必須欄の欠落と型違いを落とす。定義に無い欄があれば落とす。ルート直下に限らず、`keyExpressions[]`・`starters[]`・`candidates[]`・`rulePhrases` の各規則の中も見る |
| 2 | `id` が `[a-z0-9_]` の1〜16文字。候補の `id` がパック内で一意 |
| 3 | 候補が8件以上 |
| 4 | 候補の `ruleId` がコードに定義されており、`params` が規則IDごとの範囲（「判定関数」の表）に収まる。`words` と `letter` は英字だけからなる |
| 5 | `rulePhrases` が、候補で使うすべての規則IDの言い回しを持ち、未知の規則IDを持たない。各言い回しが、その規則IDのパラメータの穴をちょうど1回ずつ含み、他の穴を含まない |
| 6 | 文例集の中で、各候補を満たす文の割合が15%以上70%以下 |
| 7 | 候補の全組について、文例集の中で成否が分かれる文が3件以上 |
| 8 | 文例集の各文が `submit` の条件（3語以上、140文字以内）を満たし、正規化後に重複しない。文例集が60件以上 |
| 9 | `keyExpressions` が3件以上、`starters` が3件以上 |
| 10 | `starters` の各文が空欄（`...`）を1箇所以上含む |
| 11 | すべての `ja` が空でない |

検証6は、規則が易しすぎる場合と難しすぎる場合を落とす。
卓が書きそうな英文の大半が通る規則（例: 語数が3以上）は、何を書いても通るため推理にならない。
ほとんど通らない規則は、`proving` で全員が通る見込みが立たない。

検証7が、候補どうしを英文で見分けられることを保証する（「候補の抽選」）。
3件以上とするのは、成否が分かれる英文が1件しかない組は、卓がその1件に近い英文を偶然書かない限り見分けられないためである。

検証6と検証7の閾値は**未検証**の仮置きである。

検証10を置くのは、`starters` をそのまま書き写した提出を作らせないためである（[11](./11_WHOWROTETHISゲームモジュール.md) の検証10と同じ理由）。
全員が同じ書き出しの完成文を出すと `duplicate` で2人目以降が拒否され、書き出しの例が例として働かない。

検証11を置くのは、`ja` がフォントサブセットの入力になるためである（[07](./07_リポジトリとツールチェーン.md)）。

### 機械で検査しないもの

* 言い回しの英文と日本語が、判定関数の条件と同じ意味を述べているか
* `has_word` の語の一覧が、卓にとって「この種類の語」とまとまって読めるか（色の語、曜日の語など）
* 文例集の構成（文の長さ、平叙文と疑問文と感嘆文の割合）が、卓が実際に書く英文に近いか
* `starters` の枠と `keyExpressions` の英文が自然か
* `keyExpressions` に、成否の報告、仮説の提案、試し書きの依頼の型が揃っているか

いずれも人手のレビューで見る。
記録は `docs/お題レビュー/` に置く（収録6本と同じ形）。

1件目の項目は判定の公平さに直結する。
言い回しと判定関数がずれると、規則を正しく読んだ卓が誤答する。
言い回しを規則IDごとに持たせて文の数を絞ったのは、この確認の対象を減らすためでもある。

## 判定の規則

英文の成否は、正規化後のテキストに判定関数を適用した結果だけで決まる。
英文の意味、文法の正誤、提出の速さは判定に影響しない。

回答の正誤は、全員が揃えた候補のidと `ruleCandidateId` の一致だけで決まる。

アプリは英語を解釈しない（不変条件1、[ADR-0001](../adr/0001-ランタイムAI不使用.md)）。
判定関数が見るのは語数、英字の連続、文字、末尾の記号であり、いずれも文字列の処理である。

確定した成否は `entries` に保存し、後から再計算しない。
コードやコンテンツを差し替えても、進行中のゲームの記録が動かないようにする。

## 未解決の論点

| 論点 | 内容 |
| --- | --- |
| 人数による有利不利 | 1ラウンドで得られる成否の数が人数に比例する。`sentencesUsed` で数えても向きが逆になるだけで、偏りは残る（「結果」） |
| 2人卓で見分け切れるか | 2人の卓は4ラウンドで8件の英文しか試せない。候補6件を見分け切れる割合は未検証である |
| 推理の主導の偏り | 上級者が試す英文を指示し、他の人が書き写すだけになる卓がありうる（「レベル差の吸収」） |
| 発話量 | `writing` は無言のテキスト入力である。`checking` の相談で補う設計だが、発話量が収録6本と比べてどうかは未測定である |
| 閾値 | 検証6・7の閾値、ランクの閾値、`MAX_ROUNDS`、`checking` の締切はすべて仮置きである |
| 所要時間 | 最長の進行では約17分になり、受入条件の15分を超える。調整の順は「所要時間の見積り」に書いた |
| 照合語の定義の分かりにくさ | `I'm` が `i` と `m` に分かれる定義が卓に伝わるかは未確認である。伝わらない場合は `no_word` から `I` を外すか、`briefing` の例を増やす |
| 同じ規則の再登場 | `nextGame` で `gameSecret` は破棄されるため、同じ部屋で続けて遊ぶと同じ規則を引きうる。母集団から6件を抽選して確率を下げるだけに留める（[11](./11_WHOWROTETHISゲームモジュール.md) の同じ論点と合わせて判断する） |
| 偶然の一致 | 全員の選択が揃った瞬間に判定するため、相談の途中で選択が一時的に揃うと、その時点で回答が確定する。選ぶ操作を読む操作と分けたが、起きる頻度は未検証である |
| 提出内容の適切さ | 自由英文であり、場を壊す内容を機械で弾かない。同室プレイのため運用に委ねる（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断） |

## 原案からの変更

[ルール案](../収録候補ゲームのルール案.md) の案5から変えた点と、その理由を挙げる。

| 変更 | 理由 |
| --- | --- |
| 対戦型を協力型にした | 対戦型では提出と成否が全員に公開されるため、気づいたことを口に出すと他人が得をし、黙って推理するのが最適になる。2人の卓では1対1の対戦になり、レベル差がそのまま勝敗に出る（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md)） |
| 対応人数を2〜6人にした | 判定がサーバの照合と全員の一致だけで決まり、人数で成立しなくなる仕組みがない |
| 通った英文1件ごとの加点を外した | 通った英文の語を1つ替えて出し直すのが最適になり、推理が消える |
| 回答を、最後の選択から全員の一致による随時の回答にした | 回答の時期を卓が選べる方が、英文を何件使ったかをランクに反映できる。全員の一致は2〜3人でも決着する |
| 候補を最初から公開した | 自由記述の回答は機械で照合できない。候補が見えていれば、どの候補を見分ける英文を書くかという狙いが生まれる（[ADR-0030](../adr/0030-SECRETRULEの規則は表層の判定関数に限り候補を公開する.md)） |
| 「過去形を使う」を規則から外した | 語彙リストでは過去形を網羅できず、規則の説明と判定がずれる。説明と判定が一致する表層の条件に限った（[ADR-0030](../adr/0030-SECRETRULEの規則は表層の判定関数に限り候補を公開する.md)） |
| 正解の後に `proving` を置いた | 推理の段階の英文は候補を見分けるための試し書きであり、規則を満たすために書く工程がない |
| 1ゲームを最大4ラウンドにした | 原案の5ラウンドでは、最長の進行が約20分になる |
| 同じ英文の再提出を拒否した | 同じ英文の成否は変わらず、`proving` では書き写しで通過数を稼げる |

## テスト観点

`GameModule` は純粋関数のため、Durable Objectなしで全項目をテストする。

* 決定性: 同じ `seed` と同じ参加者から、同じ候補6件と同じ秘密の規則が得られること
* 抽選: 多数の `seed` で、秘密の規則が候補6件のどの位置にも現れること
* 判定関数: 規則IDごとに、満たす文と満たさない文の境界（`n` の前後、大文字と小文字、末尾の記号の有無、`I'm` の分解）を確かめること
* 判定関数: 判定がテキストだけで決まり、提出者や時刻に依存しないこと
* 秘密の非混入: `briefing` から最終ラウンドの `checking` までの公開状態に、秘密の規則（`ruleCandidateId` とその規則ID・パラメータ）が現れないこと。誤答の後も確かめる
* 秘密の非混入: `writing` 中と `proving` 中の公開状態に提出テキストが現れないこと
* 秘密の非混入: `listContents()` の戻り値に候補が含まれないこと
* 秘密の配布: `start` で秘密を送らず、`writing` と `proving` へ入るたびに全員へ送り直し、前のラウンドの `submission` が残らないこと
* `submit`: 3語未満が `too_short`、140文字超が `too_long`、文字列でない値が `invalid_submission` で拒否されること
* `submit`: 過去のラウンドの英文と、大文字と小文字だけが違う英文が `duplicate` で拒否されること
* `submit`: 同じラウンドで他人と同じ英文が `duplicate` で拒否され、本人の前の提出と同じ英文は上書きとして受理されること
* `submit`: 受理のたびに本人へ `submission` を含む秘密が返り、他のプレイヤーの秘密が書き換わらないこと
* `submit`: 接続中の全員が提出した時点で、`writing` なら `checking` へ、`proving` なら `debrief` へ進むこと
* 成否: `checking` へ入るときに、全提出の成否が `entries` に入り、`currentSubmissions` が空になること
* `select`: `roundIndex` 不一致が `stale_round`、候補に無いidと誤答済みの候補が `invalid_candidate` で拒否されること
* `select`: `null` で選択が取り消されること
* `select`: 接続中の全員が同じ候補を選んだ時点で判定され、切断中の人を待たないこと
* `select`: 正解で `solvedCandidateId` が入り、`proving` へ進み、全員へ `proving` の秘密が送られること
* `select`: 誤答で `answers` に1行増え、`selections` が空になり、ステージが変わらず、`deadlineSeconds` を返さないこと
* `select`: 誤答の後の同じラウンドの選択が `already_answered` で拒否され、次のラウンドでは受理されること
* `ready`: `checking` で全員が揃うと次のラウンドの `writing` へ、最終ラウンドなら `unsolved` の結果で `debrief` へ進むこと
* 締切: `writing` の締切で提出0件でも `checking` へ進み、ラウンドとして数えられること
* 締切: 最終ラウンドの `checking` の締切で `unsolved` の結果が返ること
* 締切: `proving` の締切で、未提出者を通過していない人として数えること
* 結果: 表の条件どおりにランクが決まること（各ランクの境界の前後で確かめる）
* 結果: `sentencesUsed` が正解の確定までの `writing` の提出数と一致すること
* 結果: 正解しなかった卓にも秘密の規則が開示されること
* 作り直し: 遷移が返した秘密を `playerId` ごとに上書きで溜めた値と `rebuildSecret` の戻り値が、各遷移の直後に全員について一致すること。提出の上書き、締切での進行、誤答、正解、`proving` の締切、正解なしでの終局を通し、2人と6人で確かめる
* 作り直し: `briefing` で `undefined` を返し、`gameSecret` が無いときと参加者でないときに例外を投げること
* 検証: 検証1〜11がそれぞれ違反を落とすこと。検証7は、成否が分かれる文が2件しかない組で落ちること
* 検証: 収録するパックで、母集団のすべての候補について検証6の割合と、全組について検証7の件数を出力できること（閾値の見直しに使う）
* ペイロード: 140文字の `submit` のペイロードが `ACTION_MAX_CHARS`（512）未満であること
* 設定: 記述子の `min` / `max` と `validateSettings` の受理範囲が一致すること
* 人数: 2人と6人で開始から `debrief` まで進むこと（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md) の「テストと動作確認」）
