# 基本設計: SECRET RULE ENGLISHゲームモジュール

## 結論

SECRET RULE ENGLISHは6ステージ（`briefing` / `writing` / `choosing` / `checking` / `proving` / `debrief`）を持つ2〜6人用の協力型ゲームモジュールであり、`GameModule` インターフェースの実装として完結する。

画面には規則の候補が6件出ており、そのうち1件だけが秘密の正解である。
毎ラウンド、全員が英文の下書きを1つ書き、卓が相談して2件を選んで判定にかける。
判定の成否は、その英文を書いた本人の画面にだけ出る。

本人が成否を英語で報告し、卓は報告を突き合わせて規則を推理する。

回答は、ラウンドの終わりに、候補を選んだ人の選択が1つに揃っていれば確定する。
正解したら、最後に全員が「正解の規則を満たし、指定した別の候補は満たさない英文」を1つずつ書く（`proving`）。

勝敗はチーム単位とし、正解の有無、誤答の数、正解したラウンド、`proving` の通過数からランクを決める。
個人の得点は持たない。

規則は英文の表層を調べる判定関数に限り、規則の意味はコードに置く（[ADR-0030](../adr/0030-SECRETRULEの規則は表層の判定関数に限り候補を公開する.md)）。
協力型にすること、成否を本人にだけ配ること、1ラウンドに判定する英文を最大2件に絞ることは [ADR-0031](../adr/0031-SECRETRULEは協力型にし成否を書いた本人にだけ配る.md) で決めた。
アプリが調べるのは語数、語と英字の有無、末尾の記号、語の長さ、最初の語の頭文字であり、英語の意味を解釈しない（不変条件1）。

gameIdは `secretrule` とする。
表示名の `ENGLISH` を落として短縮する。[10](./10_ENGLISHRANKINGゲームモジュール.md) の `ranking` と同じく、短縮した名前で足りる。

共通コアへの追加要求はない。
提出は自由英文であり、`action` ペイロードの長さ上限（[ADR-0023](../adr/0023-actionペイロードに長さ上限を課す.md)）の経路に載る。
全員同時の提出と収集、秘密情報の全量の送り直しという既存の形で足りる。

ルールの原案は [収録候補ゲームのルール案.md](../収録候補ゲームのルール案.md) の案5であり、実装順と受入条件は [実装計画/ゲーム構想20案の収録計画.md](../実装計画/ゲーム構想20案の収録計画.md) を正とする。
本文書は、そこで未定のまま残した点を決め、ルールの正本となる。
原案は対戦型であり、協力型へ変えた。原案から変更した点は末尾の「原案からの変更」に列挙する。

共通コアとの境界は [05](./05_ゲームモジュール.md)、メッセージの意味は [03](./03_プロトコル.md) を正とする。

## ステージ

| stage | 締切 | 遷移条件 |
| --- | --- | --- |
| `briefing` | 90秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `writing` | `writingSeconds`（既定60秒） | 接続中の全員が `submit` を送る、または締切到達 |
| `choosing` | 45秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `checking` | 120秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `proving` | `writingSeconds` | 接続中の全員が `submit` を送る、または締切到達 |
| `debrief` | なし | 遷移しない（`lifecycle: finished`） |

`writing`、`choosing`、`checking` を1ラウンドとし、最大 `MAX_ROUNDS`（4）ラウンド回す。
`checking` を終えるときに回答を判定し、正解なら `proving` へ進む。
正解しないまま最終ラウンドの `checking` が終わると、`proving` を経ずに `debrief` へ進む。

判定にかけられる下書き（「選べる下書き」）が2件以下のラウンドでは、`choosing` を飛ばして `writing` から `checking` へ進む。
2人の卓は毎ラウンドこれに当たり、2人の下書きがそのまま判定にかかる。

`briefing` の締切を90秒とするのは、候補6件と、語の数え方の例を読む時間を取るためである。
候補は `briefing` から公開状態に載せる。

`checking` は成否の報告と相談と回答の準備を兼ねる。
成否は書いた本人にしか見えないため、報告を聞いて仮説を英語で言い合う時間がこのゲームの発話の中心になる。

`choosing` と `checking` では Wake Lock を取得する。
下書きの並びや報告を聞きながら話す時間が長く、画面に触らない時間が続く。

## 規則

### 正規化

提出は、判定と保存の前に次の順で正規化する。

1. Unicode正規化（NFKC）をかける。全角の英数字と記号（`？` `！` `Ａ` `１`）が半角になり、`…` が `...` になる
2. 曲がった引用符（`‘` `’` `“` `”`）を直線の引用符（`'` `"`）へ置き換える
3. 空白文字（改行、タブ、全角空白を含む）の連続を半角空白1つへ畳み、前後の空白を落とす

[11](./11_WHOWROTETHISゲームモジュール.md) の正規化は手順3だけであり、本ゲームは手順1と2を足す。
スマホの日本語入力では、全角の `？` や、自動で曲がる `’` が混じりやすい。
足さないと、`Do you like cats？` が「`?` で終える」規則を満たさない。規則を正しく読んで書いた英文が不通過になる。

保存する提出、本人へ返す提出、判定にかける提出は、すべて正規化後の文字列とする。
`MAX_CHARS` も正規化後の文字数で数える。

### 語の数え方

判定関数は次の4つの量を使う。

* **語数**: 正規化後のテキストを半角空白で区切った要素のうち、英字か数字を1つ以上含む要素の数。`Do you like cats ?` は4語、`Hi ! !` は1語になる
* **照合語**: 英字の連続を取り出し、小文字にしたもの。英字に挟まれたアポストロフィとハイフンは語の内側として扱う。`I'm` は `i'm` の1語、`well-known` は `well-known` の1語、`3 cats.` は `cats` の1語になる
* **語の文字数**: 照合語に含まれる英字の数。アポストロフィとハイフンは数えない。`couldn't` は7文字、`well-known` は9文字になる
* **最初の語**: 正規化後のテキストを半角空白で区切った最初の要素。数字で始まる要素も最初の語になる

語数から記号だけの要素を除くのは、`?` の前に空白を入れる書き方で語数が1つ増え、「6語以上」を読んだ卓の数え方とずれるためである。
照合語でアポストロフィとハイフンを語の内側に置くのは、`couldn't` を `couldn` と `t` に分けると、卓が「7文字の語」と読む語が6文字の語として判定されるためである。

`I'm` は `I` という照合語を含まない。
「`I` を使わない」規則を読んだ卓が `I'm` をどう扱うかは迷いうるため、`briefing` の例で示す（「画面」）。

### 判定関数

規則の意味はコードに置き、規則IDとパラメータで参照する。
コンテンツは候補ごとに規則IDとパラメータを選び、規則IDごとの言い回しを書く（[ADR-0030](../adr/0030-SECRETRULEの規則は表層の判定関数に限り候補を公開する.md)）。

| 規則ID | パラメータ | 満たす条件 |
| --- | --- | --- |
| `min_words` | `n`（5〜8） | 語数が `n` 以上 |
| `max_words` | `n`（4〜6） | 語数が `n` 以下 |
| `has_word` | `words`（1〜10語） | `words` のどれかと一致する照合語を含む |
| `no_word` | `words`（1〜3語） | `words` のどれとも一致する照合語を含まない |
| `has_letter` | `letter`（a〜z） | 正規化後のテキストがその英字を含む（大文字と小文字を区別しない） |
| `no_letter` | `letter`（a〜z） | 正規化後のテキストがその英字を含まない（同上） |
| `ends_with` | `mark`（`?` / `!`） | 末尾の閉じ引用符と閉じ括弧（`"` `'` `)` `]`）を除いた最後の文字がその記号 |
| `long_word` | `n`（7〜9） | 文字数が `n` 以上の照合語を含む |
| `short_words` | `n`（4〜6） | すべての照合語の文字数が `n` 以下。照合語が無い文は満たす |
| `starts_with` | `letter`（a〜z） | 最初の語から先頭の開き引用符と開き括弧（`"` `'` `(` `[`）を除いた最初の文字がその英字（大文字と小文字を区別しない） |

パラメータの範囲は、自然な英文で満たす割合が極端にならない値に絞った。
判定のレビューで、自作の英文62件に対する通過率を測った結果による（`min_words` の8以上、`max_words` の7、`long_word` の10は、通過率が2%以下か98%に達した）。
範囲内でも通過率が偏る値（`has_letter` の `e` など）は、検証6で落ちる。

`max_words` の下限を4に置くのは、提出の最低語数（`MIN_WORDS`、3語）より大きくするためである。
`n` が3なら、満たす英文はちょうど3語に限られ、規則が実質「3語で書く」になる。

`ends_with` で末尾の閉じ引用符と閉じ括弧を除くのは、`(Do you like cats?)` や `He said "Really?"` を卓は疑問符で終わる文と読むためである。
`starts_with` で先頭の開き引用符と開き括弧を除くのも同じ理由による。`(Do you like cats?)` は `d` で始まる文として判定する。

`starts_with` を照合語ではなく最初の語で見るのは、`123 is my number.` の最初の語を卓は `123` と読むためである。
照合語で見ると `is` が最初になり、`i` で始まる文として判定される。

`has_word` と `no_word` の `words` は語形変化を含まない。
`cat` を指定した規則は `cats` を満たさない。

候補の英文に語の一覧をそのまま出すため、卓は一覧にある綴りだけが対象だと読める。
語形変化を自動で扱わないのは、活用の解析が英語の理解に当たるためである（不変条件1）。

### 置き場所

判定関数（規則の評価）は `server/games/secretrule/` に置き、`validate:content` もこれを使う。
正規化、語数の計数、`MIN_WORDS`、`MAX_CHARS`、規則IDとパラメータの型は `shared/games/secretrule/` に置く。
クライアントの入力欄が、送信前に語数と文字数を確かめるためである（[11](./11_WHOWROTETHISゲームモジュール.md) の `shared/games/whowrotethis` と同じ分け方）。

照合語の分解と判定関数はクライアントに置かない。
公式のクライアントは、英文に対する候補の成否を計算しない（「候補を自動で消さない」）。

### 候補の抽選

パックは候補を8件以上持つ（以下、候補の母集団と呼ぶ）。
`start` で母集団から6件（`CANDIDATE_COUNT`）を `seed` で抽選し、その6件から秘密の規則を1件抽選する。
続けて、秘密の規則以外の5件から、`proving` で満たしてはならない候補（以下、避ける候補）を1件抽選する。

母集団の全候補の順序対 (X, Y) について、「Xを満たしYを満たさない文」が検証用の文例集の5%以上あることを `validate:content` で保証する（検証7）。
このため、抽選した6件のどの組も英文の書き方しだいで見分けられ、避ける候補をどれに決めても `proving` の条件を満たす英文が存在する。

順序対で見るのは、一方が他方を含む組を母集団から落とすためである。
`min_words` の5と6では、6を満たして5を満たさない文が存在しない。
この組が候補に並ぶと、見分けるための英文が語数の調整だけになり、`proving` の避ける候補にもできない。

母集団から毎回6件を抽選するのは、同じ卓で同じパックを続けて遊んでも、候補の並びと正解が変わるようにするためである。
母集団8件なら、候補の組は28通り、正解を含めて168通りになる。

### 候補を自動で消さない

公式のクライアントは、英文に対して各候補の成否を計算して見せない。
計算すれば、矛盾する候補を画面が自動で消せる。
しかし、どの候補が残るかを報告から考える工程がこのゲームの推理であり、それを画面が代わると相談する理由が消える。

改造したクライアントは、判定にかけた英文と候補から同じ計算ができる。
ただし秘密の規則の成否は書いた本人にしか届かないため、改造しても他人の成否は分からない。
協力型であり、得をするのはその卓だけであるため、これ以上は防がない。

## 進行の要点

### 成否は書いた本人にだけ配る

判定にかけた英文そのものは全員に公開し、成否は書いた本人の秘密情報にだけ入れる（[ADR-0031](../adr/0031-SECRETRULEは協力型にし成否を書いた本人にだけ配る.md)）。
画面を他人に見せない約束のもとでは、全員の成否を知るには本人の報告（`Mine passed.`）を聞くしかない。
約束は `briefing` で示し、守られているかは機械で検出せず場に委ねる（[13](./13_ESCAPECALLゲームモジュール.md) の「自分の画面を見せない約束」と同じ扱い）。

全員の画面に成否を出すと、各自が黙って推理し、同じ候補を押すだけで完走できる。
レビューで、この形では英語を一言も話さずに正解まで進めることを確かめた。
成否を本人に限ると、報告と聞き返しが推理の前提になる。

英文を公開するのは、報告を聞いた側が、どの英文がなぜ通ったかを画面で読み比べるためである。
英文まで伏せると、推理の材料を耳だけで保持することになり、レベル1〜2の負担が大きい。

本人が誤って報告しても、アプリは訂正しない。
協力型であり、偽りの報告で得をする人がいない。

成否は `debrief` で全員に開示する。

### 1ラウンドに判定する英文は2件

`checking` で判定にかける英文は、人数によらず最大2件（`TESTS_PER_ROUND`）とする。
全員が下書きを書き、`choosing` で卓がどの2件を判定にかけるかを決める。

人数分を判定にかけると、6人の卓は1ラウンドで6件の成否を得る。
レビューのシミュレーション（自作の英文60件を使用）では、狙って書いた英文3件でサンプルの候補8件をすべて見分けられた。
6人の卓は1ラウンド目で正解が決まりうり、推理の工程が残らない。

最大2件に絞ると、人数による情報量の差が消え、どの2件を試すかを決める相談が発話になる。

### 判定にかける2件の決め方

`choosing` では、全員の下書きを作者つきで公開する。
各自は判定にかけたい下書きに印を付ける（`mark`、1人2件まで、自分の下書きにも付けられる）。
印は全員に公開する。

接続中の全員が `ready` を送るか締切に達したら、印の多い順に2件を選ぶ。
印の数が同じ下書きは、当番順で先の人の下書きを選ぶ。

当番順は、`start` で `seed` から決めた参加者の並び（`turnOrder`）を、`roundIndex` × 2 人ぶん左へ回転したものとする。
印が1つも無いときも当番順で選ぶ。

印の集計は勝敗を決める投票ではない。
同数でも当番順で必ず決まるため、2〜3人の卓で票が割れて決まらない問題（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md)）は起きない。

当番順を同数の決着に使うのは、相談がまとまらない卓でも、判定にかかる下書きの作者が特定の人に偏らないようにするためである。
2人ずつ回転するため、4人以上の卓では、隣り合うラウンドで当番順の先頭2人が重ならない。

選べる下書きは、`choosing` へ入る時点で作者が接続している下書きに限る。
作者が切断していると、成否がその人の画面にしか届かず、卓が報告を受けられない。

`checking` へ進む時点で作者が切断していた場合も、その下書きは選ばない。
除いた結果、判定にかけられる下書きが2件未満になったら、残った件数だけ判定する（0件もありうる）。

### 回答はラウンドの終わりに判定する

`checking` の間、各自が候補を1つ選べる（`select`）。
選択は全員に公開し、変更と取り消しができる。

`checking` を終えるとき（接続中の全員の `ready` か締切到達）に、次の規則で回答を判定する。

* `checking` の終わりの時点で接続している人のうち、候補を選んだ人が1人以上いて、選んだ全員が同じ候補を選んでいれば、その候補を回答とする
* 選んだ人がいない、または選択が割れていれば、回答しない

選んでいない人は棄権として扱う。
切断している人の選択は数えない。切断した人は選択を直せず、残った選択が割れたまま回答できなくなるためである。
接続したまま操作しない1人がいても、回答が止まらない。

揃った瞬間に確定させない。
相談の途中で選択が一時的に揃った時点で、回答が確定してしまうためである。
`ready` は「この選択でラウンドを終える」操作であり、全員の `ready` が卓の合意の確認になる。

誰かの選択が変わったら、全員の `ready` を解除する。先に送った `ready` が、変わる前の選択への合意として残らないようにするためである。

選択が割れたまま全員が `ready` を送ると、回答しないままラウンドが終わる。
画面は `ready` の前に「選択が揃っていないので、このラウンドは回答しない」を出す。

回答は1ラウンドに最大1回になる。
候補が6件しかないため、回答を繰り返せると英文を書かずに総当たりで正解できる。

### 誤答の扱い

回答が秘密の規則と違えば誤答とする。
誤答の候補を公開状態の `answers` に記録し、以後は選べなくする。
最終ラウンドでなければ次のラウンドの `writing` へ、最終ラウンドなら `debrief` へ進む。

誤答に時間の罰則は置かない（[13](./13_ESCAPECALLゲームモジュール.md) の「誤答に時間の罰則を置かない」と同じ理由）。
ラウンド数の上限がそのまま回答の上限になる。

### 正解したら規則を使って書く

正解すると `proving` へ進む。
`proving` では秘密の規則と避ける候補を公開し、全員が「秘密の規則を満たし、避ける候補を満たさない英文」を1つずつ書く。

`proving` を置くのは、規則が分かった後に、制約の中で英文を組み立てる工程を全員に回すためである。
推理の段階の英文は、候補を見分けるための試し書きである。

避ける候補を足すのは、規則が分かれば自明に満たせる候補が多いためである。
レビューでは、サンプルの8件のうち6件が、`?` を付ける、`The` で始めるといった書き足しで満たせた。
2つの条件を同時に満たす英文は、組み立てを考えないと書けない。

避ける候補は全員に共通とする。
人ごとに変えると、同じ条件で書いた英文を見比べられなくなる。

`proving` の提出は通過の有無を数えるだけとし、通らない英文も受理する。
受理しないと、通るまで書き直す総当たりになる。
成否は `debrief` まで伏せる。

### 重複する英文を拒否する

正規化後の英文から比較キーを作り、キーが一致する英文を `duplicate` で拒否する。
比較キーは、照合語と数字の連続を出現順に並べた列と、`ends_with` と同じ取り方の末尾の記号の組とする。

比較の対象は、判定にかけた過去の英文と、現在のステージの他人の提出である。
判定にかからなかった下書きは比較の対象にしない。次のラウンドで同じ下書きを出し直すことは、もう一度提案する正当な操作である。

句点の有無や大文字と小文字の違いだけの英文を同じとみなすのは、成否が同じであり、出し直しても情報が増えないためである。
`proving` では、他人の英文の書き写しで通過数を稼ぐ経路を塞ぐ。

1語だけ替えた英文は拒否しない。
1語の差で成否が変わるかを確かめるのは、正当な推理の手順である。

## 公開状態（gameState）

```typescript
interface SecretRulePublic {
  packId: string;
  candidates: CandidatePublic[];      // 6件。startで抽選した順
  roundIndex: number;                 // 0始まり。proving と debrief では最後のラウンドのまま
  maxRounds: number;                  // 4
  readyPlayerIds: string[];           // briefing / choosing / checking の収集状況
  submittedPlayerIds: string[];       // writing / proving の収集状況。テキストは載せない
  drafts: Draft[];                    // choosing / checking で、現ラウンドの選べる下書き
  marks: Mark[];                      // choosing の印
  entries: TestedEntry[];             // 判定にかけた英文。全ラウンド分。成否は載せない
  selections: Selection[];            // checking の選択
  answers: AnswerRecord[];            // 回答の履歴
  solvedCandidateId: string | null;   // 正解の候補。正解するまで null
  avoidCandidateId: string | null;    // 避ける候補。proving に入るまで null
  keyExpressions: KeyExpression[];    // 報告と相談に使う言い回し
  starters: Starter[];                // 英文の書き出しの例
  writingSeconds: number;
}

interface CandidatePublic {
  id: string;
  textEn: string;                     // 言い回しのパラメータを置き換えた後の文
  textJa: string;
}

interface Draft {
  playerId: string;
  text: string;
}

interface Mark {
  playerId: string;
  draftPlayerIds: string[];           // 0〜2件
}

interface TestedEntry {
  roundIndex: number;
  playerId: string;
  text: string;
}

interface Selection {
  playerId: string;
  candidateId: string;
}

interface AnswerRecord {
  roundIndex: number;
  candidateId: string;
  correct: boolean;
}
```

秘密の規則と、判定にかけた英文の成否は公開状態に置かない。
`state` は全員へブロードキャストされるため、ここに置いた値は全員の端末に届く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。
秘密の規則は、正解した後に `solvedCandidateId` で公開する。

`writing` 中と `proving` 中は提出テキストを公開状態に置かない。
公開してよいのは提出済みの人のidだけである。

下書きは `choosing` へ入るときに `drafts` へ移す。下書きを見てから書き直す経路を作らないためである。
`choosing` を飛ばした回は、判定にかけた下書きを `drafts` に入れる。

`proving` の提出は公開状態に置かず、結果にだけ載せる。
`proving` の後は `debrief` しかなく、公開状態で見せる場面がない。

避ける候補は `proving` へ入るまで公開しない。
先に分かると、避ける候補が秘密の規則でないことが分かり、推理の材料になる。

候補の母集団のうち抽選に漏れた候補は公開状態に置かない。
漏れた候補は推理の材料にならず、画面の候補一覧と区別がつきにくくなる。

`entries` は最大で4ラウンド × 2件の8件、`drafts` は最大6件であり、1件140文字以内のため、公開状態は数KBに収まる。

`drafts`、`marks`、`selections` は次のラウンドの `writing` へ入るときに空へ戻す。

## 秘密情報（secret.payload）

```typescript
interface SecretRuleSecret {
  phase: "briefing" | "writing" | "checking" | "proving";
  roundIndex: number;
  draft?: string;          // 現在の writing / proving の自分の提出。未提出なら省略する
  results: OwnResult[];    // 判定にかかった自分の英文と成否。全ラウンド分
}

interface OwnResult {
  roundIndex: number;
  text: string;
  passed: boolean;
}
```

秘密の規則はどの参加者にも配らない。
全員が当てる側であり、規則を知る参加者はいない。

`results` は、判定にかかった自分の英文の成否である（「成否は書いた本人にだけ配る」）。
過去のラウンドの分も持たせるのは、再接続した本人が前のラウンドの成否を報告できるようにするためである。

`draft` を返すのは、再接続した本人が自分の提出を確認して書き直せるようにするためである（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断）。

### 送るときと値

秘密は次の時点で送る。
`playerSecrets` は上書きであり結合ではないため、毎回全量を組み立てる。

| 時点 | 送る相手 | 値 |
| --- | --- | --- |
| `start` | 全員 | `phase: "briefing"`、`roundIndex: 0`、`results: []` |
| `writing` へ入る | 全員 | `phase: "writing"`、現在の `roundIndex`、前のラウンドまでの `results` |
| `writing` の `submit` を受理 | 本人 | 上の値に `draft` を加えたもの |
| `checking` へ入る | 全員 | `phase: "checking"`、現在の `roundIndex`、このラウンドまでの `results` |
| `proving` へ入る | 全員 | `phase: "proving"`、現在の `roundIndex`、全ラウンドの `results` |
| `proving` の `submit` を受理 | 本人 | 上の値に `draft` を加えたもの |

`submit` で接続中の全員が揃い、同じ遷移で次のステージへ進む場合も、本人の秘密を同じ遷移に載せる。
続けて次のステージの秘密を全員に送る場合は、後者が上書きする。

`start` で初期値を送るのは、同じ部屋で続けて遊んだときに、前のゲームの秘密を画面に残さないためである。
クライアントは `state` を受けても秘密を消さない（`client/core/src/connection.ts` の `state` の処理）。
`start` で送らないと、前のゲームの `results` が `briefing` の間に残る。

`choosing` へ入るときは送らない。
下書きは公開状態の `drafts` にあり、秘密に新しく加える値がない。

### 再接続での作り直し（rebuildSecret）

`rebuildSecret` は、遷移で最後に送った秘密と同じ値を返す（[ADR-0029](../adr/0029-再接続の秘密情報はゲームモジュールが作り直す.md)）。
値は、`gameSecret` の `tested`（判定にかけた英文と成否）と `currentDrafts`、公開状態の `roundIndex` とステージから決まり、コンテンツを引かずに作り直せる。

| 状態 | 返す値 |
| --- | --- |
| `briefing` | `phase: "briefing"`、`roundIndex: 0`、`results: []` |
| `writing` / `choosing` | `phase: "writing"`、現在の `roundIndex`、`currentDrafts` の本人の提出、前のラウンドまでの `results` |
| `checking` | `phase: "checking"`、現在の `roundIndex`、このラウンドまでの `results` |
| `proving` / `debrief`（正解） | `phase: "proving"`、現在の `roundIndex`、`currentDrafts` の本人の提出、全ラウンドの `results` |
| `debrief`（正解なし） | `phase: "checking"`、最終ラウンドの `roundIndex`、全ラウンドの `results` |

`choosing` で `writing` の値を返すのは、`choosing` へ入るときに送らないためである。
`debrief`（正解なし）で `checking` の値を返すのも同じ理由による。

`gameSecret` が無い場合と、参加者でない `playerId` の場合は例外を投げる。
共通コアは例外のときに保存済みの値を送るため、誤った値を返すより安全である（[13](./13_ESCAPECALLゲームモジュール.md) と同じ扱い）。

## ゲーム秘密状態（gameSecret）

```typescript
interface SecretRuleGameSecret {
  ruleCandidateId: string;                 // 秘密の規則。startで抽選する
  avoidCandidateId: string;                // 避ける候補。startで抽選する
  rules: Record<string, RuleSpec>;         // 候補id -> 規則IDとパラメータ。抽選した6件分
  turnOrder: string[];                     // 当番順の元になる参加者の並び。startで決める
  currentDrafts: Record<string, string>;   // 現在の writing / proving の playerId -> 提出
  tested: TestedResult[];                  // 判定にかけた英文と成否。全ラウンド分
}

interface RuleSpec {
  ruleId: RuleId;
  params: RuleParams;
}

interface TestedResult {
  roundIndex: number;
  playerId: string;
  text: string;
  passed: boolean;
}
```

`rules` を持つのは、判定のたびにコンテンツを引かないためである。
デプロイでパックが差し替わっても、進行中のゲームの判定は開始時の規則のまま変わらない。

避ける候補と当番順を `start` で決めるのは、`handleAction` と `onDeadline` にシードが渡らないためである（[05](./05_ゲームモジュール.md) の呼び出し規約）。

`currentDrafts` は `writing` と `proving` へ入るときに空へ戻す。
`checking` へ入るときは消さない。`choosing` の再接続で本人の下書きを作り直すためである。
`proving` の提出は `debrief` へ入るときに結果へ写し、`currentDrafts` からは消さない。終局後の再接続で `proving` の秘密を作り直すためである。

## action の受理規則

| action | 送れる人 | ステージ | 効果 |
| --- | --- | --- | --- |
| `ready` | 全員 | `briefing` / `choosing` / `checking` | 収集に加える。接続中の全員が揃えば遷移 |
| `submit` | 全員 | `writing` / `proving` | 提出を登録する。締切まで上書きできる |
| `mark` | 全員 | `choosing` | 判定にかけたい下書きの印を置き換える |
| `select` | 全員 | `checking` | 候補を選ぶ、または選択を取り消す |

ステージ違いはすべて `invalid_stage` で拒否する。
参加者でない送信者と未知の action も、専用のコードを設けず `invalid_stage` で拒否する（[13](./13_ESCAPECALLゲームモジュール.md) と同じ）。

拒否のコードはすべてゲームモジュール側で定義し、共通コアのエラーコード表には載せない。
`invalid_stage` / `invalid_submission` / `too_short` / `too_long` / `duplicate` / `stale_round` / `invalid_mark` / `invalid_candidate` の8つを持つ。

拒否は状態を変えない。
1つの action が複数の拒否条件に当たる場合は、各表の上の行から順に判定し、最初に当たったコードを返す。

### ready

二重送信は拒否せず冪等に扱う（収録6本と同じ）。
`ready` を送った後も、`mark` と `select` は受理する。
`mark` か `select` で誰かの印か選択が変わったら、そのステージの `readyPlayerIds` を空へ戻す（「回答はラウンドの終わりに判定する」）。

### submit

payloadは `{ text: string }` とする。
受理の前に正規化する（「正規化」）。

| 条件 | code |
| --- | --- |
| `text` が文字列でない | `invalid_submission` |
| 正規化後の語数が `MIN_WORDS`（3）未満 | `too_short` |
| 正規化後の文字数が `MAX_CHARS`（140）を超える | `too_long` |
| 比較キーが、判定にかけた過去の英文か、現在のステージの他人の提出と一致する | `duplicate` |

最低語数を3語とするのは、規則の多くが語や英字の組み合わせを見るため、1〜2語では試せる組み合わせが少なすぎるためである。
[11](./11_WHOWROTETHISゲームモジュール.md) の4語より少ないのは、ここでは文体を見せる必要がなく、短い英文で1つの仮説を確かめる書き方を許すためである。

上書きを許す。
最後に受理した提出のみが有効になる。

同じステージで同じ比較キーの英文を2人が出すと、後から送った方が拒否される。
拒否の画面には「同じ英文がすでに出ています」と出し、書き換えを促す。
他人の未公開の提出が拒否の有無から推せるが、協力型であり、隠す利益がない。

接続中の全員が提出した時点で、`writing` なら `choosing`（選べる下書きが2件以下なら `checking`）へ、`proving` なら `debrief` へ進む。

### mark

payloadは `{ roundIndex: number; draftPlayerIds: string[] }` とする。
送った配列で、その人の印を置き換える。空の配列は印の取り消しである。

| 条件 | code |
| --- | --- |
| `roundIndex` が数値でない、または現在のラウンドと違う | `stale_round` |
| `draftPlayerIds` が配列でない、3件以上ある、同じidを重ねている、`drafts` に無い作者を含む | `invalid_mark` |

### select

payloadは `{ roundIndex: number; candidateId: string | null }` とする。
`null` は選択の取り消しである。

| 条件 | code |
| --- | --- |
| `roundIndex` が数値でない、または現在のラウンドと違う | `stale_round` |
| `candidateId` が文字列でも `null` でもない、候補6件に無い、誤答済みの候補 | `invalid_candidate` |

`mark` と `select` に `roundIndex` を要求するのは、前のラウンドの操作が次のラウンドの同じステージに届く経路を弾くためである。
`checking` の直後に届いた遅着は、ステージが `writing` に変わっているため `invalid_stage` で弾ける。
`roundIndex` が要るのは、通信の遅れが次のラウンドの `checking` まで続いた場合と、再接続した端末が古い画面のまま操作を送った場合である。

## ステージの終わりの処理

`ready` の収集が揃ったときと締切到達のときで、同じ処理を行う。

| ステージ | 処理 |
| --- | --- |
| `briefing` | `writing` へ進む |
| `writing` | 提出を選べる下書きに絞る。2件以下なら全件を判定にかけて `checking` へ、3件以上なら `drafts` に移して `choosing` へ進む。提出が0件でも `checking` へ進む |
| `choosing` | 「判定にかける2件の決め方」で2件を選び、判定して `checking` へ進む |
| `checking` | 「回答はラウンドの終わりに判定する」で回答を判定する。正解なら `proving` へ、そうでなければ次のラウンドの `writing` へ、最終ラウンドなら `result` を返して `debrief` へ進む |
| `proving` | 提出済みの件で通過を数え、`result` を返して `debrief` へ進む |
| `debrief` | 締切を置かない |

判定にかけた英文は、成否と一緒に `gameSecret.tested` へ、成否を除いて公開状態の `entries` へ加える。
提出が0件のラウンドも1ラウンドとして数える。全員が席を外した場合の異常系であり、通常の進行では起きない。

`writing` の締切で、未提出の人は下書きを持たない。
`proving` の締切で、未提出の人は通過していない人として数える。

## 結果（result.payload）

```typescript
interface SecretRuleResult {
  outcome: "solved" | "unsolved";
  rank: "S" | "A" | "B" | "C";
  rule: CandidatePublic;              // 秘密の規則
  avoid: CandidatePublic;             // 避ける候補
  candidates: CandidatePublic[];      // 6件
  tested: TestedResult[];             // 判定にかけた英文と成否。全ラウンド分
  answers: AnswerRecord[];
  solvedRound: number | null;         // 正解したラウンド（1始まり）。正解なしは null
  wrongCount: number;
  proofEntries: ProofEntry[];         // proving の提出と通過。正解なしなら空
  proofPassedCount: number;
  playerCount: number;                // 開始時の参加者数
}

interface ProofEntry {
  playerId: string;
  text: string;
  passed: boolean;
}
```

ランクは次の表で決める。

| ランク | 条件 |
| --- | --- |
| S | 2ラウンド目までに正解し、誤答0回、`proving` で参加者全員の英文が通過 |
| A | 正解し、誤答1回以下、`proving` で参加者の過半数の英文が通過 |
| B | 正解した（SとA以外） |
| C | 正解できなかった |

判定にかける英文が1ラウンド最大2件に絞られているため、正解したラウンドは人数によらず同じ情報量で比べられる。
2ラウンドは英文4件にあたる。

`proving` の通過は、提出しなかった参加者を通過していない人として数える。
切断した参加者がいる卓ではSを取れない。

ランクの閾値は**未検証**の仮置きである。
実プレイでSとAがほとんど出ない、または大半がSになる場合は閾値を見直す。

結果に全ラウンドの成否を載せるのは、`finished` のまま再接続した人へ共通コアが `lastResult` を再送するため、結果画面が公開状態に依存しないようにするためである（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断）。

正解しなかった卓にも `rule` を開示する。
どの英文がなぜ通ったかを振り返れないと、推理のどこで外れたかが分からない。

## レベル差の吸収

4層で吸収する。

第1層は勝敗をチーム単位にすることである。
個人の得点を持たないため、1対1のレベル差が勝敗に出ない（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md) の「1対1ではレベル差がそのまま結果に出る」への対処）。

第2層は規則を表層の条件に限ることである。
語数、語の有無、英字の有無、末尾の記号は、文法の知識によらず数えて確かめられる。
推理に要るのは英文の巧拙ではなく、報告された成否の読み比べである。

第3層は報告の言い回しと日本語の補足である。
成否の報告は `Mine passed.` / `Mine failed.` の2文で足り、`keyExpressions` に置く。

候補の `textJa` と `starters` は、レベル1〜2の画面では常に開き、レベル3〜5の画面では折りたたむ。
公開状態は全員に同じ値を配り、出し分けはクライアントが自分のレベルで行う。

第4層は最低語数を3語に抑えることである。
`I like cats.` のような3語の英文で1つの仮説を確かめられる。

推理の主導が上級者に偏る構造は弱まるが、残る。
成否は本人にしか見えないため、上級者も他人の報告を聞かないと推理できない。

一方で、どの2件を試すかの相談や回答の候補を上級者が決め、他の人が従う卓はありうる。
偏りが遊びとして問題になるかは**未検証**である。

## ロビーの記述子

ゲーム選択画面とロビーへ配る値である（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）。

| 項目 | 値 |
| --- | --- |
| `title` | `SECRET RULE ENGLISH` |
| `tagline` | 英文を書いて試し、通る英文の隠れた規則を全員で見抜く |
| `icon` | 試験管の絵文字（U+1F9EA） |
| `playerCount` | `[2, 6]` |
| `contentLabelJa` | 規則パックを選ぶ |

アイコンは収録6本のアイコンと重ならないものを選んだ。
虫眼鏡はDETECTIVESが使っている（`server/games/detectives/src/module.ts` の記述子）。

対応人数を2〜6人とする（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md)）。
判定がサーバの照合で決まり、印の集計と回答の判定はどの人数でも1つに決まる。
人数によって成立しなくなる仕組みがない。

人数で変わるのは、`choosing` で比べる下書きの数である。
2人の卓では `choosing` が無く、下書きの選択を相談する工程が無い。2人の卓で発話が足りるかは**未検証**である。

## 設定

| key | labelJa | 型 | 範囲 | 既定 |
| --- | --- | --- | --- | --- |
| `writingSeconds` | 英文を書く時間（秒） | number | 45〜120、step 15 | 60 |

既定を60秒とするのは、下書きは1つの仮説を確かめる短い英文で足り、[11](./11_WHOWROTETHISゲームモジュール.md) の90秒ほど要らないと見込むためである（未検証）。
`proving` も同じ秒数を使う。

ラウンド数（4）、`choosing` の締切（45秒）、`checking` の締切（120秒）は設定にしない。
所要時間がラウンド数と各ステージの時間の積で伸びるため、可変にすると卓が長さを予測できない（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ理由）。

`validateSettings` は範囲外と型違いを拒否する。
`settings` が無い場合と `writingSeconds` が無い場合は拒否せず、既定値を使う。
記述子の `min` / `max` と受理範囲を一致させ、その一致をテストで固定する。

`step` は入力の刻みであり、受理の条件にしない。
範囲内の整数であれば受理する（収録6本と同じ扱い）。

## start の処理順

1. `contentId` からパックを引く。`listContents` に載るidだけを受理する
2. `settings.writingSeconds` を確定する（既定60秒）
3. `seed` から乱数を作り、パックの候補を `shuffle` して先頭6件を候補に固定する
4. 候補6件から秘密の規則を1件、残る5件から避ける候補を1件抽選する
5. 参加者の並びを `shuffle` して `turnOrder` に固定する
6. 候補6件の言い回しのパラメータを置き換え、`candidates` を組み立てる
7. 全員へ `briefing` の秘密を送る
8. `stage` を `briefing`、`deadlineSeconds` を90として返す

抽選は共通コアが注入した `seed` からのみ行う。
`Math.random()` と時刻を使わない（[05](./05_ゲームモジュール.md) の呼び出し規約）。
乱数は共通コアのシード付き乱数を使う（[ADR-0020](../adr/0020-ゲーム間で重複する部品は共通コアへ置く.md)）。

候補の表示順は抽選した順とし、秘密の規則の位置に偏りを持たせない。

## カタログ（listContents）

```typescript
{ id: "basic", title: "はじめての規則" }
```

候補の母集団をカタログに載せない。
ロビーで候補が分かると、`briefing` に入る前に試す英文を用意できる。

## 画面

画面は `client/games/secretrule/` に置く。

| ステージ | 画面 |
| --- | --- |
| `briefing` | 遊び方、語の数え方の例、成否は自分にしか見えないことと画面を他人に見せない約束、候補6件、準備完了ボタン |
| `writing` | 候補6件、これまでに判定した英文、自分の成否、書き出しの例、英文の入力、提出状況、残り時間 |
| `choosing` | 全員の下書きと作者、各自の印、自分の印の操作、相談の言い回し、準備完了ボタン、残り時間 |
| `checking` | 今回判定した英文、自分の成否、これまでに判定した英文、候補6件と各自の選択、誤答済みの候補、報告と相談の言い回し、準備完了ボタン、残り時間 |
| `proving` | 正解の規則、避ける候補、英文の入力、提出状況、残り時間 |
| `debrief` | 正解の有無とランク、秘密の規則、避ける候補、全ラウンドの英文と成否、`proving` の英文と通過 |

画面の要点を挙げる。

* 自分の成否は記号と「通過」「不通過」の文字で示し、色だけに頼らない
* 他人の英文には成否を出さない。報告を聞いて自分でメモする欄も置かない。報告を聞き取る工程を画面が代わらないためである
* 候補は番号つきで並べる。番号は「Number three?」と口で指すためのものであり、規則の中身を表さない
* `checking` の候補には、その候補を選んだ人のアイコンを添える。回答はラウンドの終わりに判定されることを候補一覧の上に常に出す
* `checking` の準備完了ボタンの近くに、現在の選択で回答になるか（揃っている／割れている／誰も選んでいない）を出す
* 誤答の候補は打ち消し線で示し、選べなくする
* `writing` と `proving` の入力欄は、正規化後の語数が3語未満のとき送信させない。文字数は入力したままの文字列で数え、140文字で止める。正規化の前に止めるのは、空白の多い入力でペイロードが `ACTION_MAX_CHARS` を超える経路を作らないためである
* 最終ラウンドの各ステージには「最後のラウンド」と出す
* `debrief` の英文の一覧には、規則で通った理由を示さない。照合語の分解や語数を添えると読み比べる工程が消えるため、規則の文と英文と成否だけを並べる

`briefing` に出す語の数え方の例は次の3つとする。

* `I'm happy.` は2語。`I'm` は `I` とは別の語として扱う
* `I have 3 cats!` は4語。数字も1語に数える
* `I couldn't sleep.` の `couldn't` は7文字。記号は文字に数えない

## 所要時間の見積り

締切は上限であり、実際は `ready` と収集で先に進む。
4人、`writingSeconds` 60秒、2ラウンド目で正解する卓で見積る。

| 区間 | 見積り |
| --- | --- |
| `briefing` | 60秒（締切90） |
| `writing` | 55秒 × 2 = 110秒 |
| `choosing` | 35秒 × 2 = 70秒（締切45） |
| `checking` | 90秒 × 2 = 180秒（締切120） |
| `proving` | 60秒 |
| 結果の確認 | 60秒 |
| 1ゲーム | 約540秒（約9分） |

**実測はしていない。**

最も長くなるのは、4ラウンド目で正解し、各ステージが締切まで使う場合である。
既定値では、`briefing` 90秒、`writing` と `choosing` と `checking` が4往復で900秒、`proving` 60秒、結果の確認60秒で約1110秒（約19分）となる。
`writingSeconds` を上限の120秒にすると約1410秒（約24分）になる。

[収録計画](../実装計画/ゲーム構想20案の収録計画.md) の受入条件は2ラウンド目で正解する卓を対象としており、最長の進行は条件の対象外だが、15分を超える。

最長の進行の卓が多い場合は、`checking` の締切を90秒へ、`choosing` の締切を30秒へ詰める順で見直す。
ラウンド数を3へ減らすのは最後にする。
狙って書いた英文なら3件で見分けられるが、実際の卓は見分けるのに最適な英文を書かない見込みであり（未検証）、判定できる英文が6件まで減ると見分け切れない卓が増えるためである。

## コンテンツ形式

```json
{
  "id": "basic",
  "title": "はじめての規則",
  "keyExpressions": [
    { "en": "Mine passed.", "ja": "私のは通った" },
    { "en": "Mine failed.", "ja": "私のはだめだった" },
    { "en": "Did yours pass?", "ja": "あなたのは通った？" },
    { "en": "Let's test this one.", "ja": "これを試そう" },
    { "en": "Maybe the rule is number three.", "ja": "規則は3番かも" },
    { "en": "Number two is out.", "ja": "2番は違う" }
  ],
  "starters": [
    { "en": "My favorite food is ...", "ja": "好きな食べ物は…" },
    { "en": "Yesterday I went to ...", "ja": "昨日…へ行った" },
    { "en": "Do you like ...?", "ja": "…は好き？" }
  ],
  "candidates": [
    { "id": "no_i", "ruleId": "no_word", "params": { "words": ["I"] } },
    { "id": "min6", "ruleId": "min_words", "params": { "n": 6 } },
    { "id": "question", "ruleId": "ends_with", "params": { "mark": "?" } },
    { "id": "colors", "ruleId": "has_word", "params": { "words": ["red", "blue", "green", "yellow", "black", "white"] } },
    { "id": "no_e", "ruleId": "no_letter", "params": { "letter": "e" } },
    { "id": "long7", "ruleId": "long_word", "params": { "n": 7 } },
    { "id": "short4", "ruleId": "short_words", "params": { "n": 4 } },
    { "id": "start_t", "ruleId": "starts_with", "params": { "letter": "t" } }
  ],
  "rulePhrases": {
    "min_words": { "en": "Use {n} or more words.", "ja": "{n}語以上で書く" },
    "max_words": { "en": "Use {n} words or fewer.", "ja": "{n}語以下で書く" },
    "has_word": { "en": "Use at least one of these words: {words}.", "ja": "次の語のどれかを使う: {words}" },
    "no_word": { "en": "Do not use these words: {words}.", "ja": "次の語を使わない: {words}" },
    "has_letter": { "en": "Use the letter {letter}.", "ja": "{letter}の文字を使う" },
    "no_letter": { "en": "Do not use the letter {letter}.", "ja": "{letter}の文字を使わない" },
    "ends_with": { "en": "End the sentence with {mark}", "ja": "文の最後を{mark}にする" },
    "long_word": { "en": "Use a word with {n} or more letters.", "ja": "{n}文字以上の語を使う" },
    "short_words": { "en": "Every word has {n} letters or fewer.", "ja": "どの語も{n}文字以下にする" },
    "starts_with": { "en": "The first word starts with {letter}.", "ja": "最初の語を{letter}で始める" }
  }
}
```

上の候補8件は形式の例であり、検証6と検証7を満たすかは文例集を作った段階で確かめる。
レビューでは、自作の英文62件に対して `colors` の通過率が約10%、`no_i` が約74%となり、検証6の範囲を外れた。

1ファイルが1パックであり、ロビーで選ぶ単位はパックである（収録6本と同じ形）。

`rulePhrases` は規則IDごとの言い回しであり、`{n}` `{words}` `{letter}` `{mark}` を `start` でパラメータに置き換える。
`{words}` は `words` をカンマと空白で連結して置き換える。
`words` は表示する綴りのまま持ち、照合では小文字へ揃える。`I` を `i` と書かせないのはこのためである。

候補ごとに文を書かせず、規則IDごとの言い回しにするのは、同じ規則IDの候補の文を揃えるためである。
候補ごとに書くと、`min_words` の候補どうしで言い回しが違い、文の違いを規則の違いと読む卓が出る。

### 検証用の文例集

`content/secretrule/corpus/sentences.json` に、検証用の英文を60件以上置く。
パックではないため、`content/secretrule/` の直下に置かない。
パックの読み込み（インデックスの生成、`validate:content`、フォントサブセットの生成）は直下の `*.json` だけを読むためである。

`validate:content` はパックを1ファイルずつ検証関数へ渡すため、文例集はその引数に入らない。
`server/games/secretrule/` の検証関数が文例集を直接importする（パックのインデックスが `content/` のJSONを相対パスでimportするのと同じ形）。
`validateContent` は `GameModule` の一部であるため、文例集はWorkerのバンドルに入る。60件程度であり、大きさは問題にならない。

```json
{
  "sentences": [
    "I like cats.",
    "Do you have a red umbrella?",
    "My brother went to the station yesterday."
  ]
}
```

文例集は、卓が実際に書きそうな英文の代わりとして使う。
検証6と検証7の結果は文例集の構成で決まるため、パックの作者が文例集を寄せれば検証を通せてしまう。
これを防ぐため、次の2つを置く。

* 文例集の構成を機械で検査する（検証12）
* 文例集の変更はパックの変更と別のPRで行い、PRには全パックの通過率と分離の割合の変化を載せる

文例集は全パックで共有する1ファイルであり、文を足すと他のパックの検証結果も変わる。
別のPRにするのは、その影響をパックの追加と切り離して確かめるためである。

## 検証項目

`pnpm validate:content` で検査する。

| # | 内容 |
| --- | --- |
| 1 | スキーマ。必須欄の欠落と型違いを落とす。定義に無い欄があれば落とす。ルート直下に限らず、`keyExpressions[]`、`starters[]`、`candidates[]`、`rulePhrases` の各規則の中も見る |
| 2 | `id` が `[a-z0-9_]` の1〜16文字。候補の `id` がパック内で一意 |
| 3 | 候補が8件以上。同じ規則IDの候補が2件以下 |
| 4 | 候補の `ruleId` がコードに定義されており、`params` が規則IDごとの範囲（「判定関数」の表）に収まる。`words` と `letter` は英字だけからなる。`words` は小文字に揃えて重複が無い。1文字の語は `a` と `I` に限る |
| 5 | `rulePhrases` が、候補で使うすべての規則IDの言い回しを持ち、未知の規則IDを持たない。各言い回しが、その規則IDのパラメータの穴をちょうど1回ずつ含み、他の穴を含まない |
| 6 | 文例集の中で、各候補を満たす文の割合が15%以上70%以下 |
| 7 | 母集団の全候補の順序対 (X, Y) について、文例集の中でXを満たしYを満たさない文の割合が5%以上 |
| 8 | 文例集が60件以上。各文が `submit` の条件（正規化後に3語以上、140文字以内）を満たし、比較キーが重複しない |
| 9 | `keyExpressions` が3件以上、`starters` が3件以上 |
| 10 | `starters` の各文が空欄（`...`）を1箇所以上含む |
| 11 | すべての `ja` が空でない |
| 12 | 文例集の構成。`?` で終わる文が15%以上30%以下、`!` で終わる文が5%以上15%以下、語数が3〜5、6〜9、10以上の文がそれぞれ20%以上 |

検証6は、規則が易しすぎる場合と難しすぎる場合を落とす。
卓が書きそうな英文の大半が通る規則は、何を書いても通るため推理にならない。
ほとんど通らない規則は、`proving` で全員が通る見込みが立たない。

検証7が、候補どうしを英文で見分けられることと、`proving` の条件を満たす英文が存在することを保証する（「候補の抽選」）。
割合で見るのは、件数で見ると文例集の大きさで基準が変わるためである。

検証3で同じ規則IDの候補を2件までにするのは、同じ規則IDが並ぶと、見分けるための英文が1つの量（語数など）の調整だけになるためである。

検証6、7、12の閾値は**未検証**の仮置きである。
検証は、母集団の各候補の通過率と全順序対の割合を出力し、閾値の見直しに使えるようにする。

検証10を置くのは、`starters` をそのまま書き写した提出を作らせないためである（[11](./11_WHOWROTETHISゲームモジュール.md) の検証10と同じ目的）。

検証11を置くのは、`ja` がフォントサブセットの入力になるためである（[07](./07_リポジトリとツールチェーン.md)）。

### 機械で検査しないもの

* 言い回しの英文と日本語が、判定関数の条件と同じ意味を述べているか
* `has_word` の語の一覧が、卓にとって「この種類の語」とまとまって読めるか（色の語、曜日の語など）
* 文例集の英文が、卓が実際に書く英文に近いか（検証12は構成の比率だけを見る）
* `starters` の枠と `keyExpressions` の英文が自然か
* `keyExpressions` に、成否の報告、聞き返し、試す英文の提案、仮説の提案の型が揃っているか

いずれも人手のレビューで見る。
記録は `docs/お題レビュー/` に置く（収録6本と同じ形）。

1件目の項目は判定の公平さに直結する。
言い回しと判定関数がずれると、規則を正しく読んだ卓が誤答する。
言い回しを規則IDごとに持たせて文の数を絞ったのは、この確認の対象を減らすためでもある。

## 判定の規則

英文の成否は、正規化後のテキストに判定関数を適用した結果だけで決まる。
英文の意味、文法の正誤、提出の速さは判定に影響しない。

回答の正誤は、回答とした候補のidと `ruleCandidateId` の一致だけで決まる。
`proving` の通過は、秘密の規則を満たし、避ける候補を満たさないことで決まる。

アプリは英語を解釈しない（不変条件1、[ADR-0001](../adr/0001-ランタイムAI不使用.md)）。
判定関数が見るのは語数、照合語、英字、末尾の記号、最初の語であり、いずれも文字列の処理である。

確定した成否は `gameSecret.tested` に保存し、後から再計算しない。
コードやコンテンツを差し替えても、進行中のゲームの記録が動かないようにする。

## 未解決の論点

| 論点 | 内容 |
| --- | --- |
| 難度 | 1ラウンド2件、最大4ラウンドで、推理が易しすぎないか、難しすぎないかは未検証である。レビューのシミュレーションは人間が推理を誤らない前提で行っており、実プレイの難度はそれより高い見込みである |
| 2人の卓の発話 | 2人の卓には `choosing` が無い。発話は成否の報告と回答の相談に限られる |
| 推理の主導の偏り | 試す英文と回答の候補を上級者が決め、他の人が従う卓がありうる（「レベル差の吸収」） |
| 発話量 | `writing` は無言のテキスト入力である。成否を本人に限って報告を必須にしたが、発話量が収録6本と比べてどうかは未測定である |
| 閾値 | 検証6、7、12の閾値、ランクの閾値、`MAX_ROUNDS`、`choosing` と `checking` の締切はすべて仮置きである |
| 所要時間 | 最長の進行では約19分になる。調整の順は「所要時間の見積り」に書いた |
| 照合語の定義の伝わりやすさ | `I'm` を `I` と別の語とする定義が卓に伝わるかは未確認である。伝わらない場合は `no_word` と `has_word` から `I` を外す |
| 画面を見せない約束 | 画面を見せ合うと報告の工程が消える。機械では検出せず、場に委ねる（[13](./13_ESCAPECALLゲームモジュール.md) と同じ） |
| 切断した作者 | 判定にかけた英文の作者が `checking` の途中で切断すると、その成否を卓が聞けない。下書きを選ぶ時点で接続している作者に限ったが、その後の切断は防げない |
| 同じ規則の再登場 | `nextGame` で `gameSecret` は破棄されるため、同じ部屋で続けて遊ぶと同じ規則を引きうる。母集団から6件を抽選して確率を下げるだけに留める（[11](./11_WHOWROTETHISゲームモジュール.md) の同じ論点と合わせて判断する） |
| 提出内容の適切さ | 自由英文であり、場を壊す内容を機械で弾かない。同室プレイのため運用に委ねる（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断） |

| 変更 | 理由 |
| --- | --- |
| 対戦型を協力型にした | 対戦型では、推理を口に出すと他人が得をするため、黙って推理するのが最適になる。2人の卓では1対1の対戦になり、レベル差がそのまま勝敗に出る（[ADR-0031](../adr/0031-SECRETRULEは協力型にし成否を書いた本人にだけ配る.md)） |
| 成否を書いた本人にだけ配った | 全員に公開すると、英語を話さずに完走できる（[ADR-0031](../adr/0031-SECRETRULEは協力型にし成否を書いた本人にだけ配る.md)） |
| 判定にかける英文を1ラウンド2件にし、卓が選ぶようにした | 原案は全員の提出を判定する。人数分を判定すると、6人の卓は1ラウンドで正解が決まる |
| 対応人数を2〜6人にした | 判定がサーバの照合で決まり、人数で成立しなくなる仕組みがない |
| 通った英文1件ごとの加点を外した | 通った英文の語を1つ替えて出し直すのが最適になり、推理が消える |
| 最後の1回の回答を、ラウンドごとの回答にした | 回答の時期を卓が選べる方が、正解したラウンドをランクに反映できる |
| 候補を最初から公開した | 自由記述の回答は機械で照合できない。候補が見えていれば、どの候補を見分ける英文を書くかという狙いが生まれる（[ADR-0030](../adr/0030-SECRETRULEの規則は表層の判定関数に限り候補を公開する.md)） |
| 「過去形を使う」を規則から外した | 語彙リストでは過去形を網羅できず、規則の説明と判定がずれる（[ADR-0030](../adr/0030-SECRETRULEの規則は表層の判定関数に限り候補を公開する.md)） |
| 正解の後に `proving` を置いた | 推理の段階の英文は候補を見分けるための試し書きであり、規則を満たすために書く工程がない |
| 英文を書く時間を30秒から既定60秒にした | 30秒では、レベル1〜2が仮説を確かめる英文を組み立てきれない見込みである（未検証） |
| 1ゲームを最大4ラウンドにした | 本設計の締切で原案の5ラウンドを回すと、最長の進行が約22分になる |
| 同じ英文の再提出を拒否した | 同じ英文の成否は変わらず、`proving` では書き写しで通過数を稼げる |

## テスト観点

`GameModule` は純粋関数のため、Durable Objectなしで全項目をテストする。

* 決定性: 同じ `seed` と同じ参加者から、同じ候補6件、秘密の規則、避ける候補、当番順が得られること
* 抽選: 多数の `seed` で、秘密の規則が候補6件のどの位置にも現れ、避ける候補が秘密の規則と一致しないこと
* 正規化: 全角の英数字と記号、曲がった引用符、全角空白が正規化され、保存と返送が正規化後の文字列になること
* 判定関数: 規則IDごとに、満たす文と満たさない文の境界を確かめること。`n` の前後、大文字と小文字、全角の `？`、`?"` と `?)` で終わる文、`(` や `"` で始まる文、記号だけの要素、`I'm`、`couldn't`、`well-known`、数字で始まる文、照合語の無い文を含める
* 判定関数: 判定がテキストだけで決まり、提出者や時刻に依存しないこと
* 秘密の非混入: `briefing` から最終ラウンドの `checking` までの公開状態に、`solvedCandidateId` と `avoidCandidateId` 以外で、どの候補が秘密の規則か、どれが避ける候補かを示す値が無いこと。`gameSecret.rules` が載らないこと。誤答の後も確かめる
* 秘密の非混入: どのステージの公開状態にも、判定にかけた英文の成否が現れないこと
* 秘密の非混入: `writing` 中と `proving` 中の公開状態に提出テキストが現れないこと
* 秘密の非混入: 判定にかかった英文の成否が、作者以外の秘密に入らないこと
* 秘密の非混入: `listContents()` の戻り値に候補が含まれないこと
* 秘密の配布: 「送るときと値」の表の各時点で、表どおりの相手に表どおりの値が送られること。`start` で全員に `briefing` の値が送られること
* `submit`: 3語未満が `too_short`、140文字超が `too_long`、文字列でない値が `invalid_submission` で拒否されること。語数と文字数を正規化後に数えること
* `submit`: 判定にかけた過去の英文と、句点の有無、大文字と小文字、全角と半角だけが違う英文が `duplicate` で拒否されること
* `submit`: 判定にかからなかった前のラウンドの下書きは、もう一度出せること
* `submit`: 同じステージで他人と比較キーが同じ英文が `duplicate` で拒否されること
* `submit`: 接続中の全員の提出で次へ進む遷移でも、最後の提出者の秘密が同じ遷移に載ること
* 遷移: 選べる下書きが2件以下のとき `choosing` を飛ばすこと。2人の卓で毎ラウンド飛ばすこと
* 遷移: `choosing` へ入る時点で作者が切断している下書きが `drafts` に入らないこと
* `mark`: 3件以上、重複、`drafts` に無い作者が `invalid_mark`、`roundIndex` 不一致が `stale_round` で拒否されること。空の配列で印が消えること
* 下書きの選択: 印の多い順に2件が選ばれ、同数は当番順で決まること。印が無いときも当番順で2件が選ばれること。当番順がラウンドごとにずれること
* `select`: `roundIndex` 不一致が `stale_round`、型違いと候補に無いidと誤答済みの候補が `invalid_candidate` で拒否されること。`null` で選択が消えること
* 回答: `checking` の終わりに、接続中で選んだ全員が同じ候補なら回答され、割れているか誰も選んでいなければ回答されないこと。`ready` と締切の両方で確かめる
* 回答: 切断した人の選択が数えられないこと。選択が変わると全員の `ready` が解除されること
* 下書きの選択: 作者の切断で判定にかけられる下書きが2件未満になった回で、残った件数だけ判定されること
* 回答: 選択が揃った時点では判定されず、ステージも締切も変わらないこと
* 回答: 正解で `solvedCandidateId` と `avoidCandidateId` が入り、`proving` へ進むこと
* 回答: 誤答で `answers` に1行増え、次のラウンドで誤答の候補を選べないこと。最終ラウンドの誤答で `unsolved` の結果が返ること
* `proving`: 秘密の規則を満たし避ける候補を満たさない英文だけが通過として数えられること。未提出者が通過していない人として数えられること
* 結果: 表の条件どおりにランクが決まること（各ランクの境界の前後で確かめる）
* 結果: 正解しなかった卓にも秘密の規則と全ラウンドの成否が開示されること
* 作り直し: 遷移が返した秘密を `playerId` ごとに上書きで溜めた値と `rebuildSecret` の戻り値が、各遷移の直後に全員について一致すること。提出の上書き、`choosing` を飛ばす回と通る回、締切での進行、誤答、正解、`proving` の締切、正解なしでの終局を通し、2人と6人で確かめる
* 作り直し: `gameSecret` が無いときと参加者でないときに例外を投げること
* 検証: 検証1〜12がそれぞれ違反を落とすこと。検証7は、一方が他方を含む組（`min_words` の5と6）で落ちること
* 検証: 母集団の各候補の通過率と、全順序対の割合を出力できること
* ペイロード: 正規化前に140文字の英字からなる `submit` のペイロードが `ACTION_MAX_CHARS`（512）未満であること。制御文字はJSONのエスケープで文字数が増えるため、テストの文字種に含めない
* 設定: 記述子の `min` / `max` と `validateSettings` の受理範囲が一致すること
* 人数: 2人と6人で開始から `debrief` まで進むこと（[ADR-0026](../adr/0026-対象人数を2人から6人に広げる.md) の「テストと動作確認」）
