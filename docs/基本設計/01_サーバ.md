# 基本設計: サーバ（Worker + Durable Object）

## 結論

サーバは「ルーティングだけを行うWorker」と「部屋の全状態とルールを持つ `RoomDO`」の2層で構成する。

RoomDOはWebSocket Hibernation APIで実装し、すべての状態変更を `ctx.storage` へ書いてから配信する。

タイマーはDOアラーム1本を多重化して使う。

アーキテクチャ上の前提は [設計.md](../設計.md)、メッセージの意味は [03_プロトコル.md](./03_プロトコル.md) を正とする。

## Worker（ルーティング層）

Workerはステートレスで、次の3つだけを行う。

| ルート | 処理 |
| --- | --- |
| `POST /api/rooms` | 部屋コードを採番し、RoomDOを初期化して `{code}` を返す |
| `GET /api/cases` | 事件の公開メタ情報（`CaseSummary[]`）を返す。秘密は含めない |
| `GET /room/:code/ws` | WebSocketアップグレードを `idFromName(code)` のRoomDOへ中継する |
| その他 | SPAと静的アセットを配信する |

`GET /api/cases` はホストが事件を選ぶために必要である。
返すのは `id` / `title` / `playerCount` / `briefingJa` のみとし、`facts` / `variants` / `reveal` を含めない（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。
`briefing.en` は全員に開示される情報だが、ロビー段階では不要なため含めない（`state` 経由でブリーフィングフェーズに配る）。

### 部屋コードの採番

* 紛らわしい文字（I, O, 0, 1）を除いた英大文字＋数字（32文字）から4文字を生成する
* 採番時にRoomDOへ `init` を送り、既にアクティブな部屋だったら再採番する（最大5回試行）

### レート制限

Workers Rate Limiting APIでIPごとの制限を、次の**両方**にかける。

| ルート | 目的 |
| --- | --- |
| `POST /api/rooms` | 無差別な部屋作成スパムの抑止 |
| `GET /room/:code/ws` | 部屋コード総当たりの抑止 |

WSルートに制限が必要な理由は、`idFromName(code)` が存在しないコードでもDOインスタンスを起動するためである。
制限がないと、総当たりで乱入は防げてもDOリクエスト（無料枠10万/日）を一方的に消費される。

あわせてRoomDOは、`init` を受けていない（未初期化の）状態でのWebSocketアップグレード要求を確立前に拒否し、`room_not_found` を返す。

## RoomDO（部屋 = 1インスタンス）

### 責務

* 部屋のライフサイクル（作成 → ロビー → ゲーム → 破棄）
* ゲーム状態機械の実行（フェーズ遷移は [設計.md](../設計.md) の状態機械図を正とする）
* 配役・犯人バリアント抽選・秘密情報の個別配信
* 投票の集計と開示
* タイマー（フェーズ締切）と部屋のGC

### 保持する状態

`ctx.storage` に置くキーは次の通り。

| キー | 内容 |
| --- | --- |
| `room` | 公開状態（phase, players, settings, deadline） |
| `game` | 秘密を含むゲーム状態（characterId対応、犯人、バリアント、投票内容、`playerId → reconnectToken` の対応） |
| `alarms` | アラーム多重化用 `{ phaseDeadline?: epoch, expireAt: epoch }` |

`reconnectToken` を `room`（公開状態）ではなく `game`（秘密状態）に置くのは、`state` ブロードキャストへの混入を型レベルで防ぐためである（[ADR-0006](../adr/0006-公開IDと再接続シークレットの分離.md)）。

インメモリはキャッシュとしてのみ使い、状態変更は必ず「storage書き込み → クライアント配信」の順で行う。
Hibernationからの復帰時（コンストラクタ）はstorageから再構築する。

### ストレージバックエンド

無料プランで利用できるのはSQLiteストレージバックエンドのDurable Objectのみである（key-valueバックエンドは有料プラン専用）。

`wrangler.jsonc` のマイグレーションは `new_sqlite_classes` で `RoomDO` を宣言する。
`new_classes`（key-valueバックエンド）で宣言すると無料プランではデプロイに失敗する。

`ctx.storage` のkey-value APIはSQLiteバックエンド上でも利用できるため、上記のキー設計は変わらない。

### Hibernation実装要件

* `ctx.acceptWebSocket(ws)` を使い、`webSocketMessage` / `webSocketClose` ハンドラで処理する。`ws.accept()` は使用禁止（ルートCLAUDE.mdの不変条件4）
* ソケットとプレイヤーの対応は `ws.serializeAttachment({playerId})` に保存する。インメモリのMapに依存しない。観戦ソケットは `{spectator: true}` を入れる
* `serializeAttachment` に `reconnectToken` を入れない（storageの `game` 側で引く）
* 接続断の検出は `webSocketClose` と auto-response のping設定で行う
* コードのデプロイはすべてのDurable Objectを再起動し、Hibernation中のWebSocketも切断される。これはCloudflareの仕様であり回避できない。再接続はクライアント側の責務とする（[02_クライアント.md](./02_クライアント.md)）

### アラーム多重化

DOアラームは1本しか持てないため、用途を `alarms` キーで管理する。

* アラームを設定するときは `min(phaseDeadline, expireAt)` をセットする
* `alarm()` 発火時は現在時刻と各期限を比較して該当処理へディスパッチする
  * `phaseDeadline` 到達: 現フェーズの強制遷移。briefing→investigation、investigation→voting、voting→reveal の3箇所で同じ仕組みを使う
  * `expireAt` 到達: 部屋の全stateを削除して破棄
* `expireAt` は最終アクセスのたびに「現在 + 2時間」で更新する

### フェーズ締切の既定値

| フェーズ | 締切 | 変更可否 |
| --- | --- | --- |
| briefing | 120秒 | 不可 |
| investigation | ロビーで設定（既定600秒） | ホストが `selectCase` で設定 |
| voting | 90秒 | 不可 |

briefingとvotingにも締切を置くのは、「全員ready」「全員投票」だけを遷移条件にすると、切断者が1人出た時点で `expireAt`（2時間）まで進行不能になるためである。

「全員」の判定は `connected: true` のプレイヤーのみを対象とする。
締切到達時、未readyは既読扱い、未投票は棄権扱いとする。

### メッセージ処理

受理可否は「フェーズ × 送信者の役割」で決まる。この表を実装の正とする。

| メッセージ | 受理フェーズ | 送信者条件 | 処理 |
| --- | --- | --- | --- |
| `join` | lobby（`reconnectToken` つきの再接続は全フェーズ） | — | プレイヤー追加 or 再接続。`joined` → `state` →（ゲーム中なら）`secret` を送る |
| `spectate` | 全フェーズ | — | 観戦ソケットとして登録。`state` のみ配信対象に加える |
| `selectCase` | lobby | ホスト | 事件と捜査時間を設定 |
| `start` | lobby | ホスト | 人数検証 → 配役 → バリアント抽選 → briefingへ。全員へ `secret` 個別送信。phaseDeadlineを設定 |
| `ready` | briefing | 参加者 | 接続中の全員readyで investigation へ。phaseDeadlineを設定 |
| `vote` | voting | 参加者（未投票者） | 投票記録。接続中の全員投票で集計し reveal へ |
| `nextGame` | reveal | ホスト | lobbyへ戻す（配役・投票・秘密をクリア） |

表にない組み合わせは `error` を返し、状態を変えない。

### プレイヤーの認証と再接続

* `join` に `reconnectToken` が無ければ新規参加として扱い、`playerId`（公開ID）と `reconnectToken`（秘密値、128bit以上の乱数）を発行して `joined` で本人にのみ返す
* `join` に `reconnectToken` があれば、`game` キーの対応表と照合して該当プレイヤーの席へ再接続させる
* `playerId` を認証情報として受理しない。`playerId` は `state` で全員に配られるため、これを再接続キーにすると他人の `secret` を取得できてしまう（[ADR-0006](../adr/0006-公開IDと再接続シークレットの分離.md)）
* 照合に失敗した `reconnectToken` は、ゲーム中であれば `game_in_progress`、ロビーであれば新規参加として扱う

### ホスト権限

* 部屋の最初の参加者をホストとする
* ホストが切断（`connected: false`）した時点で、接続中の参加者のうち最も参加が早い者へ自動移譲する
* 元ホストが復帰しても権限は戻さない。移譲の往復による混乱を避け、実装を単純にするためである
* 接続中の参加者が0人になった場合は権限を保留し、次に接続した者へ与える

自動移譲がないと、ホスト限定操作（`selectCase` / `start` / `nextGame`）を誰も送れずゲームが停止する。

### 事件データの読み込み

事件JSONはビルド時に `server/` へバンドルする（`import` で取り込む）。
クライアントの静的アセットには含めない。犯人・嘘・真相をネットワーク上でクライアントに渡すのは `secret` と `reveal` のみとする。

公開メタ情報（`CaseSummary`）はバンドルした事件データから起動時に射影して `GET /api/cases` で返す。
別ファイルとして二重管理しない。

## エラーコード

エラーコードの正本は本表とする（他の文書はここを参照する）。

| code | 意味 |
| --- | --- |
| `room_not_found` | 部屋が存在しない・破棄済み・未初期化 |
| `room_full` | 人数上限 |
| `game_in_progress` | ロビー以外への新規参加、または照合できない `reconnectToken` でのゲーム中の接続 |
| `not_host` | ホスト限定操作 |
| `invalid_phase` | 現フェーズで受理しないメッセージ |
| `invalid_payload` | ペイロード検証エラー |
| `unsupported_version` | プロトコルバージョン不一致（クライアントは強制リロードする） |

## 不変条件

* 秘密情報（`game` キーの内容）はブロードキャストに一切含めない。`secret` の個別送信と `reveal` の開示のみ
* `reconnectToken` は `joined` で本人へ送るときだけネットワークに載る。`state` / `reveal` / `serializeAttachment` に含めない
* 認証に使う値を公開状態（`room`）に置かない
* 状態遷移はメッセージ処理表とアラームの2経路のみ。クライアントの申告で時間切れ判定をしない
* storage書き込み前にクライアントへ配信しない（Hibernation復帰で巻き戻るため）
* 観戦ソケット（`spectate`）へ送るのは `state` のみ。`secret` の配信対象に含めない

## テスト観点

vitest-pool-workersで最低限次を常設する。

* 秘密情報の混入検査: 全フェーズを通しで実行し、`secret` 以外の受信メッセージに `isCulprit` / `cards` / `reconnectToken` / 他人の証言が含まれないこと
* なりすまし拒否: プレイヤーAが `state` から得た**プレイヤーBの `playerId`** を `reconnectToken` として `join` を送ると失敗し、Bの `secret` が送られないこと（[ADR-0006](../adr/0006-公開IDと再接続シークレットの分離.md)の退行検知）
* フェーズ×メッセージ表の全組み合わせで、表にないものが `error` になること
* アラーム多重化: phaseDeadlineとexpireAtの前後関係4通りで正しくディスパッチされること
* 再接続: Hibernation復帰後（storage再構築後）に同じ `reconnectToken` で `join` して `secret` が再送されること
* 進行のデッドロック不在: 各フェーズで1人を切断させたまま締切を経過させ、次フェーズへ遷移すること（briefing / voting）
* ホスト移譲: ホストを切断させた後、次点の参加者から `start` / `nextGame` が受理されること
* 観戦ソケット: `spectate` のみを送ったソケットに `secret` が届かないこと
* バリアント抽選: 全員レベル1〜2の構成でも `start` が成功し、最高レベルのプレイヤーが犯人になること（[ADR-0007](../adr/0007-犯人バリアントは実配役プレイヤーのレベルで抽選する.md)）
