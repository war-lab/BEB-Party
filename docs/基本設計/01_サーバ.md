# 基本設計: サーバ（Worker + Durable Object）

## 結論

サーバは「ルーティングだけを行うWorker」と「部屋の全状態を持つ `RoomDO`」の2層で構成する。

`RoomDO` はゲームのルールを持たない。ルールは `GameModule` にあり、RoomDOはそれを呼び出して結果を反映する係である（[ADR-0009](../adr/0009-部屋基盤とゲームモジュールの分離.md)）。

RoomDOはWebSocket Hibernation APIで実装し、すべての状態変更を `ctx.storage` へ書いてから配信する。

タイマーはDOアラーム1本を多重化して使う。

アーキテクチャ上の前提は [設計.md](../設計.md)、共通コアとゲームモジュールの境界は [05_ゲームモジュール.md](./05_ゲームモジュール.md)、メッセージの意味は [03_プロトコル.md](./03_プロトコル.md) を正とする。

## Worker（ルーティング層）

Workerはステートレスで、次の3つだけを行う。

| ルート | 処理 |
| --- | --- |
| `POST /api/rooms` | 部屋コードを採番し、RoomDOを初期化して `{code}` を返す |
| `GET /api/catalog` | 収録ゲームとコンテンツの公開メタ情報を返す。秘密は含めない |
| `GET /room/:code/ws` | WebSocketアップグレードを `idFromName(code)` のRoomDOへ中継する |
| その他 | SPAと静的アセットを配信する |

`GET /api/catalog` はホストがゲームとコンテンツを選ぶために必要である。
レジストリに登録された全 `GameModule` の `id` / `title` / `playerCount` と、`listContents()` の結果を並べて返す。

コンテンツの公開メタに含めてよいのは、全員が見てよい情報のみとする（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。
DETECTIVESの場合は `id` / `title` / `playerCount` / `briefingJa` までで、`facts` / `variants` / `reveal` を含めない。
`briefing.en` は全員に開示される情報だが、ロビー段階では不要なため含めない（`state` 経由でブリーフィングステージに配る）。

### 部屋コードの採番

* 紛らわしい文字（I, O, 0, 1）を除いた英大文字＋数字（32文字）から4文字を生成する
* 採番時にRoomDOへ `init` を送り、既にアクティブな部屋だったら再採番する（最大5回試行）

### レート制限

Workers Rate Limiting APIでIPごとの制限を、次の**両方**にかける。

| ルート | 閾値 | 目的 |
| --- | --- | --- |
| `POST /api/rooms` | 5回 / 60秒 | 無差別な部屋作成スパムの抑止 |
| `GET /room/:code/ws` | 60回 / 60秒 | 部屋コード総当たりの抑止 |

WSルートに制限が必要な理由は、`idFromName(code)` が存在しないコードでもDOインスタンスを起動するためである。
制限がないと、総当たりで乱入は防げてもDOリクエスト（無料枠10万/日）を一方的に消費される。

あわせてRoomDOは、`init` を受けていない（未初期化の）状態でのWebSocketアップグレード要求を確立前に拒否し、`room_not_found` を返す。

#### 閾値の根拠

Rate Limiting APIの `period` に指定できるのは10秒または60秒だけであり、60秒を選ぶ。
制限はCloudflareのロケーション単位で個別に数えられるため、実効値は表の値以上になりうる。この機構は正確な計数を目的としていない。

キーには `CF-Connecting-IP` を使う。
Cloudflareのドキュメントは共有IPを理由にIPをキーにしないことを勧めているが、認証前のスパム抑止では他に安定した識別子がない。
BEB Partyでは同室の5〜6人が同じNATの内側から接続するため、6人分のアクセスが1キーに集まる前提で閾値を決める。

`GET /room/:code/ws` を60回/60秒とするのは、再接続の集中を通すためである。
デプロイやWi-Fiの切り替えで6人が同時に切断されると、指数バックオフ（上限10秒）で1分あたり最大36回の接続試行が同一IPから発生する。
30回程度に絞ると正常な復帰が弾かれる。

この値でも総当たりの抑止としては足りる。
部屋コードの空間は32の4乗で約105万通りあり、60回/60秒では単一IPからの全走査に11日以上かかる。
さらに部屋は最終アクセスから2時間で破棄されるため、任意の時点で当たりとなるコードは実際に遊んでいる数部屋に限られる。

`POST /api/rooms` を5回/60秒とするのは、正常な利用が1セッションにつき1回だからである。
再試行と操作ミスの余地として5回を取る。

制限に達したリクエストにはHTTP 429を返す。
WebSocketアップグレードの場合はハンドシェイク前に返るため、`error` メッセージでは通知できない。
クライアントは101以外の応答を受けたときバックオフを継続し、429のときは最低30秒待ってから再試行する（[02_クライアント.md](./02_クライアント.md)）。

## RoomDO（部屋 = 1インスタンス）

### 責務

* 部屋のライフサイクル（作成 → ロビー → ゲーム → 破棄）
* 共通ライフサイクルの管理（`lobby` / `playing` / `finished` の遷移は [設計.md](../設計.md) の状態機械図を正とする）
* `GameModule` の呼び出しと、返された `GameTransition` の反映（状態の保存・配信・アラーム設定）
* 秘密情報を各プレイヤーへ個別配信する機構の提供（中身の生成はゲームモジュール）
* タイマー（ステージ締切）と部屋のGC

RoomDOはゲームのルールを判定しない。
`stage` 文字列の意味も解釈せず、`GameModule` から受け取った値をそのまま保存・配信する。

### 保持する状態

`ctx.storage` に置くキーは次の通り。

| キー | 内容 |
| --- | --- |
| `room` | 共通の公開状態（lifecycle, players, gameId, contentId, stage, deadline, gameState） |
| `secrets` | 秘密情報（`playerId → reconnectToken` の対応、ゲームモジュールが保持する秘密状態、各自へ配った `secret` の内容） |
| `alarms` | アラーム多重化用 `{ stageDeadline?: epoch, expireAt: epoch }` |

`room.gameState` はゲームモジュールが定義する**公開**状態であり、秘密を入れてはならない。
秘密は必ず `secrets` 側に置く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。

ゲームモジュールが呼び出しをまたいで持ち越す秘密状態は `secrets` キーの `gameSecret` に保存する。
RoomDOは中身を解釈せず、`handleAction` と `onDeadline` の入力へそのまま戻す（[ADR-0015](../adr/0015-ゲームモジュールの秘密状態を共通コアが預かる.md)）。

`reconnectToken` を `room`（公開状態）ではなく `secrets`（秘密状態）に置くのは、`state` ブロードキャストへの混入を型レベルで防ぐためである（[ADR-0006](../adr/0006-公開IDと再接続シークレットの分離.md)）。

インメモリはキャッシュとしてのみ使い、状態変更は必ず「storage書き込み → クライアント配信」の順で行う。
Hibernationからの復帰時（コンストラクタ）はstorageから再構築する。

### ストレージバックエンド

無料プランで利用できるのはSQLiteストレージバックエンドのDurable Objectのみである（key-valueバックエンドは有料プラン専用）。

`wrangler.jsonc` のマイグレーションは `new_sqlite_classes` で `RoomDO` を宣言する。
`new_classes`（key-valueバックエンド）で宣言すると無料プランではデプロイに失敗する。

`ctx.storage` のkey-value APIはSQLiteバックエンド上でも利用できるため、上記のキー設計は変わらない。

### Hibernation実装要件

* `ctx.acceptWebSocket(ws)` を使い、`webSocketMessage` / `webSocketClose` ハンドラで処理する。`ws.accept()` は使用禁止（ルートCLAUDE.mdの不変条件4）
* ソケットとプレイヤーの対応は `ws.serializeAttachment({playerId})` に保存する。インメモリのMapに依存しない。観戦ソケットは `{spectator: true}` を入れる
* `serializeAttachment` に `reconnectToken` を入れない（storageの `secrets` 側で引く）
* 接続断の検出は `webSocketClose` / `webSocketError` と、最終ハートビート時刻の照合で行う（下記「接続の死活判定」）
* コードのデプロイはすべてのDurable Objectを再起動し、Hibernation中のWebSocketも切断される。これはCloudflareの仕様であり回避できない。再接続はクライアント側の責務とする（[02_クライアント.md](./02_クライアント.md)）

### 接続の死活判定

クライアントは25秒間隔でハートビートを送り、サーバは `setWebSocketAutoResponse()` に登録した固定応答で返す（値は [03_プロトコル.md](./03_プロトコル.md)）。
自動応答はDOを起こさないため、待機中の実行時間を消費しない。

死活判定のための定期アラームは持たない（[ADR-0013](../adr/0013-死活監視の定期アラームを持たない.md)）。
判定は、別の理由でDOが起きたとき（メッセージ受信時とアラーム発火時）に次の手順でまとめて行う。

1. `ctx.getWebSockets()` で全ソケットを取得する
2. 各ソケットの `ctx.getWebSocketAutoResponseTimestamp(ws)` を読む
3. 90秒（ハートビート間隔の3倍を超える値）より古いものを切断済みとみなし、`connected: false` にして閉じる

この方式では、無通信の時間帯に切れた接続が `connected: true` のまま残る。
すべてのステージに締切があるため進行は止まらず、遅延は現ステージの残り時間に収まる。

### アラーム多重化

DOアラームは1本しか持てないため、用途を `alarms` キーで管理する。

* アラームを設定するときは `min(stageDeadline, expireAt)` をセットする
* `alarm()` 発火時は現在時刻と各期限を比較して該当処理へディスパッチする
  * `stageDeadline` 到達: `GameModule.onDeadline` を呼び、返された `GameTransition` を反映する。どのステージでも同じ仕組みを使う
  * `expireAt` 到達: 部屋の全stateを削除して破棄
* `expireAt` は最終アクセスのたびに「現在 + 2時間」で更新する

締切の秒数と遷移先はゲームモジュールが決める。共通コアはアラームの設定と発火だけを担う。

### ステージ締切（DETECTIVESの場合）

| ステージ | 締切 | 変更可否 |
| --- | --- | --- |
| briefing | 120秒 | 不可 |
| investigation | ロビーで設定（既定600秒） | ホストが `configure` で設定 |
| voting | 90秒 | 不可 |
| reveal | なし（`lifecycle: finished`。`nextGame` を待つ） | — |

すべてのステージに締切を置くのは、「全員ready」「全員投票」だけを遷移条件にすると、切断者が1人出た時点で `expireAt`（2時間）まで進行不能になるためである。
締切のないステージを定義してよいのは、`lifecycle: finished` で `nextGame` を待つ場合に限る。

### 全員完了の判定

「接続中の全員から入力が揃ったか」の判定は共通コアが行わない。

共通コアは `handleAction` / `onDeadline` へ `room` を渡す。
`room.players[].connected` から接続中の顔ぶれが分かり、収集状況はゲームモジュールが自分の公開状態に持つため、判定はゲームモジュール側で完結する（[05](./05_ゲームモジュール.md)）。

* 「全員」の判定対象を `connected: true` のプレイヤーに限る規則は、ゲームモジュールが実装する。共通コアはその規則を知らない
* 締切到達時は揃っていない状態で `onDeadline` を呼ぶ。未入力者の扱い（DETECTIVESでは未readyを既読扱い、未投票を棄権扱い）はゲームモジュールが決める

共通コアが収集機構を持たない理由は、「1人1件か」「上書きを許すか」「棄権をどう数えるか」がゲームごとに異なり、共通化すると規則をゲーム側から共通コアへ持ち上げることになるためである。

### メッセージ処理

受理可否は「`lifecycle` × 送信者の役割」で決まる。この表を実装の正とする。

| メッセージ | 受理lifecycle | 送信者条件 | 処理 |
| --- | --- | --- | --- |
| `join` | lobby（`reconnectToken` つきの再接続は全lifecycle） | — | プレイヤー追加 or 再接続。`joined` → `state` →（ゲーム中なら）`secret` を送る |
| `spectate` | 全lifecycle | — | 観戦ソケットとして登録。`state` のみ配信対象に加える。上限を超えていれば `spectator_limit` |
| `selectGame` | lobby | ホスト | ゲームを選択。`contentId` と `settings` をクリアする |
| `configure` | lobby | ホスト | `contentId` が `listContents()` にあることと `GameModule.validateSettings` を検証し、通ればコンテンツとゲーム固有設定を保存する |
| `start` | lobby | ホスト | 人数検証 → コンテンツ選択の検証 → シード生成 → `GameModule.start` → 返り値を反映（stage設定、`secret` 個別送信、stageDeadline設定） |
| `action` | playing | 参加者 | `GameModule.handleAction` へディスパッチし、`GameTransition` を反映 |
| `nextGame` | finished | ホスト | lobbyへ戻す（`gameId` / `contentId` / `settings` / `gameState` と秘密をクリア。持ち越すのは参加者とそのレベルだけ。[ADR-0011](../adr/0011-部屋単位の通算スコアを持たない.md)） |

表にない組み合わせは `error` を返し、状態を変えない。

`action` の受理可否（現ステージで許される操作か、送信者が対象か、二重送信か）は `GameModule.handleAction` が判定し、`GameTransition.reject` で返す。
共通コアが判定するのは `lifecycle: playing` であることと、送信者が観戦ソケットでないことだけである。

`configure` の `settings` を共通コアが検証しないのは、スキーマの記述形式を共通コアが規定しないためである（[ADR-0012](../adr/0012-ゲーム固有設定の検証をゲームモジュールに委ねる.md)）。
共通コアが検証するのは共通メッセージのフィールド（`name` / `level` / `gameId` / `contentId` の型と範囲）に限る。
`validateSettings` が失敗を返したら `error(invalid_payload)` を返し、状態を変えない。

`contentId` の範囲は `GameModule.listContents()` の結果と照合する。
未登録の `contentId` を保存すると `start` でゲームモジュールがコンテンツを引けず、`GameModule.start` は拒否を返せない形になっているため、`configure` の時点で弾く。

`start` は、コンテンツを持つゲーム（`listContents()` が空でない）でコンテンツが選択されていなければ `error(invalid_payload)` を返す。
コンテンツを持たないゲームはこの検査の対象外とする。

### 観戦ソケットの上限

1部屋あたりの観戦ソケットは2本までとする。
超過した `spectate` は `spectator_limit` を返して接続を閉じる。

観戦ソケットは `state` と `result` のブロードキャスト対象に加わるため、本数がそのままDOの送信量になる。
参加者と違って人数上限（事件の対応人数）で頭打ちにならないため、別に上限が要る。

想定する用途は大画面表示1台であり、2本目は表示端末の切り替え中に前の接続が残っている場合の余地である。

### ゲームモジュールの呼び出し規約

* `GameModule` は `server/core/registry.ts` の `gameId → GameModule` テーブルから引く。この1箇所以外でゲームIDによる分岐を書かない（[05_ゲームモジュール.md](./05_ゲームモジュール.md)）
* `GameModule` のメソッドは純粋関数として呼ぶ。storage・WebSocket・現在時刻・乱数を渡さない。乱数は `start` の `seed` として注入し、生成した値を `secrets` へ保存する（再現とデバッグのため）
* 返された `GameTransition` の反映順は「storage書き込み → `secret` 個別送信 → `state` ブロードキャスト → `result`（あれば） → アラーム再設定」とする
* `GameTransition.reject` が返った場合は状態を一切変えず、`error` を本人へ返す

### プレイヤーの認証と再接続

* `join` に `reconnectToken` が無ければ新規参加として扱い、`playerId`（公開ID）と `reconnectToken`（秘密値、128bit以上の乱数）を発行して `joined` で本人にのみ返す
* `join` に `reconnectToken` があれば、`secrets` キーの対応表と照合して該当プレイヤーの席へ再接続させる
* `playerId` を認証情報として受理しない。`playerId` は `state` で全員に配られるため、これを再接続キーにすると他人の `secret` を取得できてしまう（[ADR-0006](../adr/0006-公開IDと再接続シークレットの分離.md)）
* 照合に失敗した `reconnectToken` は、ゲーム中であれば `game_in_progress`、ロビーであれば新規参加として扱う

### ホスト権限

* 部屋の最初の参加者をホストとする
* ホストが切断（`connected: false`）した時点で、接続中の参加者のうち最も参加が早い者へ自動移譲する
* 元ホストが復帰しても権限は戻さない。移譲の往復による混乱を避け、実装を単純にするためである
* 接続中の参加者が0人になった場合は権限を保留し、次に接続した者へ与える

自動移譲がないと、ホスト限定操作（`selectGame` / `configure` / `start` / `nextGame`）を誰も送れずゲームが停止する。

### コンテンツの読み込み

`content/<gameId>/` のJSONはビルド時に `server/` へバンドルする（`import` で取り込む）。
クライアントの静的アセットには含めない。秘密をネットワーク上でクライアントに渡すのは `secret` と `result` のみとする。

公開メタ情報はバンドルしたコンテンツから `GameModule.listContents()` で射影し、`GET /api/catalog` で返す。
別ファイルとして二重管理しない。

## エラーコード

エラーコードの正本は本表とする（他の文書はここを参照する）。

| code | 意味 |
| --- | --- |
| `room_not_found` | 部屋が存在しない・破棄済み・未初期化 |
| `room_full` | 人数上限 |
| `spectator_limit` | 観戦ソケットの上限（2本）超過 |
| `game_in_progress` | ロビー以外への新規参加、または照合できない `reconnectToken` でのゲーム中の接続 |
| `not_host` | ホスト限定操作 |
| `invalid_lifecycle` | 現 `lifecycle` で受理しないメッセージ |
| `invalid_payload` | ペイロード検証エラー |
| `unknown_game` | 未登録の `gameId`、またはゲーム未選択のまま `start` |
| `player_count_mismatch` | 参加人数が選択中ゲーム・コンテンツの対応範囲外 |
| `unsupported_version` | プロトコルバージョン不一致（クライアントは強制リロードする） |

ゲームモジュールが `GameTransition.reject` で返すコードは上表に含めず、ゲームモジュール側で定義する（DETECTIVESの `already_voted` / `invalid_stage` 等）。
クライアントは未知のコードを汎用エラー表示にフォールバックする。

## 不変条件

* 秘密情報（`secrets` キーの内容）はブロードキャストに一切含めない。`secret` の個別送信と `result` の開示のみ
* `reconnectToken` は `joined` で本人へ送るときだけネットワークに載る。`state` / `result` / `serializeAttachment` に含めない
* 認証に使う値を公開状態（`room`）に置かない
* 状態遷移はメッセージ処理表とアラームの2経路のみ。クライアントの申告で時間切れ判定をしない
* storage書き込み前にクライアントへ配信しない（Hibernation復帰で巻き戻るため）
* 観戦ソケット（`spectate`）へ送るのは `state` と `result` のみ。`secret` の配信対象に含めない
* RoomDOにゲーム固有の判定を書かない。`registry.ts` 以外でゲームIDによる分岐をしない（[ADR-0009](../adr/0009-部屋基盤とゲームモジュールの分離.md)）
* 死活監視・進行監視のための定期アラームを設定しない。アラームの用途はステージ締切と部屋の破棄に限る（[ADR-0013](../adr/0013-死活監視の定期アラームを持たない.md)）

## テスト観点

vitest-pool-workersで最低限次を常設する。

* 秘密情報の混入検査: 全ステージを通しで実行し、`secret` 以外の受信メッセージに `reconnectToken` / ゲームモジュールの秘密状態（DETECTIVESでは `isCulprit` / `cards` / 他人の証言）が含まれないこと
* なりすまし拒否: プレイヤーAが `state` から得た**プレイヤーBの `playerId`** を `reconnectToken` として `join` を送ると失敗し、Bの `secret` が送られないこと（[ADR-0006](../adr/0006-公開IDと再接続シークレットの分離.md)の退行検知）
* lifecycle×メッセージ表の全組み合わせで、表にないものが `error` になること
* アラーム多重化: stageDeadlineとexpireAtの前後関係4通りで正しくディスパッチされること
* 再接続: Hibernation復帰後（storage再構築後）に同じ `reconnectToken` で `join` して `secret` が再送されること
* 進行のデッドロック不在: 各ステージで1人を切断させたまま締切を経過させ、次ステージへ遷移すること
* ホスト移譲: ホストを切断させた後、次点の参加者から `start` / `nextGame` が受理されること
* 観戦ソケット: `spectate` のみを送ったソケットに `secret` が届かないこと。3本目の `spectate` が `spectator_limit` で拒否されること
* 死活判定: ハートビートを止めたソケットが、90秒経過後の任意のメッセージ受信を契機に `connected: false` になること。定期アラームによる自動的な検出を期待するテストは書かない（[ADR-0013](../adr/0013-死活監視の定期アラームを持たない.md)）
* 設定検証: 範囲外の `settings` を含む `configure` が `invalid_payload` で拒否され、保存されないこと
* ゲーム非依存性: RoomDOのテストをスタブの `GameModule`（ステージ2つだけを持つダミー）で通し、DETECTIVESを一切importせずに全ライフサイクルが動くこと。これが通らなければ分離が壊れている
* `GameTransition` の反映: `reject` が返ったとき状態が変わらないこと、`result` が返ったとき `lifecycle` が `finished` になること
