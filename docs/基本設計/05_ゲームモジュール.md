# 基本設計: 共通コアとゲームモジュール

## 結論

BEB Partyは英語パーティゲーム集であり、コードは「共通コア」と「ゲームモジュール」の2層に分かれる（[ADR-0009](../adr/0009-部屋基盤とゲームモジュールの分離.md)）。

共通コアは部屋の器だけを提供し、ゲームのルールを一切知らない。
ゲームモジュールはステージ定義・配役・秘密情報・ルール判定・結果生成・コンテンツ検証を持つ。

本文書は境界の定義とゲーム追加手順を正とする。
共通コアの実装詳細は [01_サーバ.md](./01_サーバ.md) と [02_クライアント.md](./02_クライアント.md)、メッセージの意味は [03_プロトコル.md](./03_プロトコル.md) を正とする。

### 共通コアに入れる判断基準

**2本目以降でも確実に必要と言えるものだけを入れる。迷ったらゲームモジュール側に置く。**

共通コアの肥大化は分離の目的に反する。
「投票の集計」のように複数ゲームで使いそうに見える処理も、勝敗判定と不可分なためゲームモジュールに置く。

「接続中の全員から入力が揃ったか」の判定も共通コアに置かない。
`handleAction` には `room`（`players[].connected` を含む）が渡り、収集状況はゲームモジュールが自分の公開状態に持つため、揃ったかどうかはゲームモジュール側で判定できる。
共通コアが収集機構を持つと、「1人1件」「上書き可否」「棄権の扱い」といったゲームごとに異なる規則を共通コア側で表現することになる。

共通コアのコードがゲームIDで分岐していたら設計の失敗とみなす。
分岐はディスパッチテーブル1箇所に閉じる。

## 状態モデル

共通コアの状態は2階層になる。

```typescript
type Level = 1 | 2 | 3 | 4 | 5;

// 共通コア。ゲーム固有の語彙を含まない
interface Room {
  code: string;
  lifecycle: 'lobby' | 'playing' | 'finished';
  players: Player[];
  gameId?: string;       // 選択中のゲーム
  contentId?: string;    // 選択中のコンテンツ(事件・お題セット等)
  stage?: string;        // ゲーム固有のステージid。共通コアは中身を解釈しない
  deadline?: number;     // 現ステージの締切(epoch ms)
  gameState?: unknown;   // ゲーム固有の公開状態。ゲームモジュールが型を定義する
}
```

* `lifecycle` は共通コアが管理する。`lobby`（準備中） → `playing`（進行中） → `finished`（結果表示中） → `nextGame` で `lobby` へ戻る
* `nextGame` で `lobby` へ戻る際に持ち越すのは参加者とそのレベルだけとする。ゲームをまたぐ通算スコアを `Room` に持たない（[ADR-0011](../adr/0011-部屋単位の通算スコアを持たない.md)）
* `stage` はゲームモジュールが定義する文字列。共通コアは比較も分岐もしない
* `gameState` はゲームモジュールが定義する公開状態。ここに秘密を入れることは禁止（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）

DETECTIVESの場合、`stage` は `briefing` / `investigation` / `voting` / `reveal` を取る。
`reveal` に入った時点で `lifecycle` は `finished` になる。

## GameModuleインターフェース

ゲームモジュールは次の形で共通コアへ登録する。
共通コアはこのインターフェースだけを通してゲームに触る。

```typescript
// gameIdはregistryのキーが正。モジュール側に持たせない(二重管理になる)
interface GameModule<TPublic, TSecret, TResult, TGameSecret = unknown> {
  title: string;                    // 'ENGLISH DETECTIVES'
  tagline: string;                  // 選択画面に出す一行の説明
  icon: string;                     // 選択画面のアイコン(絵文字)
  playerCount: [number, number];    // 対応人数
  contentLabelJa: string;           // ロビーのコンテンツ選択の見出し(ADR-0018)
  settingsFields: SettingField[];   // ロビーで変更できる設定の記述子(ADR-0018)

  // ロビーで配るコンテンツ一覧(公開メタのみ)
  listContents(): ContentSummary[];

  // configure受理時のゲーム固有設定の検証(ADR-0012)
  validateSettings(settings: unknown): ValidationResult;

  // 開始。配役・抽選を行い、初期ステージと各自の秘密情報を返す
  // seedは共通コアが生成して注入する(テストの再現性のため)
  start(input: {
    players: Player[]; contentId: string; settings: unknown; seed: number;
  }): {
    stage: string;
    deadlineSeconds: number;
    publicState: TPublic;
    secrets: Map<string, TSecret>;   // playerId -> 秘密情報
    gameSecret?: TGameSecret;        // モジュールが持ち越す秘密状態(ADR-0015)
  };

  // ゲーム固有操作の受理。受理不可なら reject を返す
  handleAction(input: {
    room: Room; publicState: TPublic; gameSecret: TGameSecret | undefined;
    playerId: string; action: string; payload: unknown;
  }): GameTransition<TPublic, TResult, TGameSecret>;

  // ステージ締切の到達。強制遷移を返す
  onDeadline(input: {
    room: Room; publicState: TPublic; gameSecret: TGameSecret | undefined;
  }): GameTransition<TPublic, TResult, TGameSecret>;

  // コンテンツ検証(CI用)。ランタイムでは呼ばない
  validateContent(content: unknown): ValidationResult;
}

interface GameTransition<TPublic, TResult, TGameSecret = unknown> {
  publicState?: TPublic;            // 更新後の公開状態
  stage?: string;                   // 遷移先(省略時は変えない)
  deadlineSeconds?: number;         // 新ステージの締切
  secrets?: Map<string, unknown>;   // 追加で個別送信する秘密情報
  gameSecret?: TGameSecret;         // 更新後の秘密状態(ADR-0015)
  result?: TResult;                 // 設定するとlifecycleがfinishedになる
  reject?: { code: string };        // 受理不可。状態を変えない
}
```

`gameSecret` は、ゲームモジュールが呼び出しをまたいで持ち越す秘密状態である。
共通コアは中身を解釈せず、storageの `secrets` キーへ保存して次の呼び出しへ戻す（[ADR-0015](../adr/0015-ゲームモジュールの秘密状態を共通コアが預かる.md)）。
DETECTIVESの投票先のように、開示まで伏せたまま蓄積する値をここに置く。

設計上の要点は3つある。

* `handleAction` と `onDeadline` は純粋関数として書く。storage・WebSocket・時刻取得に触らない。副作用は共通コアが `GameTransition` を解釈して行う。これによりゲームルールをDOなしでユニットテストできる
* 乱数（配役シャッフル、バリアント抽選）は共通コアがシード付きで注入する。テストの再現性を確保するためである
* `validateContent` は `tools/` から呼ぶ。ランタイムのコードパスに検証を残さない
* `validateSettings` はランタイムで呼ぶ唯一の検証である。共通コアはバリデーションライブラリを持たず、`settings` を `unknown` のまま渡す（[ADR-0012](../adr/0012-ゲーム固有設定の検証をゲームモジュールに委ねる.md)）。設定を持たないゲームは常に成功を返す

## ディレクトリ構成

```text
shared/
├── core/            # Room, Player, Level, エンベロープ, 共通メッセージ
├── engine/          # 汎用前方推論エンジン(ゲーム非依存。ADR-0014)
└── games/
    └── detectives/  # ステージ定数, 秘密情報の型, 事件データスキーマ
server/
├── core/            # Worker routing, RoomDO(ゲーム非依存)
│   ├── registry.ts     # gameId -> GameModule のディスパッチテーブル(唯一の分岐点)
│   └── wrangler.jsonc
└── games/
    └── detectives/  # GameModule実装, validateContent(検証8項目)
client/
├── app/             # Viteエントリ。ゲーム画面テーブルを組み立ててcoreへ渡す
├── core/            # ホーム, ロビー, 接続管理, 共通UI, デザイントークン
└── games/
    └── detectives/  # ステージごとの画面
content/
└── detectives/      # 事件データJSON
tools/
└── validate-content.ts  # 各GameModuleのvalidateContentを呼び分けるCLI
```

`content/<gameId>/` の配下構造はゲームモジュールが決める。共通コアは走査してディレクトリ名をgameIdとして扱うだけである。

`client/app` を `client/core` から分けるのは、クライアントのゲームモジュールがデザイントークンと共通UIのために `client/core` へ依存し、`client/core` が画面を動的importすると循環するためである（[07](./07_リポジトリとツールチェーン.md)）。
サーバ側は `GameModule` が純粋関数で共通コアに依存しないため、この分離が要らない。

## ゲームを追加する手順

1. `shared/games/<id>/` に型とステージ定数を追加する（`shared/` 単独PR。[開発ガイド](../開発ガイド.md)の並行作業ルールに従う）
2. `server/games/<id>/` に `GameModule` の実装とユニットテストを追加する
3. `server/core/registry.ts` にエントリを1行追加する
4. `client/games/<id>/` にステージごとの画面を追加する
5. `content/<id>/` にコンテンツと検証プラグインを追加する
6. 共通コアに変更が必要になったら**実装を止めて本文書の境界定義の議論に戻す**。ゲーム追加のために共通コアへゲーム固有の概念を持ち込まない

手順6は分離を維持するための歯止めである。
共通コアの変更が本当に必要な場合は、本文書の境界表を更新し、既存ゲームへの影響を確認したうえで別PRで行う。

## 収録予定ゲームと共通コアへの要求

MVPはDETECTIVES 1本（[ADR-0005](../adr/0005-MVPはENGLISH-DETECTIVES.md)）。
以下は候補であり、DON'T SAY ITを除いて実装順も収録可否も未確定である。
DON'T SAY ITは2本目として収録すると決定済みである（[ADR-0019](../adr/0019-2本目のゲームをDONT-SAY-ITにする.md)、[実装計画](../実装計画/ゲーム構想20案の収録計画.md)のP1）。
境界設計が特定のゲームに寄っていないかの確認材料として記載する。

| ゲーム | 概要 | 共通コアへの追加要求 |
| --- | --- | --- |
| ENGLISH DETECTIVES | 質問と推理。証言の突き合わせで犯人を当てる | なし（MVPで実装） |
| DON'T SAY IT | 禁止語を避けて英語で人物を説明する。伝わったかで採点 | ロビーの表示と設定の記述子（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）。ゲーム固有の概念は持ち込まない |
| ENGLISH ESCAPE | 協力型。難度の異なる情報を統合して脱出する | なし（推論エンジンをコンテンツ検証に再利用） |
| LOST IN TRANSLATION | 伝言ゲーム。各自に異なる伝達制約が付く | 手番制（1人ずつ順に操作する進行）が必要 |
| BROKEN STORY | カードを引いて順に英文物語を継ぎ足す | 手番制が必要 |
| WORD BLACK MARKET | 単語の交渉・取引 | プレイヤー間の1対1やり取りが必要 |
| CORPORATE SURVIVAL | ビジネス英語の状況対応 | 未検討 |

手番制とプレイヤー間やり取りは現在の共通コア（全員同時 + 全員から1件収集）では扱えない。
必要になった時点で境界表を見直す。先回りして実装しない。

## テスト観点

* `GameModule` の純粋性: `handleAction` / `onDeadline` をDOなしで呼び、同じ入力に同じ出力が返ること
* 共通コアのゲーム非依存性: `registry.ts` 以外に `'detectives'` という文字列リテラルが現れないことをlintで検査する
* 秘密の非混入: `gameState`（公開状態）に秘密情報が入っていないこと。ゲームごとに常設する
* `validateSettings` の純粋性: 範囲外・型違い・欠損の各設定に対し、DOなしで拒否が返ること
