# 基本設計: リポジトリとツールチェーン

## 結論

pnpm workspaceのパッケージ境界で、共通コアとゲームモジュールの依存の向きを機械的に強制する。

パッケージは下表の18とし、`package.json` の `dependencies` に書かれていない参照はビルドが通らない状態にする。
package graphで表現できない制約（`registry.ts` だけがゲームモジュールを知ってよい、など）はESLintで補う。

型定義はビルドせずTypeScriptのまま参照する。バンドルはwranglerとViteが行う。

本文書はM0で確定させる宿題（[設計.md](../設計.md)、[開発ガイド](../開発ガイド.md)のコマンド表）に対する回答であり、実装の作業分解は [実装計画/M0.md](../実装計画/M0.md) を正とする。

## パッケージ構成

`pnpm-workspace.yaml` に登録するパッケージは次の18とする。

| ディレクトリ | パッケージ名 | 依存 |
| --- | --- | --- |
| `shared/core` | `@beb/shared-core` | なし |
| `shared/engine` | `@beb/engine` | なし |
| `shared/games/detectives` | `@beb/shared-detectives` | shared-core |
| `shared/games/dontsayit` | `@beb/shared-dontsayit` | shared-core |
| `shared/games/ranking` | `@beb/shared-ranking` | shared-core |
| `shared/games/whowrotethis` | `@beb/shared-whowrotethis` | shared-core |
| `server/core` | `@beb/server-core` | shared-core, server-detectives, server-dontsayit, server-ranking, server-whowrotethis |
| `server/games/detectives` | `@beb/server-detectives` | shared-core, shared-detectives, engine |
| `server/games/dontsayit` | `@beb/server-dontsayit` | shared-core, shared-dontsayit |
| `server/games/ranking` | `@beb/server-ranking` | shared-core, shared-ranking |
| `server/games/whowrotethis` | `@beb/server-whowrotethis` | shared-core, shared-whowrotethis |
| `client/core` | `@beb/client-core` | shared-core |
| `client/games/detectives` | `@beb/client-detectives` | shared-core, shared-detectives, client-core |
| `client/games/dontsayit` | `@beb/client-dontsayit` | shared-core, shared-dontsayit, client-core |
| `client/games/ranking` | `@beb/client-ranking` | shared-core, shared-ranking, client-core |
| `client/games/whowrotethis` | `@beb/client-whowrotethis` | shared-core, shared-whowrotethis, client-core |
| `client/app` | `@beb/client-app` | client-core, 各ゲームの client パッケージ |
| `tools` | `@beb/tools` | shared-core, engine, 各ゲームの shared / server パッケージ |

`content/` はパッケージにしない。JSONだけを置き、`tools` が読む。

ゲームを1本増やすと、`shared/games/<id>` `server/games/<id>` `client/games/<id>` の3つが加わり、`server-core` と `client/app` と `tools` の依存に1行ずつ増える。
4本目のWHO WROTE THIS?（[11](./11_WHOWROTETHISゲームモジュール.md)）の3パッケージを収録して18になった。
残るのは質問データ（`content/whowrotethis/`）であり、パッケージではない。

### `client/app` を分ける理由

クライアントのゲームモジュールは、デザイントークンと共通UI部品を使うため `client-core` に依存する（[02](./02_クライアント.md)）。
ここで `client-core` が画面を動的importするために `client-detectives` へ依存すると、2つのパッケージが相互に依存して循環する。

そのため、Viteのエントリを `client/app` として分離する。
`client/app` は `gameId → () => import('@beb/client-detectives')` のテーブルを組み立て、`client-core` へ渡す。
`client-core` は渡されたテーブルを引くだけで、どのゲームが登録されているかを知らない。

テーブルは3つある。ステージ画面（`gameScreens`）、遊び方（`gameGuides`）、ホスト画面のステージ表示文言（`gameStageLabels`）であり、後の2つはゲームモジュールの `./guide` / `./stage-labels` サブパスを指す（[02](./02_クライアント.md)）。

サーバ側は同じ問題が起きない。
`GameModule` は純粋関数であり、storage・WebSocket・時刻に触らないため `server-core` に依存しない（[05](./05_ゲームモジュール.md)）。
依存は `server-core → server-detectives` の一方向で閉じるため、エントリを分けずに `server/core/registry.ts` へ置く（ルートCLAUDE.mdの不変条件4）。

この非対称は、クライアントだけが見た目の共通資産を双方向に必要とすることから生じる。

### `server-core` がゲームモジュールに依存する件

`registry.ts` が `server/core/` にある以上、package graph上は共通コアがゲームモジュールへ依存する。
「共通コアはゲームを知らない」という不変条件を、package.jsonの依存だけでは表現できない。

この1点はESLintで補う。`server/core/` 配下で `@beb/*-detectives` をimportしてよいのは `registry.ts` だけとする。

### `tools` がサーバ側パッケージに依存する件

`validateContent` の実装は `server/games/detectives` にあるため、`tools` はそこへ依存する（[05](./05_ゲームモジュール.md)）。
`tools` はCIとローカルでのみ動き、Workerのバンドルには入らない。
`GameModule` が純粋関数である限りこの依存は安全であり、逆向き（`server` が `tools` を参照する）が発生しないことをlintで禁じる。

### 推論エンジンを独立パッケージにする件

汎用前方推論エンジンは `shared/engine` に置き、`server/games/<id>` と `tools` の双方から参照する（[ADR-0014](../adr/0014-推論エンジンを独立パッケージにする.md)）。

エンジンを `tools` の中に置くと、`validateContent` の実装（`server/games/<id>`）がエンジンを使うために `tools` を参照することになり、上の一方向の依存と循環する。
`shared/engine` はどのパッケージにも依存しないため、`engine ← server-detectives ← tools` の順で閉じる。

このパッケージは `server/games/<id>` 経由でWorkerのバンドルに入る。ランタイムでは呼ばないが、Node固有のAPIに触れてはならない。

## TypeScriptの構成

* 各パッケージの `exports` は `./src/index.ts` を直接指す。`shared/` を事前ビルドしない。wranglerとViteがTypeScriptをそのまま解決する
* `tsconfig.base.json` をルートに置き、各パッケージが `extends` する
* `strict: true`、`noUncheckedIndexedAccess: true`、`module`/`moduleResolution` は `bundler` とする
* 型チェックは各パッケージの `tsc --noEmit` で行う。project referencesは使わない（ビルド成果物を持たないため）
* `shared/` に `any` を書かない。外部入力（WebSocket受信値）は `unknown` で受け、検証してから型を付ける

## テスト

| 対象 | ランナー | 理由 |
| --- | --- | --- |
| `shared/*`, `tools` | vitest（Node環境） | Workers APIに触れない |
| `server/games/*` | vitest（Node環境） | `GameModule` は純粋関数のためDOが要らない |
| `server/core` | vitest + `@cloudflare/vitest-pool-workers` | DO・Hibernation・アラームの検証が必要 |
| `client/*` | Playwright | 画面の同期はブラウザを複数立てないと確認できない |

`server/core` のテストはスタブ `GameModule` だけで全ライフサイクルを通す（[01](./01_サーバ.md)）。
このテストが `@beb/server-detectives` をimportしていたら分離が壊れている。

## Lintで強制する不変条件

ドキュメントに書いただけでは守られない制約を、機械検査へ落とす。

| # | 検査内容 | 手段 |
| --- | --- | --- |
| 1 | `server/core/` でゲームモジュールをimportできるのは `registry.ts` だけ | `no-restricted-imports`（ファイル単位のoverride） |
| 2 | `shared/core/` `client/core/` はゲームモジュールをimportしない | `no-restricted-imports` |
| 3 | gameIdの文字列リテラルは `registry.ts` と `client/app` にのみ現れる | `no-restricted-syntax`（`Literal` の値一致） |
| 4 | `server/` で WebSocketの `.accept()` を呼ばない（Hibernation必須） | `no-restricted-syntax`（`CallExpression` のプロパティ名一致） |
| 5 | Svelte 4系のレガシー構文を使わない | Viteの `dynamicCompileOptions` によるrunesモードの強制。コンパイラが弾かない構文だけESLintで補う（[ADR-0010](../adr/0010-Svelte5とrunes構文の採用.md)） |
| 6 | `wrangler.jsonc` に `new_classes` が現れない（無料プランでデプロイ不能になる） | CIでの文字列検査 |
| 7 | `server/` で `@beb/tools` をimportしない（依存の逆流） | `no-restricted-imports` |
| 8 | `shared/engine/` が `@beb/*` をimportしない（エンジンのゲーム非依存、[ADR-0014](../adr/0014-推論エンジンを独立パッケージにする.md)） | `no-restricted-imports` |

検査1と検査3の対象は、`eslint.config.js` の `GAME_IDS` を正とする。
ゲームを追加したらこの一覧へ1行足す。
検査をゲームごとに複製すると、追加のたびに規則が増え、片方だけ更新される。

\#3と\#4はESLintの構文一致で書けるため、カスタムプラグインを作らない。

\#5をESLintで行わないのは、`eslint-plugin-svelte` の公式ルール一覧にレガシー構文を禁止するルールがないためである。
runesモードでは `export let` と `$:` がビルドエラーになる。`on:` と `<slot>` が同様に弾かれるかは未検証であり、PR0で実測して不足分をESLintで補う。

\#6はJSONの構造検査ではなく文字列検査で足りる。誤検出したらコメントの書き方を変える。

秘密情報が `state` に混入しないことはlintで検出できない。DO統合テストで担保する（[01](./01_サーバ.md)、[開発ガイド](../開発ガイド.md)）。

## wrangler設定

`server/core/wrangler.jsonc` に置く。パッケージのルートに置くことで `pnpm --filter @beb/server-core` から実行できる。

宣言する内容は次の通り。

* `migrations` は `new_sqlite_classes: ["RoomDO"]`。`new_classes` は使わない（[ADR-0002](../adr/0002-CloudflareDurableObjects採用.md)）
* `durable_objects.bindings` に `RoomDO` を1つ
* `assets` にクライアントのビルド成果物のディレクトリを指定し、`run_worker_first: true` を付ける。
  既定では拡張子を持たないパス（`/room/:code` 等のSPA内部ルート）がWorkerより先にアセット側の
  自動ルーティングで処理され、`html_handling` の正規化リダイレクトによりSPAとして開けない
  （PR3で実測）。Workerを常に先に通し、`server/core/src/index.ts` 側でSPAフォールバック
  （拡張子を持たないパスは `env.ASSETS.fetch()` で `/` の内容を返す）を自前で行う
* `ratelimit` バインディングを2つ。`namespace_id` は `"1001"`（`POST /api/rooms` 用）と `"1002"`（WSルート用）とする
* `compatibility_date` は `"2026-08-13"` とする。変更するPRでは理由を書く
* `observability` を有効にする。既定は無効であり、無効のままだと本番障害時にルートの例外が一切残らない
* 名前付き環境（`env.dev` / `env.production`）を使わない。環境は1つとする

### Cloudflareアカウントの共有

同じCloudflareアカウントで別プロジェクト（BEB-Raid）が稼働している。

ローカルの認証はマシン単位で保存されており（`%APPDATA%` 配下の wrangler 設定）、リポジトリごとの `wrangler login` は要らない。
BEB-Raidで認証済みの端末では、本プロジェクトの `wrangler` がそのまま同じアカウントを見る。

`account_id` を `wrangler.jsonc` に書かない。
トークンに紐づくアカウントが1つであれば省略でき、CIへはシークレット経由で渡す。

共有してはならないものが3つある。

| 対象 | 理由 |
| --- | --- |
| Worker名 | 同名だと相手のWorkerを上書きする。本プロジェクトは `beb-party` を使う |
| Durable Objectのバインディングとmigrationsタグ | Workerごとに独立しており、流用の余地がない |
| Rate Limitingの `namespace_id` | 同じidを別のWorkerで使うとレート制限のカウンタが共有される。BEB-Raidは Rate Limiting API を使っていないため現時点で衝突はないが、採番の重複を避けるため本プロジェクトの使用値を上表に固定する |

名前付き環境を使わないのは、BEB-Raidが `--env` の指定漏れで本番Workerを上書きする経路を踏んでいるためである。
本プロジェクトはデプロイ先が1つしかなく、名前付き環境を導入しなければこの事故経路自体が存在しない。

### フォントとサブセット化

書体2種は [ビジュアルデザイン.md](../ビジュアルデザイン.md) の指定に従い、`google/fonts` リポジトリの `ofl/` 配下から取得する。

サブセット化には `subset-font`（BSD-3-Clause）を使う。
harfbuzzのwasmビルドを同梱しており、Pythonや system-level のツールを必要としないため、GitHub Actionsで追加のセットアップなしに動く。

Reserved Font Nameの有無は書体ごとに異なる。

* Dela Gothic One: 指定なし（`ofl/delagothicone/OFL.txt` で確認済み）
* M PLUS Rounded 1c: **未確認**。取得時に同梱の `OFL.txt` を読み、指定があればサブセット後のフォント内部名を変更する

指定がある書体の内部名をそのまま使うとOFL違反になる。確認をPR3のチェック項目とする。

## コマンド

ルートの `package.json` に定義する。ルートCLAUDE.mdのコマンド表は、PR0のマージ時にこの表で更新する。

| コマンド | 実体 |
| --- | --- |
| `pnpm dev` | `client/app` のVite devサーバと `server/core` の `wrangler dev` を並行起動する |
| `pnpm check` | 全パッケージの ESLint と `tsc --noEmit` |
| `pnpm test` | 全パッケージのvitest |
| `pnpm e2e` | Playwright。webServerとして `pnpm e2e:server` を自動起動する |
| `pnpm e2e:server` | E2E用のサーバ。`client/app` をビルドし、`wrangler dev` を監督プロセス下で起動する |
| `pnpm validate:content` | `tools` のコンテンツ検証CLI。引数にファイルパスを渡すとその1件だけを検証する（執筆時の確認用） |

E2Eのサーバを `pnpm dev` と分ける理由、および監督プロセス（`scripts/e2e-server.mjs`）を置く理由は [ADR-0021](../adr/0021-E2Eのwrangler-devは監督プロセスで再起動する.md) を正とする。
`wrangler dev` がProxyWorkerの `Network connection lost.` でプロセスごと終了する未修正の上流バグ（[workers-sdk#15203](https://github.com/cloudflare/workers-sdk/issues/15203)）を踏むため、終了を検知して再起動する。

サーバの出力はPlaywrightの `stdout: "pipe"` でCIログへ出す。
プロセスがテスト中に終了した場合、既定の設定（stdoutを破棄）では原因が残らないためである。
ログ量を抑えるため、E2E用の起動は `--log-level warn` とし、リクエスト単位のログを出さない。

生成物を作るコマンドは各パッケージに置く。いずれも生成物をコミットし、CIで再生成との差分を検査する。

| コマンド | 実体 |
| --- | --- |
| `pnpm --filter @beb/server-detectives run generate:cases` | `content/detectives/` を走査して `src/cases.generated.ts` を作る |
| `pnpm --filter @beb/server-dontsayit run generate:sets` | `content/dontsayit/` を走査して `src/sets.generated.ts` を作る |
| `pnpm --filter @beb/client-app run fonts:generate` | UI文言・カタログの文言・`content/` 配下すべての日本語からフォントをサブセット化する |

## CI

GitHub Actionsで全PRに対して実行する。ジョブの構成は次の通り。

1. 依存の導入（`pnpm install --frozen-lockfile`）
2. `pnpm check`
3. `pnpm test`
4. `pnpm e2e`（Playwright。ブラウザは `playwright install --with-deps chromium` で用意する）
5. 失敗時のみ、Playwrightのレポートとトレースを `actions/upload-artifact` で保存する（保持7日）
6. `pnpm validate:content`
7. 事件インデックス（`cases.generated.ts`）の再生成と差分チェック
8. お題インデックス（`sets.generated.ts`）の再生成と差分チェック
9. フォントサブセットの再生成と差分チェック
10. `wrangler.jsonc` の文字列検査（`new_classes` の不在）
11. `main` へのマージ時のみ `cloudflare/wrangler-action@v3` でデプロイ（`dev` へのマージではデプロイしない）

5はE2Eの失敗調査のために置く。
E2Eはアプリの不具合だけでなくサーバプロセスの死亡でも落ちるため、実行ログの `ERR_CONNECTION_REFUSED` だけでは原因を切り分けられない。

デプロイに必要なGitHub Secretsは `CLOUDFLARE_API_TOKEN`（権限は「Edit Cloudflare Workers」）と `CLOUDFLARE_ACCOUNT_ID` の2つとする。
ローカルのOAuth認証はCIから使えないため、これは別に用意する必要がある。
トークンはアカウント単位の権限であり、BEB-Raidで使っているものと同じ値を使えるが、GitHub Secretsはリポジトリ単位のため本リポジトリへの設定が要る。

シークレットが未設定の場合、デプロイをスキップしてワークフローを成功として終える。
リポジトリ作成直後やシークレットを失った場合に、CIが恒常的に赤くなるのを避けるためである。
スキップしたことは `::notice::` でログに残す。

3はM0時点で検証対象が存在しなかった。
`content/<gameId>/` ディレクトリ自体が無い場合はスキップし、ディレクトリがあって0件の場合はエラーとする（[04](./04_事件データと検証.md)）。
M0では `content/detectives/` を作らない。

4はM1以降に意味を持つが、M0から有効にしておく。事件追加PRで再生成を忘れる経路を最初から塞ぐためである。

## バージョン固定

| 対象 | 値 | 固定場所 |
| --- | --- | --- |
| Node.js | 24系（Active LTS） | `.node-version`。CIも同じ値を読む。開発機にはvoltaが入っているため `volta install node@24` で切り替える |
| pnpm | 11系 | `package.json` の `packageManager` |
| TypeScript | 6系 | 各パッケージのdevDependencies |
| ESLint | 10系 | ルートのdevDependencies |
| vitest | 4系 | ルートのdevDependencies |

TypeScript・ESLint・vitestの系列を上記にするのは、同じアカウントで運用している別プロジェクト（BEB-Raid）と揃えるためである。
2つのリポジトリを行き来する際に設定の書き方が変わると、移植した設定が静かに壊れる。

### npmではなくpnpmを使う理由

BEB-Raidはnpm workspacesを使っているが、本プロジェクトはpnpmを維持する。

npm workspacesは依存を巻き上げるため、`package.json` に書いていないパッケージへの `import` も解決してしまう。
本文書の不変条件「依存関係を `package.json` に書かずにimportしない」が、npmでは強制できない。

pnpmは各パッケージの `node_modules` を隔離するため、宣言のない依存は解決時点で失敗する。
共通コアとゲームモジュールの分離（[ADR-0009](../adr/0009-部屋基盤とゲームモジュールの分離.md)）が本プロジェクトの中心的な制約であり、それを型検査より前の段階で守れることを優先する。

## 不変条件

* パッケージの依存関係を `package.json` に書かずにimportしない。相対パスでワークスペースをまたがない
* `server/core` のテストがゲームモジュールをimportしない
* `client/core` がどのゲームが登録されているかを知らない。テーブルは `client/app` が渡す
* Workerのバンドルに `tools` とテストコードを含めない
* lintルールの追加・削除は、対応する不変条件の出典（ADRまたは基本設計）をコメントで示す。理由の書かれていないルールは後で消される
