# 基本設計: 推論エンジンと検証アルゴリズム

## 結論

推論エンジン（`tools/engine`）は「事実の集合と規則の集合から、到達できる結論の集合を求める」だけの汎用推論器とする。

犯人・嘘・証言といったDETECTIVESの語彙をエンジンに持ち込まない。
事件データの検証はエンジンの上に載る `GameModule.validateContent` の実装であり、検証項目の意味はゲームモジュール側にある。

検証は7項目とし、バリアント1つを1つの検証インスタンスとして独立に判定する。
5人版は6人版のデータから機械的に導出し、導出後のインスタンスにも同じ7項目を課す。

事件データの形式と制作手順は [04_事件データと検証.md](./04_事件データと検証.md)、共通コアとゲームモジュールの境界は [05_ゲームモジュール.md](./05_ゲームモジュール.md) を正とする。
本文書は「どう判定するか」を定め、04は「何を・なぜ検証するか」を定める。

## エンジンの責務範囲

### データモデル

エンジンが扱うのは文字列シンボルの集合と規則の集合だけとする。

```typescript
// 規則: 前提がすべて揃えば結論を1つ導く
interface Rule {
  id: string;
  requires: string[];
  yields: string;
}

// 到達集合の計算
function saturate(initial: Set<string>, rules: Rule[]): Saturation;

interface Saturation {
  reached: Set<string>;        // 到達したシンボル(initialを含む)
  fired: string[];             // 発火した規則のid
  support: Map<string, string[]>; // シンボル -> それを導いた規則のrequires
}
```

事件データの `facts[].value` と `contradictions[].yields` が、そのままシンボルになる。
`contradictions` が `Rule` になる。

エンジンは `value` の文字列を解釈しない。
`customer_in_red_left_at=14:10` は等号を含むが、エンジンにとっては不透明な識別子であり、時刻の比較も含意の判定も行わない。
証言どうしの意味的な矛盾は、事件データの作者が `contradictions` として明示的に書く。

### 推論の意味論

`requires` の全要素が現在の集合に含まれる規則を発火させ、`yields` を集合へ加える。
追加がなくなるまで繰り返す（不動点）。

`requires` の要素は、事実の `value` だけでなく、他の規則の `yields` でもよい。
多段の推論を許すのは、この エンジンをESCAPEの解法グラフ検証と共用するためである（[構想v2](../構想v2.md)）。
単発の集合包含判定に制限すると、段階的に情報が開く形式のコンテンツを検証できない。

DETECTIVESの事件データが多段推論を使うかは事件ごとの自由とする。
現行のスキーマ例は `requires` に事実のみを並べているが、これは制約ではない。

### 停止性と決定性

到達集合は単調増加し、シンボルの種類は事件データ内で有限であるため、反復は必ず停止する。

同じ入力に対する出力は規則の評価順に依存しない。
不動点は集合演算の結果であり、どの順で発火させても同じ集合に到達する。
`fired` の並び順だけは評価順に依存するため、反例出力では規則idの昇順に整列してから表示する。

無限ループが起きないことをコードの構造で保証できないため、反復回数の上限を「規則数」とし、超過した場合は検証エラーとして落とす。
正常なデータでは、1反復につき最低1つの規則が発火するため、規則数を超える反復は起こらない。

### 必須性の判定

「ある要素を取り除くと目標に到達しなくなるか」の判定は、コンテンツの種類に依存しないためエンジン側に置く。

```typescript
function isRequired(
  initial: Set<string>, rules: Rule[], goal: string, drop: string[]
): boolean;
```

`drop` に指定したシンボルを `initial` から除いて再計算し、`goal` に到達しなくなれば `true` を返す。
検証2（全員必須）と検証5（未使用なし）はどちらもこの関数で表現する。

## DETECTIVESの検証アルゴリズム

### 検証インスタンスの構成

バリアント1つと人数版1つの組を、1つの検証インスタンスとする。
バリアントを同時に投入しない。犯人が誰かは1回のプレイで1人だけであり、複数バリアントを混ぜた集合は実際のプレイに存在しない。

インスタンスの入力集合は次の手順で作る。

1. 全キャラクターの全 `facts` の `value` を集める
2. 当該バリアントの `lie.replaces` が指す事実を集合から外し、代わりに `lie.value` を入れる
3. 規則集合は当該バリアントの `contradictions` とする（他バリアントの `contradictions` は含めない）

この入力集合を「嘘あり集合」と呼ぶ。
手順2を行わない集合を「正直集合」と呼ぶ。検証4で使う。

### 検証7項目

| # | 検証 | 判定 |
| --- | --- | --- |
| 1 | 可解性 | 嘘あり集合の到達集合が、当該バリアントの `contradictions` の `yields` を1つ以上含む |
| 2 | 全員必須 | 犯人以外の各キャラクターについて、そのキャラクターが所有する全事実を除くと検証1が不成立になる |
| 3 | 単独不可 | 発火した各規則の `requires` を推移的に展開し、犯人以外が所有する事実が2つ以上、かつその所有者が2人以上 |
| 4 | 冤罪なし | 正直集合の到達集合が `yields` を1つも含まない |
| 5 | 未使用なし | 各事実が、少なくとも1つのインスタンスで発火した規則の推移的な `requires` に現れる |
| 6 | 表示完全性 | 全事実（嘘を含む）の `text` にレベル1〜5すべてと `hintJa` があり、`briefing` / `reveal` / `keyExpressions` が揃っている |
| 7 | バリアント非干渉 | あるバリアントの嘘あり集合に他バリアントの `contradictions` を適用しても、`yields` が1つも導出されない |

各項目の判定手順のうち、誤解しやすいものを以下に定める。

#### 検証2の「除く」の単位

キャラクター単位で除く。そのキャラクターが `owner` である事実の `value` をすべて `drop` に渡す。
事実1枚ずつではない。
実プレイで起きるのは「その人が寡黙で何も話さない」であり、特定の1枚だけ黙る状況ではないためである。

犯人自身を除いたケースは検査対象から外す。
犯人を除くと嘘の事実も消え、検証1は必ず不成立になる。これを合格として数えると、検証2は犯人以外の必須性を何も保証しないまま通る。

#### 検証3の推移的展開

発火した規則の `requires` に他の規則の `yields` が含まれる場合、その規則の `requires` も展開して事実まで辿る。
展開後の事実集合について、犯人以外が所有するものを数える。

多段推論を使う事件で展開を行わないと、直接の `requires` が1件でも合格してしまう。

#### 検証5の「寄与」

「発火した規則の推移的な `requires` に現れること」を寄与とする。
「除くと解けなくなること」ではない。

後者を採ると、同じ情報を2人が持つ冗長な証言が不合格になる。
ただし検証2がキャラクター単位の必須性を要求するため、キャラクターをまたぐ完全な冗長は結果的に成立しない。
検証5が検出するのは、同一キャラクターが持つ使われない事実である。

判定は全バリアントを通した和で行う。バリアントごとに使う事実は異なるためである。

#### 検証7の必要性

検証1と検証4だけでは、犯人の一意性を保証できない。

検証1はバリアントVの入力でVの矛盾が発火することを見る。
検証4は正直な証言だけでは何も発火しないことを見る。
どちらも「Vが犯人の回に、Wを指す矛盾も同時に発火する」事件を検出しない。

この事件は実プレイで、犯人ではないWが開示のたびに黒く見える形で破綻する。
検証7は、各バリアントの嘘あり集合に対して他の全バリアントの `contradictions` を適用し、1つも発火しないことを確認する。

## 5人版の導出手順

6人版のデータを原本とし、5人版は次の順で機械的に導出する。順序が結果に影響する。

1. `merge5p` が非nullのキャラクターXを、指定先Yへ統合する。Xはキャラクター一覧から消える
2. Xが `owner` である全事実の `owner` をYに付け替える。事実のidと `value` は変更しない
3. 各 `contradictions` について、`requires5p` が非nullならそれを `requires` として使う。nullなら `requires` をそのまま使う
4. `culprit` がXであるバリアントを5人版から除外する

手順1と2の後に手順3を適用するのは、`requires5p` が統合後の所有関係を前提に書かれるためである。

手順4でXのバリアントを除外するのは、Xというキャラクターが5人版に存在しないためである。
統合先Yのバリアントとして読み替える案は、Yのバリアントと重複するため採らない。

その結果、5人版のバリアント数は6人版より少なくなる。
04の「バリアント数がキャラクター数と一致しない場合は警告する」リントは6人版に対してのみ適用する。

統合によって、ある規則の `requires` に含まれる事実の所有者が犯人以外1人になり、かつ `requires5p` が未指定の場合は検証エラーとする（[04](./04_事件データと検証.md)）。

## 反例出力

検証失敗時は、失敗したインスタンスの識別と反例を出力し、非0で終了する。

インスタンスの識別は「事件id / バリアントの `culprit` / 人数版（6p または 5p） / 検証項目番号」の4点を必ず含める。

反例として出す情報は項目ごとに異なる。

| 項目 | 出力する反例 |
| --- | --- |
| 1 | 到達集合と、発火しなかった規則ごとの不足シンボル |
| 2 | 除いても検証1が成立してしまったキャラクターid |
| 3 | 該当規則のidと、展開後の事実の所有者一覧 |
| 4 | 発火した規則のidと、その `requires` を満たした事実のid |
| 5 | どのインスタンスでも使われなかった事実のid |
| 6 | 欠けているフィールドのJSONパス |
| 7 | 干渉したバリアントの `culprit` と、発火した規則のid |

不足シンボルを出すのは、事件データの修正で最も知りたいのが「あと何があれば導出できたか」だからである。
到達集合だけを出すと、作者が差分を手で取ることになる。

## 不変条件

* エンジンにDETECTIVESの語彙（犯人・嘘・証言・キャラクター）を持ち込まない。エンジンが扱うのはシンボルと規則だけとする（[ADR-0009](../adr/0009-部屋基盤とゲームモジュールの分離.md)）
* エンジンは `value` の文字列構造を解釈しない。等号・時刻・場所の意味を推論規則として内蔵しない
* 検証はランタイムのコードパスに置かない。`validateContent` は `tools/` からのみ呼ぶ（[05](./05_ゲームモジュール.md)）
* 検証項目を事件データ側の都合で緩めない。5人版だけ項目を減らすことをしない
* 検証が対象0件で終了した場合はPASSではなくエラーとする（[04](./04_事件データと検証.md)）

## テスト観点

エンジンとDETECTIVESの検証は別々にテストする。

エンジン（`tools/engine`、DETECTIVESを一切importしない）。

* 不動点: 多段の規則を含む入力で、規則の並び順を変えても同じ到達集合になること
* 停止性: `yields` が自分の `requires` に含まれる規則（自己参照）を与えても停止し、反復上限で落ちること
* `isRequired`: 単一経路の入力で必須と判定され、2経路ある入力で不要と判定されること
* `support`: 到達したシンボルから、それを導いた規則を辿れること

DETECTIVESの検証（`server/games/detectives/` または `tools/`）。

* 7項目それぞれについて、意図的に違反させた事件データを用意し、その項目だけが落ちること
* 検証2で犯人自身が検査対象から除かれていること（犯人を除いたケースを合格として数えると項目全体が無意味になる退行の検出）
* 検証7で、2つのバリアントが同じ `contradictions` を共有する事件が落ちること
* 5人版導出: 統合後に所有者が1人になる規則を持ち `requires5p` が未指定の事件が、検証エラーになること
* 反例出力: 各項目の失敗で、上表の情報が欠けずに出ること
