# 基本設計: MIND MELDゲームモジュール

## 結論

MIND MELDは4ステージ（`briefing` / `input` / `reveal` / `debrief`）を持つ4〜8人用のチーム対抗戦のゲームモジュールであり、`GameModule` インターフェースの実装として完結する。

参加者は2人ずつのペアに分かれる。
お題（`Something in a kitchen` など）に対し、ペアの2人が英単語を1語ずつ画面上で同時に出し、2人の語が一致すれば成功とする。
一致しなければ、次は2人の語の両方につながる1語を同時に出す。

1つのお題で語を出せるのは最大4回であり、少ない回数で一致したペアほど高い点を得る。
お題は4つ続け、合計点の高いペアが勝つ。

全ペアの語は、全員の提出が揃った時点で一斉に開示する。
一致の判定は照合キー（大文字小文字と区切りを落とした文字列）の一致で行い、英語の意味を解釈しない（不変条件1）。
複数形やつづりの英米差のように照合キーが一致しない語は、ペアが「同じ語」と申告し、他のペアが異議を出して決める。

奇数の人数では3人組を1つ作り、3人組は試行ごとに語を出す2人を交代する。
チームは `start()` で `formBalancedTeams` を使って編成し、全員に公開する（[ADR-0032](../adr/0032-チーム編成は自己申告レベルで揃えて開始時に抽選する.md)）。

gameIdは `mindmeld` とする。
`dontsayit` や `escapecall` と同じく、空白を落として連結する規則を適用する。

共通コアへの追加要求はない。
チーム編成は共通コアの既存部品（`shared/core/src/teams.ts` の `formBalancedTeams`）で足り、全員同時の提出と収集、秘密情報の全量の送り直しという既存の形に載る。

草案の段階で未決として残したルール判断は、2026-11-12にユーザーが判断して確定し、本文の該当節に反映した。
表記ゆれを申告と異議で補い、申告を近い語に限る判断は [ADR-0034](../adr/0034-MINDMELDの表記ゆれは申告と異議で補い申告を近い語に限る.md) に記録する。

原案は [ゲーム構想.md](../ゲーム構想.md) の案31であり、原案から変更した点は末尾の「原案からの変更」に列挙する。

共通コアとの境界は [05](./05_ゲームモジュール.md)、メッセージの意味は [03](./03_プロトコル.md) を正とする。

## ステージ

| stage | 締切 | 遷移条件 |
| --- | --- | --- |
| `briefing` | 90秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `input` | `inputSeconds`（既定30秒） | この試行で語を出す人のうち、接続中の全員が `submit` を送る、または締切到達 |
| `reveal` | 30秒（`REVEAL_SECONDS`） | 接続中の全員が `ready` を送る、または締切到達 |
| `debrief` | なし | 遷移しない（`lifecycle: finished`） |

`input` と `reveal` の1往復を**試行**と呼ぶ。
1つのお題で最大 `MAX_ATTEMPTS`（4）回の試行を行い、お題を `MAX_ROUNDS`（4）個続ける。
お題1個ぶんの試行の列を**ラウンド**と呼ぶ。

お題ごとにステージを分けない。
ラウンドの切り替えは `reveal` から次のラウンドの `input` へ進むときに公開状態の `roundIndex` を進めて表す。
お題の結果は `reveal` の画面で示せるため、お題の結果だけを見せるステージを置く理由がない。

`briefing` の締切を90秒とするのは、近い語の申告と異議の手順、入力中に語を口に出さない約束を読む時間を取るためである。
最初のお題は `briefing` では公開せず、最初の `input` で公開する。

`reveal` で申告を受理したときは、締切を `REVEAL_SECONDS` に置き直す（「近い語の申告と異議」）。

Wake Lock は取得しない。
`input` は入力で画面に触り続け、`reveal` は30秒で終わるため、画面に触らない時間が長く続くステージがない。

## 語の扱い

### 正規化

提出は、判定と保存の前に次の順で正規化する。

1. Unicode正規化（NFKC）をかける
2. 書式制御文字（Unicodeの一般カテゴリ `Cf`）を取り除く
3. 曲がった引用符（`‘` `’`）を直線の `'` へ置き換える
4. 空白文字の連続を半角空白1つへ畳み、前後の空白を落とす
5. 前後にある英字以外の文字（`!` `.` `"` など）を落とす
6. 英字を小文字にする

手順1〜4は [14](./14_SECRETRULEゲームモジュール.md) の「正規化」と同じであり、手順5と6を足す。
正規化後の文字列を**表示形**と呼び、保存と開示と結果はすべて表示形で行う。

手順5を置くのは、`cook!` や `"cook"` のように記号を付けた語を、記号の無い語と同じ語として受けるためである。
1語の提出では、記号に意味を持たせる理由がない。

手順6で小文字にそろえるのは、開示の画面で `Cook` と `cook` が並んだときに、一致した語が違う語に見えるのを避けるためである。
固有名詞（`Japan`）も小文字で表示する。

表示形は次の条件を満たさなければならない。

* 英字（`a`〜`z`）、半角空白、ハイフン、アポストロフィだけからなる
* 半角空白で区切った要素が2つ以下
* 文字数が24以下
* 照合キー（次節）が2文字以上20文字以下

要素を2つまで許すのは、`ice cream` や `hot dog` のように空白を含む語をお題の答えとして書けるようにするためである。
3つ以上を許すと、1語ではなく句を出す提出を受けることになる。

かなや漢字を含む提出は、手順1〜6の後も英字以外の文字が残るため受理しない。
日本語入力のまま送った語が、英語の語として扱われることはない。

### 照合キー

表示形から半角空白、ハイフン、アポストロフィを取り除いたものを**照合キー**と呼ぶ。
2人の語の照合キーが一致すれば、その試行は一致とする（「完全一致」）。

区切りを落とすのは、`ice cream` と `ice-cream` と `icecream` を同じ語として扱うためである。
落とした結果として `we'll` と `well` も同じ照合キーになるが、どちらもお題の答えとして出る見込みは低く、許容する。

照合キーの計算は文字の削除と比較だけであり、英語の意味を解釈しない（不変条件1）。

正規化、照合キー、次節の「近い語」の判定、文字数の上限は `shared/games/mindmeld/` に置く。
クライアントの入力欄が、送信前に表示形の条件と使用済みの語を確かめるためである（[14](./14_SECRETRULEゲームモジュール.md) の `shared/games/secretrule` と同じ分け方）。

### 使用済みの語

ラウンドの中で、次のいずれかと照合キーが一致する語は出せない（`used_word`）。

* そのラウンドのお題の英文に含まれる語
* そのラウンドで開示済みの語。自分のペアの語に限らず、全ペアの語を含む

開示済みの語を禁止しないと、つなぎの1語として「相手が前に出した語」を2人とも出せば必ず一致する。
自分の語を出すか相手の語を出すかの取り決めを1つ作るだけで、連想を寄せる工程が消える。

他のペアの語まで禁止するのは、先に一致したペアの語を2人で写して一致させる経路を塞ぐためである。
お題の語を禁止するのは、`Something in a kitchen` に `kitchen` と答えるような、お題を読み返すだけの一致を除くためである。

お題の英文の語には `a` や `in` も入るが、照合キーが2文字以上の語だけが対象であり、答えとして出る見込みが低い語の禁止は遊びに影響しない。

禁止はラウンドの中に限る。
次のラウンドでは、お題が変われば同じ語を出してよい。

禁止する照合キーの一覧は公開状態の `usedKeys` に載せる。
クライアントは送信前にこの一覧で確かめ、入力中に「使用済み」と示す。

### 近い語の申告と異議

照合キーが一致しない2語のうち、次の条件を満たすものを**近い語**と呼ぶ。

* 短い方の照合キーが3文字以上であり、かつ次のいずれかに当たる
  * 一方の照合キーが他方の先頭部分であり、長さの差が3文字以下（`apple` と `apples`、`bus` と `buses`、`child` と `children`）
  * 編集距離（1文字の挿入、削除、置換の最小回数）が1（`color` と `colour`、`man` と `men`）
  * 短い方が5文字以上であり、編集距離が2（`theater` と `theatre`、`knife` と `knives`）

近い語になったペアは、`reveal` の間に「同じ語」と**申告**できる。
申告はペアの誰か1人が送れば成立する。

申告に対し、そのペアに属さない参加者は**異議**を出せる。
`reveal` を終えるとき、接続中の異議の数が、接続中の判定者（申告したペアに属さない参加者）の数の半分を超えていれば申告を退け、そうでなければ認める。
認めた申告は完全一致と同じ点を得る。

判定者が4人なら3人以上、2人なら2人の異議で退ける。
4人で遊ぶと判定者は相手ペアの2人だけであり、1人の異議では退けられない。
判定者が0人のとき（他の全員が切断している）は申告を認める。

近い語を機械で一致とみなさないのは、`cat` と `car`、`new` と `news` のように、近い語の中に別の語が混ざるためである。
どれが同じ語かは英語の意味で決まり、アプリには決められない（[ADR-0001](../adr/0001-ランタイムAI不使用.md)）。

近い語に限って申告を受けるのは、`pan` と `cook` のような明らかに違う語を申告し、異議が揃わないことに賭ける経路を塞ぐためである。
近い語の条件は文字列の比較だけで決まり、申告できるかどうかの門としてだけ使う。
一致の判定そのものは、完全一致か、人の申告と異議で決まる。

この門がアプリは英語を理解しないという不変条件1に抵触しないと判断した根拠は、[ADR-0034](../adr/0034-MINDMELDの表記ゆれは申告と異議で補い申告を近い語に限る.md) に書く。

近い語の条件で拾えない語形の違い（`mouse` と `mice`、`foot` と `feet`）は申告できない。
取りこぼしは不規則な複数形の一部に限られ、許容する。

申告の基準は `briefing` と `reveal` の画面に常に出す。
基準は「複数形、つづりの英米差、1〜2文字の打ち間違いは同じ語として認める。意味の違う語は認めない」とする。

申告を受理したら、締切を `REVEAL_SECONDS` に置き直し、全員の `ready` を解除する。
締切の直前に申告すると判定者が異議を出す時間が無く、過半数の異議が揃わないまま申告が通るためである。
共通コアは締切を「適用時刻 + 秒数」で置き直すため（[13](./13_ESCAPECALLゲームモジュール.md) の「誤答に時間の罰則を置かない」）、置き直しで締切が早まる場合もある。

申告は1つの試行でペアごとに1回までであり、延長の回数はペアの数で頭打ちになる。

異議の多数決には、敵対するペアが正当な申告を退ける余地が残る。
基準を画面に出し、誰が異議を出したかを公開状態と結果に残して、場の目で抑える。

異議を退けられたペアへの罰点のような機械の抑止は置かない。
罰点を与えるには「その異議が誤りだった」を誰かが判定する必要があり、判定の工程がもう1段増えるためである。

## 進行の要点

### チームの編成と3人組

`start()` で、人数から人数構成を決めて `formBalancedTeams(players, sizes, random)` を呼ぶ（[ADR-0032](../adr/0032-チーム編成は自己申告レベルで揃えて開始時に抽選する.md)）。

| 人数 | `sizes` | チーム数 |
| --- | --- | --- |
| 4 | `[2, 2]` | 2 |
| 5 | `[2, 3]` | 2 |
| 6 | `[2, 2, 2]` | 3 |
| 7 | `[2, 2, 3]` | 3 |
| 8 | `[2, 2, 2, 2]` | 4 |

チームは公開状態の `teams` に載せ、全員に公開する。
チームを伏せる理由がなく、開示の画面でどの語がどのペアの語かを示す必要があるためである。

チームには `A` から順にラベルを付ける。
ラベルは `formBalancedTeams` が返した並び順に付け、並び順は乱数で入れ替わっている（`shared/core/src/teams.ts`）。

3人組は、試行ごとに語を出す2人を交代する。
3人を `start()` で並べた順を (P, Q, R) とすると、3人組が語を出す回の数え（`trioTurns`）が 0, 1, 2 のとき、出すのはそれぞれ (P, Q)、(Q, R)、(R, P) とする。
数えはラウンドをまたいで続け、3人組が一致済みで語を出さない試行では進めない。

語を出さない1人は、その試行では入力しない。
`reveal` では他の参加者と同じく、自分のチームの申告と、他のチームへの異議を出せる。

交代の方式を採るのは、判定が「2語の照合キーの一致」のまま変わらず、ペアと3人組の得点を同じ尺度で比べられるためである。
3人の一致を求めると3人組が不利になり、3人のうち2人の一致を認めると、毎回3組の組み合わせで一致を狙える3人組が有利になる。
どちらも有利不利の大きさを机上で見積もれず、実プレイの記録が無い段階では補正の値を決められない。

交代では、つなぎの1語を出す2人のうち1人が前の試行で語を出していないことがある。
前の試行の2語は全員に開示されているため、出していない人も両方の語を見てつなぎの1語を考えられる。

### 対応人数

対応人数を4〜8人とする。
2〜3人ではチームが1つしか作れず、対抗戦にならないうえに、近い語の申告を判定する人がいない。

2〜3人で協力型として遊ぶ形は採らない。
協力型の別モードを置くと、規則が2系統になるためである。

### 同時提出と一斉開示

`input` の間、語を出す人は語を1つ提出する（`submit`）。
提出は締切まで上書きできる。

提出した語は公開状態に置かず、提出済みの人のidだけを公開する。
同じペアの相手の語が先に見えると、その語に合わせるだけで一致できるためである。

語を出す人のうち、接続中の全員が提出した時点で `reveal` へ進み、全員の語を公開状態に移す。
画面は全ての語を同時に出す。
原案の「声を揃えて数える」は、この開示の瞬間に置く（「口頭の約束」）。

締切に達したときに提出していない人は、その試行で語を持たない。
語を持たない人がいるペアは、その試行では一致しない。

切断している人は提出の揃いを待たない。
ペアの相手が切断したままだと、残った1人が語を出しても一致しない。
そのペアは得点を伸ばせないが、他のペアの進行は止まらない。

### 1回の試行とラウンドの終わり

ラウンドの最初の試行では、お題に合う語を出す。
2回目以降の試行では、前の試行で自分のペアが出した2語の両方につながる語を出す。

前の試行で自分のペアの片方が語を持たなかった場合、つなぐ相手は残った1語だけになる。
アプリは何をつなぐかを判定しないため、この場合も扱いを変えない。

`reveal` を終えるとき、完全一致したペアと申告が認められたペアを、そのラウンドで一致したペアとする。
一致したペアは、ラウンドの残りの試行では語を出さない。

全ペアが一致したか、`MAX_ATTEMPTS` 回目の試行を終えたら、ラウンドを終える。
最終ラウンドなら `debrief` へ、そうでなければ次のお題で `input` へ進む。

一致したペアの待ち時間は、試行1回あたり約45秒である（「所要時間の見積り」）。
待つ間も他のペアの語は開示ごとに見え、異議も出せる。

### 得点

ラウンドの `a` 回目（1始まり）の試行で一致したペアは、`MAX_ATTEMPTS + 1 - a` 点を得る。
既定値では1回目が4点、4回目が1点であり、4回で一致しなければ0点とする。

1回目の一致にも最高点を与える。
お題に対して最初に思い付く語が揃うことも、2人の連想が近いことの表れとして扱う。

合計点の同じチームは同じ順位とし、順位を分ける基準を置かない。
勝敗をチーム単位で決め、個人の得点は持たない。

ラウンド数4、試行の上限4、4点から1点の配点は、既定値で8人の卓が20分以内に収まるように逆算した値である（「所要時間の見積り」）。
値は仮置きであり、実プレイで見直す（「未解決の論点」の閾値）。

### 口頭の約束

同室であり、声は全員に聞こえる。
次の約束を `briefing` で示し、守られているかは機械で検出せず場に委ねる（[13](./13_ESCAPECALLゲームモジュール.md) の「自分の画面を見せない約束」と同じ扱い）。

* `input` の間は、出す語やその手がかりを口に出さない
* 開示のカウントダウンでは全員で `Three, two, one!` と数え、`one` に合わせて自分の語を声に出す

1つ目の約束を破れば、ペアの相手にも他のペアにも聞こえる。
声が全員に届くこと自体が、違反を場に知らせる。

2つ目の約束は、英単語を声に出す機会を作るためである。
画面に語が出るだけだと、このゲームの発話は申告と異議の場面に限られる。

開示の後、一致しなかったペアが「なぜその語にしたか」を英語で言い合うことを勧める。
言い回しを `keyExpressions` に置くが、義務にはしない。

## 公開状態（gameState）

```typescript
interface MindMeldPublic {
  packId: string;
  teams: TeamPublic[];                // startで編成した順
  roundIndex: number;                 // 0始まり。debrief では最後のラウンドのまま
  maxRounds: number;                  // 4
  attemptIndex: number;               // 0始まり。ラウンドごとに0へ戻る
  maxAttempts: number;                // 4
  prompt: PromptPublic | null;        // いまのお題。briefing 中は null
  activePlayerIds: string[];          // この試行で語を出す人
  submittedPlayerIds: string[];       // input の収集状況。語は載せない
  readyPlayerIds: string[];           // briefing / reveal の収集状況
  usedKeys: string[];                 // このラウンドで出せない照合キー
  attempts: AttemptPublic[];          // このラウンドの開示済みの試行
  rounds: RoundSummary[];             // 終わったラウンドの記録
  scores: TeamScore[];                // 累計点。teams の順
  keyExpressions: KeyExpression[];
  inputSeconds: number;
}

interface TeamPublic {
  id: string;
  label: string;                      // "A"〜"D"
  memberIds: string[];                // 2人、または3人組の3人。交代の順
}

interface PromptPublic {
  id: string;
  en: string;
  ja: string;
}

interface AttemptPublic {
  attemptIndex: number;
  teams: TeamAttempt[];               // この試行で語を出したチームだけ
}

interface TeamAttempt {
  teamId: string;
  words: { playerId: string; word: string | null }[];  // 2件。未提出は null
  exact: boolean;                     // 照合キーが一致した
  near: boolean;                      // 近い語である
  claim: ClaimPublic | null;
  matched: boolean | null;            // reveal の終わりで決まる。それまで null
}

interface ClaimPublic {
  claimedBy: string;
  objectorIds: string[];
  accepted: boolean | null;           // reveal の終わりで決まる。それまで null
}

interface RoundSummary {
  roundIndex: number;
  prompt: PromptPublic;
  attempts: AttemptPublic[];
  matchedAt: { teamId: string; attempt: number | null }[];  // 1始まり。一致しなければ null
}

interface TeamScore {
  teamId: string;
  points: number;
}
```

`input` の間は、提出された語を公開状態に置かない。
`state` は全員へブロードキャストされるため、ここに置いた値は全員の端末に届く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。
公開してよいのは提出済みの人のidだけである。

後のラウンドのお題は公開状態に置かない。
先に分かると、ペアの2人がそのお題の答えを `input` の外で相談できる。

`usedKeys` を公開状態に持つ。
お題と `attempts` から導けるが、導き方がサーバとクライアントで二重になるため、サーバが計算した値を配る（[13](./13_ESCAPECALLゲームモジュール.md) の `currentLockIndex` と同じ判断）。

`exact` と `near` もサーバが計算して載せる。
クライアントは、申告のボタンを `near` が真のペアにだけ出す。

`attempts` は最大4件、1件あたりチーム4つと語2件であり、`rounds` を含めても公開状態は数KBに収まる。

`attempts` と `usedKeys` は、次のラウンドの `input` へ入るときに `rounds` へ写して空へ戻す。
`usedKeys` はお題の語で初期化する。

## 秘密情報（secret.payload）

```typescript
interface MindMeldSecret {
  roundIndex: number;
  attemptIndex: number;
  word?: string;          // この試行で自分が提出した語（表示形）。未提出なら省略する
}
```

秘密は自分の提出だけである。
自分の語を返すのは、再接続した本人が提出済みの語を確認して書き直せるようにするためである（[14](./14_SECRETRULEゲームモジュール.md) の `draft` と同じ判断）。

`roundIndex` と `attemptIndex` を持たせるのは、前の試行の語を、いまの試行の提出として画面に出さないためである。
クライアントは公開状態の値と一致しない秘密を表示しない。

### 送るときと値

| 時点 | 送る相手 | 値 |
| --- | --- | --- |
| `start` | 全員 | `roundIndex: 0`、`attemptIndex: 0` |
| `input` へ入る | 全員 | 現在の `roundIndex` と `attemptIndex` |
| `submit` を受理 | 本人 | 上の値に `word` を加えたもの |

`playerSecrets` は上書きであり結合ではないため（[14](./14_SECRETRULEゲームモジュール.md) の「送るときと値」）、毎回全量を組み立てる。
`submit` で揃って同じ遷移で `reveal` へ進む場合も、本人の秘密を同じ遷移に載せる。

`input` へ入るときに全員へ送るのは、前の試行の `word` を秘密から消すためである。
語を出さない人（一致済みのペアと、休む3人組の1人）にも送る。

`reveal` と `debrief` へ入るときは送らない。
語は公開状態に移り、秘密に新しく加える値がない。

### 再接続での作り直し（rebuildSecret）

`rebuildSecret` は、遷移で最後に送った秘密と同じ値を返す（[ADR-0029](../adr/0029-再接続の秘密情報はゲームモジュールが作り直す.md)）。

| 状態 | 返す値 |
| --- | --- |
| `briefing` | `roundIndex: 0`、`attemptIndex: 0` |
| `input` / `reveal` / `debrief` | 公開状態の `roundIndex` と `attemptIndex`、`gameSecret.currentWords` に本人の語があればその語 |

`reveal` と `debrief` で `currentWords` を引けるのは、`currentWords` を次の `input` へ入るときまで消さないためである。
`debrief` では `roundIndex` と `attemptIndex` を最後の試行のまま残すため、最後に送った値と一致する。

`gameSecret` が無い場合と、参加者でない `playerId` の場合は例外を投げる。
共通コアは例外のときに保存済みの値を送るため、誤った値を返すより安全である（[13](./13_ESCAPECALLゲームモジュール.md) と同じ扱い）。

## ゲーム秘密状態（gameSecret）

```typescript
interface MindMeldGameSecret {
  prompts: PromptPublic[];                 // startで抽選した MAX_ROUNDS 件。出す順
  currentWords: Record<string, string>;    // この試行の playerId -> 語（表示形）
  trioTurns: number;                       // 3人組が語を出した試行の数。3人組が無ければ0のまま
}
```

`prompts` を `start` で決めて持つのは、`handleAction` と `onDeadline` にシードが渡らないためである（[05](./05_ゲームモジュール.md) の呼び出し規約）。
デプロイでパックが差し替わっても、進行中のゲームのお題は開始時のまま変わらない。

`currentWords` は `input` へ入るときに空へ戻す。
`reveal` へ入るときは公開状態の `attempts` に写すが、消さない（「再接続での作り直し」）。

`trioTurns` は秘密ではないが、サーバの進行にだけ使う値であり、公開状態に置かない。
画面は `activePlayerIds` で語を出す人を知れば足りる。

## action の受理規則

| action | 送れる人 | ステージ | 効果 |
| --- | --- | --- | --- |
| `ready` | 全員 | `briefing` / `reveal` | 収集に加える。接続中の全員が揃えば遷移 |
| `submit` | この試行で語を出す人 | `input` | 語を登録する。締切まで上書きできる |
| `claim` | 近い語になったチームの全員 | `reveal` | 自分のチームの2語を同じ語と申告する |
| `object` | 申告したチームに属さない全員 | `reveal` | 申告への異議を出す、または取り下げる |

ステージ違いはすべて `invalid_stage` で拒否する。
参加者でない送信者と未知の action も、専用のコードを設けず `invalid_stage` で拒否する（[13](./13_ESCAPECALLゲームモジュール.md) と同じ）。

拒否のコードはすべてゲームモジュール側で定義し、共通コアのエラーコード表には載せない。
`invalid_stage` / `stale_attempt` / `not_active` / `invalid_word` / `used_word` / `not_claimable` / `invalid_objection` の7つを持つ。

拒否は状態を変えない。
1つの action が複数の拒否条件に当たる場合は、各表の上の行から順に判定し、最初に当たったコードを返す。

`submit`、`claim`、`object` は `roundIndex` と `attemptIndex` を持つ。
前の試行の操作が次の試行の同じステージに届く経路を弾くためである。
`reveal` の直後に届いた `claim` はステージが `input` に変わっているため `invalid_stage` で弾けるが、通信の遅れが次の `reveal` まで続いた場合と、再接続した端末が古い画面のまま操作を送った場合は、試行の番号でしか弾けない（[14](./14_SECRETRULEゲームモジュール.md) の `mark` と同じ理由）。

### ready

二重送信は拒否せず冪等に扱う（収録7本と同じ）。
`claim` を受理したら、`reveal` の `readyPlayerIds` を空へ戻す。

`object` では `ready` を解除しない。
異議を出したことは開示の画面に出るが、判定者以外が新しく判断する事柄が生まれないためである。

### submit

payloadは `{ roundIndex: number; attemptIndex: number; word: string }` とする。

| 条件 | code |
| --- | --- |
| `roundIndex` か `attemptIndex` が数値でない、または現在の値と違う | `stale_attempt` |
| 送信者が `activePlayerIds` に無い | `not_active` |
| `word` が文字列でない、または正規化後に表示形の条件を満たさない | `invalid_word` |
| 照合キーが `usedKeys` にある | `used_word` |

上書きを許す。
最後に受理した提出のみが有効になる。

同じペアの2人が同じ語を出すことは、このゲームの目的であり拒否しない。
他のペアと同じ語も拒否しない。

語を出す人のうち、接続中の全員が提出した時点で `reveal` へ進む。

### claim

payloadは `{ roundIndex: number; attemptIndex: number }` とする。
対象は送信者のチームである。

| 条件 | code |
| --- | --- |
| `roundIndex` か `attemptIndex` が数値でない、または現在の値と違う | `stale_attempt` |
| 送信者のチームがこの試行で語を出していない、または `near` が偽である | `not_claimable` |

`near` は、2人がともに語を持ち、照合キーが一致せず、近い語の条件を満たすときに限り真になる。

同じチームの2回目以降の `claim` は拒否せず、状態を変えずに受理する（冪等）。
締切と `ready` の置き直しも2回目以降は行わない。
置き直すと、1つのチームが申告を繰り返して `reveal` を延ばし続けられる。

申告の取り下げは置かない。
申告したペアに不利な操作を、申告したペア自身が行う理由がない。

### object

payloadは `{ roundIndex: number; attemptIndex: number; teamId: string; objecting: boolean }` とする。
`objecting: false` は異議の取り下げである。

| 条件 | code |
| --- | --- |
| `roundIndex` か `attemptIndex` が数値でない、または現在の値と違う | `stale_attempt` |
| `teamId` のチームに申告が無い、送信者がそのチームに属する、`objecting` が真偽値でない | `invalid_objection` |

異議は申告ごとに1人1件であり、`objecting` の値で置き換える。

## ステージの終わりの処理

`ready` や `submit` の収集が揃ったときと締切到達のときで、同じ処理を行う。

| ステージ | 処理 |
| --- | --- |
| `briefing` | 最初のお題を `prompt` に入れ、`usedKeys` をお題の語で初期化し、`input` へ進む |
| `input` | 語を出した各チームの2語を `attempts` に加え、`exact` と `near` を計算して `reveal` へ進む |
| `reveal` | 申告を判定し、一致したチームに点を加える。次の表に従って進む |
| `debrief` | 締切を置かない |

`reveal` を終えるときの進み先は次のとおりとする。

| 条件 | 進み先 |
| --- | --- |
| 一致していないチームが残り、`MAX_ATTEMPTS` 回目の試行でない | 同じラウンドの次の試行の `input`。開示した語を `usedKeys` に加える |
| 全チームが一致した、または `MAX_ATTEMPTS` 回目の試行を終えた。最終ラウンドでない | 次のラウンドの `input`。このラウンドを `rounds` へ写す |
| 同上で、最終ラウンドである | `result` を返して `debrief` へ進む |

申告の判定は「近い語の申告と異議」の規則に従う。
異議と判定者の数は、`reveal` を終える時点の接続状態で数える。
切断した人の異議を数えないのは、切断した人が異議を取り下げられないまま残るためである。

次の試行の `activePlayerIds` は、一致していないチームの語を出す人とする。
ペアは2人とも、3人組は `trioTurns` で決まる2人とする。
3人組が語を出す試行に入るときに `trioTurns` を1つ進める。

## 結果（result.payload）

```typescript
interface MindMeldResult {
  teams: TeamPublic[];
  standings: Standing[];              // 点の高い順
  rounds: RoundSummary[];             // 全ラウンド
  playerCount: number;                // 開始時の参加者数
}

interface Standing {
  teamId: string;
  points: number;
  place: number;                      // 1始まり。同点は同じ順位
  matchedCount: number;               // 一致したラウンドの数
}
```

結果に全ラウンドの語と申告と異議を載せるのは、`finished` のまま再接続した人へ共通コアが `lastResult` を再送するため、結果画面が公開状態に依存しないようにするためである（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断）。

異議を出した人の名前を結果に残す。
申告を退けた異議が妥当だったかを、場で振り返れるようにするためである（「近い語の申告と異議」）。

得点表は共通コアの `ScoreBoard` を使わず、ゲーム側の画面で描く。
`ScoreBoard` は1人1行の得点（`ScoreEntry` の `playerId` と `points`）を受ける形であり（`client/core/src/score-entry.ts`）、チームの得点を受けられない。
TWO-HEADED SPEAKER と SECRET TEAMS もチームの得点表を要する場合は、3本目の時点で共通コアへの移動を判断する（[ADR-0020](../adr/0020-ゲーム間で重複する部品は共通コアへ置く.md) の条件2）。

## レベル差の吸収

4層で吸収する。

第1層はチームの編成である。
`formBalancedTeams` が、チームごとのレベルの偏りが小さい分け方から1つを選ぶ（[ADR-0032](../adr/0032-チーム編成は自己申告レベルで揃えて開始時に抽選する.md)）。
勝敗をチーム単位にし、個人の得点を持たない。

第2層はお題の作り方である。
お題は「台所にあるもの」のように、レベル1でも答えを複数思い付く範囲の語で答えられるものに限る（「機械で検査しないもの」）。
お題の `ja` は、レベル1〜2の画面では常に開き、レベル3〜5の画面では折りたたむ。

語の一覧は画面に出さない。
一覧から選ぶと、2人とも一覧の先頭の語を選ぶだけで一致し、連想を寄せる工程が消える。

第3層は近い語の申告である。
つづりを覚えきれていない人が1〜2文字を打ち間違えても、申告で一致として扱える。

第4層はペアの中の歩み寄りである。
レベルの違う2人が組むと、高い方が低い方の知っていそうな易しい語を選ぶことが一致への近道になる。
レベル差がペアの中では不利として働かず、相手に合わせる判断として遊びに入る。

それでも、語彙の多い人が多いチームほど、つなぎの1語の候補を多く持つ。
編成の許容幅の内側に残る偏りが勝敗にどれだけ出るかは**未検証**である。

## ロビーの記述子

ゲーム選択画面とロビーへ配る値である（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）。

| 項目 | 値 |
| --- | --- |
| `title` | `MIND MELD` |
| `tagline` | ペアで同時に英単語を出し、同じ語にそろうまで連想を寄せ合う |
| `icon` | 脳の絵文字（U+1F9E0） |
| `playerCount` | `[4, 8]` |
| `contentLabelJa` | お題を選ぶ |

アイコンは収録7本のアイコン（`server/games/*/src/module.ts` の記述子）と重ならないものを選んだ。

## 設定

| key | labelJa | 型 | 範囲 | 既定 |
| --- | --- | --- | --- | --- |
| `inputSeconds` | 語を出す時間（秒） | number | 20〜60、step 10 | 30 |

既定を30秒とするのは、1語を考えて打つ時間として、つなぎの1語に迷う場合を含めて足りると見込むためである（未検証）。

ラウンド数（4）、1ラウンドの試行の上限（4）、`reveal` の締切（30秒）は設定にしない。
所要時間がラウンド数と試行数の積で伸びるため、可変にすると卓が長さを予測できない（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ理由）。

`validateSettings` は範囲外と型違いを拒否する。
`settings` が無い場合と `inputSeconds` が無い場合は拒否せず、既定値を使う。
記述子の `min` / `max` と受理範囲を一致させ、その一致をテストで固定する。

`step` は入力の刻みであり、受理の条件にしない。
範囲内の整数であれば受理する（収録7本と同じ扱い）。

## start の処理順

1. `contentId` からパックを引く。`listContents` に載るidだけを受理する
2. `settings.inputSeconds` を確定する（既定30秒）
3. `seed` から乱数を作る
4. 人数から `sizes` を決め、`formBalancedTeams(players, sizes, random)` でチームを編成し、並び順に `A` からラベルを付ける
5. パックのお題を `shuffle` し、先頭 `MAX_ROUNDS` 件を `gameSecret.prompts` に固定する
6. 全員へ `roundIndex: 0`、`attemptIndex: 0` の秘密を送る
7. `stage` を `briefing`、`deadlineSeconds` を90として返す

3人組の交代の順は、`formBalancedTeams` が返したチーム内の並び（入力の順を保つ）とする。
入力の順は `room.players` の順であり、参加の早い人が先に語を出す。
この偏りは3人組の最初の試行の順番だけであり、交代で均される。

抽選は共通コアが注入した `seed` からのみ行う。
`Math.random()` と時刻を使わない（[05](./05_ゲームモジュール.md) の呼び出し規約）。
乱数は共通コアのシード付き乱数を使う（[ADR-0020](../adr/0020-ゲーム間で重複する部品は共通コアへ置く.md)）。

## カタログ（listContents）

```typescript
{ id: "basic", title: "はじめてのお題" }
```

お題の一覧をカタログに載せない。
ロビーでお題が分かると、ペアの2人が答えを先に相談できる。
ただしペアは `start()` で決まるため、ロビーの時点では誰と組むかが分からず、効果は限られる。

## 画面

画面は `client/games/mindmeld/` に置く。

| ステージ | 画面 |
| --- | --- |
| `briefing` | 遊び方、チームの一覧、申告の基準と例、口頭の約束、準備完了ボタン |
| `input` | お題、ラウンドと試行の番号、自分のペアの前の試行の2語、使用済みの語、語の入力、提出状況、残り時間 |
| `reveal` | カウントダウン、全チームの語、一致の結果、申告と異議の操作、累計点、準備完了ボタン、残り時間 |
| `debrief` | チームの順位と点、全ラウンドのお題と語の流れ、申告と異議の記録 |

画面の要点を挙げる。

* `input` の入力欄は、表示形の条件を満たさない語と、使用済みの語を送信させない。理由を「英字だけで書く」「このお題ではもう出た語」のように示す
* `input` で語を出さない人（一致済みのペアと、休む3人組の1人）には「今回は待つ」と出し、他のペアの提出状況を見せる
* 自分のペアの前の試行の2語を、入力欄の上に大きく出す。つなぎの1語を考える材料であり、2回目以降の試行で最も見る情報だからである
* `reveal` に入ったら、全員の画面で `3`、`2`、`1` のカウントダウンを出し、`1` の後に語を出す。状態の届く時刻は端末ごとに少しずれるが、声を合わせる目安には足りる見込みである（未検証）
* 一致したペアには記号と「一致」の文字を添え、色だけに頼らない
* 近い語のペアには申告のボタンを出す。申告の基準を、ボタンの近くに常に出す
* 申告があったペアの行に、異議のボタンと、異議を出した人のアイコンを出す。アイコンには名前の読み上げを付ける
* 黄の輪郭は「いまやること」の案内だけに使う（[ビジュアルデザイン.md](../ビジュアルデザイン.md) の「色付きの輪郭は画面ごとに意味を1つだけ持たせる」）。一致したペアと、自分が異議を出した申告は背景の膜（`--yellow-veil`）で示す
* チームの区別は `A` `B` のラベルとメンバーのアイコンで示す。参加者の顔色は8色をハッシュで割り当てるため（[ADR-0033](../adr/0033-対象人数の上限を8人に上げる.md) の影響）、チームの色としては使わない
* 最終ラウンドの各ステージには「最後のお題」と出す
* `keyExpressions` は `reveal` に出し、自分のレベルが1〜2なら開いて出す

## 所要時間の見積り

締切は上限であり、実際は提出と `ready` の揃いで先に進む。
`inputSeconds` 30秒、試行1回を `input` 20秒と `reveal` 25秒の計45秒と置いて見積る。

ラウンドは最も遅いペアが一致するまで続く。
チームが多いほど、ラウンドが試行の上限まで続く見込みが高い。

| 区間 | 4人（2チーム） | 8人（4チーム） |
| --- | --- | --- |
| `briefing` | 75秒（締切90） | 75秒（締切90） |
| ラウンド | 平均3試行 × 45秒 × 4 = 540秒 | 平均4試行 × 45秒 × 4 = 720秒 |
| 結果の確認 | 60秒 | 60秒 |
| 1ゲーム | 約675秒（約11分） | 約855秒（約14分） |

**実測はしていない。**
ラウンドあたりの平均試行数は仮の値である。

最も長くなるのは、全試行が締切まで使われ、全ラウンドが4試行に達する場合である。
既定値では、`briefing` 90秒、試行16回 × 60秒で960秒、結果の確認60秒で約1110秒（約18.5分）となる。
申告による `reveal` の置き直しが毎試行1回ずつ入ると、さらに最大480秒延びる。

`inputSeconds` を上限の60秒にすると、最長の進行は約1590秒（約26.5分）になる。

[ADR-0033](../adr/0033-対象人数の上限を8人に上げる.md) の目安（6人は15分以内、8人は20分以内）には、既定値の通常の進行で収まる見込みである。

最長の進行で20分を超える卓が多い場合は、`reveal` の締切を20秒へ詰め、次に `MAX_ATTEMPTS` を3へ減らす順で見直す。
ラウンド数を3へ減らすのは最後にする。
お題が少ないと、1つのお題との相性で勝敗が決まりやすくなるためである。

## コンテンツ形式

収録パック `basic` を例に示す。

```json
{
  "id": "basic",
  "title": "はじめてのお題",
  "prompts": [
    { "id": "kitchen", "en": "Something in a kitchen", "ja": "台所にあるもの" },
    { "id": "yellow", "en": "Something yellow", "ja": "黄色いもの" },
    { "id": "summer", "en": "Something you think of in summer", "ja": "夏といえば" },
    { "id": "school", "en": "Something at school", "ja": "学校にあるもの" },
    { "id": "zoo", "en": "An animal at the zoo", "ja": "動物園にいる動物" },
    { "id": "bag", "en": "Something in your bag", "ja": "かばんの中にあるもの" }
  ],
  "keyExpressions": [
    { "en": "Three, two, one!", "ja": "せーの！" },
    { "en": "We matched!", "ja": "そろった！" },
    { "en": "So close!", "ja": "惜しい！" },
    { "en": "Apple and apples. It's the same word.", "ja": "apple と apples は同じ語" },
    { "en": "Sorry, cat and car are different words.", "ja": "cat と car は別の語だと思う" },
    { "en": "Pan and fire... so I said cook.", "ja": "pan と fire だから cook にした" },
    { "en": "Why did you say that?", "ja": "なぜその語にしたの？" }
  ]
}
```

例ではお題を6件に省略している。
収録するパックは検証3の件数を満たす。

1ファイルが1パックであり、ロビーで選ぶ単位はパックである（収録7本と同じ形）。

お題の正解の語や答えの候補を書く欄を設けない。
一致の判定はペアの2語の比較だけで決まり、お題の側に正解が無いためである。

## 検証項目

`pnpm validate:content` で検査する。

| # | 内容 |
| --- | --- |
| 1 | スキーマ。必須欄の欠落と型違いを落とす。定義に無い欄があれば落とす。`prompts[]` と `keyExpressions[]` の要素の中も見る |
| 2 | パックとお題の `id` が `[a-z0-9_]` の1〜16文字。お題の `id` がパック内で一意 |
| 3 | お題が12件以上（`MAX_ROUNDS` の3倍） |
| 4 | お題の `en` が英字、半角空白、`'` `-` `,` `?` だけからなり、2〜8語、60文字以内 |
| 5 | お題の `en` を正規化した文字列がパック内で重複しない |
| 6 | `keyExpressions` が5件以上 |
| 7 | すべての `en` と `ja` が空でない |

検証3で12件以上を求めるのは、同じ部屋で続けて遊んだときに、同じお題が続けて出にくくするためである。
12件から4件を抽選すると、続く2ゲームでお題が1件も重ならない確率は約14%（C(8,4)/C(12,4) = 70/495）であり、重なる件数の期待値は約1.3件になる。

12件では重なりを避けきれないため、件数の下限を上げるかは収録時のお題レビューで判断する。
重なりを減らす仕組み（前回のお題を除く）は、`nextGame` で `gameSecret` が破棄されるため持てない（[14](./14_SECRETRULEゲームモジュール.md) の「同じ規則の再登場」と同じ制約）。

検証4は、お題の英文から `usedKeys` の初期値を作るために、語の区切りを英字と空白で決められることを保証する。

検証7を置くのは、`ja` がフォントサブセットの入力になるためである（[07](./07_リポジトリとツールチェーン.md)）。

### 機械で検査しないもの

* お題の答えの範囲が、レベル1〜2でも3語以上思い付く広さを持つか
* お題の答えの範囲が広すぎないか（`Something you like` のように、何を出しても答えになるお題は連想が寄らない）
* 1つの語が支配的な答えにならないか（`Something yellow` で全員が `banana` を出すと、全ペアが1回目に一致して点差が付かない）
* お題の `en` と `ja` が同じ範囲を指しているか
* `keyExpressions` に、カウントダウン、申告、異議、つなぎの理由の説明の型が揃っているか

いずれも人手のレビューで見る。
記録は `docs/お題レビュー/` に置く（収録7本と同じ形）。

## 判定の規則

完全一致は、2人の語の照合キーの文字列一致だけで決まる。
近い語かどうかは、照合キーの長さ、先頭部分の一致、編集距離だけで決まる。
申告が認められるかは、異議の数と判定者の数だけで決まる。

英語の意味、お題との関連、つなぎの1語が前の2語につながっているかは、アプリは判定しない（不変条件1、[ADR-0001](../adr/0001-ランタイムAI不使用.md)）。
お題との関連とつながりは、口頭の約束として場に委ねる（「未解決の論点」）。

確定した一致と点は公開状態の `attempts` と `scores` に保存し、後から再計算しない。
コードやコンテンツを差し替えても、進行中のゲームの記録が動かないようにする。

## 未解決の論点

| 論点 | 内容 |
| --- | --- |
| 発話量 | 語を出す工程は無言の入力である。発話はカウントダウン、語の読み上げ、申告と異議、任意の理由の説明に限られ、収録7本と比べた量は未測定である |
| お題との関連 | 「毎回 `thing` と出す」ような取り決めは機械で防げない。取り決めは声に出さないと共有できず、全員に聞こえる。初版は異議の対象にせず、場に委ねる |
| 異議の悪用 | 2チームの卓では、相手ペアの2人が揃えば正当な申告も退けられる。名前を残すだけで足りるかは未検証である |
| 待ち時間 | 先に一致したペアは、ラウンドの残りの試行を待つ。4チームでは最大3試行（約135秒）待つ |
| 3人組の休み | 3人組の1人は3試行に1回語を出さない。休む人が退屈しないかは未検証である |
| カウントダウンの同期 | 状態の届く時刻のずれで、端末ごとにカウントダウンの開始がずれる。声を合わせられる程度に収まるかは実機で確かめていない |
| 切断したペアの相手 | ペアの1人が切断したまま戻らないと、残った1人は一致できない。チームの付け替えは持たない |
| 同じお題の再登場 | `nextGame` で `gameSecret` は破棄されるため、同じ部屋で続けて遊ぶと同じお題を引きうる |
| 閾値 | `MAX_ROUNDS`、`MAX_ATTEMPTS`、点数、`REVEAL_SECONDS`、近い語の条件、異議の過半数はすべて仮置きである |
| 提出内容の適切さ | 自由入力の語であり、場を壊す語を機械で弾かない。同室プレイのため運用に委ねる（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断） |

## 原案からの変更

[ゲーム構想.md](../ゲーム構想.md) の案31から変えた点と、その理由を挙げる。

| 変更 | 理由 |
| --- | --- |
| 奇数の人数で3人組を作り、語を出す2人を交代にした | 原案はペアだけで、5人と7人の扱いが無い（同書の「追加案（27〜33）」の前提3） |
| 対応人数を4〜8人にした | 2〜3人はチームが1つで対抗戦にならない |
| 「数えてから同時に入力する」を「同時に提出し、開示の瞬間に数える」にした | 画面上の入力は同時にそろわない。提出をそろえて一斉に開示すれば、入力の速さに関係なく同時に出したことになる |
| 正規化の範囲を定めた | 原案は「大文字小文字と空白」だけだった。記号、全角、区切りの違いも機械で吸収できる |
| 申告を近い語に限った | 原案は申告の範囲を定めていない。範囲が無いと、明らかに違う語を申告して異議の不足に賭けられる |
| 異議を過半数で決めるようにした | 原案は異議の決め方を定めていない。1人の異議で退けると、相手ペアの1人だけで正当な申告を潰せる |
| ラウンド内で開示済みの語を禁止した | 相手の前の語をそのまま出す取り決めで、必ず一致する |
| 試行の上限と点数を定めた | 原案は「少ない回数ほど高得点」だけだった。上限が無いと所要時間が決まらない |

## テスト観点

`GameModule` は純粋関数のため、Durable Objectなしで全項目をテストする。

* 決定性: 同じ `seed` と同じ参加者から、同じチームとラベルとお題が得られること
* 編成: 4〜8人の各人数で、`sizes` が表のとおりになり、全員がちょうど1つのチームに入ること
* 3人組: 交代が (P, Q)、(Q, R)、(R, P) の順に進み、ラウンドをまたいで続き、3人組が一致済みの試行では進まないこと
* 正規化: 全角の英字、曲がった `'`、前後の記号、大文字が正規化され、保存と開示が表示形になること
* 正規化: かなを含む語、3要素以上の語、24文字を超える語、照合キーが1文字の語が `invalid_word` になること
* 照合キー: `ice cream`、`ice-cream`、`icecream` が同じ照合キーになること
* 近い語: 本文の例（`apple`/`apples`、`bus`/`buses`、`child`/`children`、`color`/`colour`、`theater`/`theatre`、`knife`/`knives`）が近い語になり、`pan`/`cook`、`mouse`/`mice`、2文字の語どうしが近い語にならないこと。各条件の境界（差3と4、5文字未満の編集距離2）を確かめる
* 使用済みの語: お題の語、同じラウンドの開示済みの語（他のペアの語を含む）が `used_word` になり、次のラウンドでは出せること
* 秘密の非混入: `input` 中の公開状態に、提出された語が現れないこと。どのステージの公開状態にも、後のラウンドのお題が現れないこと
* 秘密の非混入: 遷移ごとに、公開状態のキーと配列の要素のキーが許可リストと一致すること（名前を変えた漏洩を落とす）
* 秘密の配布: 「送るときと値」の表の各時点で、表どおりの相手に表どおりの値が送られること。最後の提出で `reveal` へ進む遷移にも本人の秘密が載ること
* `submit`: `not_active`（一致済みのペア、休む3人組の1人）、`stale_attempt`、`invalid_word`、`used_word` の各拒否と、上書きを確かめること
* 遷移: 語を出す人のうち接続中の全員の提出で `reveal` へ進み、切断した人を待たないこと
* 遷移: 締切で未提出の人がいるペアは一致せず、申告もできないこと
* `claim`: 近い語のペアだけが申告でき、2回目は状態を変えないこと。初回の受理で締切が置き直され、`ready` が解除されること
* `object`: 申告したチームの人と、申告の無いチームへの異議が `invalid_objection` になること。取り下げで異議が消えること
* 判定: 異議が判定者の過半数で退け、半数ちょうどでは認めること。判定者が0人なら認めること。切断した人の異議と判定者を数えないこと
* 得点: 1〜4回目の一致で4〜1点、一致しなければ0点になること。申告が認められた一致も同じ点になること
* ラウンドの終わり: 全チームの一致で試行の途中でも次のラウンドへ進み、4回目の試行の後は一致の有無にかかわらず進むこと
* 結果: 同点のチームが同じ順位になり、全ラウンドの語と申告と異議の記録が載ること
* 作り直し: 遷移が返した秘密を `playerId` ごとに上書きで溜めた値と `rebuildSecret` の戻り値が、各遷移の直後に全員について一致すること。提出の上書き、締切での進行、申告、ラウンドの切り替え、終局を通し、4人と5人と8人で確かめる
* 作り直し: `gameSecret` が無いときと参加者でないときに例外を投げること
* 検証: 検証1〜7がそれぞれ違反を落とすこと
* ペイロード: 24文字の語と番号を持つ `submit` のペイロードが `ACTION_MAX_CHARS`（512、`shared/core/src/validate.ts`）未満であること
* 設定: 記述子の `min` / `max` と `validateSettings` の受理範囲が一致すること
* 人数: 4人、5人、8人で開始から `debrief` まで進むこと（[ADR-0033](../adr/0033-対象人数の上限を8人に上げる.md) の「影響」）
* 通しE2E: 4人と8人で結果まで進み、`input` 中に他人の画面へ提出した語が出ないこと。8人のE2Eの実行時間と安定性は未検証である（[ADR-0033](../adr/0033-対象人数の上限を8人に上げる.md)）
