# 基本設計: TWO-HEADED SPEAKERゲームモジュール

## 結論

TWO-HEADED SPEAKERは4ステージ（`briefing` / `handoff` / `explaining` / `debrief`）を持つ6〜8人用のチーム対抗戦であり、`GameModule` インターフェースの実装として完結する。

参加者は `start` でペアに分かれる。
7人のときだけ1組を3人組にする。

ペアが1組ずつ説明役を務め、全ペアが同じ回数ずつ説明役を回る。
説明役のペアにだけお題を配り、2人は英語を1語ずつ交互に声に出して、お題を説明する。

他のペアは答えを声で言う。
最初に当てたペアを説明役のペアが画面で申告し、当てたペアと説明役のペアに1点ずつ入る。

アプリは「1語ずつ交互に話したか」と「答えが合っているか」を判定しない（不変条件1）。
交互の手番は画面に話す順を示すだけで、1語ごとの操作を求めない。
交互の違反は聞いている全員が指摘し、説明をやり直させる。

gameIdは `twoheaded` とする。

共通コアへの追加要求はない。
チーム編成は共通コアの `formBalancedTeams` を使う（[ADR-0032](../adr/0032-チーム編成は自己申告レベルで揃えて開始時に抽選する.md)）。
提出は自由英文を含まず、ボタン操作だけである。

ルールの原案は [ゲーム構想.md](../ゲーム構想.md) の案32である。
原案は答えを画面に入力する形であり、本設計は声で答える形へ変えた。
原案から変えた点は末尾の「原案からの変更」に列挙する。

草案の段階で未決として残したルール判断は、2026-11-12にユーザーが判断して確定し、本文の該当節に反映した。

共通コアとの境界は [05](./05_ゲームモジュール.md)、メッセージの意味は [03](./03_プロトコル.md) を正とする。
3役の構造と申告の仕組みは [09](./09_DONTSAYITゲームモジュール.md) を下敷きにした。

## ステージ

| stage | 締切 | 遷移条件 |
| --- | --- | --- |
| `briefing` | 90秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `handoff` | 30秒 | 説明役のペアの1人が `startTurn` を送る、または締切到達 |
| `explaining` | `turnSeconds`（既定90秒） | 消費上限に到達、締切到達、または山札が尽きる |
| `debrief` | なし | 遷移しない（`lifecycle: finished`） |

`handoff` と `explaining` を1手番とし、手番の数は「ペアの数 × 周回数」になる。
`explaining` が終わると次の手番の `handoff` へ戻り、最後の手番の `explaining` が終わったときだけ `debrief` へ進む。

山札が尽きた場合は、残りの手番があっても `debrief` へ進む（[09](./09_DONTSAYITゲームモジュール.md) と同じ扱い）。

`handoff` を独立したステージにするのは、説明役のペアが1枚目のお題を読む時間を制限時間の外に置くためである（[09](./09_DONTSAYITゲームモジュール.md) と同じ理由）。
このゲームでは、2人が同じお題を読み、どちらが先に話すかを確かめる時間も兼ねる。

1手番でお題を次へ送れる回数に上限（`MAX_CARDS_PER_TURN`、5回）を置く。
正解と送りの合計に課し、上限に達した時点でその手番を終える。
上限がないと、送りを連打して山札を掘り尽くし、残りのペアが説明役を務められないままゲームが終わる（[09](./09_DONTSAYITゲームモジュール.md) の消費上限と同じ理由）。

`explaining` では Wake Lock を取得する。
全員が画面を見ずに話し、聞く時間が続くためである。

## 進行の要点

### アプリが検証できないことの扱い

このゲームの規則のうち、アプリが観測できるのは画面の操作だけである。
発話は声で行われ、アプリは音声を扱わない（不変条件1、[ADR-0001](../adr/0001-ランタイムAI不使用.md)）。
したがって、次の3点はアプリが判定できない。

* 説明役のペアが1語ずつ交互に話したか
* 答えたペアの答えがお題と合っているか
* どのペアが最初に当てたか

本設計は、この3点を人の判断に置き、アプリは判断の結果だけを受け取る。
人が判断する場面には、判断する人を1人（または1組）に決め、判断に迷ったときの扱いを規則で決めておく。
[09](./09_DONTSAYITゲームモジュール.md) の `claimCorrect`（説明者の申告を正とする）と同じ考え方である。

### 交互の手番は画面に話す順を示すだけにする

画面には、いまのお題で最初に話す人と、話す順を出す。
1語ごとの交代を画面で追う操作（1語言うたびにタップして手番を渡す形）は置かない。

1語ごとのタップを採らない理由は3つある。

* 検証にならない。タップの回数と言った語の数が一致しているかを、アプリは確かめられない
* 発話を止める。1語ごとに画面を見てタップすると、相方の語を聞いてすぐ続ける速さが失われる。このゲームの面白さは、相方の語を受けてすぐに次の語を選ぶところにある
* 画面が発話より遅れる。タップからサーバを経て相方の画面が切り替わるまでに通信の往復がかかり、相方は画面が切り替わる前に話し始める（往復の時間は未計測）

話す順は、お題ごとに最初に話す人を1人ずつずらす（「話す順の決め方」）。
最初に話す人は文の方向を決めやすいため、同じ人に偏らないようにする。

この形では、共通コアに手番制（1人ずつ順に操作する進行。[05](./05_ゲームモジュール.md) の「収録予定ゲームと共通コアへの要求」）を求めない。
手番の進行が発話の中で閉じ、アプリに届く操作は正解と送りの申告だけだからである。

### 交互の違反は説明のやり直しで扱う

交互の違反は次の3つとする。

* 1人が続けて2語以上言う
* 相方の番に言う
* 説明役のペアどうしで、1語ずつの形を外れて相談する（日本語の相談を含む）

違反を見つけたら、聞いている誰でも「Two words!」などと声で指摘する。
指摘された説明役のペアは、言いかけの文を捨てて、話す順の先頭の人から文を言い直す。
アプリには違反を記録しない。

罰則を持ち時間の消費だけにするのは、違反の申告ボタンを置くと、申告に利害が生じるためである。
申告でお題が無効になる形では、当てられそうにない相手ペアが、説明役のペアの得点を消すために申告できる。
やり直しなら、指摘で得をする人がいない。

判定に迷ったらセーフとする。
同室で全員に声が聞こえるため、明らかな違反は場の全員が気付く。
迷う程度の違反で場を止めるほうが、持ち時間の損失が大きい。

説明役のペアが当てる側の答えに反応するときも、1語ずつの形を守る（`No!` や `Close!` は1語で言える）。

### 身振りは禁止しない

説明役のペアが身振りを添えることを禁止しない。

禁止しても、守られているかを判定する人がおらず、禁止の規則だけが残る。
身振りでお題が当たると英語の発話が減るが、1語ずつの説明に身振りを足すこと自体はレベル1〜2の参加者の助けになる。

### 言えない語

説明役のペアが言えないのは次の語である。

| 範囲 | 例 |
| --- | --- |
| お題の名前そのもの | `vending machine` |
| 名前を空白とハイフンで区切った語 | `vending` / `machine` |
| ひと続きの名前に含まれる構成要素 | `toothbrush` の `tooth` と `brush` |
| 別名（`Card.aliases`） | `refrigerator` の `fridge` |
| 上のいずれかの語形変化 | 複数形、過去形、ing形、「〜する人」 |
| 日本語名を口に出すこと | 英語で説明していないため |

範囲と判定の考え方は [09](./09_DONTSAYITゲームモジュール.md) の「言えない語の範囲」と「禁止語の語形変化」に合わせる。
禁止語（DON'T SAY ITの `taboo`）は課さない。
1語ずつ交互に話す制約がすでに難所であり、禁止語を重ねると説明が成り立たないお題が増える見込みだからである（未検証）。

言えない語を言った場合、説明役のペアはそのお題を送る（`passCard`）。
送ったお題は得点を動かさない。

当てる側はお題を知らないため、言えない語を言ったかどうかをその場で判断できない。
そのため、お題を正解か送りで終えるたびに、お題の答えを全員の画面に出す（公開状態の `lastCard`）。

言えない語を言ったのに送らずに正解を申告した場合、当てる側が後から気付ける。
気付いた後の扱い（得点の取り消し）はアプリに置かず、場に委ねる。
直前の申告を取り消す操作を置かない理由は「claimCorrect」に書く。

### 答えは声で言い、説明役のペアが申告する

当てる側のペアは、分かった時点で答えを英語で声に出す。
説明役のペアは、最初に正しい答えを言ったペアを画面で選んで申告する（`claimCorrect`）。
アプリは申告をそのまま正とする。

画面に答えを入力する形（原案）を採らない理由は3つある。

* 表記ゆれとタイプミスを吸収できない。正規化で大文字と小文字、空白、全角と半角は揃えられるが、`colour` と `color`、`refrigerator` と `refrigirator` のような違いは文字列の比較では扱いきれない。別名を足しても網羅にならない（[ゲーム構想.md](../ゲーム構想.md) の案31でも同じ課題が挙がっている）
* 「最初に当てた」がタイプの速さで決まる。スマホで英単語を打つ速さは英語力と別の能力であり、レベル1〜2の参加者が不利になる
* 発話が減る。当てる側が画面に打ち込む間は声が出ない。声で答える形なら、当てる側も英語を口に出す

選択肢から選ぶ形も採らない。
選択肢が見えていると、説明の最初の1語（`kitchen` など）で候補が絞れ、説明役のペアが文を組み立てる前に当たる。
1語ずつ交互に話して文を作る工程が短くなり、このゲームの発話の中心が失われる。

声で答える形の弱点は、当てる側が思いつく答えを次々に言う当てずっぽうを防げないことである。
アプリは誤答を観測できないため、誤答に罰則を置けない。
当てずっぽうが遊びとして問題になるかは未検証である。

### 「最初に当てた」の判定

最初に当てたペアは、説明役のペアが聞いて決める。
アプリはサーバの受理順を使わない。

声で答える形では、アプリに届くのは説明役のペアの申告1件だけであり、受理順を比べる対象がない。
画面入力の形でサーバの受理順を使う場合は、端末と回線の差（Wi-Fiとモバイル回線の遅延の差）が順位に入る。
同室で同時に答えるゲームでは、この差が人の反応の差と同じ桁になりうる（未計測）。

ほぼ同時に2組が言った場合も、説明役のペアが1組を選ぶ。
判断に迷ったら、先に聞こえたと説明役のペアが判断した方とする。

説明役のペアがどのペアを選ぶかで、相手ペアどうしの順位を動かせる（[09](./09_DONTSAYITゲームモジュール.md) の `claimCorrect` にも同じ性質がある）。
申告の時点で、選んだペアを全員の画面に出す（公開状態の `lastCard`）。
不自然な申告は場の全員に見える。

同時の場合に2組とも加点する案は採らない。
説明役のペアは誰を選んでも自分の得点が変わらないため、迷ったときに全組へ加点する申告が続き、先に当てる競争が薄れる。

### 話す順の決め方

`start` でペアの中の並び（`members`）を決め、ゲーム中は変えない。
お題ごとに、最初に話す人を並びの中で1人ずつずらす。

ずらし方は、そのペアがゲームの中で説明したお題の通し番号（手番をまたいで数える）を、ペアの人数で割った余りとする。
2人のペアでは、お題ごとに先に話す人が入れ替わる。
3人組では、`A → B → C`、`B → C → A`、`C → A → B` の順で回る。

手番をまたいで数えるのは、各手番の1枚目を毎回同じ人が始めないようにするためである。
1手番に1〜2枚しか説明しない卓では、手番ごとに数え直すと先頭の人に偏る。

### ペアの編成と奇数人数

`start` で `formBalancedTeams` を呼び、参加者をペアに分ける（[ADR-0032](../adr/0032-チーム編成は自己申告レベルで揃えて開始時に抽選する.md)）。
ペアは全員に公開する（公開状態の `teams`）。

| 人数 | `sizes` | 組数 |
| --- | --- | --- |
| 6 | `[2, 2, 2]` | 3 |
| 7 | `[2, 2, 3]` | 3 |
| 8 | `[2, 2, 2, 2]` | 4 |

`formBalancedTeams` はペアの合計レベルの差を小さくするため、レベルの高い人と低い人が組みやすい。
このゲームでは、上級者が文の骨格を作り、相方が1語を足す形で、レベル1〜2の参加者も説明に加われる（「レベル差の吸収」）。

7人のときは1組を3人組にする。
3人組は話す順を3人で回す。

3人組を採るのは、7人目を説明に加えない形（審判役など）では、その人が英語を話す機会がほとんど無くなるためである。
3人組は当てる側として頭数が多く、声を出せる人が1人多い。
この差が勝敗に出るかは未検証である。

### 対応人数の下限を6人にする理由

ペアが2組（4人、5人）では、得点の付け方が競争として成り立たない。
説明役のペアと当てたペアに1点ずつ入るため、当てる側が常に相手の1組だけになり、お題が当たるたびに両ペアが1点ずつ得る。
送りと時間切れを除けば、2組の得点は常に同じになる。

2組で競争を残そうとして説明役のペアだけに加点すると、当てる側は相手の得点を増やさないために、分かっても答えない方が得をする。

3組以上なら、当てる側のペアどうしが先に当てる競争をするため、分かったのに答えない動機が生じない。
そのため対応人数を6〜8人とする。

4〜8人とし、2組の卓だけを協力型（合計の当てた枚数でランクを付ける）にする案は採らない。
協力型の別モードを置くと、規則が2系統になるためである。

## 公開状態（gameState）

```typescript
interface TwoHeadedPublic {
  setId: string;
  teams: TeamPublic[];               // startで編成した順
  turnOrder: string[];               // 説明役のteamIdの列。周回数ぶん繰り返す
  turnIndex: number;                 // 0始まり
  readyPlayerIds: string[];          // briefingの収集状況
  speakingOrder: string[];           // 現在のお題で話す順(playerId)。先頭が最初に話す人。handoff と explaining で使う
  scores: TeamScore[];
  turns: TurnSummary[];              // 終了した手番の記録
  solvedThisTurn: number;
  passedThisTurn: number;
  lastCard: RevealedCard | null;     // 直前に終えたお題。手番が変わると null に戻す
  turnSeconds: number;
  laps: number;
}

interface TeamPublic {
  teamId: string;                    // "t1"〜"t4"
  members: string[];                 // playerId。話す順の元になる並び
}

interface TeamScore {
  teamId: string;
  points: number;
}

interface TurnSummary {
  teamId: string;
  solved: number;
  passed: number;
  skipped: boolean;                  // 説明役のペアの未接続で手番を飛ばした
}

interface RevealedCard {
  answer: string;
  ja: string;
  outcome: "solved" | "passed";
  guessedTeamId: string | null;      // solved のときだけ入る
}
```

お題（`answer` / `ja` / `aliases`）と山札の残り枚数は、お題を終えるまで公開状態に置かない。
`state` は全員へブロードキャストされるため、ここに置いた値は当てる側にも届く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。

`lastCard` は、正解か送りで終えたお題だけを載せる。
終えたお題は説明が済んでおり、答えを公開しても当てる側の得にならない。
公開するのは、言えない語の違反に当てる側が気付けるようにするためと、聞いた説明と答えを結び付けて覚えられるようにするためである。

`lastCard` は次のお題を終えるまで残し、手番が変わると `null` に戻す。
`explaining` の締切で捨てたお題は `lastCard` に載せず、結果で開示する（「結果」）。

`speakingOrder` を公開状態に置くのは、当てる側も話す順を知っていないと、交互の違反を指摘できないためである。

ペアの合計レベルと各自のレベルは公開状態に追加しない。
レベルは共通コアの `Player` にあり、ロビーで既に見えている値を重ねて持つ必要がない。

## 秘密情報（secret.payload）

```typescript
type TwoHeadedSecret = ExplainerSecret | GuesserSecret;

interface ExplainerSecret {
  role: "explainer";
  card: {
    cardId: string;
    answer: string;
    ja: string;
    aliases: string[];
  };
}

interface GuesserSecret {
  role: "guesser";
}
```

説明役のペアの全員に同じお題を送る。
2人が同じお題を見ていないと、相方の語の意図を読めない。

日本語名（`ja`）を送るのは、英語名を見てお題を認識できない説明役を救うためである（[09](./09_DONTSAYITゲームモジュール.md) の「日本語のお題補助」と同じ理由）。

### 送るときと値

`playerSecrets` は上書きであり結合ではないため、役が変わるときは全員へ送り直す。

| 時点 | 送る相手 | 値 |
| --- | --- | --- |
| `start` | 全員 | `role: "guesser"` |
| `handoff` へ入る | 全員 | 説明役のペアには現在のお題の `ExplainerSecret`、他は `GuesserSecret` |
| `claimCorrect` / `passCard` を受理し、次のお題へ進む | 説明役のペア | 次のお題の `ExplainerSecret` |

`start` で全員に `GuesserSecret` を送るのは、同じ部屋で続けて遊んだときに、前のゲームのお題を画面に残さないためである（[14](./14_SECRETRULEゲームモジュール.md) と同じ判断）。

1枚目のお題は `start` ではなく `handoff` へ入るときに送る。
`start` で送ると、最初の説明役のペアだけが `briefing` の間にお題を読める。

### 再接続での作り直し（rebuildSecret）

`rebuildSecret` は、遷移で最後に送った秘密と同じ値を返す（[ADR-0029](../adr/0029-再接続の秘密情報はゲームモジュールが作り直す.md)）。

| 状態 | 返す値 |
| --- | --- |
| `briefing` | `role: "guesser"` |
| `handoff` / `explaining` | 説明役のペアには `gameSecret.currentCardId` のお題、他は `GuesserSecret` |
| `finished` | `undefined`（送らない） |

`finished` で送らない理由は [09](./09_DONTSAYITゲームモジュール.md) と同じである。
終局の時点で次のお題を引いている場合があり、同じ式で作り直すと誰も見ていないお題が届く。
`debrief` の画面は秘密情報を読まない。

お題セットが無い場合、表示中のお題がセットに無い場合、`playing` の間に `gameSecret` が無い場合は例外を投げる。
共通コアは例外のときに保存済みの値を送るため、誤った値を返すより安全である。

## ゲーム秘密状態（gameSecret）

```typescript
interface TwoHeadedGameSecret {
  deck: string[];                    // シャッフル済みのcardId列
  cursor: number;                    // 次に配るお題のdeck内位置
  currentCardId: string | null;
  cardsExplained: Record<string, number>;  // teamId -> そのペアが説明したお題の通し番号の次の値
  usedCards: UsedCard[];             // debriefで開示する対象
}

interface UsedCard {
  cardId: string;
  teamId: string;                    // 説明したペア
  outcome: "solved" | "passed" | "timeout";
  guessedTeamId: string | null;
}
```

`cardsExplained` は話す順のずらし（「話す順の決め方」）に使う。
`handleAction` と `onDeadline` は呼び出しをまたいで状態を持たないため、`gameSecret` に置く（[ADR-0015](../adr/0015-ゲームモジュールの秘密状態を共通コアが預かる.md)）。

`cardsExplained` は秘密ではないが、公開状態に置くと `speakingOrder` と二重管理になる。
話す順は公開状態の `speakingOrder` で公開しており、元になる計数を公開する必要がない。

## action の受理規則

| action | 受理stage | 受理条件 | 違反時のコード |
| --- | --- | --- | --- |
| `ready` | `briefing` | 送信者が参加者 | `invalid_stage` |
| `startTurn` | `handoff` | 送信者が説明役のペアの一員 | `invalid_stage` / `not_explainer` |
| `claimCorrect` | `explaining` | 送信者が説明役のペアの一員、`teamId` が説明役以外のペア、`cardId` が現在のお題 | `invalid_stage` / `not_explainer` / `invalid_target` / `stale_card` |
| `passCard` | `explaining` | 送信者が説明役のペアの一員、`cardId` が現在のお題 | `invalid_stage` / `not_explainer` / `stale_card` |

これらのコードは共通コアのエラーコード表に含めず、ゲームモジュールが `GameTransition.reject` で返す。
参加者でない送信者と未知の action は `invalid_stage` で拒否する（[14](./14_SECRETRULEゲームモジュール.md) と同じ）。
1つの action が複数の拒否条件に当たる場合は、表の左から順に判定し、最初に当たったコードを返す。

自由英文の提出はない。
`action` ペイロードはidと数値だけであり、長さ上限（[ADR-0023](../adr/0023-actionペイロードに長さ上限を課す.md)）に収まる。

### ready

二重送信は拒否せず冪等に扱う（収録7本と同じ）。
接続中の全員が揃ったら最初の `handoff` へ進む。

### startTurn

`explaining` へ遷移し、`deadlineSeconds` に `turnSeconds` を設定する。
説明役のペアのどちらが送ってもよい。
先に送った1件で遷移し、後から届いた1件はステージ違いで `invalid_stage` になる。

### claimCorrect

payloadは `{ cardId: string; teamId: string }` とする。

1. `scores` の説明役のペアと `teamId` のペアに各+1
2. `solvedThisTurn` を1増やす
3. 現在のお題を `usedCards` へ `solved` として加え、`lastCard` に載せる
4. `cardsExplained` を1増やし、次のお題を引いて `speakingOrder` を更新し、説明役のペアへ送る
5. 消費上限に達したか山札が尽きたら、その手番を終える

説明役のペアの2人がほぼ同時に申告した場合、後から届いた申告は `cardId` が古くなるため `stale_card` で拒否される。
同じお題に二重に加点されない。

申告の取り消しは設けない。
[09](./09_DONTSAYITゲームモジュール.md) の `reportViolation` と同じく、取り消しを許すと、誰がいつまで取り消せるかの規則が要る。
誤操作は1点の差にとどまる。

確認シートは送信できたときだけ閉じる（[09](./09_DONTSAYITゲームモジュール.md) の `claimCorrect` と同じ）。

### passCard

payloadは `{ cardId: string }` とする。

現在のお題を `usedCards` へ `passed` として加え、`lastCard` に載せる。
得点は動かさない。
次のお題へ進む処理は `claimCorrect` の4と5と同じである。

送りの回数は手番ごとに制限せず、消費上限（5回）に含める。

[09](./09_DONTSAYITゲームモジュール.md) は送りを1ラウンド1回に限るが、本ゲームでは送りが2つの用途を持つ。
知らないお題を飛ばす用途と、言えない語を言ったお題を捨てる用途である。
1回に限ると、知らないお題で送りを使った後に言えない語を言った場合に、捨てる手段がなくなる。

回数を制限しないと、説明しやすいお題が出るまで送り続けられる。
この掘り方は、消費上限と持ち時間で抑える。
1語ずつ交互に話す説明は1枚に時間がかかるため、送りを重ねると持ち時間の大半を失う見込みである（未検証）。

1手番2回までに制限する案も採らない。
送りの総数は消費上限で頭打ちになり、回数の制限を別に重ねると、知らないお題と言えない語が重なった手番で捨てる手段が尽きる。

## ステージの終わりの処理

| ステージ | 処理 |
| --- | --- |
| `briefing` | 最初の `handoff` へ進む |
| `handoff` | 説明役のペアの接続中の人数が2人以上なら `explaining` へ進む。2人未満ならその手番を飛ばす |
| `explaining` | 現在のお題を `usedCards` へ `timeout` として加え、`turns` に集計を足して3つのカウンタを戻す。最後の手番なら `result` を返して `debrief` へ、そうでなければ次の `handoff` へ進む |
| `debrief` | 締切を置かない |

`explaining` の締切で終えた手番のお題は捨て札にし、次の手番は新しいお題から始める。
持ち越すと、場がすでに聞いた説明のお題を次のペアが説明することになる（[09](./09_DONTSAYITゲームモジュール.md) と同じ理由）。

`handoff` で説明役のペアの接続中の人数が2人未満なら、1人では交互に話せないため、その手番を飛ばす。
3人組は2人が接続していれば進める。
飛ばした手番は `turns` に `skipped: true` として記録する。

飛ばした手番で引いていたお題は山札から落とし、`usedCards` へは加えない。
`explaining` に一度も入っていないお題は誰も説明していないため、結果で開示しない（[09](./09_DONTSAYITゲームモジュール.md) と同じ扱い）。

`explaining` の途中で説明役の1人が切断しても、手番は続ける。
残った人が1人で話す状態になるが、持ち時間の範囲で場に委ねる。

## 得点

| 事象 | 説明役のペア | 当てたペア |
| --- | --- | --- |
| 正解の申告 | +1 | +1 |
| 送り | 0 | なし |
| 時間切れ | 0 | なし |

得点はペア単位とし、個人の得点を持たない。

説明役のペアにも加点するのは、伝わる説明を目指す動機を説明役に持たせるためである（[09](./09_DONTSAYITゲームモジュール.md) の「得点」と同じ理由）。
当てる側にだけ加点すると、説明役のペアは当てさせても得をしない。

違反に減点を置かない。
交互の違反は説明のやり直しで扱い、言えない語の違反は送りで扱う。

得点は1ゲーム内で閉じる（[ADR-0011](../adr/0011-部屋単位の通算スコアを持たない.md)）。
同点の扱いは決めず、同じ順位として表示する。

## 結果（result.payload）

```typescript
interface TwoHeadedResult {
  teams: TeamPublic[];
  scores: TeamScore[];               // points降順
  turns: TurnSummary[];
  usedCards: { answer: string; ja: string; teamId: string; outcome: "solved" | "passed" | "timeout"; guessedTeamId: string | null }[];
  keyExpressions: { en: string; ja: string }[];
}
```

`usedCards` には、正解、送り、時間切れのお題をすべて載せる。
時間切れのお題も説明役のペアが説明したお題であり、何を説明していたかを振り返れる。

結果にペアの構成を載せるのは、`finished` のまま再接続した人へ共通コアが `lastResult` を再送するため、結果画面が公開状態に依存しないようにするためである（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断）。

## レベル差の吸収

4層で吸収する。

第1層はペアの編成である。
`formBalancedTeams` がペアの合計レベルの差を小さくするため、ペアどうしの強さが揃い、上級者と初級者が組みやすい（[ADR-0032](../adr/0032-チーム編成は自己申告レベルで揃えて開始時に抽選する.md)）。

第2層は1語ずつの制約そのものである。
1人が言うのは1回に1語であり、`is`、`a`、`very` のような短い語でも文に加われる。
文の骨格を上級者が作り、初級者が1語を足す形でも、説明は進む。

第3層はお題の日本語名と書き出しの例である。
説明役のペアには日本語名を出し、英語名でお題を認識できない経路を塞ぐ。
書き出しの例（`starters`。`It is a ...`、`You use it to ...` など）は、レベル1〜2の画面では常に開き、レベル3〜5の画面では折りたたむ。

第4層は、答えを声で言う形である。
画面に英単語を打つ速さと正確さを競わないため、タイプの速さの差が勝敗に出ない。

上級者が文の行き先を決め、相方の語を上書きするように話す偏りは残る。
1語ずつ交互に話す以上、上級者も相方の語を受けないと文を続けられないため、偏りは弱まる見込みである。
偏りが遊びとして問題になるかは未検証である。

## 設定

| key | labelJa | 型 | 範囲 | 既定 |
| --- | --- | --- | --- | --- |
| `turnSeconds` | 1手番の説明時間（秒） | number | 60〜120、step 15 | 90 |
| `laps` | 周回数 | select | `"1"` / `"2"` | `"2"` |

`turnSeconds` の下限を60秒に置くのは、1語ずつの説明は1枚に時間がかかり、60秒未満では1枚も当たらない手番が増える見込みだからである（未検証）。
上限を120秒に置くのは、8人で2周で所要時間が20分を超えるためである（「所要時間の見積り」）。

`laps` の既定を2周とするのは、1周ではペアが説明役を1回しか務めないためである。
6人で1周では3手番で終わり、1人が説明に加わる時間は合計90秒にとどまる。

DON'T SAY ITの既定は1周であり、本ゲームと異なる。
DON'T SAY ITは1人が1手番を務めるため、1周でも人数分の手番がある。

周回数の選択肢はDON'T SAY ITとBLIND ROOMの同名の定数と同じ形である。
本ゲームで3つ目のコピーになるため、共通コアへ移す条件（[ADR-0020](../adr/0020-ゲーム間で重複する部品は共通コアへ置く.md) の条件2）を満たす。

本ゲームに複製せず、共通コアへ移すことに決めた。
複製して移す判断を先送りする案は、ADR-0020が移すとした状態をそのまま残すため採らない。

移す作業は本ゲームの実装より前に、`shared/core/` を変える単独のPRで行う（[開発ガイド.md](../開発ガイド.md) の「モジュール境界と並行作業」）。
本文書を確定した時点では、コードは移していない。

`validateSettings` は範囲外と型違いを拒否し、`settings` が無い場合とキーが欠けている場合は既定値を使う。
記述子の `min` / `max` と受理範囲の一致をテストで固定する。

## start の処理順

1. `contentId` からお題セットを引く。`listContents` に載るidだけを受理する
2. `settings` を確定する（既定 `turnSeconds` 90秒、`laps` 2周）
3. `seed` から乱数を作り、参加者の並びを `shuffle` する
4. 人数から `sizes` を決め（「ペアの編成と奇数人数」）、`formBalancedTeams` でペアに分ける。返った順に `t1` から `teamId` を振る
5. `turnOrder` を、ペアの並びを周回数だけ繰り返した列にする
6. 山札を `shuffle` し、`cursor` を0、`cardsExplained` を全ペア0にする
7. 全員へ `GuesserSecret` を送る
8. `stage` を `briefing`、`deadlineSeconds` を90として返す

手順3で先に並びを入れ替えるのは、`formBalancedTeams` が各ペアの中の並びを入力の順のまま返すためである（`shared/core/src/teams.ts`）。
入れ替えないと、入室の早い人がペアの中で常に先頭になり、最初のお題で先に話す。

抽選は共通コアが注入した `seed` からのみ行う（[05](./05_ゲームモジュール.md) の呼び出し規約）。

## 画面

画面は `client/games/twoheaded/` に置く。

| ステージ | 説明役のペアの画面 | 当てる側の画面 |
| --- | --- | --- |
| `briefing` | 遊び方、ペアの一覧、交互の違反とやり直しの規則、言えない語の規則、準備完了ボタン | 説明役のペアと同じ |
| `handoff` | お題（伏せ面のカットインで開く）、日本語名、言えない語、話す順、開始ボタン、得点 | 次の説明役のペア、話す順、得点 |
| `explaining` | お題、日本語名、言えない語、話す順、書き出しの例、「だれが当てた？」の申告、送りボタン、残り時間 | 説明役のペア、話す順、答えるときの言い回し、直前のお題の答え、残り時間 |
| `debrief` | ペアごとの得点と順位、使ったお題と結果 | 説明役のペアと同じ |

画面の要点を挙げる。

* 話す順は、最初に話す人を大きく出す。自分が最初なら「あなたから」と出す。1語ごとに表示を切り替えない（「交互の手番は画面に話す順を示すだけにする」）
* 「だれが当てた？」のシートには、説明役以外のペアをペア単位のボタンで並べ、各ボタンにペアの全員のアイコンと名前を添える
* 説明役のペアの画面を当てる側に見せない約束を `briefing` で示す。守られているかは機械で検出せず、場に委ねる（[13](./13_ESCAPECALLゲームモジュール.md) の「自分の画面を見せない約束」と同じ扱い）
* 当てる側の画面には、直前に終えたお題の答えと、当てたペアを出す（公開状態の `lastCard`）
* 自分のペアは、色だけでなく「あなたのペア」の文字で示す

当てる側の言い回し（`Is it a ...?` / `Say it again, please.` / `One more word!` など）はモジュールの定数とし、コンテンツに持たせない（[09](./09_DONTSAYITゲームモジュール.md) の「表示文言の定数」と同じ判断）。

## 所要時間の見積り

締切は上限であり、`handoff` は説明役のペアが操作すれば短くなる。
1手番は最大120秒（`handoff` 30秒 + `explaining` 90秒）であり、`briefing` 90秒と結果の確認60秒を加えた上限は次のとおりである。

| 卓 | 手番の数 | 1ゲームの上限 |
| --- | --- | --- |
| 6人で2周（既定） | 6 | 870秒（14.5分） |
| 7人で2周 | 6 | 870秒（14.5分） |
| 8人で2周 | 8 | 1110秒（18.5分） |
| 6人で1周 | 3 | 510秒（8.5分） |
| 8人で1周 | 4 | 630秒（10.5分） |

既定値で6人は15分以内、8人は20分以内に収まる。
`turnSeconds` を上限の120秒にすると、8人で2周は1350秒（22.5分）となり、20分を超える。

**実測はしていない。**
1語ずつの説明で1手番に何枚当たるかも未実測であり、2〜4枚と見込む。

実プレイで超過する場合は、`turnSeconds` の既定を75秒へ下げる。
周回数の既定を1周へ戻すのは最後にする。説明役を1回しか務めない人が出るためである。

### DON'T SAY ITのお題セットとの関係

カードの形はDON'T SAY ITのカード（`content/dontsayit/*.json`）から `taboo` を除いたものと同じである。
ただし、DON'T SAY ITのファイルを直接読まず、`content/twoheaded/` に独自のセットを置く。

直接読まない理由は2つある。

* 検証の基準が違う。DON'T SAY ITのセットは禁止語の検証（検証1〜3、9〜17）を通すために編集されており、禁止語の編集が本ゲームの差分として現れる。逆に本ゲームの都合でカードを足すと、DON'T SAY ITの検証が落ちる
* 向くお題が違う。1語ずつの説明では、人物名の多いFamous FiguresとGreat Figuresは難所が多い見込みである（未検証）。身の回りのもの（`everyday-things.json`）と場所（`places.json`）を起点にする

初版のセットは、DON'T SAY ITの `everyday-things.json` から `id`、`answer`、`ja`、`aliases` を写して作る。
写した後は別のセットとして扱い、DON'T SAY ITのセットの変更を追わない。

同じ部屋でDON'T SAY ITと本ゲームを続けて遊ぶと、同じお題が再登場する。
[09](./09_DONTSAYITゲームモジュール.md) の「正解の重複はセット内しか検査しない」と同じく、セットをまたぐ重複は機械で検査しない。

## 検証項目

`pnpm validate:content` で検査する。

| # | 検証 | 判定 |
| --- | --- | --- |
| 1 | スキーマ | 必須欄の欠落、型違い、定義に無い欄を落とす。カードidがセット内で一意 |
| 2 | 正解名の文字種 | `answer` が英字、空白、ハイフン、アポストロフィのみで構成され、先頭が英字 |
| 3 | 正解の一意 | 正規化した `answer` がセット内で重複しない |
| 4 | 山札の枚数 | カードが40枚以上ある |
| 5 | 日本語名 | `ja` に日本語の文字が1文字以上含まれる |
| 6 | 別名の形 | 各別名が `answer` と同じ文字種で、3件以内で、`answer` と重複しない |
| 7 | 書き出しと言い回し | `starters` が3件以上で各文が空欄（`...`）を含む。`keyExpressions` が1件以上 |
| 8 | 表示文言 | すべての `ja` と `en` が空でない |

検証4の下限は、1手番の消費上限（5枚）、ペアの数の上限（4組）、周回数の上限（2周）の積から導く（5 × 4 × 2 = 40）。
下限を下回ると、最後のペアに説明役が回らない山札が検証を通る。

検証8を置くのは、`ja` がフォントサブセットの入力になるためである（[07](./07_リポジトリとツールチェーン.md)）。

### 機械で検査しないもの

* 参加者がそのお題を知っているか
* 1語ずつ交互に話す形で、お題が説明できる範囲にあるか

いずれも人手で確認し、[お題レビュー/](../お題レビュー/) に記録する。

## 判定の規則

得点に直結する裁定であり、遊び方の画面はこの規則の表示である。

* 交互の違反があれば、言いかけの文を捨てて話す順の先頭から言い直す。判定に迷ったらセーフとする
* 言えない語を言ったら、そのお題を送る
* 答えは日本語読み、語順違い、広く通じる通称でも、お題を一意に指していれば正解とする（[09](./09_DONTSAYITゲームモジュール.md) の「正解の判定」と同じ）
* 最初に当てたペアは説明役のペアが決める。ほぼ同時なら、説明役のペアが先に聞こえたと判断した方とする
* 身振りは違反にしない

## 原案からの変更

| 変更 | 理由 |
| --- | --- |
| 答えを画面への入力から声へ変え、説明役のペアが当てたペアを申告するようにした | 文字列の比較では表記ゆれを吸収しきれない。タイプの速さが勝敗に出る。当てる側の発話が減る |
| 「最初に当てた」の判定をサーバの受理順から説明役のペアの判断へ変えた | 声で答える形では受理順を比べる対象がない。受理順には端末と回線の差が入る |
| 1つの文に限らず、文を続けて説明してよいことにした | 1文で伝わらないお題で手番が止まる。交互の順は文をまたいで続ける |
| 対応人数を6〜8人にした | 2組では得点の付け方が競争として成り立たない |
| 7人のときに3人組を作るようにした | 7人目を説明に加えないと、その人が英語を話す機会がほとんど無くなる |
| 1手番に時間と消費上限を置いた | 原案は1手番の終わりを決めていない |

## テスト観点

`GameModule` は純粋関数のため、Durable Objectなしで全項目をテストする。

* 決定性: 同じ `seed` と同じ参加者から、同じペア、`turnOrder`、山札の順序が得られること
* 編成: 6人で `[2, 2, 2]`、7人で `[2, 2, 3]`、8人で `[2, 2, 2, 2]` のペアができ、全員がちょうど1組に入ること
* 編成: 入室順の先頭の人が、多数の `seed` でペアの中の先頭に偏らないこと
* 手番の巡回: 全ペアが周回数と同じ回数ずつ説明役を務めること
* 話す順: 2人のペアでお題ごとに先に話す人が入れ替わり、3人組で3人が順に先頭になること。手番をまたいでも数え直さないこと
* 秘密の非混入: どのステージの公開状態にも、終えていないお題の `answer`、`ja`、`aliases` と山札の残り枚数が現れないこと
* 秘密の非混入: 遷移ごとに、公開状態のキーと配列の要素のキーが許可リストと一致すること
* 秘密の非混入: `listContents()` の戻り値にお題が含まれないこと
* 秘密の配布: 説明役のペアの全員に同じお題が届き、当てる側にお題が届かないこと。`start` で全員に `GuesserSecret` が届き、1枚目は `handoff` で届くこと
* 役の切り替え: `handoff` のたびに全員へ秘密が送り直され、前の手番の説明役にお題が残らないこと
* `startTurn`: 説明役のペア以外が `not_explainer` で拒否されること
* `claimCorrect`: 自分のペアと存在しないペアが `invalid_target`、古い `cardId` が `stale_card` で拒否され、得点が動かないこと
* `claimCorrect`: 説明役のペアの2人がほぼ同時に申告しても、加点が1回だけであること
* `passCard`: 得点が動かず、消費上限に数えられること
* 消費上限: 5回で手番が終わり、`turns` に集計が入ること
* 山札: 8人で2周の8手番で毎手番上限まで消費しても、下限枚数の山札が尽きないこと
* 未接続: `handoff` の締切で説明役のペアの接続中が2人未満なら手番が飛ばされ、そのお題が `usedCards` に入らないこと。3人組は2人で進むこと
* 締切: `explaining` の締切で表示中のお題が `timeout` として記録され、3つのカウンタが戻ること
* `lastCard`: 正解と送りで更新され、手番が変わると `null` に戻ること
* 結果: 得点の降順に並び、同点が同じ順位になること。`usedCards` に飛ばした手番のお題が含まれないこと
* 作り直し: 遷移が返した秘密を `playerId` ごとに上書きで溜めた値と `rebuildSecret` の戻り値が、各遷移の直後に全員について一致すること。消費上限、送り、締切、未接続での手番の飛ばし、山札切れ、1周と2周、6人、7人、8人を通す
* 作り直し: `finished` で全員に `undefined` を返すこと。お題セットが無い場合、表示中のお題がセットに無い場合、`gameSecret` が無い場合に例外を投げること
* 設定: 記述子の `min` / `max` と `validateSettings` の受理範囲が一致すること
* 人数: 6人と8人で開始から `debrief` まで進むこと（[ADR-0033](../adr/0033-対象人数の上限を8人に上げる.md) の申告範囲の両端）
* 検証: 検証1〜8がそれぞれ違反を落とすこと
* 通しE2E: 6人と8人で結果まで進み、当てる側の画面にお題が出ないこと
