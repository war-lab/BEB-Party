# 基本設計: 事件データと検証

## 結論

事件データは `content/detectives/*.json` の静的ファイルとし、スキーマの正本は `shared/games/detectives/case.ts` の型定義とする。

すべての事件は前方推論による6項目の機械検証（`pnpm validate:content`）をCIで通過しない限りマージできない。

制作は「Claude Codeで生成 → 機械検証 → 人手レビュー → 実プレイ確認」のパイプラインで行う。

本文書はDETECTIVESのコンテンツと検証を対象とする。
推論エンジン（`tools/engine`）はゲーム非依存の汎用推論器であり、DETECTIVESの検証はその上に載る `GameModule.validateContent` の実装である（[05_ゲームモジュール.md](./05_ゲームモジュール.md)）。

データ構造の全体像は [設計.md](../設計.md) の事件データモデルを正とし、本文書は検証アルゴリズムと制作手順を定める。

## 検証エンジン（tools/engine）

検証は決定論的な前方推論で行う。

* 入力: 事実の集合（facts + バリアントの嘘による差し替え）と、矛盾定義（contradictions）
* 推論: `requires` がすべて満たされた `contradictions` / 導出を繰り返し発火させ、不動点まで進める
* 出力: 到達した結論の集合

このエンジンは将来のESCAPEモード（解法グラフの可解性検証）と共用するため、DETECTIVES固有の語彙に依存しない汎用の推論器として実装する。

## 矛盾定義の規約

`contradictions[].requires` には、そのバリアントの嘘fact（`lie.replaces` が指すid）を必ず含める（[ADR-0008](../adr/0008-矛盾定義は嘘factを明示的に含める.md)）。

嘘factを含めないと、正直な証言だけで矛盾が発火し、検証項目4（冤罪なし）に必ず違反する。
矛盾は「犯人の主張と他者の証言の突き合わせ」で生じるものであり、嘘を前提に明記するのが意味論として正しい。

したがって `requires` は最小で3要素（嘘fact + 他者2人分のfact）になる。

## 検証6項目

全事件 × 全バリアント × 対応人数（5人版は `merge5p` 適用後）に対して検査する。

| # | 検証 | 判定方法 |
| --- | --- | --- |
| 1 | 可解性 | 全員の証言（犯人は嘘に差し替え）を投入し、犯人を一意に指す矛盾が導出される |
| 2 | 全員必須 | 任意の1キャラクターの証言を除くと、#1が不成立になる |
| 3 | 単独不可 | すべての矛盾の `requires` のうち、犯人以外が所有するfactが2つ以上あり、かつその所有者が2人以上である |
| 4 | 冤罪なし | 嘘factを投入しない状態では矛盾が1つも導出されない |
| 5 | 未使用なし | すべての事実が、少なくとも1つのバリアントの推論経路に寄与する |
| 6 | 表示完全性 | 全fact（嘘factを含む）の `text` にレベル1〜5すべての英文と `hintJa` があり、briefing・reveal・keyExpressions が揃っている |

\#3で嘘factを頭数に数えない理由は、数えると「犯人1人 + 他者1人」で条件を満たし、他者1人の証言だけで嘘が割れる事件を通してしまうためである。

\#6が全レベルを要求する理由は、配役が相対的な割り当てであり、キャラクターの `recommendedLevel` と実プレイヤーのレベルが一致する保証がないためである（[ADR-0007](../adr/0007-犯人バリアントは実配役プレイヤーのレベルで抽選する.md)）。

検証失敗時は、どの事件・バリアント・人数版・項目で落ちたかと、反例（除いたキャラクター、導出できなかった結論）を出力する。

`content/detectives/` が空、または対象0件で検証が終了した場合はPASSではなくエラーとする（骨組み段階で検証が空回りしていることに気付けるようにする）。

## 5人版（merge5p）の扱い

`merge5p` で2キャラクターを統合すると、`requires` に含まれるfactの所有者が統合されて1人になる場合がある。
このとき6人版では通っていた検証3（単独不可）が5人版で落ちる。

これは自動解決しない。該当する矛盾には `requires5p` を明示し、5人版では別のfact組で矛盾が成立するよう事件データ側で設計する。

* `requires5p` が `null` の矛盾は、5人版でも `requires` をそのまま使う
* 検証は5人版に対しても6項目すべてを課す。5人版だけ緩めることはしない
* 統合によって所有者が1人になる `requires` を持ち、かつ `requires5p` が未指定の場合は検証エラーとする（設計漏れの検出）

## 追加のリント項目

推理の成立とは別に、ゲーム体験のための機械チェックを行う。

* レベル1〜2のキャラクターが、少なくとも1つの矛盾の `requires` に含まれる（初級者が推理に必須である）。検証2があれば理論上は含意されるが、落ちたときの原因が分かりやすいので独立の項目として残す
* `hintJa` は語義のみとし、文全体の和訳を禁止する。機械側では「`hintJa` が `value` の構成要素（時刻・場所・人物）を2つ以上同時に含む場合」を警告する
* 英文の目安長: レベル1は8語以内、レベル5は15語以上を警告（エラーにはしない）
* バリアント数がキャラクター数と一致しない場合は警告する（誰が犯人でも成立させる方針の逸脱検知）

バリアントの `culprit` をキャラクターの `recommendedLevel` で制限するリントは廃止した。
制限は配役後に実プレイヤーのレベルで行うため、事件データ側の静的リントでは達成できない（[ADR-0007](../adr/0007-犯人バリアントは実配役プレイヤーのレベルで抽選する.md)）。

## 制作パイプライン

1. **生成**: Claude Codeに既存事件と本文書を読ませ、新しい事件JSONを生成させる（開発時のみ。ランタイム生成はしない）
2. **機械検証**: `pnpm validate:content` で6項目 + リントを通す。失敗したら反例を添えて修正させる
3. **人手レビュー**: 下記チェックリストで確認する
4. **実プレイ確認**: 1回以上のテストプレイを経てから既定の事件リストに載せる

### 人手レビューのチェックリスト

機械検証が保証しない品質を人が見る。

* 嘘が英会話の中で自然に発話できる内容か（数値の暗記合戦になっていないか）
* 各レベルの英文がそのレベル帯にとって適切な難度か
* 事件の題材が全員で笑える内容か（実在の人物・差別的な設定・重すぎる犯罪を避ける）
* `hintJa` が語義の説明にとどまっているか。「英文を読まずヒントだけで発話できる」状態になっていないか（機械側の警告は補助であり、最終判断は人が行う）

## ファイル規約

* ファイル名: `content/detectives/<英語スラッグ>.json`（例: `cafe-theft.json`）
* `id` はファイル名スラッグ + バージョン（例: `cafe_theft_v1`）とし、内容の互換性を壊す修正で版を上げる
* 事件の一覧はビルド時に `content/detectives/` を走査して生成し、手動の目次ファイルを持たない
* クライアントへ配る公開メタ情報（`CaseSummary`）も同じ走査結果から射影する（[01_サーバ.md](./01_サーバ.md)）

## 日本語グリフのサブセット化

`hintJa` と `briefing.ja` は事件データ由来の日本語であり、事件を追加するたびに必要なグリフが増える。

自前配信するフォントを「使用グリフへサブセット化」する方針（[ビジュアルデザイン.md](../ビジュアルデザイン.md)）を成立させるため、サブセット生成の入力は次の2つを合わせた集合とする。

1. `client/` のUI固定文言から抽出した文字
2. `content/detectives/*.json` の日本語フィールド（`briefing.ja`、`hintJa`、`meaningJa`、`keyExpressions[].ja`）から抽出した文字

この抽出はCIのビルド工程に組み込む。
事件追加PRでフォントの再生成を忘れると、その事件だけ文字が欠けて表示される（豆腐になる）ため、抽出は手動手順にしない。
