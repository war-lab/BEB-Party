# 基本設計: 事件データと検証

## 結論

事件データは `content/detectives/*.json` の静的ファイルとし、スキーマの正本は `shared/games/detectives/case.ts` の型定義とする。

すべての事件は前方推論による8項目の機械検証（`pnpm validate:content`）をCIで通過しない限りマージできない。

制作は「Claude Codeで生成 → 機械検証 → 人手レビュー → 実プレイ確認」のパイプラインで行う。

本文書はDETECTIVESのコンテンツと検証を対象とする。
推論エンジン（`shared/engine`）はゲーム非依存の汎用推論器であり、DETECTIVESの検証はその上に載る `GameModule.validateContent` の実装である（[05_ゲームモジュール.md](./05_ゲームモジュール.md)、[ADR-0014](../adr/0014-推論エンジンを独立パッケージにする.md)）。

データ構造の全体像は [設計.md](../設計.md) の事件データモデルを正とし、本文書は検証項目の意味と制作手順を定める。
判定アルゴリズムと5人版の導出手順は [06_推論エンジンと検証アルゴリズム.md](./06_推論エンジンと検証アルゴリズム.md) を正とする。

## 検証エンジン（shared/engine）

検証は決定論的な前方推論で行う。

* 入力: 事実の集合（facts + バリアントの嘘による差し替え）と、矛盾定義（contradictions）
* 推論: `requires` がすべて満たされた規則を繰り返し発火させ、不動点まで進める
* 出力: 到達した結論の集合

このエンジンは将来のESCAPEモード（解法グラフの可解性検証）と共用するため、DETECTIVES固有の語彙に依存しない汎用の推論器として実装する。
エンジンの意味論・停止性・APIは [06](./06_推論エンジンと検証アルゴリズム.md) を正とする。

## 矛盾定義の規約

`contradictions[].requires` には、そのバリアントの嘘fact（`lie.replaces` が指すid）を必ず含める（[ADR-0008](../adr/0008-矛盾定義は嘘factを明示的に含める.md)）。

嘘factを含めないと、正直な証言だけで矛盾が発火し、検証項目4（冤罪なし）に必ず違反する。
矛盾は「犯人の主張と他者の証言の突き合わせ」で生じるものであり、嘘を前提に明記するのが意味論として正しい。

したがって `requires` は最小で3要素（嘘fact + 他者2人分のfact）になる。

### バリアント間で変わる事実の扱い

v1スキーマが表現できるのは「犯人の正直な証言1枚を嘘に差し替える」ことだけとする。
犯人が誰かによって事件の真相そのものが変わる事件（他者の証言の意味も変わる事件）は、v1では作らない。

facts全体をバリアントごとに切り替える仕組みを先に用意しない理由は2つある。
第一に、反例出力がバリアント単位で複雑になり、事件データの修正が難しくなる。
第二に、1枚差し替え方式でも「誰が犯人でも成立する」というリプレイ性の要件（[構想v2](../構想v2.md)）は満たせる。

必要になった場合は、`variants[].lie` を1件から配列へ拡張し、他者のfactの差し替えも許す方向で検討する。
スキーマを変える際は、既存事件の `id` の版を上げる。

## 検証8項目

全事件 × 全バリアント × 対応人数（5人版は `merge5p` 適用後）に対して検査する。

| # | 検証 | 何を保証するか |
| --- | --- | --- |
| 1 | 可解性 | 全員の証言が揃えば犯人に到達できる |
| 2 | 全員必須 | 犯人以外の誰か1人が黙ると真相に届かない |
| 3 | 単独不可 | 犯人以外の2人以上の証言を突き合わせないと嘘が割れない |
| 4 | 冤罪なし | 正直な証言だけからは矛盾が生まれない |
| 5 | 未使用なし | どの証言も推理のどこかで使われる |
| 6 | 表示完全性 | 全事実にレベル1〜5の英文と `hintJa` があり、briefing・reveal・keyExpressions が揃っている |
| 7 | バリアント非干渉 | ある人が犯人の回に、別の人を指す矛盾が同時に成立しない |
| 8 | 犯人が握らない | 矛盾の成立に、犯人自身の証言（嘘カードを除く）を必要としない |

判定手順は [06_推論エンジンと検証アルゴリズム.md](./06_推論エンジンと検証アルゴリズム.md) を正とする。

\#3で嘘factを頭数に数えない理由は、数えると「犯人1人 + 他者1人」で条件を満たし、他者1人の証言だけで嘘が割れる事件を通してしまうためである。

\#6が全レベルを要求する理由は、配役が相対的な割り当てであり、キャラクターの `recommendedLevel` と実プレイヤーのレベルが一致する保証がないためである（[ADR-0007](../adr/0007-犯人バリアントは実配役プレイヤーのレベルで抽選する.md)）。

\#7が必要なのは、#1と#4の組み合わせでは犯人の一意性を保証できないためである。
#1はそのバリアントの矛盾が発火することしか見ず、#4は正直な証言だけの状態しか見ない。
どちらも「Aが犯人の回にBを指す矛盾も同時に発火する」事件を通してしまい、実プレイでは無実のBが毎回黒く見える形で破綻する。

\#8が必要なのは、犯人が自分の証言を出す義務を持たないためである。
`disclosure` が `free` でも「話してよい」であって「話さなければならない」ではない。
矛盾の `requires` に犯人自身の事実が入っていると、犯人はその1枚を黙っているだけで卓が真相へ到達できなくなる。

この形は5人版で統合先が犯人になる回に起きやすい。統合されたキャラクターの証言が犯人の手札へ移るためである。
検証3は犯人所有の事実を頭数から除くだけで存在は許し、検証2は犯人自身を検査対象から外すため、どちらもこの形を検出しない。

検証失敗時は、どの事件・バリアント・人数版・項目で落ちたかと、項目別の反例を出力する（形式は [06](./06_推論エンジンと検証アルゴリズム.md)）。

`content/detectives/` が存在するのに対象0件で検証が終了した場合は、PASSではなくエラーとする（検証が空回りしていることに気付けるようにする）。

`content/<gameId>/` ディレクトリ自体が存在しない場合はスキップする。
M0では事件データを作らないため、この区別がないとCIが恒常的に赤になる。
ディレクトリを作った時点で検証の対象となり、以後は0件がエラーになる。

## 5人版（merge5p）の扱い

`merge5p` で2キャラクターを統合すると、`requires` に含まれるfactの所有者が統合されて1人になる場合がある。
このとき6人版では通っていた検証3（単独不可）が5人版で落ちる。

これは自動解決しない。該当する矛盾には `requires5p` を明示し、5人版では別のfact組で矛盾が成立するよう事件データ側で設計する。

* `requires5p` が `null` の矛盾は、5人版でも `requires` をそのまま使う
* 検証は5人版に対しても8項目すべてを課す。5人版だけ緩めることはしない
* 統合によって所有者が1人になる `requires` を持ち、かつ `requires5p` が未指定の場合は検証エラーとする（設計漏れの検出）
* 統合先のキャラクターが犯人であるバリアントは5人版に存在しない。導出の手順と順序は [06](./06_推論エンジンと検証アルゴリズム.md) を正とする

## 追加のリント項目

推理の成立とは別に、ゲーム体験のための機械チェックを行う。

* レベル1〜2のキャラクターが、少なくとも1つの矛盾の `requires` に含まれる（初級者が推理に必須である）。検証2があれば理論上は含意されるが、落ちたときの原因が分かりやすいので独立の項目として残す
* `hintJa` は語義のみとし、文全体の和訳を禁止する。機械側では「`hintJa` が `value` の構成要素（時刻・場所・人物）を2つ以上同時に含む場合」を警告する
* 英文の目安長: レベル1は8語以内、レベル5は15語以上を警告（エラーにはしない）
* バリアント数がキャラクター数と一致しない場合は警告する（誰が犯人でも成立させる方針の逸脱検知）。5人版は統合で必ずバリアントが減るため、このリントは6人版にのみ適用する
* 5人版で統合されるキャラクターの名前が `meaningJa`・`reveal`・`briefing` に出る場合はエラーとする（上記の制約の検査）。照合は表示名と、敬称を除いた各語で行い、英字の途中では一致させない（`Ken` が `Kenji` に一致しない）。5人版に残るキャラクターと共通する語（姓の共有）は照合から外す
* 2つ以上のバリアントが同じ `lie.value` を使う場合はエラーとする。検証7は相手の `requires` が揃ったときにしか発火しないため、値の共有そのものを見る

バリアントの `culprit` をキャラクターの `recommendedLevel` で制限するリントは廃止した。
制限は配役後に実プレイヤーのレベルで行うため、事件データ側の静的リントでは達成できない（[ADR-0007](../adr/0007-犯人バリアントは実配役プレイヤーのレベルで抽選する.md)）。

## 検証を通す事件の組み立て方

検証8項目は独立していない。片方を満たすと他方が壊れる組み合わせがあるため、次の型で組むと通しやすい。
収録済みの `content/detectives/cafe-theft.json` がこの型の実例である。

1. キャラクターは6人。`recommendedLevel` は1〜5を最低1つずつ置く
2. 各キャラクターに事実を2枚持たせる。1枚目を「自分の居場所・見ていたもの」、2枚目を「店や場所の状態」にすると嘘の差し替え先が決めやすい
3. バリアントは6本。犯人の1枚目を嘘へ差し替える
4. 各バリアントの矛盾は1本にし、`requires` を「嘘fact + 犯人以外5人から1枚ずつ」とする
5. バリアントごとに「嘘を直接崩す証言」を1枚決め、それを犯人以外の誰かに持たせる。残り4枚は時間帯と経路を確定させる役に充てる
6. 12枚の事実すべてが、どこかのバリアントの `requires` に現れるように配分する

この型が要る理由は次のとおりである。

* 検証2（全員必須）は、犯人以外の全員の証言が矛盾に要ることを求める。矛盾を1本にして5人分を要求すれば自動的に満たせる
* 検証1が「`yields` を1つ以上」であるため、多段推論にすると途中結論だけで解けたことになり、検証2と両立しない（[06](./06_推論エンジンと検証アルゴリズム.md)）
* 検証3（単独不可）は、展開後の事実の所有者が2人以上であることを求める。5人分を要求していれば満たせる

`merge5p` には2つの基準がある。どちらも機械検証で検出できないため、人が確認する。

**第1基準: 統合後に「嘘を直接崩す証言」が犯人自身の手に渡らない相手を選ぶ**。
渡ってしまうと、犯人が自分の嘘を崩す証言を持つ形になり、実プレイで自明になる。

**第2基準: 統合されるキャラクターの事実は「物や場所の状態」にとどめ、自分の居場所を主張しない**。
居場所を主張する事実（「私は厨房から店内を見ていた」等）が統合先へ移ると、その人物が犯人になった回に、自分の嘘（「私は裏口から出た」）と自分の手札が正面から衝突する。
犯人は嘘以外のカードを正直に読む前提なので、誰かに質問された時点で他人の証言を待たずに露見する。
矛盾を「犯人以外2人以上の突き合わせでしか割れない」ものにする設計（[構想v2](../構想v2.md)）が、5人版でだけ崩れる。

この2基準に加えて、`meaningJa` の書き方に制約がある。

**統合されるキャラクターの名前を `meaningJa` に書かない**。
統合されたキャラクターの証言は統合先の手札に入るが、`meaningJa` の文面は人数版で切り替わらない。
名前を書くと、5人版の開示画面の解説に、その卓にいない人物の名前が出る。
証言は「厨房の床が濡れたままだったという証言」のように、人ではなく物や場所の呼称で指す。
開示画面は矛盾を構成するカードを所有者名つきで別に並べるため（[08](./08_DETECTIVESゲームモジュール.md)）、解説文が誰の証言かを書かなくても対応は追える。

統合されるキャラクター自身が犯人であるバリアントは5人版に存在しないため（[06](./06_推論エンジンと検証アルゴリズム.md) の手順4）、この制約の対象外とする。
制約は機械検証で検査する（`merge5p` の2基準と違い、名前の突き合わせは機械で判定できる）。

そのほかの注意点。

* `playerCount` の上限はキャラクター数と一致させ、下限は統合後のキャラクター数と一致させる。食い違うと検証を全項目通ったうえでランタイムの配役が例外になる
* `yields` は fact の `id` とも `value` とも衝突させない。`requires` の解決は fact を先に引くため、衝突すると書いた規則が黙って別のものに解決される
* `lie.value` はバリアントごとに違う値にする。同じ値を共有すると検証7（バリアント非干渉）で落ちる。ただし相手のバリアントの `requires` の揃い方によっては発火しないため、共有そのものをリントで警告する
* 事実の `value` は全件で一意にする。推論エンジンのシンボルになるため、重複すると別々の事実が同一視される
* レベル1の英文は8語以内、レベル5は15語以上にする。外れるとリントが警告する
* `hintJa` は「英単語 = 和の語義」の並記にとどめ、時刻や数値を書かない。書くと和訳とみなされて警告する

執筆中は単一ファイルだけを検証できる。

```bash
pnpm --filter @beb/tools exec tsx src/validate-content.ts <ファイルパス>
```

## 制作パイプライン

1. **生成**: Claude Codeに既存事件と本文書を読ませ、新しい事件JSONを生成させる（開発時のみ。ランタイム生成はしない）
2. **機械検証**: `pnpm validate:content` で8項目 + リントを通す。失敗したら反例を添えて修正させる
3. **人手レビュー**: 下記チェックリストで確認する
4. **実プレイ確認**: 1回以上のテストプレイを経てから既定の事件リストに載せる

### 人手レビューのチェックリスト

機械検証が保証しない品質を人が見る。

* 嘘が英会話の中で自然に発話できる内容か（数値の暗記合戦になっていないか）
* 各レベルの英文がそのレベル帯にとって適切な難度か
* 事件の題材が全員で笑える内容か（実在の人物・差別的な設定・重すぎる犯罪を避ける）
* `hintJa` が語義の説明にとどまっているか。「英文を読まずヒントだけで発話できる」状態になっていないか（機械側の警告は補助であり、最終判断は人が行う）

## ファイル規約

* ファイル名: `content/detectives/<英語スラッグ>.json`（例: `cafe-theft.json`）
* `id` はファイル名スラッグ + バージョン（例: `cafe_theft_v1`）とし、内容の互換性を壊す修正で版を上げる
* 事件の一覧はビルド時に `content/detectives/` を走査して生成し、手動の目次ファイルを持たない
* クライアントへ配る公開メタ情報（`CaseSummary`）も同じ走査結果から射影する（[01_サーバ.md](./01_サーバ.md)）

## 日本語グリフのサブセット化

`hintJa` と `briefing.ja` は事件データ由来の日本語であり、事件を追加するたびに必要なグリフが増える。

自前配信するフォントを「使用グリフへサブセット化」する方針（[ビジュアルデザイン.md](../ビジュアルデザイン.md)）を成立させるため、サブセット生成の入力は次の2つを合わせた集合とする。

1. `client/` のUI固定文言から抽出した文字
2. `content/detectives/*.json` の日本語フィールド（`briefing.ja`、`hintJa`、`meaningJa`、`keyExpressions[].ja`）から抽出した文字

この抽出はCIのビルド工程に組み込む。
事件追加PRでフォントの再生成を忘れると、その事件だけ文字が欠けて表示される（豆腐になる）ため、抽出は手動手順にしない。
