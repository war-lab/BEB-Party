# 基本設計: ENGLISH RANKINGゲームモジュール

## 結論

ENGLISH RANKINGは4ステージ（`briefing` / `discussion` / `confirming` / `reveal`）を持つゲームモジュールであり、`GameModule` インターフェースの実装として完結する。

5つの項目を英語の議論で1位から5位まで並べる。
各プレイヤーには秘密の目標（例: sleepを2位以内に入れる）が配られ、目標が通れば加点される。

卓は1つの順位に合意し、ホストがそれを記録して全員の承認で確定させる。
アプリは順位と目標の照合しか行わず、英語の当否は判定しない（不変条件1）。

1ゲームは3ラウンドとし、参加人数に依存しない。
ラウンドごとに項目セットと目標が入れ替わる。

gameIdは `ranking` とする。
文書名とゲーム名は `ENGLISH RANKING` だが、既収録の2本が `detectives` / `dontsayit` と短縮している規約に合わせる。

ルールの原案は [収録候補ゲームのルール案.md](../収録候補ゲームのルール案.md) の案12であり、実装順と受入条件は [実装計画/ゲーム構想20案の収録計画.md](../実装計画/ゲーム構想20案の収録計画.md) を正とする。
本文書は、そこで未定のまま残した点を決め、ルールの正本となる。
原案から変更した点は末尾の「原案からの変更」に列挙する。

共通コアとの境界は [05](./05_ゲームモジュール.md)、メッセージの意味は [03](./03_プロトコル.md) を正とする。
共通コアへゲーム固有の概念は持ち込まない。
本ゲームの追加による共通コアの変更は生じない見込みである（乱数・タイマーバー・伏せ面・Wake Lockはすでに共通コアにある。[ADR-0020](../adr/0020-ゲーム間で重複する部品は共通コアへ置く.md)）。

## ステージ

| stage | 締切 | 遷移条件 |
| --- | --- | --- |
| `briefing` | 90秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `discussion` | `discussionSeconds`（既定120秒） | 締切到達のみ |
| `confirming` | 90秒 | 接続中の全員が `approveRanking` を送る、または締切到達 |
| `reveal` | 90秒（最終ラウンドはなし） | 接続中の全員が `ready` を送る、または締切到達 |

`reveal` が終わると次のラウンドの `briefing` へ戻る。
最終ラウンドの `reveal` へ入る時点で `result` を返し、部屋は `finished` になる。

`finished` の画面には2つの操作を置く。
「ロビーへ戻る」は `nextGame` を送って部屋をロビーへ戻す操作であり、「部屋を出る」は自分の接続を切る操作である。
2つを1つのボタンにまとめると、押した本人が部屋から出る（[08](./08_DETECTIVESゲームモジュール.md)・[09](./09_DONTSAYITゲームモジュール.md)と同じ切り分け）。

`discussion` に早期終了の操作を置かない。
議論を切り上げたい卓は締切を待たずに黙るだけで済み、操作を置くと「まだ話したい人がいるのに1人が進めてしまう」経路が増える。

`confirming` を `discussion` から分けるのは、順位の記録を議論時間の外に置くためである。
議論の締切が動いている間にホストが入力すると、ホストだけ議論に参加できない時間が生まれる。

`discussion` では Wake Lock を取得する。
全員が画面を触らずに話し続けるステージであり、スリープすると発言の途中でロック解除から始まる。

`briefing` の端末では目標を伏せ面のカットインで開く（[ビジュアルデザイン.md](../ビジュアルデザイン.md)）。
隣の席から覗かれると目標が割れるため、DETECTIVESの配役発表と同じ手順を踏む。

ラウンド間の得点表示に専用ステージを置かない。
得点は公開状態にあり、`reveal` と `briefing` の画面で見られる。

## 目標カード

目標は5項目の並びに対する述語であり、4種に限る。

| type | 意味 | 例（日本語文） |
| --- | --- | --- |
| `above` | `item` を `than` より上位に | musicをmoneyより上にする |
| `top` | `item` を `within` 位以内に | sleepを2位以内に入れる |
| `bottom` | `item` を下から `within` 位以内に | moneyを下から2位以内にする |
| `exact` | `item` をちょうど `rank` 位に | foodを3位ぴったりにする |

述語を閉じた4種に限るのは、確定順位との照合を純粋関数で書けるようにするためである。
自由記述の目標を許すと、達成の判定に人の解釈が入り、サーバ権威（不変条件5）が崩れる。

目標には日本語文（`ja`）を必ず持たせる。
目標を読み違えると議論そのものが噛み合わないため、意味の伝達を英語力に依存させない。

## 公開状態（gameState）

```typescript
interface RankingPublic {
  packId: string;
  roundIndex: number;              // 0始まり
  totalRounds: number;             // 3
  question: { en: string; ja: string };
  items: RankingItem[];            // 現ラウンドの5項目
  keyExpressions: KeyExpression[]; // 議論で使える言い回し
  readyPlayerIds: string[];        // briefing / reveal の収集状況
  proposedRanking: string[] | null;    // confirming中の提案（itemIdの並び）
  approvedPlayerIds: string[];         // 現在の提案への承認者
  scores: ScoreEntry[];
  rounds: RoundRecord[];           // 確定したラウンドの記録
  discussionSeconds: number;
}

interface RankingItem {
  id: string;
  en: string;   // 議論で使う語。画面では大きく出す
  ja: string;   // 意味の取り違えを防ぐ短い注記
}

interface ScoreEntry {
  playerId: string;
  points: number;
}

interface RoundRecord {
  setId: string;
  ranking: string[];               // 確定順位（itemIdの並び）
  goals: RevealedGoal[];           // 全員の目標と達成
}

interface RevealedGoal {
  playerId: string;
  ja: string;
  achieved: boolean;
}
```

現ラウンドの目標は公開状態に置かない。
`state` は全員へブロードキャストされるため、ここに置いた値は他のプレイヤーにも届く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。

確定したラウンドの目標は `RoundRecord.goals` に載せる。
そのラウンドは終わっており、達成の可否を全員で見ることが得点の説明になる。

`proposedRanking` は公開する。
卓が「いまホストが入れた順位」を見て承認するための値であり、伏せると承認の意味がなくなる。

未使用のセットと、抽選で選ばれた3セットのidは公開状態に置かない。
次のラウンドの項目が分かると、議論中に先の目標を考えられる。

## 秘密情報（secret.payload）

```typescript
interface RankingSecret {
  roundIndex: number;
  goal: {
    id: string;
    ja: string;        // 目標の日本語文
    hintEn: string[];  // 主張に使える英文の例
  };
}
```

配るのは自分の目標だけとする。
他人の目標が見えると、議論が「相手の目標を潰す」だけの作業になり、英語で主張を組む動機が消える。

秘密は `briefing` のたびに全員へ送り直す。
`playerSecrets` は上書きであり結合ではないため、前のラウンドの目標は残らない。

## レベル差の吸収

2層で吸収する。

第1層は目標の難度である。
目標カードは難度1〜3を持ち、参加者をレベルの昇順、カードを難度の昇順に並べて対応させる。
レベルの同値はseed由来のシャッフルで崩し、同じレベルの2人が毎回同じ難度にならないようにする。

難度は述語の型で決める。

| 難度 | 述語 | 主張に要する英語 |
| --- | --- | --- |
| 1 | `above`、`top`/`bottom` の `within` が2以上 | 2項目の比較、または1項目を上下へ寄せる主張 |
| 2 | `top`/`bottom` の `within` が1 | 1項目を端に固定する主張。他の候補を退ける根拠が要る |
| 3 | `exact` | 特定の位置に合わせる主張。前後の項目まで動かす必要がある |

絶対的な割り当てにしないのは、6枚のカードで参加者のレベル分布を選べないためである。
全員がレベル5の卓に難度3のカードを6枚配るには、コンテンツ側に難度3を6枚持たせることになり、レベル1〜2の卓では使われないカードが増える。

第2層は言い回しの支援である。
目標には `hintEn` を持たせ、その目標を主張するための英文を渡す。
レベル1〜2には3件以上、レベル3以上には1件を渡す。

`keyExpressions` は公開状態に置き、議論に使える一般的な言い回しを全員へ見せる。
目標に紐づかない汎用の表現であり、伏せる理由がない。

## 設定

| key | labelJa | 範囲 | 既定 |
| --- | --- | --- | --- |
| `discussionSeconds` | 議論時間（秒） | 60〜240、step 30 | 120 |

ラウンド数は3固定とし、設定にしない。
所要時間がラウンド数と議論時間の積で決まるため、両方を可変にすると卓が長さを予測できない。

`validateSettings` は範囲外・型違い・欠損を拒否する。
ロビーの記述子（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）の `min` / `max` と受理範囲を一致させ、その一致をテストで固定する。

## ゲーム秘密状態（gameSecret）

```typescript
interface RankingGameSecret {
  setIds: string[];                       // 使う3セットのid
  goalsByRound: Record<string, GoalCard>[]; // ラウンドごとの playerId -> 目標カード
}
```

セットの抽選と目標の割り当ては、どちらも `start` で全ラウンド分を決める。
`handleAction` と `onDeadline` にはシードが渡らないため（[05](./05_ゲームモジュール.md)の呼び出し規約）、ラウンドが進むたびに抽選する形は取れない。

過去のラウンドの目標は `RoundRecord.goals` として公開状態にも現れる。
`goalsByRound` を残すのは、得点の再計算ではなく開示済みかどうかの判断を公開状態側に寄せるためである。

## start の処理順

1. `contentId` からパックを引く。未登録なら例外ではなく空の遷移を返さず、`listContents` に載るidだけを受理する
2. `seed` から乱数を作り、パックのセットを `shuffle` して先頭3件を `setIds` に固定する
3. ラウンド0のセットで目標を配る（後述の割り当て）
4. `stage` を `briefing`、`deadlineSeconds` を90として返す

セットの抽選と目標の割り当ては共通コアが注入した `seed` からのみ行う。
`Math.random()` と時刻を使わない（[05](./05_ゲームモジュール.md)の呼び出し規約）。

### 目標の割り当て

1. 参加者をレベルの昇順に並べる。同値はseed由来のシャッフルで崩す。未接続者も含める（再接続時に目標が無い状態を作らない）
2. セットの目標カード6枚を難度の昇順に並べる
3. 参加者が5人のときは難度3のカードを1枚落とす（どれを落とすかはseedで決める）
4. 並べた順に1対1で対応させる

難度3を落とすのは、6枚の難度構成を `1,1,2,2,3,3` に固定しているためである（検証項目）。
5人で難度1を落とすと、最もレベルの低い参加者が難度2から始まる。

## カタログ（listContents）

```typescript
{ id: "values", title: "価値観", setCount: 9 }
```

項目・目標・日本語文をカタログに載せない。
ロビーで見えると、開始前に目標の候補が読める。

## action の受理規則

| action | 送れる人 | ステージ | 効果 |
| --- | --- | --- | --- |
| `ready` | 全員 | `briefing` / `reveal` | 収集に加える。接続中の全員が揃えば遷移 |
| `proposeRanking` | ホストのみ | `confirming` | 提案を差し替える。承認はすべて取り消す |
| `approveRanking` | 全員 | `confirming` | 現在の提案を承認する。接続中の全員が揃えば確定 |

ステージ違いはすべて拒否する。

### ready

二重送信は拒否せず冪等に扱う（[08](./08_DETECTIVESゲームモジュール.md)・[09](./09_DONTSAYITゲームモジュール.md)と同じ）。
結果に影響せず、再送を拒否すると画面が止まる経路が増える。

接続中の全員が送った時点で次のステージへ進む。

### proposeRanking

payloadは `{ ranking: string[] }` とする。

拒否する条件は4つある。

* ホスト以外（`not_host`）
* 要素数が5でない（`invalid_ranking`）
* 現ラウンドの `items` に無いidを含む（`invalid_ranking`）
* 同じidを2回含む（`invalid_ranking`）

提案を差し替えたら `approvedPlayerIds` を空にする。
承認した順位と確定する順位が違う状態を作らないためである。

ホストに限るのは、入力の主体が2人以上になると締切直前の上書きで先の承認が無効化され続けるためである。
ホストが卓の合意と違う順位を入れる余地は残る。
同室で全員が `proposedRanking` を見ており、承認を止めれば入れ直しになるため、機械的な防止は置かない（この限界は「未解決の論点」に記録する）。

### approveRanking

`proposedRanking` が `null` のときは拒否する（`no_proposal`）。
二重送信は `ready` と同じく冪等に扱う。

接続中の全員が承認した時点で確定し、`reveal` へ進む。

## onDeadline

| ステージ | 締切到達時の扱い |
| --- | --- |
| `briefing` | `ready` が揃っていなくても `discussion` へ進む |
| `discussion` | `confirming` へ進む |
| `confirming` | `proposedRanking` があればそれで確定する。`null` なら項目の定義順で確定する |
| `reveal` | 次のラウンドの `briefing` へ進む |

`confirming` の締切で提案が無い場合に定義順で確定するのは、進行を止めないためである。
全員が席を外した、あるいはホストが切断したままのラウンドでも、得点計算を経て次へ進む。

定義順の確定では誰の目標が通るかがコンテンツ次第になる。
これは異常系の扱いであり、通常の進行では起きない。

## 得点

目標を達成したら2点。
未達は0点とする。

減点は置かない。
議論で押し切れなかったことに罰を与えると、レベル1〜2が発言しない方が有利になる。

達成者が複数いても全員に2点入る。
目標は同時に達成できる組み合わせを持つように作るため（検証項目）、達成者が並ぶことは想定内である。

3ラウンドで取り得る点は0・2・4・6の4段階である。
同点が出やすいが、部屋単位の通算スコアを持たない方針（[ADR-0011](../adr/0011-部屋単位の通算スコアを持たない.md)）のもとでは順位付けの厳密さより読みやすさを優先する。

## 結果（result.payload）

```typescript
interface RankingResult {
  rounds: RoundRecord[];      // 3ラウンド分
  scores: ScoreEntry[];       // 降順
}
```

使わなかったセットは結果に載せない。
場に出ていない項目を振り返りに混ぜても読む理由がない。

`rounds` は公開状態と同じ内容を持つ。
`finished` のまま再接続した人へ共通コアが `lastResult` を再送するため、結果画面が公開状態に依存しないようにする。

## 所要時間の見積り

締切は上限であり、実際は `ready` と承認で先に進む。

| 区間 | 見積り |
| --- | --- |
| `briefing` | 30秒（締切90） |
| `discussion` | 120秒（設定。締切がそのまま経過する） |
| `confirming` | 40秒（締切90） |
| `reveal` | 40秒（締切90） |
| 1ラウンド | 約230秒 |
| 1ゲーム（3ラウンド） | 約12分 |

議論時間を上限の240秒にすると1ゲームは約18分になり、[収録計画](../実装計画/ゲーム構想20案の収録計画.md)の受入条件「6人で15分以内」を超える。
既定値で収まる見積りであるが、**実測はしていない**。

## コンテンツ形式

```json
{
  "id": "values",
  "title": "価値観",
  "sets": [
    {
      "id": "happy_life",
      "question": { "en": "What matters most for a happy life?", "ja": "幸せな人生に一番効くのは？" },
      "items": [
        { "id": "sleep", "en": "sleep", "ja": "睡眠" },
        { "id": "money", "en": "money", "ja": "お金" },
        { "id": "friends", "en": "friends", "ja": "友人" },
        { "id": "food", "en": "food", "ja": "食事" },
        { "id": "work", "en": "work", "ja": "仕事" }
      ],
      "goals": [
        {
          "id": "sleep_top2",
          "difficulty": 1,
          "ja": "sleepを2位以内に入れる",
          "hintEn": ["Sleep is the base of everything.", "Without sleep, nothing works.", "I put sleep first."],
          "goal": { "type": "top", "item": "sleep", "within": 2 }
        }
      ],
      "keyExpressions": [
        { "en": "I think X is more important than Y.", "ja": "XはYより重要だと思う" }
      ]
    }
  ]
}
```

1ファイルが1パックであり、パックは複数のセットを持つ。
ロビーで選ぶ単位はパックである（DON'T SAY ITのお題セットと同じ形）。

セット数の下限は6とする。
1ゲームで3セット使うため、同じ部屋で2ゲーム続けても重複しない下限である。

## 検証項目

`pnpm validate:content` で検査する。

| # | 内容 |
| --- | --- |
| 1 | スキーマ。必須欄の欠落と型違いを落とす |
| 2 | セット数が6以上 |
| 3 | セットidとパック内の一意性 |
| 4 | 項目がちょうど5件、`id` が一意 |
| 5 | 目標がちょうど6件、`id` が一意 |
| 6 | 難度の構成が `1,1,2,2,3,3` |
| 7 | 述語の参照する `item` と `than` が項目に存在する |
| 8 | `within` と `rank` が1〜5 |
| 9 | 述語の型と難度が対応表と一致する |
| 10 | 同じ述語を持つ目標が2枚ない |
| 11 | 各目標が達成可能（120通りのうち1つ以上で真） |
| 12 | 6枚を同時に達成できる順位が存在しない |
| 13 | 同時達成の最大が3枚以上 |
| 14 | `ja` が空でなく、`hintEn` が3件以上 |

検証11から13は5項目の全順列120通りを総当たりする。
項目数が5固定であり、計算量は問題にならない。

検証11は単独では発火しない。
検証7（参照の存在）と検証8（順位の範囲）を通った述語は、5項目に対して必ず達成可能な順位を持つ。
参照が壊れたときに検証7と一緒に落ちる安全網として置く。

検証12を置くのは、全員の目標が同時に通る順位があると議論に対立が生まれないためである。
検証13を置くのは、誰も他人と協調できない設定だと説得が成立しないためである。

`hintEn` を3件以上にするのは、レベル1〜2へ3件渡す設計（レベル差の吸収）に合わせるためである。

### 機械で検査しないもの

* 項目5つが同じ土俵で比べられるか（`sleep` と `money` は比べられるが、`sleep` と `Monday` は比べにくい）
* 日本語文が目標の述語を正しく言い表しているか
* `hintEn` の英文が自然か
* 議論が英語で盛り上がるか

いずれも人手のレビューで見る。
記録は `docs/お題レビュー/` に置く（DON'T SAY ITと同じ形）。

## 判定の規則

達成の判定は確定順位に対してのみ行う。
議論の内容、提案の途中経過、承認の有無は判定に影響しない。

確定順位は `RoundRecord.ranking` として保存し、後から再計算しない。
コンテンツを差し替えても過去のラウンドの記録が動かないようにする。

## 未解決の論点

| 論点 | 内容 |
| --- | --- |
| ホストが合意と違う順位を入れられる | 承認を止めれば入れ直しになるが、締切到達では承認が揃わなくても確定する。機械的な防止は置いていない |
| 同点が出やすい | 3ラウンドで0・2・4・6の4段階しかない。実プレイで得点分布を見てから、達成者が1人のときの加点などを検討する |
| 議論時間の既定値 | 120秒が6人で足りるかは未実測。足りなければ既定を上げ、ラウンド数を2へ落とす判断になる |
| 難度の相対割り当て | レベルが全員同じ卓では、難度1から3までが機械的に配られる。難度3を引いた人が不利になるかは未実測 |

## 原案からの変更

[ルール案](../収録候補ゲームのルール案.md)の案12から変えた点と、その理由を挙げる。

| 変更 | 理由 |
| --- | --- |
| ホストの入力に全員の承認を足した | 得点に直結する入力をホスト1人が握ると、卓の合意と違う順位を記録できる |
| 1ゲームを3ラウンドにした | 原案はラウンド数に言及がない。1ラウンドだと得点が0か2の2段階しかなく、結果画面が成立しない |
| 目標を機械判定可能な4種の述語に限った | 原案は「sleepを2位以内」という例のみで形式が未定だった。自由記述だと達成の判定に人の解釈が入る |
| 目標に難度を持たせ、レベルの昇順に対応させた | 原案はレベル差の吸収に触れていない。全員へ同じ難度を配ると、レベル1〜2は主張を組めない |
| 議論を180秒から既定120秒（可変）にした | 3ラウンドに増やしたため、180秒固定では1ゲームが15分を超える |
| `confirming` を独立したステージにした | 議論の締切が動いている間にホストが入力すると、ホストだけ議論に参加できない |

## テスト観点

`GameModule` は純粋関数のため、Durable Objectなしで全項目をテストする。

* 決定性: 同じ `seed` と同じ参加者から、同じ3セットと同じ目標の割り当てが得られること
* 秘密の非混入: `RankingPublic` に現ラウンドの目標が現れないこと
* 秘密の非混入: `listContents()` の戻り値に項目・目標・日本語文が含まれないこと
* 目標の配布: レベルの昇順と難度の昇順が対応すること
* 目標の配布: 5人のとき難度3が1枚落ち、残り5枚が配られること
* 目標の切り替え: `briefing` のたびに全員へ秘密が送り直され、前のラウンドの目標が残らないこと
* `proposeRanking`: ホスト以外が `not_host` で拒否されること
* `proposeRanking`: 要素数・未知のid・重複が `invalid_ranking` で拒否されること
* `proposeRanking`: 差し替えで `approvedPlayerIds` が空になること
* `approveRanking`: 提案が無い状態で `no_proposal` が返ること
* `approveRanking`: 二重送信が冪等であること（承認者が重複しない）
* `approveRanking`: 接続中の全員が承認した時点で確定し、`reveal` へ進むこと
* 達成判定: 4種の述語それぞれについて、真と偽の両方の順位で正しく判定されること
* 得点: 達成者が複数いても全員に2点入ること
* 締切: `confirming` の締切で提案があればそれが確定すること
* 締切: `confirming` の締切で提案が無ければ項目の定義順で確定すること
* 未接続: 承認していない未接続者がいても確定が進むこと
* 遷移: 最終ラウンドの確定で `result` が返ること
* 結果: `rounds` が3件になり、各件に全員の目標と達成が入ること
* 設定: 記述子の `min` / `max` と `validateSettings` の受理範囲が一致すること
* 人数: 5人でも6人でも成立すること
