# 基本設計: BLIND ROOMゲームモジュール

## 結論

BLIND ROOMは4ステージ（`briefing` / `handoff` / `building` / `reveal`）を持つゲームモジュールであり、`GameModule` インターフェースの実装として完結する。

説明者1人だけが3×3の見本を見る。
他の全員は英語の説明を聞き、同じ配置を自分の盤面に作る。
締切後に見本と全員の盤面を並べ、マス単位の一致数で採点する。

説明者を1人ずつ交代し、参加人数と同じ回数のラウンドを回す。

収録済み4本と違い、勝敗が「人の意図を当てる」ことで決まらない。
説明者と聞き手の利害が一致し、正解は見本との照合だけで決まる。
このため得点に投票が入らず、判定の主観が残らない。

gameIdは `blindroom` とする。
`dontsayit` `whowrotethis` と同じく、空白と句読点を落として連結する規則を適用する。

共通コアへの追加要求はない。
提出は9要素のアイテムID配列であり、`action` のペイロード上限（[ADR-0023](../adr/0023-actionペイロードに長さ上限を課す.md)）の範囲に収まる。
手番制も要らない。全員同時の配置と、聞き手全員から1件を収集する既存の形で足りる。

見本の配置はコンテンツとして持たず、`start` で `seed` から生成する（[ADR-0024](../adr/0024-BLINDROOMの見本盤面は生成する.md)）。

ルールの原案は [収録候補ゲームのルール案.md](../収録候補ゲームのルール案.md) の案23であり、実装順と受入条件は [実装計画/ゲーム構想20案の収録計画.md](../実装計画/ゲーム構想20案の収録計画.md) を正とする。
本文書は、そこで未定のまま残した点を決め、ルールの正本となる。
原案から変更した点は末尾の「原案からの変更」に列挙する。

共通コアとの境界は [05](./05_ゲームモジュール.md)、メッセージの意味は [03](./03_プロトコル.md) を正とする。

## ステージ

| stage | 締切 | 遷移条件 |
| --- | --- | --- |
| `briefing` | 60秒 | 接続中の全員が `ready` を送る、または締切到達 |
| `handoff` | 30秒 | 説明者が `startRound` を送る、または締切到達 |
| `building` | `buildingSeconds`（既定75秒） | 接続中の聞き手全員が `done` を送る、または締切到達 |
| `reveal` | 45秒 | 接続中の全員が `ready` を送る、または締切到達 |

`reveal` が終わると次のラウンドの `handoff` へ戻る。
最終ラウンドの `reveal` へ入る時点で `result` を返し、部屋は `finished` になる。

`handoff` を独立したステージにするのは、次の説明者が見本を読む時間を制限時間の外に置くためである（[09](./09_DONTSAYITゲームモジュール.md) の `handoff` と同じ理由）。

説明者の端末では、`handoff` の見本を伏せ面のカットインで開く（[ビジュアルデザイン.md](../ビジュアルデザイン.md)）。
交代のたびに隣の席から覗かれる位置で見本が開くため、DETECTIVESの配役発表と同じ手順を踏む。

`handoff` と `building` では Wake Lock を取得する。
説明者は `building` のあいだ画面に触らずに話し続けるため、放置すると画面が消える。

ラウンド間で得点だけを表示する専用のステージは置かない。
`reveal` が見本・盤面・一致数・加点を同じ画面で扱う。

## 進行の要点

### 盤面と配置数

盤面は3×3の9マスであり、配列の添字0〜8を左上から右下へ行優先で対応させる。

見本には5個のアイテムを置く。
残る4マスは空白である。

聞き手が置けるアイテムも5個までとする。
同じアイテムを2マスに置くことは、見本と聞き手のどちらでも認めない。

配置数を5に固定するのは、ラウンドごとの満点を揃えるためである。
配置数を説明者のレベルで変えると、聞き手が取れる最大点がラウンドごとに動き、誰が説明者だったかで得点機会が変わる。

### 採点

見本でアイテムが置かれている5マスだけを採点の対象とする。
そのマスのアイテムIDが見本と一致すれば1点であり、聞き手1人の1ラウンドの得点は0〜5になる。

空白マスを採点に含めない。
含めると、何も置かずに待つだけで4マスが一致し、聞き手が説明を聞かない方向へ利得が動く。

見本が空白のマスに聞き手がアイテムを置いても減点しない。
置ける数が5個に制限されているため、対象外のマスへ置くこと自体が持ち駒1個の損になる。

### 座標を画面に出さない

盤面のマスに番号・記号・行列のラベルを描かない。

理由は、ラベルがあれば必ず使われるためである。
`A1` や `3番` が画面にあると、説明が座標の読み上げに退化し、英語の位置表現を使う理由が消える。
ルールとして禁じるより、指し示す手段を画面から消す方が確実に働く。

一方で、番号による指定をルールとして禁じることはしない。
`second row, middle` のような順序を含む位置表現は英語として正当であり、これと「マス番号の読み上げ」の線引きが機械でも人間の合意でもできない。
判定できない禁止を置くと、違反の申告そのものが場を荒らす（[09](./09_DONTSAYITゲームモジュール.md) の違反ボタンは、正解語という機械にも人にも一意に決まる対象を持つため成立している）。

盤面の向きは全員で共通とし、説明者の見本と聞き手の盤面を同じ向きで描く。
向きが共通であれば、向きを英語で伝える工程そのものが要らない。

### 質問の扱い

聞き手の質問は口頭で行い、アプリは受け取らない。
同室で遊ぶ前提であり、質問を入力にするとテキスト入力の往復が発話を置き換える。

質問に使う言い回しは `keyExpressions` として公開状態に載せ、`building` の画面に出す。

## 公開状態（gameState）

```typescript
interface BlindRoomPublic {
  packId: string;
  roundIndex: number;                 // 0始まり
  totalRounds: number;                // 参加人数と同じ
  describerOrder: string[];           // 全ラウンド分の説明者（playerId）
  itemSetId: string;                  // 現ラウンドのアイテムセット
  palette: PaletteItem[];             // 現ラウンドのアイテム一覧（表示用）
  placeCount: number;                 // 5
  readyPlayerIds: string[];           // briefing / reveal の収集状況
  donePlayerIds: string[];            // building の完了申告。盤面は載せない
  keyExpressions: KeyExpression[];    // 聞き手の質問に使う言い回し
  rounds: RoundRecord[];              // 確定したラウンドの記録。末尾が開示対象
  scores: ScoreEntry[];
  buildingSeconds: number;
}

interface PaletteItem {
  id: string;
  en: string;
  ja: string;
  icon: string;   // client/public/items/blindroom/<icon>.svg（ADR-0025）
}

interface BoardResult {
  playerId: string;
  cells: (string | null)[];           // 9要素
  matched: number;                    // 0〜5
}

// 開示中のラウンドも確定したラウンドもこの型1つで表す
interface RoundRecord {
  roundIndex: number;
  describerId: string;
  itemSetId: string;
  sample: (string | null)[];          // 9要素。reveal で初めて公開する
  boards: BoardResult[];              // 聞き手の盤面
  describerPoints: number;
}

interface ScoreEntry {
  playerId: string;
  points: number;
}
```

`building` 中は見本を公開状態に置かない。
`state` は全員へブロードキャストされるため、ここに置いた値は聞き手にも届く（[ADR-0003](../adr/0003-サーバ権威と秘密情報の個別送信.md)）。

`building` 中は聞き手の盤面も公開状態に置かない。
他人の盤面が見えると、説明を聞かずに写す経路ができる。
公開してよいのは完了申告を出した人のidだけである。

`describerOrder` は全ラウンド分を公開する。
自分が何ラウンド目に説明者になるかが分かる方が、卓の進行を読める（[09](./09_DONTSAYITゲームモジュール.md) の `speakerOrder` と同じ扱い）。

`palette` は現ラウンドのアイテムセットだけを載せる。
パック内の他のセットを先に見せると、次のラウンドで出るアイテムを準備できる。

`palette` に `icon` を載せる。
アイテムの見た目は自作のSVGであり、絵文字を使わない（[ADR-0025](../adr/0025-盤面アイコンはSVGで持つ.md)）。
端末のシステムフォントが描く絵文字は、同じ符号位置でも絵柄がベンダーごとに違い、名前が主張する色と食い違う。

開示中のラウンド専用のフィールドは持たない。
`reveal` へ入るときに `RoundRecord` を `rounds` へ積み、開示画面は末尾の1件を読む。
開示用と確定済みで別のフィールドを持つと、同じ内容が公開状態の2箇所に載り、移し替えの経路が増える。

`scores` はゲーム全体の通算とする。
ラウンドごとの内訳は `rounds` から読めるため、別に持たない。

## 秘密情報（secret.payload）

```typescript
type BlindRoomSecret = DescriberSecret | ListenerSecret;

interface DescriberSecret {
  roundIndex: number;
  role: "describer";
  sample: (string | null)[];   // 9要素
  hintEn: string[];            // 位置表現の枠
}

interface ListenerSecret {
  roundIndex: number;
  role: "listener";
  board: (string | null)[];    // 自分の現在の盤面。再接続で復元する
}
```

秘密は `handoff` へ入るたびに全員へ送り直す。
`playerSecrets` は上書きであり結合ではないため、前のラウンドの `sample` と `board` は残らない。

`board` を返すのは、再接続した本人が自分の盤面を復元できるようにするためである。
`place` を受理するたびに本人へ送り直す。

送り直すときは `ListenerSecret` の全体を組み立てる。
共通コアは `playerSecrets[playerId]` をペイロードごと差し替えるため、部分的に返すと他の欄が消える。

聞き手の秘密に言い回しを持たせない。
質問に使う言い回しは全員が使う値であり、公開状態の `keyExpressions` に載る。
同じ一覧を秘密側にも配ると、公開済みの値を二重に持つだけになる。

`hintEn` は説明者にだけ配り、件数をレベルで変える（後述の「レベル差の吸収」）。

`hintEn` は完成文にしない。空欄（`...`）を1箇所以上含む枠とする（検証11）。
位置表現の枠にアイテム名を入れて初めて文になるため、枠であることが説明の組み立てを促す。

## ゲーム秘密状態（gameSecret）

```typescript
interface BlindRoomGameSecret {
  itemSetIds: string[];                        // ラウンドごとのアイテムセットid
  samples: (string | null)[][];                // ラウンドごとの見本。startで全ラウンド分を生成する
  boards: Record<string, (string | null)[]>;   // 現ラウンドの playerId -> 盤面
}
```

見本の生成とアイテムセットの選択は、どちらも `start` で全ラウンド分を行う。
`handleAction` と `onDeadline` にはシードが渡らないため（[05](./05_ゲームモジュール.md) の呼び出し規約）、ラウンドが進むたびに生成する形は取れない。

`describerOrder` は公開状態にあるため `gameSecret` には入れない。

`boards` は `reveal` へ入るときに `RoundRecord.boards` へ移し、空へ戻す。
公開済みの盤面を秘密側に二重で持たない。

## action の受理規則

| action | 送れる人 | ステージ | 効果 |
| --- | --- | --- | --- |
| `ready` | 全員 | `briefing` / `reveal` | 収集に加える。接続中の全員が揃えば遷移 |
| `startRound` | そのラウンドの説明者 | `handoff` | `building` へ進む |
| `place` | 説明者以外 | `building` | 盤面を上書きする |
| `done` | 説明者以外 | `building` | 完了申告を切り替える |

ステージ違いはすべて `invalid_stage` で拒否する。

拒否のコードはすべてゲームモジュール側で定義し、共通コアのエラーコード表には載せない（[01](./01_サーバ.md)、[10](./10_ENGLISHRANKINGゲームモジュール.md)、[11](./11_WHOWROTETHISゲームモジュール.md) と同じ）。
`not_describer` / `describer_cannot_place` / `invalid_board` / `unknown_item` / `too_many_items` / `duplicate_item` / `invalid_stage` の7つを持つ。

### ready

二重送信は拒否せず冪等に扱う（収録4本と同じ）。

### startRound

説明者以外からの送信は `not_describer` で拒否する。

### place

payloadは `{ cells: (string | null)[] }` とする。

拒否する条件は5つある。

| 条件 | code |
| --- | --- |
| 送信者がそのラウンドの説明者 | `describer_cannot_place` |
| `cells` が配列でない、要素数が9でない、要素が文字列でも `null` でもない | `invalid_board` |
| 現ラウンドの `palette` に無いidが含まれる | `unknown_item` |
| `null` でない要素が5個を超える | `too_many_items` |
| 同じidが2マス以上にある | `duplicate_item` |

盤面は差分ではなく全体を送る。
配置・移動・撤去のどれも「9マスの現在値」で表せるため、操作の種類ごとにactionを増やす理由がない。
同じ盤面を2回送っても結果が変わらないため、再送で状態が壊れない。

ペイロードは9要素の短い文字列であり、`JSON.stringify` した長さは200文字前後になる。
`ACTION_MAX_CHARS`（512）に収まるため、共通コアの変更は要らない（[ADR-0023](../adr/0023-actionペイロードに長さ上限を課す.md)）。
この見積りを保つため、itemIdの長さを検証6で16文字以内に縛る。

クライアントは操作のたびに送るが、送信を間引く。
最短の送信間隔を1秒とし、最後の操作から400ms後に必ず1回送る。

間引きが要るのは、間引かない場合に流量制限へ触れるためである。
ソケットあたりの制限は10秒で20通であり（[ADR-0017](../adr/0017-メッセージ流量の制限はインメモリで持つ.md)）、タップのたびに送ると連続操作で超える。
超えた時点でそれ以降の `place` が落ち、盤面がサーバ側で古いまま締切を迎える。

クライアントは `done` を送る前に、保留中の盤面を先に送る。
`done` は間引かれずに届くため、最後の1手が保留のままだとサーバは1手前の盤面で採点する。
これは押したときと、再接続で送り直すときの両方に要る。
再接続の側だけ `done` を送ると、切断中に置いて申告した聞き手が古い盤面で完了扱いになり、
その人が最後の聞き手ならそのまま採点が確定する。順序は `client/games/blindroom/src/done-sender.ts` が持つ。

送れなかった盤面を捨てない。
`sendAction` は未接続のとき送らずに戻るため（[02](./02_クライアント.md)）、捨てると再接続後もサーバ側の盤面が1手前のまま残る。
保留を持ったまま再送を予約する。

締切で `building` が終わる場合は、最後の操作から最大1秒ぶんが届かないことがある。
間引きの間隔をそのまま短くすると流量制限に触れるため、この取りこぼしは残す（「未解決の論点」に記録する）。

サーバは受理のたびに `gameSecret.boards` を書き換える。
書き込み量は「未解決の論点」に記録する。

### done

payloadは `{ done: boolean }` とする。

取り消せる形にするのは、押し間違いで得点機会を失う経路を作らないためである。
`ready` と違い `done` は締切前の入力を打ち切る操作であり、冪等な確定にすると、誤操作した聞き手はそのラウンドを見ているだけになる。

取り消しを許しても遷移条件は壊れない。
「接続中の聞き手全員が `done` の状態にある」ことを毎回判定するため、最後の1人が押した瞬間だけ遷移する。

`done` を出した後の `place` は受理する。
`done` は完了の申告であって盤面の確定ではない。
受理した時点でその人の `done` を取り消し、`donePlayerIds` から外す。

クライアントは申告の意思を持ち、接続が戻った瞬間にサーバの状態と食い違っていれば送り直す。
未接続のときに押した申告は送られずに消え、締切まで場が止まる（通しE2Eで実際に踏んだ）。
送り直すのは接続が戻った瞬間に限る。状態が届くたびに送ると、サーバが拒否し続ける場合に流量制限（[ADR-0017](../adr/0017-メッセージ流量の制限はインメモリで持つ.md)）へ触れる。

## onDeadline

| ステージ | 締切到達時の扱い |
| --- | --- |
| `briefing` | `ready` が揃っていなくても `handoff` へ進む |
| `handoff` | 説明者が押さなくても `building` へ進む |
| `building` | その時点の盤面で採点し、`reveal` へ進む |
| `reveal` | 次のラウンドの `handoff` へ進む。最終ラウンドなら `result` を返す |

盤面を1度も送っていない聞き手は、9マスすべてが空白の盤面として採点する。
一致は0になる。

説明者が未接続のまま `handoff` の締切に到達したラウンドは、そのラウンドを飛ばして次のラウンドの `handoff` へ進む。
見本を読む人がいないラウンドは、進めても全員が0点になるだけである。

飛ばしたラウンドは `rounds` に記録せず、後から戻らない。
`describerOrder` は公開済みであり、順序を組み替えると公開値と実際の進行が食い違う。

残るラウンドの説明者が全員未接続の場合は `result` を返す。

## 得点

| 事象 | 加点 |
| --- | --- |
| 聞き手の盤面が見本と一致した | 一致したマス1つにつき1点（0〜5） |
| 説明者 | 接続中の聞き手の一致数の平均（小数点以下切り捨て、0〜5） |

減点は置かない。

説明者の得点を聞き手の平均に置くのは、説明者と聞き手の利害を一致させるためである。
説明者が伝わりやすさを最大化するほど自分の点も伸びる。

平均から未接続の聞き手を除くのは、途中で落ちた端末の0点が説明者の得点を削るためである。
接続中の聞き手が0人のラウンドでは説明者の得点を0とする。

6人卓では、聞き手として5ラウンド、説明者として1ラウンドに参加する。
取り得る最大は 5×5 + 5 = 30点である。

5人卓では 4×5 + 5 = 25点になる。
人数で最大値が変わるが、同じ卓の全員に同じ上限が適用されるため、順位付けに影響しない。

## レベル差の吸収

3層で吸収する。

第1層は見本の難度である。
説明者のレベルでアイテムセットを切り替える。

| 説明者のレベル | アイテムセット |
| --- | --- |
| 1〜2 | `easy`（互いに大きく異なるアイテムだけで構成する） |
| 3〜5 | `standard`（色違い・大小違いの組を含み、修飾語がないと言い分けられない） |

配置数ではなくアイテムの区別しにくさで難度を変えるのは、満点を揃えるためである（「進行の要点」の配置数を参照）。

第2層は位置表現の支援である。
説明者へ配る `hintEn` の件数をレベルで変える。

| 説明者のレベル | `hintEn` の件数 |
| --- | --- |
| 1〜2 | 4件 |
| 3〜5 | 2件 |

聞き手への支援はレベルで変えない。
質問に使う言い回しは公開状態の `keyExpressions` として全員へ同じものを出す。
聞き手の課題は聞き取りであり、配る言い回しを増やしても聞き取れる量は変わらない。

第3層は得点の主軸を聞き手側に置くことである。
6人卓の最大30点のうち25点は聞き手として得る点であり、聞き手の得点は位置表現を聞き取れるかで決まる。
産出できる語彙の量では決まらない。

聞き取れない場合は英語で質問できるため、1回で聞き取れないことが直ちに0点にはならない。

この3層でも、`standard` のラウンドは聞き手側の難度も上がる。
説明者のレベルが高いラウンドほど卓全体の一致数が下がる可能性がある。
確度: **未検証**（構造からの推論であり、実プレイでの計測はしていない）。

## ロビーの記述子

ゲーム選択画面とロビーへ配る値である（[ADR-0018](../adr/0018-ロビーの表示と設定はゲームモジュールが記述子で配る.md)）。

| 項目 | 値 |
| --- | --- |
| `title` | `BLIND ROOM` |
| `tagline` | 見えない部屋の配置を英語で伝え、同じ形を作る |
| `icon` | 🧩 |
| `playerCount` | `[5, 6]` |
| `contentLabelJa` | 部屋を選ぶ |

対応人数を収録4本と同じ5〜6人にする。
4人でも進行は成立するが、ラウンド数が人数と同じであるため1ゲームが短くなり、説明者の当たり外れが結果を左右する割合が上がる。

## 設定

| key | labelJa | 範囲 | 既定 |
| --- | --- | --- | --- |
| `buildingSeconds` | 配置の時間（秒） | 60〜120、step 15 | 75 |

ラウンド数は参加人数と同じとし、設定にしない。
全員が1回ずつ説明者を務める性質が壊れる。

既定を75秒とするのは、5個の配置に対して質問1〜2往復が入る想定であるためである（未検証）。

上限を120秒に置くのは、6人卓で1ゲームが15分を超えるためである（「所要時間の見積り」を参照）。

`validateSettings` は範囲外・型違い・欠損を拒否する。
記述子の `min` / `max` と受理範囲を一致させ、その一致をテストで固定する。

`step` は入力の刻みであり、受理の条件にしない。
範囲内の整数であれば受理する（収録4本と同じ扱い）。

## start の処理順

1. `contentId` からパックを引く。`listContents` に載るidだけを受理する
2. `settings.buildingSeconds` を確定する（既定75秒）
3. 参加者を `seed` でシャッフルし、`describerOrder` に固定する。`totalRounds` は参加人数と同じになる
4. ラウンドごとに、説明者のレベルから `itemSetIds` を決める
5. ラウンドごとに見本を生成し、`samples` に固定する（次節）
6. 各プレイヤーへラウンド0の秘密を配る。説明者には `sample`、聞き手には空の `board` を渡す
7. `stage` を `briefing`、`deadlineSeconds` を60として返す

抽選と生成は共通コアが注入した `seed` からのみ行う。
`Math.random()` と時刻を使わない（[05](./05_ゲームモジュール.md) の呼び出し規約）。

説明者の順にレベルの重みを掛けない。
全員が1回ずつ説明者になるため、順序が有利不利を生まない（[09](./09_DONTSAYITゲームモジュール.md) と同じ）。

## 見本の生成

見本はコンテンツとして持たず、`start` で生成する（[ADR-0024](../adr/0024-BLINDROOMの見本盤面は生成する.md)）。

1. そのラウンドのアイテムセットの items を `shuffle` し、先頭5件を取る
2. マスの添字 `[0..8]` を `shuffle` し、先頭5件へ手順1のアイテムを順に置く
3. 残る4マスを `null` にする

生成が満たす不変条件は3つである。
アイテムがちょうど5個であること、同じアイテムが2マスに無いこと、すべてのidがそのラウンドの `palette` に含まれることである。
モジュールのユニットテストでこの3つを固定する。

配置の見た目に制約は課さない。
5個が1列に並ぶ配置も、四隅へ散る配置も生成しうる。
説明の難しさはアイテムの区別しにくさに主に依存するという判断であり、この判断は**未検証**である（「未解決の論点」に記録する）。

## カタログ（listContents）

```typescript
{ id: "room", title: "部屋のもの", itemSetCount: 2 }
```

アイテムの一覧をカタログに載せない。
ロビーで出るアイテムが分かると、`building` へ入る前に英語名を調べられる。

## 結果（result.payload）

```typescript
interface BlindRoomResult {
  rounds: RoundRecord[];
  items: PaletteItem[];    // 使用したアイテムセットの全アイテム
  scores: ScoreEntry[];    // 降順
}
```

`items` を結果に含めるのは、結果画面が盤面を描くのにidから表示物を引く必要があるためである。
`finished` のまま再接続した人へ共通コアが `lastResult` を再送するため、結果画面が公開状態に依存しないようにする（[11](./11_WHOWROTETHISゲームモジュール.md) と同じ判断）。

飛ばしたラウンドは結果に載せない。

## 所要時間の見積り

締切は上限であり、実際は `ready` と収集で先に進む。
6人・`buildingSeconds` 75秒で見積る。

| 区間 | 見積り |
| --- | --- |
| `briefing` | 40秒（締切60） |
| `handoff` × 6 | 20秒 × 6 = 120秒（締切30） |
| `building` × 6 | 75秒 × 6 = 450秒 |
| `reveal` × 6 | 20秒 × 6 = 120秒（締切45） |
| 1ゲーム | 約730秒（約12分） |

`buildingSeconds` を上限の120秒にすると約16.5分になり、[収録計画](../実装計画/ゲーム構想20案の収録計画.md) の受入条件「6人で15分以内」を超える。
既定値で収まる見積りであるが、**実測はしていない**。

実測が15分を超えた場合の調整先を先に決めておく。
`reveal` の締切を30秒へ、`handoff` を20秒へ、`buildingSeconds` の既定を60へ、の順で詰める。
ラウンド数は下げない。全員が説明者を務める性質が失われる。

5人卓では5ラウンドとなり、約10分になる。

## コンテンツ形式

```json
{
  "id": "room",
  "title": "部屋のもの",
  "keyExpressions": [
    { "en": "Which row is it in?", "ja": "どの段？" },
    { "en": "Is it next to the cat?", "ja": "猫のとなり？" },
    { "en": "Say that again, please.", "ja": "もう一度お願い" }
  ],
  "itemSets": [
    {
      "id": "room_easy",
      "tier": "easy",
      "describerHints": [
        "Put the ... in the top-left corner.",
        "The ... is next to the ...",
        "There is nothing in the ... row.",
        "The ... is under the ..."
      ],
      "items": [
        { "id": "cat", "en": "cat", "ja": "猫", "icon": "cat" },
        { "id": "book", "en": "book", "ja": "本", "icon": "book" }
      ]
    },
    {
      "id": "room_standard",
      "tier": "standard",
      "describerHints": [
        "The red ... goes above the blue ...",
        "The bigger ... is in the middle of the ... row."
      ],
      "items": [
        { "id": "red_book", "en": "red book", "ja": "赤い本", "icon": "red_book" },
        { "id": "blue_book", "en": "blue book", "ja": "青い本", "icon": "blue_book" }
      ]
    }
  ]
}
```

1ファイルが1パックであり、パックは `easy` と `standard` のアイテムセットを持つ。
ロビーで選ぶ単位はパックである（収録4本と同じ形）。

`describerHints` をアイテムセットごとに置く。
`standard` は修飾語が要るため使う言い回しが違い、パック直下に1組だけ置くと `easy` 側に不要な語が混じる。

`keyExpressions` はパック直下に置く。
聞き手の質問はアイテムの種類に依存しない。

`icon` はアイコンのファイル名を指す。
実体は `client/public/items/blindroom/<icon>.svg` にあり、絵文字を使わない（[ADR-0025](../adr/0025-盤面アイコンはSVGで持つ.md)）。

アイコンをコンテンツ側のidで参照するのは、アイテムを1件足すのにクライアントの変更を要らなくするためである。
対応表をクライアントへ置くと、コンテンツだけを増やせなくなる。

色違いのアイテムは、同じ図形の塗りだけを変えて作る。
形まで変えると、聞き手は色ではなく形で見分けられてしまい、修飾語を言わせるという狙いが消える。
図形が一致することは `tools` のテストで検査する（後述の「アイコンの検査」）。

同じアイコンを1つのアイテムセット内で使い回さない（検証8）。
`red_book` と `blue_book` に同じ絵を割り当てると、盤面の上で2つが区別できず、正しく聞き取った聞き手が採点で落ちる。

## 検証項目

`pnpm validate:content` で検査する。

| # | 内容 |
| --- | --- |
| 1 | スキーマ。必須欄の欠落と型違いを落とす |
| 2 | `itemSets` に `tier` が `easy` のものと `standard` のものが各1件以上ある |
| 3 | 各アイテムセットの `items` が8件以上 |
| 4 | itemIdがパック内で一意 |
| 5 | アイテムセットidがパック内で一意 |
| 6 | itemIdが `[a-z0-9_]` の1〜16文字 |
| 7 | `icon` が `[a-z0-9_]` の1〜16文字 |
| 8 | 同一アイテムセット内で `icon` が重複しない |
| 9 | 同一アイテムセット内で `en` が重複せず、1〜3語である |
| 10 | 各アイテムセットの `describerHints` が4件以上 |
| 11 | `describerHints` の各文が空欄（`...`）を1箇所以上含む |
| 12 | `keyExpressions` が3件以上 |
| 13 | すべての `ja` が空でない |

検証3の下限を8件に置くのは、5個を配置しても選ばれない候補が3件以上残る状態を作るためである。
候補がちょうど5件だと、聞き手はアイテムの特定を考えずに配置だけを当てればよくなる。

検証6はペイロード長の見積りを固定するために置く（「action の受理規則」の `place` を参照）。

検証10の下限を4件に置くのは、レベル1〜2の説明者へ4件配るためである。
`hintEn` は先頭から切って配るため、4件未満のセットではレベル1〜2への支援が減る。

検証13を置くのは、`ja` がフォントサブセットの入力になるためである（[07](./07_リポジトリとツールチェーン.md)）。

アイコンは生成物である。
形状の正本は `client/games/blindroom/scripts/generate-icons.mjs` にあり、10種の形状と色の組み合わせから20点を作る。
SVGを直接編集すると色違いの形が揃わなくなるため、`pnpm --filter @beb/client-blindroom run icons:generate` で作り直す（[07](./07_リポジトリとツールチェーン.md)）。

### アイコンの検査

`pnpm test`（`tools/src/blindroom-icons.test.ts`）で検査する。
ファイルを読む検査を `validateContent` に置かないのは、`validateContent` がWorkerのバンドルに入るためである（[05](./05_ゲームモジュール.md)）。

| # | 内容 |
| --- | --- |
| A | 収録したすべてのアイテムにSVGがある |
| B | 使われていないSVGが残っていない |
| C | `<script>` `<image>` `href` `@import` を含まない（外部参照とスクリプトを持たない） |
| D | 塗りが決めた5色に収まる |
| E | 1件2KB以内 |
| F | `red_x` と `blue_x` は、塗りを除いた図形の定義が完全に一致する |
| G | ペアの2件が実際には違うファイルである（色が変わっている） |

検査Fが、standardセットの前提である「色だけが違う」を機械で固定する。

### 機械で検査しないもの

* アイテムが英語で説明しやすいか（`en` が卓の全員に通じる語か）
* アイコンの絵と `en` が同じものを指して見えるか
* `standard` のアイテムの差が英語で言い分けられる差か（色は言えるが、形の微差は言えない）
* 44pxまで縮めたときに20点が互いに取り違えられないか
* `describerHints` と `keyExpressions` の枠が文として成立するか
* `describerHints` の先頭が、どの見本でも使える枠か（レベル別に届くのは先頭から数件であり、easyは4件、standardは2件。位置を条件つきでしか指定できない枠を先頭に置くと、その条件を満たさない見本で説明の取っかかりが無くなる）

いずれも人手のレビューで見る。
記録は `docs/お題レビュー/` に置く（収録3本と同じ形）。

## 判定の規則

得点の判定は、見本と聞き手の盤面のマス単位の照合に対してのみ行う。
説明の内容、質問の回数、配置の速さは判定に影響しない。

アプリは英語を解釈しない（不変条件1、[ADR-0001](../adr/0001-ランタイムAI不使用.md)）。
照合の対象はアイテムIDであり、`en` も `ja` も判定に使わない。

確定した内訳は `RoundRecord` として保存し、後から再計算しない。
コンテンツを差し替えても過去のラウンドの記録が動かないようにする。

## 未解決の論点

| 論点 | 内容 |
| --- | --- |
| 配置操作の負担 | スマホでの配置はパレットのタップとマスのタップの2手で行う想定である。1ラウンドで5個を置き直す操作量が75秒に収まるかは未検証であり、実機で測る |
| `place` の書き込み量 | 聞き手1人が1ラウンドで最大75回（1秒間隔）送りうる。6人・6ラウンドで最悪2000回超の書き込みになる。日次10万行に対する比率は見積れるが、実測していない。超える場合は送信間隔を2秒へ延ばす |
| 締切時の取りこぼし | 締切で `building` が終わると、最後の操作から最大1秒ぶんの配置が届かない。完了申告を経由した場合は保留分を先に送るため起きない。実プレイでどの程度起きるかは未計測である |
| 生成の偏り | 見本の配置に制約を課さないため、1列に並ぶ配置や四隅へ散る配置が出る。説明の難しさがアイテムの区別しにくさに主に依存するという前提は未検証である |
| 説明者の得点が卓に依存する | 説明者の得点は聞き手の平均であり、聞き手のレベルが低い卓では説明者が損をする。レベルで難度を変える対象が説明者側だけであるため、この非対称は残る |
| 聞き手の発話 | 聞き手は質問せずに置くだけでも成立する。`keyExpressions` で質問を促すが、1ゲームあたりの聞き手側の発話量は未測定である |
| マス番号の口頭指定 | 画面に座標を出さないことで抑えるが、口頭での「上から2番目の左」のような指定は起こる。禁止も検出もしない判断であり、これが説明を退化させるかは実プレイで見る |
| 小さい端末での収まり | 390×844の実機相当で配置画面の文書高が約920pxになり、80px前後のスクロールが残る。375×667ではパレットの下段と「できた」がスクロール前提になる。実機での操作負担は未測定である |
| 同じ部屋で続けて遊んだときの重複 | 見本は `seed` から生成されるため重複しにくいが、アイテムセットは同じパックなら同じである（収録4本の同じ論点と合わせて判断する） |

## 原案からの変更

[ルール案](../収録候補ゲームのルール案.md) の案23から変えた点と、その理由を挙げる。

| 変更 | 理由 |
| --- | --- |
| 採点を「見本でアイテムが置かれているマスの一致数」にした | 原案は採点単位（マス単位か完全一致か）を未定としていた。空白マスを含めると、何も置かずに待つだけで一致するマスが生まれる |
| 配置数を5に固定し、聞き手の配置上限も5にした | 上限がないと、9マスを埋めるだけで期待一致数が上がる |
| 難度を配置数ではなくアイテムセットで調整した | 配置数をレベルで変えると、説明者が誰かでラウンドの満点が動く |
| 盤面の向きを全員共通とし、マスに座標を描かないことで解決した | 原案は「盤面の向きの伝え方」を未定としていた。向きが共通なら伝える工程が要らない |
| マス番号の読み上げ禁止をルールから外した | 判定できない禁止であり、`second row, middle` のような正当な位置表現と線引きできない。画面から座標を消す方が確実に働く |
| ラウンド数を参加人数と同じにした | 原案は交代回数を未定としていた。全員が1回ずつ説明者を務めると役割の偏りが出ない |
| 説明者の得点を「接続中の聞き手の一致数の平均（切り捨て）」にした | 原案は「全員の一致率に応じて加点」とだけ述べる |
| 聞き手の完了申告（`done`）を置いた | 原案は締切だけで終わる。全員が置き終えた後の待ち時間が1ラウンドごとに生じる |
| 見本をコンテンツではなく生成にした | 原案はコンテンツに「見本の配置」を含めていた。配置はアイテムセットと乱数の直積であり、人手で書く価値のある情報を持たない（[ADR-0024](../adr/0024-BLINDROOMの見本盤面は生成する.md)） |
| 質問をアプリの入力にしなかった | 原案は「聞き手は英語で質問できる」とだけ述べる。テキスト入力にすると発話が置き換わる |

## テスト観点

`GameModule` は純粋関数のため、Durable Objectなしで全項目をテストする。

* 決定性: 同じ `seed` と同じ参加者から、同じ `describerOrder` と同じ見本列が得られること
* 生成: 見本のアイテムがちょうど5個で、重複が無く、すべてが現ラウンドの `palette` に含まれること
* 生成: 説明者のレベル1〜2で `easy`、3〜5で `standard` のセットが選ばれること
* 秘密の非混入: `building` 中の `BlindRoomPublic` に見本が現れないこと
* 秘密の非混入: `building` 中の公開状態に聞き手の盤面が現れないこと
* 秘密の非混入: `listContents()` の戻り値にアイテムが含まれないこと
* 秘密の配布: 見本が説明者の秘密にだけ入り、聞き手の秘密に入らないこと
* `place`: 説明者からの送信が `describer_cannot_place` で拒否されること
* `place`: 9要素でない配列と型違いの要素が `invalid_board` で拒否されること
* `place`: パレット外のidが `unknown_item`、6個目の配置が `too_many_items`、同一idの重複が `duplicate_item` で拒否されること
* `place`: 上書きが受理され、最後の盤面で採点されること
* `place`: 受理のたびに本人へ `board` を含む秘密が返り、その秘密に見本が入らないこと
* `place`: 他のプレイヤーの秘密が書き換わらないこと
* `done`: `false` で取り消せること
* `done`: `done` の後の `place` が受理され、`donePlayerIds` から外れること
* `done`: 接続中の聞き手全員が `done` の状態になった時点で `reveal` へ進むこと
* `done`: 説明者からの送信が拒否されること
* 得点: 一致したマス数がそのまま聞き手の得点になること
* 得点: 見本が空白のマスへ置いても減点も加点もされないこと
* 得点: 説明者の得点が聞き手の平均の切り捨てになること
* 得点: 未接続の聞き手が説明者の平均から除かれること
* 得点: 盤面を1度も送らなかった聞き手が0点になること
